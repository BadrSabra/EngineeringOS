# UXW-03 Runner Contract V1

**Status:** The shared signed start/stop command core is implemented. Transport,
durable replay/fencing, observations, Local Agent execution, and a qualified
Runner remain unimplemented.

**Authority:** Additive contract for UXW-03.1–03.4; it does not enable Backend Preview

## 1. Purpose

Define one provider-neutral boundary between the API control plane, a trusted
Runner Agent, and an isolated Preview Runtime. The contract prevents AWS task
identifiers, local file paths, shell commands, or Candidate-controlled
configuration from becoming shared API concepts.

The selected minimum isolation class is stronger than standard shared-kernel
`runc`:

- `shared_kernel`: ordinary OCI/runc container; **rejected** for Backend
  Candidate execution.
- `syscall_sandbox`: a separately qualified sandbox runtime such as
  gVisor/runsc, with the exact runtime version and policy approved by the
  server.
- `microvm`: a separately qualified VM/microVM boundary.

Naming a provider does not qualify it. Only a server-owned qualification record
for the exact provider/runtime version and policy may satisfy the minimum.

## 2. Ownership and reuse

| Existing boundary | Contract rule |
|---|---|
| `PreviewSessionStore` and `preview_sessions` | Remain the source of truth for Session identity and lifecycle. Do not create a second Session/job ledger. A schema migration may add provider-neutral execution fields after review; do not encode a local handle as an ECS ARN. |
| `VerifiedPreviewRuntimeProfile` / `preview-runtime-profile.ts` | This is currently AWS-specific (`imageDigest`, `taskDefinitionArn`). Preserve it for the AWS adapter; do not silently redefine it as the provider-neutral profile. |
| `PreviewControlCommand` / `preview-control-command.ts` | The existing signed command is ECS-specific and uses AWS task-definition fields. Keep it compatible; introduce a separately versioned, domain-separated Runner message rather than widening its meaning. |
| `PreviewEcsRunner` | Keep as an AWS adapter. Its Task Definition checks do not attest a stronger-than-runc boundary and do not qualify a live Runner. |
| `WorkspaceRuntime` and its supervisor | Remain project-development process management. They never execute Candidate Preview code. |
| `PreviewNodeRegistry` / `PreviewPlacementPolicy` | Own node registration, fresh capability lookup, and deterministic eligibility. The protocol below supplies evidence to those existing planned responsibilities; it is not a second registry or placement policy. |

The control-plane abstraction is `PreviewSessionRuntime` with
`start / observe / stop`. A node-side `PreviewRunnerAgent` is the authenticated
transport and command verifier; it delegates execution to one qualified
`PreviewSandboxProvider`. These are separate roles, not competing sources of
Session state.

## 3. Trust and identity

Candidate code is arbitrary code, including when generated by an Agent. The
API remains the authorization and lifecycle authority. The Runner receives
only a short-lived, signed command, immutable Artifact references/digests, a
fixed Runtime Profile, and the minimum session channel needed to serve the
Preview. It receives no database, Git, AI-provider, cloud, or application
credentials and has no direct database access.

Every command, result, and observation is bound to:

`sessionId + stateVersion + commandId + executionGeneration + projectId + proposalId + operationId + candidateRevision + changeSetHash + buildReceiptId + artifactDigest + runtimeProfileDigest`

The API rechecks this tuple against current durable state before accepting a
write. A stale lease/generation, Candidate revision, receipt, or profile is
rejected. Runner evidence is provenance only: it is not Canonical Proof,
Acceptance, delivery authorization, or permission to mutate project files.

## 4. Capability evidence

`PreviewNodeRegistry` consumes a server-validated capability snapshot. The
snapshot must include at least:

```text
protocolVersion
nodeId
agentVersion
sandboxProviderId
sandboxRuntimeVersion
isolationClass                 # shared_kernel | syscall_sandbox | microvm
runtimeProfileDigest
sandboxPolicyDigest
observedAt
expiresAt
evidenceMode                   # local_observed | remote_attested
evidenceKeyId
signature
```

The signed policy evidence must establish, rather than merely claim:

- the approved isolation class and exact sandbox runtime version;
- immutable Runtime image and launcher digests;
- non-root execution, read-only Runtime root, no host project mounts, no
  Docker/container-control socket, and no inherited secrets;
- no general network interface or egress; the only allowed Preview path is a
  server-created per-Session channel;
- bounded CPU, memory, writable scratch, PID count, startup time, idle time,
  and total Session TTL;
- process/VM ownership and the ability to confirm termination and cleanup.

Evidence is rejected when missing, expired, malformed, signed by an
unregistered key, or inconsistent with the server's qualification record.
`local_observed` is not `remote_attested`; a local Agent signature alone cannot
claim independent or hardware-backed assurance.

## 5. Runtime Profile

The provider-neutral `PreviewRuntimeProfileV1` is server-owned and immutable:

```text
profileId
version
runtimeImageDigest
launcherDigest
requiredIsolationClass         # syscall_sandbox | microvm
filesystemPolicyDigest
networkPolicyDigest
resourcePolicyDigest
exposureProtocol                # session_uds_v1 initially
qualificationRecordId
```

Candidate input is an immutable, digest-bound `ArtifactRef`. The Candidate
cannot select an image, command, entrypoint, environment variable, port,
mount, network, quota, or upstream. Runtime configuration is derived only
from this Profile and the signed Session command.

## 6. Versioned Runner messages

Messages use a new domain-separated signature protocol, for example
`EngineeringOS Preview Runner Command v1`. The existing ECS control-command
signature and payload remain unchanged. Every message has a bounded issue/expiry
window, canonical serialization, replay protection, and a monotonic Session
`stateVersion`.

### Start

The signed `StartPreviewV1` contains:

- `commandId`, `idempotencyKey`, `sessionId`, `stateVersion`,
  `issuedAt`, `expiresAt`, and current lease/fencing generation;
- the full Candidate/operation identity tuple above;
- `artifactRef`, `artifactDigest`, `buildReceiptId`;
- `runtimeProfileId`, `runtimeProfileDigest`, and required isolation class;
- server-owned resource/TTL limits and an opaque per-Session exposure-channel
  reference.

It contains **no** filesystem path, S3 URL, AWS ARN, arbitrary command,
Candidate environment, raw credential, or browser-selected destination.

The Runner returns one of:

- `accepted` with an opaque `executionRef` and the exact image, launcher,
  isolation-evidence, and policy digests it applied;
- `already_accepted` with the same `executionRef` for an identical retry; or
- `outcome_unknown` when it cannot prove whether launch occurred.

An acknowledgement is not `ready`. Readiness requires a later, fresh
`observe` result matching the same identity and verified through the
server-owned exposure path. `outcome_unknown` triggers reconciliation with the
same idempotency identity; it must not create a second sandbox.

### Observe

`observe(executionRef, sessionId, stateVersion, fencingGeneration)` returns a
bounded observation:

```text
state: provisioning | ready | stopping | stopped | failed | unknown
observedAt
executionGeneration
candidateRevision
artifactDigest
runtimeImageDigest
launcherDigest
isolationEvidenceDigest
policyDigest
channelRef                   # opaque; never a public URL or port
terminationConfirmed
cleanupConfirmed
```

`unknown` is not equivalent to `failed`, `stopped`, or `ready`. Missing or
ambiguous observations remain retryable and cannot authorize Session access.

### Stop

`stop(executionRef, sessionId, expectedStateVersion, fencingGeneration,
reason)` is idempotent and can affect only the exact owned execution. A stop
acknowledgement reports `stopped` only after process/VM termination, channel
closure, and owned scratch cleanup are observed. Otherwise it returns
`outcome_unknown` or `stop_unconfirmed`; the API must not persist a false
terminal state.

## 7. Session exposure channel

The initial local transport candidate is `session_uds_v1`:

- The trusted exposure component creates and owns one private socket namespace
  per Session; the Candidate receives no IP interface and cannot choose a
  socket path or upstream.
- The Gateway resolves the socket only from the durable Session record and
  forwards the authorized browser request to that one service.
- Socket creation/opening must be race-safe: use a private directory, no
  symlink following, verify file type/owner/inode, bind it to the Session and
  execution generation, and delete it only after the owned Runtime is stopped.
- The Candidate cannot access the Gateway control socket, another Session's
  socket, arbitrary host sockets, or the host filesystem outside this one
  communication channel.

The local probe in the ADR proves only that a harmless host HTTP client can
reach a fixed container handler over one mounted UDS with `--network none`. It
does not satisfy these ownership, race, authorization, or lifecycle rules.

## 8. Lifecycle, retry, and fencing

- PostgreSQL Session state remains authoritative. The Runner has no authority
  to create or finalize Session rows.
- `start` claims the current attempt/generation before dispatch. All retries
  use the same command/idempotency identity; a changed Candidate, receipt,
  profile, or generation requires a new command and invalidates the old one.
- A late response from an expired lease/generation cannot attach an execution,
  mark a Session ready, or stop a newer Session.
- After worker loss, reconcile the exact `executionRef` and command identity
  before retrying or cleaning up. Do not claim exactly-once execution.
- `ready` requires a fresh observation, matching artifact/runtime/isolation
  digests, and a successful session-bound Gateway health request.
- TTL, cancellation, and failed startup deny new Preview requests first, then
  stop the exact owned sandbox and channel. Persist `stopped`/`expired` only
  after termination/cleanup is observed; otherwise retain an explicit
  unresolved state.

## 9. Error contract

Return stable, non-sensitive error codes; never return raw provider diagnostics,
host paths, command output, socket paths, or credentials:

```text
RUNNER_CAPABILITY_UNAVAILABLE
RUNNER_ISOLATION_BELOW_MINIMUM
RUNNER_PROFILE_NOT_QUALIFIED
RUNNER_COMMAND_INVALID
RUNNER_COMMAND_EXPIRED
RUNNER_FENCE_STALE
RUNNER_IDENTITY_MISMATCH
RUNNER_ARTIFACT_MISMATCH
RUNNER_START_OUTCOME_UNKNOWN
RUNNER_OBSERVATION_UNKNOWN
RUNNER_STOP_UNCONFIRMED
RUNNER_RESOURCE_LIMIT
RUNNER_CHANNEL_UNAVAILABLE
```

Only documented transient failures are retried, with bounded backoff and the
same idempotency/fencing identity. Capability, signature, identity, digest,
policy, or isolation failures are fail-closed and are not retried as a weaker
profile.

## 10. Closure tests

The contract is not complete until independent tests prove:

1. `shared_kernel`/standard `runc` is rejected; absent, stale, forged, revoked,
   or policy-mismatched capability evidence is rejected.
2. A Candidate with stale revision, mismatched receipt/artifact digest, or
   wrong project/session identity cannot start or attach.
3. Lost start response and duplicate command reconcile to one execution;
   old fencing generations cannot attach, stop, or mark a newer execution ready.
4. Candidate cannot read host/project files, secrets, runtime control sockets,
   another Session's files, or private/metadata networks.
5. Candidate has no egress or extra listener; only the exact session UDS path
   reaches the Gateway, with symlink/race/cross-Session attempts rejected.
6. Resource exhaustion, TTL, cancellation, Agent death, Runner death, restart,
   and cleanup failures remain explicit and bounded; no orphan process or
   falsely terminal Session.
7. `ready` and `stopped` require independent observations, not command success,
   HTTP health alone, or a process leader exit.

Until these tests run against the actual stronger-than-runc Runner and the
product Gateway, `node-express-managed-v1` remains unsupported. The current
AWS-specific profile, local runc probe, and UDS feasibility probe do not close
this gate.
