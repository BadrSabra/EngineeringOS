# عقد قبول مسار النتيجة: Apply Changes → Mission → تسليم اختياري

**الحالة:** مقترح للمراجعة، 2026-09-30. هذه وثيقة قبول وليست تفويضًا بالتنفيذ أو الدفع الخارجي.

## الهدف والحد

إثبات رحلة واحدة لمشروع Git تجريبي يملكه المستخدم: من مقترح تغيير معتمد إلى أثر
Apply مرصود، ثم نتيجة هدف Mission التابع المرئية بعد إعادة التحميل. التسليم إلى
مستودع خارجي **مرحلة قبول مستقلة واختيارية**؛ نجاح Apply أو إطلاق الهدف التابع
لا يعنيان اكتمال التقرير أو التسليم. لا تُنشأ سلطة قبول أو مخزن حقيقة جديد:
Canonical Proof وEffect وWorld Transition وإيصالات Git القائمة هي المصادر
المخولة؛ النص الذي ينتجه النموذج وعرض الواجهة ليسا دليلًا.

## شروط الدخول

- جلسة Clerk لمالك مشروع **تجريبي قابل للتخلص منه**، جذر Git معروف، ومراجعة مصدر
  ثابتة؛ مقترح معتمد يربط `proposalId` و`candidateTreeHash` و`changeSetHash`
  والمراجعة الأساسية بخطة Mission النشطة (`apply-changes` ثم `report-applied`).
- محاولة تنفيذ واحدة قابلة للتتبع عبر `projectId` و`missionId` و`goalId`
  و`executionId` و`attempt` و`operationId` و`planRevision`. أي اختلاف في الهوية
  أو المراجعة يوقف قبول تلك المرحلة، ولا يُصلح بتغيير العرض.
- **للمرحلة الحية فقط:** قرار بوابة الإصدار الكامل، بما فيها Preview، محفوظ
  ومربوط بمراجعة الشيفرة؛ harness مزود حي مقيد بالقراءة وهدف canonical صالح؛
  موافقة صريحة على مستودع/فرع خارجي تجريبي. عدم تحقق أي شرط يبقي المرحلة الحية
  `blocked`، ولا يحول نجاح fixture إلى إثبات حي.

## مستويات القبول؛ لا يُستنتج مستوى من سابقه

| المستوى | الدليل المطلوب | ما يظهر للمستخدم |
|---|---|---|
| **A — Apply مثبت** | قبول التنفيذ `SUCCEEDED/PROVEN`، وEffectBundle بحكم `OBSERVED`، وملاحظتا شجرة قبل/بعد مباشرتان وكاملتان وحديثتان ومتطابقتان مع النطاق والبيئة والشجرتين، وWorld Transition بحالة `materialized/fresh` مربوط بالمحاولة والأثر و`resultingWorldRevision`. | «تم تطبيق التغيير وإثبات أثره» مع مراجع الدليل؛ لا ادعاء بإتمام Mission أو التسليم. |
| **B — نتيجة Mission مثبتة** | بوابة D2 تعيد `proven`، ويُطلق `report-applied` مرة واحدة فقط؛ تُقرأ حالة الهدف التابع الفعلية من السجل الدائم حتى يصبح نهائيًا. يعرض تفصيل التنفيذ الانتقال الخاص بـApply، والقبول، وحالة الهدف بالهويات نفسها بعد reload/reconnect. | «التقرير جارٍ/مكتمل/متوقف» بحسب حالته الحقيقية؛ مجرد dispatch ليس اكتمالًا. |
| **C — تسليم خارجي مثبت، إن طُلب وأُجيز** | إيصال commit مربوط بالمقترح والشجرة المعتمدة، ثم push واحد قابل للاستعادة، وفحص مستقل لحالة الفرع البعيد وcommit/tree المتوقعين؛ Canonical delivery receipt يطابق التنفيذ والمحاولة والعملية والمراجعة والمرشح. | «تم التسليم» فقط بعد فحص الحالة البعيدة؛ وإلا «قيد التحقق/غير مكتمل» مع السبب. |

## الاختبار والفشل المغلق

يبدأ الاختبار الحتمي بالمسار المصادق عليه عبر API وDashboard القائمين، ثم يعيد
تحميل Mission Control ويتحقق من استمرار مراجع A وB. يُستخدم تفصيل التنفيذ
الحالي بدل projection موازٍ؛ تحميل `worldTransitions` المقصور اليوم على
`runtime.start` لا يكفي لإظهار انتقال Apply. لا يُجرى اختبار C الحي إلا بعد
شروط دخوله، وعلى وجهة تجريبية مستقلة، مع حفظ تقرير نتيجة منقّح لا أسرار فيه.

تُختبر حالات مراجعة/شجرة/مقترح/محاولة غير متطابقة، أو ملاحظة ناقصة، أو انتقال
مفقود، أو إلغاء/انقطاع وإعادة اتصال، أو اختلاف حالة البعيد. نتيجتها
`INCOMPLETE` أو `BLOCKED` للمرحلة المعنية، بلا نجاح صامت أو ترقية/دفع جديد.
إعادة المحاولة لا تكرر dispatch أو الأثر الخارجي. **الخروج المقبول:** تقرير واحد
يربط هوية كل مرحلة بدليلها، ويعلن صراحة آخر مستوى اجتازته الرحلة وما بقي غير
مثبت؛ لا يُسمّى المسار end-to-end خارجيًا قبل اجتياز C فعليًا.

**خارج النطاق:** جمع أو معايرة P7.5، shadow-loop، توسعة `runtime.start`،
اختيار أفعال جديد، أو اعتبار هذه الرحلة إثباتًا لتعميم الوكيل أو جاهزية الإنتاج.
