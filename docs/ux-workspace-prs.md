## 0. سلطة الوثيقة وطريقة استخدامها

هذه الوثيقة هي المرجع الواحد لتنفيذ تجربة UX Workspace. وهي تجمع المتطلبات المستهدفة، والحدود المعمارية، والعقود المقترحة، وإعادة الاستخدام المسموح، وترتيب حزم العمل، واختبارات القبول.

كل ادعاء عن الموجود الآن موسوم ضمنيًا أو صراحةً بأنه **موجود** أو **جزئي** أو **مقترح**. ذكر واجهة أو مسار في قسم «الموجود» لا يعني أنه يحقق تجربة Workspace كاملة.

ترتيب السلطة عند التعارض:

1. صلاحيات الخادم وعقود القبول والإثبات والتسليم الحالية.
2. هذه الوثيقة لمتطلبات UX Workspace وقرارات تنفيذها.
3. ملاحظات التصميم والاستراتيجية السابقة، وهي سياق وليست تفويضًا لتجاوز هذه الوثيقة.

إذا كشف التنفيذ أن عقدًا حاليًا أو بوابة أمان لا يطابق هذا التصميم، يتوقف التنفيذ عند الحزمة المتأثرة. تُحدّث هذه الوثيقة ونتائج التدقيق أولًا؛ لا يُنشأ مسار بديل أو حالة واجهة توحي بنجاح غير مثبت.

لا تعني هذه الوثيقة أن جميع الحزم معتمدة للتنفيذ بالتوازي. لكل حزمة شروط دخول وإغلاق، والبوابات الأمنية والاعتمادية تتقدم على الجدول.

## 1. الملخص التنفيذي

يبني EngineeringOS تجربة **Intent-to-Outcome Workspace**: يصف المستخدم نتيجة يريدها، ويحافظ النظام على سياق المشروع والطلب، ويعرض العمل الجاري ونسخته المرشحة والتحقق والقرار والأثر في مساحة واحدة.

الهدف ليس إعادة بناء Agent Core أو نقل الجداول إلى مخطط موحد. الهدف هو وضع طبقة UX وقراءة موحدة فوق مصادر الحقيقة القائمة، مع إبقاء المحادثة والمهام والتنفيذ والقبول والتطبيق والتسليم مفاهيم منفصلة.

التميّز المطلوب:

- **بدء من الهدف:** لا يُطلب من المستخدم غير المتخصص اختيار أداة أو كيان داخلي قبل شرح النتيجة.
- **استقلالية مرئية:** يرى المستخدم ما يفعله الوكيل، وما ينتظره، وما يحتاجه منه.
- **نتائج تحمل دليلها:** لا تُعرض «مكتملة» على أنها «متحقق منها» أو «مطبقة» أو «مسلمة».
- **معاينة مرتبطة بالنسخة:** لا يراجع المستخدم نسخة قديمة على أنها المرشح الحالي.
- **موافقة ذات أثر واضح:** القبول والتطبيق والتسليم إجراءات منفصلة، وكل إجراء يعاد التحقق منه على الخادم.

تُبنى أولًا شريحة رأسية واحدة:

> الهدف → فهم قابل للمراجعة → عمل في مرشح معزول → معاينة للمرشح نفسه → تحقق ومراجعة → موافقة وتطبيق → سجل نتيجة يوضح الأثر المثبت.

لا تُفعّل المعاينة التفاعلية لمرشح أو التوازي الكتابي قبل إثبات عزل مساحة المرشح، وربط التنفيذ والأدلة والمعاينة والتطبيق بالنسخة نفسها.

## 2. المستخدم والوعد المنتجّي

### 2.1 المستخدم الأساسي

مستخدم عربي لا يلزم أن يعرف البرمجة أو المصطلحات الهندسية. يريد وصف ما يريد، وفهم التقدم والقرارات المهمة، ثم مراجعة نتيجة حقيقية قبل اعتمادها.

المستخدم المتمرس يجب أن يستطيع فتح التفاصيل التقنية عند الحاجة، من دون أن تصبح تلك التفاصيل الطريق الإلزامي للمستخدم العادي.

### 2.2 وعد المنتج

يستطيع المستخدم الإجابة من مساحة العمل على الأسئلة التالية:

1. ماذا فهم النظام من طلبي؟
2. ما الذي يعمل الآن، وما الذي ينتظرني؟
3. أي مشروع ونسخة ومرشح يعرضهم النظام؟
4. ماذا تغيّر وما الذي اختُبر؟
5. ماذا ثبت بالدليل، وما الذي لم يثبت؟
6. ما القرار المطلوب مني، وما عاقبة كل خيار؟
7. هل طُبق التغيير؟ وهل سُلّم إلى GitHub فعلًا؟

### 2.3 مبادئ UX ملزمة

- المحادثة وسيلة تحكم وليست المنتج كله.
- إظهار الحالة بحسب الحاجة؛ التفاصيل التقنية قابلة للكشف التدريجي.
- المصطلحات العربية تشرح الهدف والخطوة والتنفيذ ولا تخلط بينها.
- لا يُستبدل غياب البيانات بعبارة «لا يوجد عمل»؛ تُعرض حالة عدم التوفر أو نقص التغطية.
- لا يعرض الربع الأخضر أو اكتمال التنفيذ ما لم تثبت الاستجابة المعنية ذلك.
- تبقى اللغة العربية RTL؛ مسارات الملفات والمعرّفات والأوامر والقيم اللاتينية معزولة باتجاه LTR.
- القيم المعروضة في الواجهة لا تمنح صلاحية، ولا تصبح بديلًا عن تحقق الخادم.

## 3. النطاق والاستبعادات

### 3.1 داخل النطاق

- مدخل هدف واضح لمسار مشروع جديد أو مشروع قائم.
- غلاف Workspace متمحور حول المشروع والطلب.
- ملخص قراءة يجمع حالة مصادر العمل المدعومة من دون نسخ مصادر الحقيقة.
- حالة محادثة وتقدم وإجراءات موحدة قابلة للاستعادة بعد إعادة التحميل أو انقطاع الاتصال.
- معاينة تفاعلية للمشروع أو المرشح عبر بوابة مصادق عليها، إذا اجتازت بوابة العزل والأمان.
- مراجعة المرشح وربط Diff ونتائج التحقق والقبول والتطبيق والتسليم بهويته.
- عرض مهام العمل المدعومة والتخطيط لطلب آخر مع منع التوازي الكتابي غير المعزول.
- Canvas بصري محدود ومربوط بمصدر تغيير قابل للمراجعة.
- استعادة تشغيل العمل داخل حدوده، مع تمييزها عن استرجاع ملفات المشروع أو البيانات الخارجية.

### 3.2 خارج النطاق

- إعادة بناء Agent Core أو موفري الذكاء الاصطناعي أو محرك التنفيذ.
- توحيد كل أنواع السجلات في كيان أو حالة واحدة.
- اعتماد شاشات أو حقول أو حالات أو مسارات تعتمد على كيان Mission؛ هذه الوثيقة تخص القدرات المدعومة فقط.
- تعديل سياسات الإذن أو القبول أو إثبات Canonical Proof أو حواجز التطبيق والتسليم بغرض تبسيط الواجهة.
- تشغيل كتابي متوازٍ قبل إثبات ملكية وعزل كل مساحة مرشح وقاعدة فض التعارض.
- Infinite Canvas، أو محرر بصري عام، أو عدة أنواع مخرجات قبل نجاح الشريحة الرأسية.
- اعتبار الاستعادة العامة للمشروع أو استعادة قاعدة بيانات أو خدمة خارجية زرًا واحدًا غير مقيّد.
- نشر المشروع تلقائيًا أو تسليم التغيير إلى GitHub تلقائيًا بعد المعاينة.
- إعادة تصميم الصفحات التقنية كلها. تبقى التفاصيل المتقدمة متاحة، لكنها ليست الطريق الرئيسي.

### 4.1 نتائج الفحص المعمارية

1. توجد القدرات الأساسية في مسارات منفصلة؛ لا يوجد بعد عقد Workspace واحد أو شاشة واحدة تجمعها.
2. لا يوجد حاليًا `WorkspaceSnapshot` أو Workspace Event Stream موحد في واجهة API.
3. المعاينة التفاعلية للمستخدم ليست هي Browser Preview Verification.
4. لوحة Runtime الحالية لا تثبت أن النسخة المعروضة هي Candidate محدد.
5. إعادة استخدام Delivery Workspace لا تثبت وحدها عزل كل تنفيذ من بدايته.
6. ملخص العمل الحالي جزئي وذو نطاق تغطية معلوم، لذلك لا يجوز استخدام غياب عنصر منه كدليل على غياب العمل.

## 5. التصميم المستهدف

### 5.1 سطح الوصول والمسارات

المسار الأساسي المقترح:

```text
/projects/:projectId/workspace
```

أسباب الاختيار:

- يبقي Workspace تحت هوية المشروع الحالي.
- يسمح بروابط عميقة قابلة للمشاركة وفق صلاحيات المشروع.
- لا يتطلب تغيير artifact أو تغيير المسارات التقنية القديمة دفعة واحدة.

تبقى `/ai` و`/projects/:id` و`/tasks` تفاصيل متقدمة أو مداخل توافقية. أي تحويل لها يكون صريحًا ويحفظ `projectId` و`sessionId` ومعرّفات العنصر المستهدف؛ لا يحذف سياقًا ولا يختار مشروعًا آخر بصمت.

### 5.2 مناطق Workspace

#### أ. Agent Panel

المسؤولية: الهدف، الحوار، أسئلة التوضيح، ملخص الفهم، القرارات التي تحتاج المستخدم.

يعرض:

- وصف الهدف الحالي ومصدره.
- ما فهمه النظام كنطاق وقيود ومعايير مقترحة، مع تمييز ما أكده المستخدم عما استنتجه النظام.
- رسائل المحادثة والتقدم والطلب الذي يعمل عليه.
- أسئلة وقرارات لها سبب وأثر لكل اختيار.
- استعادة الجلسة بعد Reload أو انقطاع الاتصال.

لا يعرض التخمين على أنه مواصفة مؤكدة، ولا يخفي أن إجراءً ينتظر موافقة أو مدخلًا بشريًا.

#### ب. Project Canvas

المسؤولية: عرض النتيجة التي تخص نسخة محددة، والتفاعل معها، لا تقديم iframe عام بلا هوية أو حماية.

الإصدارات المتدرجة:

1. Preview للمشروع الحالي، إذا كان تشغيل المشروع متاحًا.
2. Preview مرشح معزول، بعد نجاح بوابة العزل.
3. أوضاع عرض Desktop / Tablet / Mobile.
4. تحديد عنصر مرئي وربطه بمصدره، بعد إثبات مصدر الربط.
5. مقارنة بدائل بصرية قابلة للمراجعة.

كل معاينة تعرض نوع الهدف (مشروع حالي أو Candidate)، بصمة النسخة، حالة التشغيل، وقت آخر تحديث، وحالة القِدم. عند عدم توفر Preview يعرض السبب أو الإجراء الممكن، ولا يعرض Preview قديمًا على أنه حي.

#### ج. Work & Trust Panel

المسؤولية: العمل النشط، حالة التنفيذ، التحقق، المراجعة والقبول والتطبيق والتسليم.

يعرض الأقسام الوظيفية:

- يعمل الآن.
- ينتظر قرارًا أو معلومة.
- جاهز للمراجعة.
- نتائج مسجلة مؤخرًا.

تظل مصادر الحالة منفصلة خلف العرض. لا تُسقط `failed verification` أو `pending acceptance` بسبب `completed execution`.

### 5.3 السلوك حسب الجهاز

| الجهاز  | السلوك المستهدف                                                                                                                 |
| ------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Desktop | المناطق الثلاث مرئية، مع مساحة أكبر للمعاينة وإمكانية تغيير حجم اللوحات أو طيّها.                                               |
| Tablet  | منطقتان ظاهرتان؛ يمكن إظهار اللوحة الثالثة كدرج أو تبويب مع بقاء المشروع والطلب المحددين.                                       |
| Mobile  | تبويبات أو خطوات واضحة للوكيل والمعاينة والعمل والمراجعة. لا تُخفى حالة الانتظار أو زر الموافقة في لوحة أفقية غير قابلة للوصول. |

المقاسات النهائية تُحسم بالاختبارات البصرية الفعلية. لا تُفرض ثلاث أعمدة على الهاتف.

### 5.4 الهيكل الوظيفي المقترح

```text
Project identity + current revision
├── Agent Panel
│   ├── Intent Brief
│   ├── Conversation / streamed progress
│   └── Decision Inbox
├── Project Canvas
│   ├── Current-project preview or Candidate preview
│   ├── Viewport modes
│   └── Revision / freshness indicator
└── Work & Trust
    ├── Task and execution progress
    ├── Candidate diff
    ├── Verification evidence
    ├── Human review and acceptance
    ├── Apply receipt
    └── Delivery receipt
```

هذا تقسيم للمسؤوليات، وليس إلزامًا بأن تظهر كل التفاصيل في آن واحد.

## 6. دورة المستخدم المستهدفة

### 6.1 بدء مشروع جديد

1. يختار المستخدم «إنشاء مشروع جديد» ويصف ما يريد إنجازه.
2. يعرض النظام فهمًا مختصرًا، والأسئلة الضرورية فقط، وحدود ما سيبدأ به.
3. يراجع المستخدم النطاق قبل أي تغيير مؤثر.
4. ينشأ المشروع أو العملية عبر المسارات الحالية المخولة.
5. ينتقل المستخدم إلى Workspace من دون فقد وصفه أو رسائله.

### 6.2 العمل على مشروع قائم

1. يختار المستخدم مشروعًا يملك صلاحية الوصول إليه.
2. يقرأ النظام سياق المشروع والإصدار الفعلي.
3. يصف المستخدم النتيجة أو يختار هدفًا من مسودته.
4. تعرض بطاقة Intent Brief: الهدف، ما فُهم، النطاق، القيود، ومعيار النجاح المقترح.
5. يوضح النظام المعلومات الناقصة أو يواصل ضمن النطاق المؤكد.

### 6.3 من الهدف إلى نتيجة متحقق منها

```text
Describe
  → Understand
  → Plan
  → Build in Candidate
  → Candidate Preview
  → Verify
  → Review
  → Apply
  → Verify applied effect
  → Deliver (separate, explicit operation)
```

قواعد الدورة:

- لا يكتب بناء Candidate إلى النسخة الأساسية مباشرة.
- Preview وVerification يرتبطان ببصمة Candidate نفسها.
- إذا تغيرت بصمة الأساس بعد التحقق، يتوقف التطبيق حتى يعاد التحقق.
- موافقة المستخدم على Proposal ليست إثباتًا أن التطبيق نجح.
- نجاح التطبيق ليس إثباتًا أن GitHub استلم التغيير.
- يكون لكل خطوة فاشلة تفسير واضح وإجراء استعادة آمن، لا نجاحًا بصريًا متفائلًا.

### 6.4 Decision Inbox

كل قرار معروض يجيب:

1. ما المطلوب؟
2. لماذا لا يستطيع النظام المتابعة من دونه؟
3. ما أثر كل اختيار؟

أمثلة: توضيح نطاق، اختيار بديلين، مراجعة Candidate، قبول تطبيق، قرار تسليم إلى GitHub، أو إقرار خطر محدد.

لا تتحول كل الأحداث الداخلية إلى إشعار. تجمع الواجهة فقط ما يحتاج انتباه المستخدم، مع رابط إلى السجل التقني عند الطلب.

## 7. عقد قراءة Workspace المقترح

### 7.1 قواعد العقد

- `WorkspaceSnapshot` **Read Model** تجميعي، وليس مصدر حقيقة جديدًا ولا سجلًا بديلًا.
- يقرأ الحالة من مصادرها الحالية: المشروع، المحادثة، المهمة، التنفيذ، Proposal/Candidate، التحقق، القبول، التطبيق، Runtime والتسليم.
- لا يخزن حالة تنفيذ مكررة لمجرد أن الواجهة تحتاج تجميعها.
- لا يضمّن أي حقل أو كيان غير مدعوم ليبدو العقد شاملًا.
- لا يختزل الحالات المستقلة إلى `completed`.
- أي استجابة جزئية أو قديمة أو غير متاحة تصف ذلك صراحةً.
- معرّفات الإجراء والقيم المقدمة من العميل لا تمنح صلاحية؛ يعاد التحقق عند كل أمر.

### 7.2 واجهة TypeScript المقترحة

### 7.3 أحكام العقد

- `rawStatus` قيمة مصدرية معروفة؛ الترجمة والعرض منفصلان.
- `nextActions` اقتراحات واجهة، وليست قائمة صلاحيات. كل أمر يعاد فحصه خادميًا.
- `intentBrief` ملخص قابل للمراجعة؛ المعايير المقترحة ليست عقد قبول حتى يؤسسها المسار الخادمي المعتمد.
- `candidateRevision` و`changeSetHash` قد يكونان `null` قبل وجود Candidate؛ لا يخترع العميل بصمة.
- `acceptance.status = "proven"` لا يصدره النموذج أو المتصفح؛ يصدر فقط بعد تحميل دليل القبول المعتمد والتحقق من هويته.
- `application.status = "applied"` يتطلب إيصالًا أو حالة خادمية تثبت التطبيق.
- `delivery.status = "delivered"` يتطلب إيصال التسليم الخارجي ومرجعه البعيد.
- `sources` و`freshness` تمنعان تحويل عطل مصدر القراءة إلى شاشة فارغة أو حالة نجاح.
- يجب إسقاط الحقول غير المدعومة أو إظهارها `unknown`؛ لا نستنتج حالة من النص أو لون Badge.

### 7.4 مسارات القراءة والأحداث

#### Snapshot

```http
GET /api/projects/:projectId/workspace
```

**مقترح، غير موجود حاليًا.** يتطلب مصادقة وحاجز صلاحية المشروع. يعيد `WorkspaceSnapshotV1` في قراءة متماسكة قدر الإمكان، أو يحدد المصادر التي تعذر قراءتها. لا يكتب بيانات تشغيلية جديدة ولا ينفذ إجراءً.

#### Workspace Event Stream

```http
GET /api/projects/:projectId/workspace/events
Accept: text/event-stream
Last-Event-ID: <opaque-cursor>
```

غرضه تنبيه العميل إلى تغير حالة المشروع، ثم إعادة قراءة Snapshot موثوقة. عند أول اتصال يرسل `workspace.resync` لإغلاق الفجوة بين جلب Snapshot وبدء الاشتراك؛ وعند إعادة الاتصال يستخدم الخادم `Last-Event-ID` لإعادة تشغيل الأحداث ضمن نافذة محدودة. لا يستبدل:

- تدفق رسائل AI Chat الحالي.
- تدفق سجلات مهمة بعينها.
- سجل الأحداث التاريخي `/api/events`.

صيغة الحدث المقترحة:

```json
{
  "eventVersion": 1,
  "projectId": "…",
  "entityKind": "project",
  "entityId": "…",
  "eventId": "…",
  "occurredAt": "…",
  "snapshotCursor": "opaque"
}
```

الشروط:

- `id`/cursor معتم ومعرّف من الخادم؛ يستخدم فقط لإعادة تشغيل سجل الأحداث الحالي ولا يمنح صلاحية قراءة.
- يعاد فحص صلاحية المشروع عند إنشاء البث، مع إغلاقه عند انتهاء الجلسة أو صلاحية الوصول.
- تُرسل بيانات إبطال محدودة فقط؛ لا يُكشف `message` أو `payload` أو السجلات أو مخرجات المزود.
- التكرار مسموح؛ الحدث لا يغيّر حالة الواجهة مباشرة، بل يبطل Snapshot ويُعاد قراءته.
- عند انتهاء نافذة الاستعادة يرسل الخادم حدث إعادة مزامنة ويعيد العميل قراءة Snapshot كامل.
- لا يحمل الحدث نصوص ملفات أو أسرارًا أو سجلات خامًا أو مخرجات مزود غير منقحة.
- لا يُبنى استدلال «لا تغيير» من غياب حدث؛ إعادة اتصال ناجحة تعيد قراءة Snapshot.
- يظل Snapshot هو مصدر الحقيقة؛ إعادة قراءة دورية محدودة تعالج التغييرات التي لا ينتج عنها حدث محفوظ أو التي تُكتب بطابع زمني خارج ترتيب الإدراج.

### 7.5 أوامر UX مقابل API

لا يقدم الإصدار الأول سطح أوامر عامًّا جديدًا. يربط محول الواجهة الأوامر الواضحة بمساراتها الحالية، ويضيف مسارات جديدة فقط إذا أثبت التدقيق عدم كفاية العقد الحالي.

| نية المستخدم            | السطح الحالي المرشح لإعادة الاستخدام                                  | قاعدة التنفيذ                                                                        |
| ----------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| إرسال طلب ومتابعته      | `POST /api/ai/chat/stream`                                            | الحفاظ على `sessionId` وملكية الطلب وسياق المشروع، مع استمرار قيود التنفيذ الخادمية. |
| إعادة قراءة رسائل وجلسة | `/api/ai/chat/sessions` و`/api/ai/chat/:sessionId/messages`           | لا تعتمد الاستعادة على التخزين المحلي وحده.                                          |
| قراءة العمل             | `/api/tasks`, `/api/tasks/:taskId`, `/api/ai/executions/:executionId` | كل نوع يعرض مصدره وحالته ومحاولته؛ لا تخلط Task مع Execution.                        |
| قراءة اختلاف Candidate  | `/api/ai/executions/:executionId/diff` ومسار Proposal المرتبط         | يجب أن يطابق الطلب `projectId`, `operationId`, الإصدار والمرشح المقروء.              |
| مراجعة أو رفض Proposal  | `POST /api/ai/chat/proposals/:proposalId/approve` ومسار الرفض الحالي  | المراجعة لا تعني تطبيق التغيير.                                                      |
| تطبيق تغيير             | `POST /api/ai/chat/apply-changes`                                     | يستخدم موافقة المستخدم وبوابات الصلاحية وبصمة المرشح والتحقق الحالية.                |
| تشغيل Runtime الحالي    | `/api/projects/:projectId/runtime` و`/start`, `/restart`, `/stop`     | لا يعاد تعريف هذا كـ Candidate Preview.                                              |
| سجل مهمة                | `/api/tasks/:taskId/logs` و`/logs/stream`                             | يستخدم للتفاصيل عند الطلب، ولا يصبح الحالة العامة للWorkspace.                       |
| تسليم إلى GitHub        | مسارات Git Delivery الحالية                                           | يظل قرارًا منفصلًا وصريحًا ويتطلب إيصالًا خارجيًا.                                   |

أي خريطة نهائية للمسارات يجب تأكيدها في UXW-00 من OpenAPI/المخطط المولد قبل التنفيذ؛ الأسماء أعلاه توضح سطح إعادة الاستخدام الموجود في مصدر المشروع الحالي.

#### شروط أوامر التغيير

كل أمر يغيّر حالة أو ملفات أو Runtime أو وجهة خارجية يجب أن يربط، بحسب عقد ذلك المسار:

- المستخدم والمشروع المستهدفين.
- معرّف العملية أو Proposal أو التنفيذ والمحاولة.
- `expectedSourceRevision` أو `candidateRevision` عندما يكون الإجراء معتمدًا على نسخة.
- مفتاح idempotency ثابت لإعادة المحاولة للطلب نفسه، ومختلف للقرار الجديد.
- إيصالًا أو حالة خادمية قابلة لإعادة القراءة بعد انقطاع الاتصال.

هذه شروط تصميم للعقود الجديدة؛ لا تفترض أن كل مسار قائم يدعم الحقول نفسها. في UXW-00 يُدقق العقد الفعلي لكل مسار، ثم تُضاف حماية خادمية لازمة قبل أن تعرض الواجهة زرًا يعيد تنفيذ أثر غير idempotent. إعادة المحاولة لا تعيد استعمال مفتاح مع محتوى أو نسخة مختلفة.

## 8. Candidate وPreview: عقد الثقة

### 8.1 هوية المرشح

هوية المرشح في العرض مرتبطة على الأقل بـ:

```text
projectId
proposalId
operationId
executionId
attempt
baseRevision
candidateRevision
changeSetHash
```

لا يُقبل Diff أو دليل أو Preview أو إيصال إذا لم تتفق الهويات التي يتطلبها مسار المصدر. ليست هناك قيمة «مرشح نشط» عالمية تكفي وحدها.

### 8.2 Candidate Preview

عقد الجلسة المقترح:

```ts
type PreviewSessionRequest = {
  target: "project" | "candidate";
  expectedSourceRevision: string;
  proposalId?: string;
  operationId?: string;
  candidateRevision?: string;
};

type PreviewSessionResponse = {
  sessionId: string;
  target: "project" | "candidate";
  sourceRevision: string;
  candidateRevision: string | null;
  status: "starting" | "ready" | "failed";
  accessPath: string | null;
  expiresAt: string;
};
```

المسارات التالية **مقترحة فقط**، ولا تُنشأ قبل إغلاق بوابة الأمان في UXW-03:

```http
POST   /api/projects/:projectId/preview-sessions
GET    /api/projects/:projectId/preview-sessions/:sessionId
DELETE /api/projects/:projectId/preview-sessions/:sessionId
```

### 8.3 متطلبات Preview Gateway

- أضيف مخطط سجل جلسات في PostgreSQL الحالي: يربط `proposalId` ونسخته وهاش Candidate وهاش التغييرات وهاش صورة OCI ونسخة Task Definition بالمالك والحالة وموعد الانتهاء ومرجع ECS Task ARN. يرفض بدء الجلسة إذا لم تعد Proposal مملوكة للمستخدم وبحالة Candidate معزول أو متحقق وبالبصمات نفسها.
- انتقالات الجلسة تستخدم `stateVersion` لمنع كتابة عامل قديم فوق حالة أحدث؛ لا يقبل الانتقال إلى `ready` إلا قبل الانتهاء ومع بقاء Candidate وملكيته مطابقين. على المُنسّق ألا يكتب `ready` قبل نجاح فحص صحة المهمة من Gateway. حد العمر الأولي للجلسة 30 دقيقة.
- اختير أن يعمل ECS Gateway داخل AWS، وأن يبقى PostgreSQL تحت ملكية API الحالي. يرسل API أوامر Start/Stop موقعة بـEd25519 قصيرة العمر؛ يحتفظ API بالمفتاح الخاص، ويحمل Gateway المفتاح العام فقط، فلا يحتاج Gateway بيانات اتصال PostgreSQL أو سرًا مشتركًا لأوامر التحكم.
- نُفذت نواة تنسيق محلية: أمر Start يثبت Candidate والـimage digest وTask Definition، ويطلق مهمة واحدة في private subnets مع `assignPublicIp=DISABLED` و`clientToken=sessionId`. لا يقبل Runner إلا صورة مطابقة للهاش، وTask Definition بلا `taskRole`, بلا أسرار أو environment أو volumes، وبمستخدم غير root وfilesystem للقراءة فقط وإسقاط كل Linux capabilities.
- أضيف عقد DynamoDB مساعد لا يمثل حالة المنتج: قيد ذري يحفظ أعلى `stateVersion` وبصمة الأمر لكل جلسة، مع TTL بعد انتهاء الجلسة. يرفض Gateway Start قديمًا بعد Stop، ويتحقق مرة أخرى بعد RunTask ويوقف المهمة إذا سبقها Stop. يسجل API ARN الناتج عبر CAS على `stateVersion`; وإذا خسر تحديث الربط، يرسل Stop للمهمة نفسها.
- إذا فُقد رد الإطلاق قبل معرفة ARN تبقى الجلسة `starting` قابلة لإعادة المحاولة بمفتاح idempotency نفسه. ما زال عامل المصالحة الدوري غير موصول، ولا يكتب Gateway `ready`؛ يلزم إثبات صحة المهمة عبر بوابة البيانات قبل قبول تذكرة Preview.
- أضيفت نواة تذكرة موقعة قصيرة العمر (30 ثانية) وسجل منع إعادة الاستخدام في PostgreSQL الحالي. تُشتق مفتاحيتها بنطاق مستقل من `SESSION_SECRET`؛ يخزن السجل بصمة `ticketId` لا التذكرة نفسها، ويربط الاستهلاك ذريًا بالمستخدم والمشروع والجلسة و`proposalId` ونسختها و`candidateRevision` و`changeSetHash` والانتهاء. الإصدار والاستهلاك يتطلبان جلسة `ready` ومهمة ECS مسجلة وCandidate ما زال مطابقًا. لا تُمرر التذكرة في URL أو السجلات.
- أصبح لـGateway HTTP runtime مستقل داخل حزمة API، بمسار تحكم محدود وفحص صحة ومسار رفع ZIP موقّع. يخزن الرفع في S3 عبر Task Role، مع حد حجم وتزامن وبصمة SHA-256؛ لا يستخدم مفاتيح AWS ثابتة أو بيانات PostgreSQL.
- قوالب Terraform المحلية تضيف ECS private endpoint وجدول DynamoDB للـfence ومخزن S3 خاصًا ببادئات `build-inputs/` و`preview-build-outputs/` و`builder-job-envelopes/` بعمر يوم واحد، مع فصل أدوار Gateway/Runner/Builder Execution. يبقى تفعيلها `false` افتراضيًا؛ لا يوجد Load Balancer أو Gateway ECS service أو صورة Gateway أو Candidate Task Definition منشورة.
- طُبّق مخطط الجلسات والتذاكر على قاعدة التطوير فقط، واجتاز `schema:check`. بقيت الجداول بلا سجلات، ولم تُنشأ موارد AWS.
- أضيف مُجهّز محلي لمدخلات Builder يقرأ Candidate المثبتة ببصمتها، ويرفض الروابط الرمزية والملفات الحساسة ويفحص أنماطًا معروفة للأسرار ضمن حدود الحجم. هذا الفحص استدلالي وليس ضمانًا شاملًا؛ لا يقبل أي مسار من العميل، ولا يشغّل كود المشروع أو ينقل الملفات إلى AWS.
- أضيف عقد مهمة بناء موقّع قصير العمر من API بـEd25519. يتحقق Builder من التوقيع والمهلة والحقول الدقيقة قبل أي طلب S3، ويستمد هوية المشروع وCandidate و`sourceRoot` وبصمة المصدر والمدخل والمخرج وصورة Builder من المطالبات الموقّعة بدل متغيرات بيئة يختارها المستدعي. اختبارات API وBuilder تتحقق من التوافق بين التنفيذين.
- يأتي مفتاح التحقق من إعداد ثابت في تعريف مهمة Builder؛ يتحقق Gateway من تطابق المفتاح والبيئة الثابتة والصورة وExecution Role، ولا يسمح بتمرير المفتاح عبر overrides. يقبل مسار `POST /internal/v1/preview/builds` التذكرة الموقعة فقط، ويشتق مفاتيح النقل منها، ثم ينشئ روابط S3 قصيرة العمر. لتجنب وضع التذكرة وروابط النقل في حقول بيئة طلب ECS، يحفظها Gateway في ملف بيئة فريد مشفر بـSSE-S3 ومقيّد ببادئة IAM، ويمرر إلى `RunTask` ARN الملف فقط. يسمح Execution Role لـBuilder بقراءة هذه البادئة لتجهيز البيئة، ولا يملك Builder Task Role. يحجز Gateway `jobId` بقيد DynamoDB ذري؛ ولا يسمح باستئناف الطلب إلا إذا أثبتت قراءة قوية تطابق البصمة وإعداد الإطلاق وبيانات الملف. عندها يعيد طلب ECS نفسه بـ`clientToken` نفسه ليحصل على المهمة الأصلية عند ضياع الرد، لا لإنشاء بناء آخر. يرفض أي بصمة مختلفة أو مهمة منتهية أو ملف غير مطابق.
- لا يثبت هذا العقد وحده أن المهمة المنشورة استخدمت الصورة المتوقعة أو أن الخرج سليم. تعريف Builder الثابت والصورة لم يُنشرا بعد؛ وما زال يلزم عامل مصالحة، وفحص هوية المهمة من AWS، وAttestor مستقل يتحقق من الخرج قبل قبول الإيصال.
- أضيف مصدر مستقل `preview_build_jobs` لدورة حياة البناء، بدل وضع حالات البناء في سجل الجلسة الذي لا يُنشأ إلا بعد إيصال موثّق. يربط الطلب بمفتاح idempotency و`jobId/buildId` ومالك المشروع ونسخة Candidate وبصمات المصدر والأرشيف، مع حالات `queued → launching → running → builder_succeeded → verified` والحالات النهائية للفشل/الإلغاء/الانتهاء. لا يخزن التذكرة الموقعة أو روابط S3 الموقعة؛ وتبقى `builder_succeeded` غير كافية لإنشاء جلسة Preview، ولا تتحقق `verified` إلا مع إيصال مستقل. يربط `preview_sessions.build_job_id` جلسة واحدة فقط بمهمة بناء موثقة.
- أضيف مسار API لبدء بناء Candidate عبر `POST /projects/:projectId/proposals/:proposalId/preview-builds`، مع `clientRequestId` ثابت لإعادة المحاولة، ومسار قراءة حالة مقيّد بمالك المشروع عبر `GET /projects/:projectId/preview-builds/:jobId`. يقرأ الخادم `sourceRoot` وبصمة صورة Builder من إعداداته، ويرفض Candidate غير الحالي أو وجود بناء نشط آخر قبل نقل الملفات متى أمكن؛ ويعيد فحص النسخة والمالك داخل معاملة إنشاء السجل. ينقل API الأرشيف المقيّد إلى Gateway ثم يحفظ سجل البناء، وينقل حالته بـCAS قبل إرسال المطالبة الموقعة. إذا ضاع رد Gateway، تبقى الحالة `launching` ويعيد الطلب نفسه المطالبة نفسها ضمن مهلة صلاحيتها؛ بعد انتهاء المهلة لا يعيد إطلاق ECS تخمينًا، وتبقى المصالحة المستقلة مطلوبة. إسقاط الاستجابة لا يكشف مفاتيح التوقيع أو روابط S3 أو مفاتيح الأرشيف. يتطلب التشغيل إعداد `PREVIEW_GATEWAY_URL` ومفاتيح API الخاصة وبصمة Builder و`PREVIEW_BUILD_SOURCE_ROOT`؛ إن غابت الإعدادات يفشل المسار مغلقًا. اختبارات API والخدمة تثبت رفض الطلب غير الصحيح، وعزل الحالة حسب المالك، ومنع بناءين نشطين، وإعادة المحاولة بنفس الهوية بعد غموض النقل.
- أضيف callback خادمي `POST /api/internal/preview-build-jobs/:jobId/receipt` يقبل إيصالًا قصير العمر موقّعًا بمفتاح Attestor العام المنفصل. لا يثق في `status` أو digest من المستدعي، ويرفض الإيصال إلا إذا كانت المهمة `builder_succeeded` وكان digest يطابق سجل البناء. قبل `verified` يقفل المشروع وCandidate ثم يعيد التحقق من المالك والعملية والمراجعة والبصمات والحالة الحالية داخل المعاملة، وبعدها ينفّذ انتقالًا بإصدار حالة متوقع. يبقى المسار غير مهيأ ما لم يتوفر `PREVIEW_BUILD_RECEIPT_PUBLIC_KEY_PEM`؛ ولم يُنشأ أو يُنشر Attestor مستقل بعد، لذا لا يستطيع هذا callback وحده إثبات نجاح البناء أو استعادة مهام ECS.
- أضيفت مصالحة دورية محدودة لمهام ECS: يوقّع API استعلامًا قصير العمر ومقيدًا بهوية البناء، ويتحقق Gateway من توقيعه ثم يعيد المهمة الوحيدة ذات `startedBy` المطابق. يستعيد API حالة `launching → running` بعد ضياع رد البدء، ويسجل فشل الخروج غير الصفري، ولا يسجل `builder_succeeded` إلا بعد خروج صفر وحساب SHA-256 فعليًا لخرج S3 المشفر والمحدود الحجم. غياب الخرج أو هويته يبقي المهمة غير معتمدة؛ هذا لا ينتج إيصال Attestor ولا يجيز Preview. لم يُنشر Gateway أو Builder على AWS.
- أضيف مخطط Drizzle وحارس انتقالات لـ`preview_build_jobs` وربطه بجلسة المعاينة، وطُبّق المخطط الإضافي على قاعدة التطوير واجتاز فحص التطبيق الكامل للمخطط. أضيف مخزن لإنشاء السجل ونقل حالاته والتحقق من الإيصال؛ لكنه لا يثبت وحده نجاح Builder أو سلامة الخرج. لا توجد بعد API لإيقاف جلسة Preview أو إصدار تذكرة للمستخدم، ولا Builder معزول/Attestor أو عامل reconciler يراقب ECS ويصدر أثر البناء. لا ينشئ Candidate صورة OCI أو يسجّل Task Definition.
- أصبح عقد إيصال Builder يفرض توقيع Ed25519 مستقلًا، وبصمة صورة Builder موثوقة، وربط Candidate ومدخلات الأرشيف وهاش ومفتاح ناتج `dist`. لا يتضمن الإيصال صورة التشغيل أو Task Definition؛ تختارهما API من `PREVIEW_ECR_REPOSITORY_URI` و`PREVIEW_RUNTIME_IMAGE_DIGEST` و`PREVIEW_TASK_DEFINITION_ARN` المثبتة خادميًا. تحفظ الجلسة `buildReceiptId` بقيد uniqueness لمنع إعادة استعماله، ويجب الاحتفاظ بصف الجلسة كأثر منع إعادة التشغيل. لم توجد بعد خدمة Attestor أو نقل ناتج إلى Runtime تُصدر هذه الإيصالات وتستهلكها.
- ارتبط مفتاح ناتج البناء وبصمة SHA-256 في سجل الجلسة وأمر Start الموقّع حتى يصلان إلى ECS كقيمتين ثابتتين لا يختارهما Candidate. يرفض المنسّق جلسة قديمة بلا هذا الربط؛ لكنه لا يثبت أن صورة Runtime مبنية أو منشورة أو شغّلت الأثر فعليًا.
- يتحقق Gateway من وجود ناتج S3 وحد الحجم وبصمة SHA-256 المخزنة قبل الإطلاق، ثم يوقّع رابط GET قصيرًا (5 دقائق) للكائن نفسه ويمرره كـoverride للحاوية. كما أضيف مزود نقل يتحقق من أثر الإدخال المشفر وبصمته، ويصدر رابط GET للإدخال ورابط PUT شرطيًا لمرة واحدة إلى مفتاح خرج فريد. تمر هذه الروابط إلى Builder عبر ملف بيئة S3 قصير العمر؛ أما طلب ECS فيحمل ARN الملف فقط. يسمح S3 endpoint وIAM بالنقل ضمن بادئات الإدخال والخرج وملف البيئة، وتنتهي الكائنات بعد يوم. مصدر صورة Runtime الثابتة موجود: ينزّل الرابط دون تحويلات، يتحقق من SHA-256، يرفض أرشيفات غير POSIX ustar والروابط والمسارات المتجاوزة والملفات الزائدة، ثم يخدم ملفات ثابتة من الذاكرة فقط. لم تُبنَ الصورة أو تُنشر، ولم يوجد بعد Builder ينشئ المخرجات.
- أضيفت حقول `build_receipt_id` و`build_output_artifact_key` و`build_output_digest` إلى مصدر Drizzle ومدقق المخطط، مع فهرس uniqueness لـ`build_receipt_id`، وطُبّق المخطط الإضافي على قاعدة التطوير فقط مع فحوص الجاهزية والعلاقات والفهارس. لا توجد تغييرات على الإنتاج.
- لم يُثبت الاتصال الفعلي بـAWS بعد: لا توجد خدمة Gateway عامة منشورة أو إعدادات تشغيل API مُتحقق منها في بيئة نشر. لا يستطيع المسار بدء بناء فعلي حتى تتوفر بوابة TLS وإعدادات التوقيع والصورة ومسار المصدر؛ كما لا توجد بعد مصالحة ECS أو Attestor أو تذكرة/عرض Preview تفاعلي. يجب إبقاء الواجهة مغلقة حتى تكتمل هذه الحدود وتتحقق من Host/Origin والإلغاء وعزل الشبكة.
- يتحقق الخادم من المشروع والمستخدم ومرجع Candidate والإصدار المتوقع.
- كل جلسة مقيدة بمشروع ونسخة ووقت انتهاء وحدود موارد.
- لا يُعرض المنفذ الداخلي الخام أو PID أو مسار نظام الملفات في رابط المستخدم.
- تمر حركة Preview عبر بوابة مصادق عليها ومقيدة؛ لا يختار العميل أصلًا أو عنوان IP أو منفذًا اعتباطيًا.
- يحظر الوصول إلى loopback وعناوين الشبكات الداخلية والخدمات الإدارية وواجهات metadata.
- تُراجع حماية WebSocket وOrigin وHost وCSRF بحسب طريقة البوابة.
- لا تُمرر أسرار تطبيق الخادم أو بيانات اعتماد Git إلى Preview.
- تنتهي الجلسة ويوقف العامل المملوك لها بعد انتهاء TTL أو الإلغاء؛ لا يوقف عامل مشروع آخر.
- تكون سجلات المستخدم منقحة ولا تكشف متغيرات بيئة أو ملفات خاصة.
- معاينة Candidate لا تقع تلقائيًا إلى Runtime المشروع الأساسي عند تعذر Candidate.
- إذا تغيرت ملفات Candidate، توسم الجلسة `stale` ويمنع اعتبارها المعاينة الحالية حتى إنشاء جلسة مرتبطة بالبصمة الجديدة.

### 8.4 الفصل عن Browser Preview Verification

| المستخدم التفاعلي                            | التحقق الآلي                                            |
| -------------------------------------------- | ------------------------------------------------------- |
| يشاهد النتيجة ويتفاعل معها ويختار عنصرًا.    | ينفذ سيناريو تحقق محددًا على بيئة اختبار.               |
| جلسة لها هوية مستخدم وصلاحية وعمر وصول.      | تشغيل آلي محدود بالملف الشخصي والنسخة والإجراء.         |
| لا يثبت النجاح الهندسي بمجرد أن الصفحة فتحت. | ينتج دليلًا يربط محاولة تحقق ونسخة ومخرجات مسموحًا بها. |

يمكن للاثنين تشغيل Candidate واحد فقط إذا اتفقت هوية المصدر والبصمة؛ أحدهما لا يحل محل الآخر.

## 9. فصل الحالات والمصادر

### 9.1 أبعاد الحالة المستقلة

| البعد        | السؤال الذي يجيب عنه                       | ما لا يعنيه                                    |
| ------------ | ------------------------------------------ | ---------------------------------------------- |
| Work / Task  | ما حالة العمل الذي طلبه المستخدم؟          | لا يثبت أن محاولة تنفيذ بعينها نجحت.           |
| Execution    | هل جرى التنفيذ، وبأي محاولة؟               | `completed` لا يعني نجاح التحقق أو القبول.     |
| Verification | هل اجتاز المرشح الاختبار المطلوب؟          | لا يعني أن المستخدم وافق أو أن التغيير طُبق.   |
| Acceptance   | هل استوفى العقد وقُبل بالدليل المطلوب؟     | لا يعني أن التغيير وصل إلى المشروع الحي.       |
| Application  | هل طُبق التغيير على النسخة المستهدفة؟      | لا يعني أن GitHub استلم Commit.                |
| Delivery     | هل استلمت الوجهة الخارجية الإصدار المقصود؟ | لا تستنتج من نجاح Commit محلي أو HTTP بدأ فقط. |
| Preview      | أي إصدار معروض وهل هو حديث؟                | العرض المرئي ليس دليلًا على الصحة.             |

### 9.2 قواعد الحالة

- الحالة المجهولة ليست «معلقة» ولا «ناجحة».
- العطل في مصدر القراءة لا يتحول إلى قائمة فارغة.
- حدث قديم أو محاولة سابقة لا يحدّث الحالة الحالية.
- المستخدم يرى «مسجل كمنتهٍ» عند غياب إثبات مستقل، لا «تم التحقق».
- `Applied` و`Delivered` لا يظهران قبل استجابة أو إيصال موثوق للخطوة نفسها.
- إذا اختلفت `candidateRevision` عن `verification.candidateRevision` فالنتيجة `stale` أو `unknown`، لا `passed`.
- لا تعرض الواجهة ضمانًا كليًا من تجميع حالات جزئية.

### 10.3 الحد بين UX وAgent Core

طبقة Workspace مسؤولة عن:

- العرض والتجميع وإعادة القراءة وحالات التحميل والتعذر.
- توجيه المستخدم إلى الأمر الحالي المناسب.
- حفظ اختيار سطح العمل غير السلطوي واستعادة السياق.
- عرض التفريق بين الحقيقة والدليل والاقتراح.

طبقة Workspace غير مسؤولة عن:

- إنشاء إثبات قبول من كلام النموذج.
- تخفيف صلاحية أو Lease أو قفل أو حارس تنفيذ.
- اختيار عملية كتابة من نص واجهة فقط.
- استنتاج التسليم من رسالة ناجحة.
- إعادة تفسير فشل مصدر الحقيقة على أنه عدم وجود عنصر.

## 11. حزم التنفيذ

ترتيب الحزم هو ترتيب تبعيات وبوابات، وليس دعوة إلى إطلاق عدة تغييرات متزامنة.

```text
UXW-00
  └── UXW-01
       └── UXW-02
            ├── UXW-03 ── UXW-04
            │              └── UXW-06
            └── UXW-05
                   └── UXW-07 (بعد إثبات عزل الكتابة)
```

### UXW-00 — تثبيت عقد المنتج وخط الأساس

**الغرض:** توثيق المسارات المدعومة والرحلات الفعلية وحدود إعادة الاستخدام قبل تغيير الصفحة.

**النطاق:**

- اعتماد هذه الوثيقة كمرجع تنفيذي.
- رسم رحلة مستخدم جديد، وربط مشروع، إصلاح مشكلة، ومراجعة نتيجة.

**الاختبارات:** مخطط Zod، اختبارات Snapshot/ownership/partial source، إعادة تشغيل/replay للحدث، out-of-order/duplicate events، Playwright للانتقال والعودة وإعادة التحميل.

**التنفيذ الأولي — 2026-11-10:**

 - قوالب `infra/aws-preview` تشمل شبكة خاصة وEndpoints وECS Cluster وECR وS3 وDynamoDB والأدوار، مع `enable_foundation_resources=false` افتراضيًا. لا تنشئ ALB أو Listener عام أو خدمة Gateway. تسجّل تعريفَي Builder وAttestor اختياريًا فقط عند تزويد بصمات الصور المثبتة ومفتاح التحقق المطابق؛ ولم يُشغّل plan أو apply.
- لا تُفتح معاينة حية حتى يُبنى Builder وRuntime من صور مثبتة بالبصمة، ويُوصل Builder بمصدر أمر خادمي موثوق وAttestor مستقل، وتُثبت مصادقة الخدمة والتحقق من التذكرة وHost/Origin وTTL والإلغاء وعزل الشبكة.

**حدود التنفيذ المحلي:** توجد شيفرة API وGateway وBuilder وAttestor، وبُنيت صورتا Builder وAttestor واختُبرتا محليًا. لم تُنشر الصور إلى ECR، ولم تُنشأ خدمة Gateway أو مهام/Endpoints على AWS. لذلك لا تزال معاينة المرشح غير متاحة للمستخدم حتى تُنشر الصور وتُطبّق البنية وتُثبت مفاتيح التوقيع.

**النطاق:**

- جلسة Preview معرّفة بنوع الهدف والإصدار ووقت الانتهاء.
- بوابة وصول مصادق عليها؛ لا منفذ داخلي خام.
- عرض Desktop/Tablet/Mobile.
- إيقاف الجلسة بعد انتهاء المدة أو الإلغاء.
- علامة واضحة إذا أصبحت النسخة قديمة.
- استخدام تحقق المتصفح الآلي في مساره المنفصل فقط.

**المخرجات:** Preview تفاعلي لمشروع/مرشح معزول، وإظهار نسخة المصدر وحالتها.

**معيار الإغلاق:**

- Candidate Preview لا يخدم المشروع الأساسي عند فشل العزل.
- الوصول عبر تغيير `sessionId` أو رابط لا يسمح بعبور مشروع/مستخدم.
- لا تُسرب الأسرار أو المسارات الداخلية أو سجلات غير منقحة.
- يوقف العامل المملوك للجلسة وحده.
- يرفض المراجع أو التطبيق Preview قديمًا على أنه النسخة الحالية.

**الاختبارات:** اختبارات حدود الشبكة وHost/Origin وWebSocket إن وجد وTTL والإلغاء وcross-project access وcandidate revision mismatch؛ اختبار متصفح تفاعلي للمستخدم مع اختبار تحقق آلي منفصل.

### UXW-04 — Candidate Review وOutcome Ledger

**التبعيات:** UXW-02 ونجاح UXW-03 للمعاينة المرئية؛ يمكن تطوير عرض Diff على Snapshot إذا لم تكن Preview متاحة بعد.

**النطاق:**

- عرض الملفات وDiff بنطاق Proposal/operation واضح.
- وصل Candidate بالمهمة والتنفيذ والمحاولة وبصمة الأساس والمرشح.
- عرض الاختبار والأدلة والقرار في مساحة واحدة.
- فصل قبول Proposal وتطبيق Candidate وتسليم GitHub.
- سجل زمني يعرض فقط أحداثًا موثقة مع مصدرها.

**المخرجات:** شاشة مراجعة موثوقة تجعل أثر القرار مفهومًا وتمنع حالات نجاح زائفة.

**معيار الإغلاق:**

- المعاينة وDiff ونتائج الاختبار تشير إلى `candidateRevision` و`changeSetHash` نفسيهما.
- تعارض `baseRevision` يمنع التطبيق حتى إعادة التحقق.
- لا يظهر `Applied` دون إيصال تطبيق أو ملاحظة أثر خادمية معتمدة.
- لا يظهر `Delivered` دون إيصال GitHub يثبت الهوية والمرجع البعيد.
- كلمة «مكتمل» لا تُستخدم كبديل عن التحقق أو القبول.

**الاختبارات:** contract tests لربط الهويات؛ اختبارات stale candidate/revision؛ سيناريو رفض؛ سيناريو نجاح؛ فشل تطبيق؛ إعادة محاولة؛ تسليم خارجي؛ Playwright لمراجعة المرشح نفسه بعد Reload.

### UXW-05 — Work Board وPlan While Building

**التبعيات:** UXW-02.

**النطاق الأولي:**

- عرض خطط/مهام/تنفيذ مدعوم في لوحة من دون نسخ حالة مخزنة.
- محادثة أو تخطيط لطلب آخر أثناء نشاط الطلب الحالي، مع توضيح الاستقلال.
- إظهار الاعتماد بين الطلبات عندما يكون معروفًا.
- حصر العمل المتزامن في التحليل والقراءة أو خطط لا تكتب.

**بوابة التوازي الكتابي:** لا يبدأ Candidate كاتب جديد أثناء وجود كاتب آخر على المشروع إلا إذا أثبتت الخدمة أن لكل عملية مساحة مستقلة وملكية وLease وبصمة أساس ومسار دمج.

**معيار الإغلاق:**

- كل بطاقة تعرض مصدرها ومعرّفها ومحاولتها الفعلية.
- لا تتغير الحالة بسبب event قديم أو query cache فقط.
- التخطيط المتزامن لا ينفذ تغييرات ضمنية.
- أي عملية كتابة متزامنة موثقة في Candidate مستقل؛ وإلا تمنع وتشرح السبب.

**الاختبارات:** بيانات مختلطة الحالات؛ الأحداث المتأخرة؛ محادثات متعددة؛ خطط متعارضة؛ إثبات أن رفض التوازي لا يستدعي الكاتب ولا يغير الشجرة.

### UXW-06 — Proof-Aware Visual Canvas

**التبعيات:** UXW-03 وUXW-04.

**النطاق:**

- اختيار عنصر من Preview محدد النسخة.
- تمرير مرجع عنصر آمن محدود إلى حوار الوكيل.
- إنشاء تغيير قابل للمراجعة عبر مسار Candidate الحالي.
- مقارنة بدائل بصرية قابلة للحفظ والمراجعة.
- تغيير حجم viewport دون تحويله إلى محرر DOM وقتي.

**معيار الإغلاق:**

- كل اختيار مربوط بجلسة Preview ونسخة صالحة؛ الاختيار من معاينة قديمة يبطل أو يطلب تحديثها.
- لا يسمح للمتصفح بإرسال مسار نظام ملفات حر أو كود/محدد يفتح وصولًا غير مقيد.
- التعديل الناتج موجود في Diff وCandidate ويمكن إعادة تحميله.
- تظهر أدلة التحقق ذات الصلة بالمرشح.

**الاختبارات:** اختيار عنصر عبر Playwright؛ نسخ عنصر/جلسة بين المشاريع؛ DOM متغير؛ عنصر لا يملك source map؛ التحديث وإعادة تحميل Preview؛ التحقق أن التعديل لا يختفي.

### UXW-07 — Safe Parallel Execution وRecovery

**التبعيات:** UXW-05 وUXW-04، مع إثبات عزل كل مسار كتابة قبل تمكينه.

**النطاق:**

- Workspace مستقل لكل Candidate كاتب.
- Dependency Graph وConflict Detection وReconciliation.
- هوية attempt وowner/lease متسقة عبر الاستئناف والعامل القديم والجديد.
- نقاط استعادة للعمل المحدود وعقوده.
- عرض الفرق بين استعادة محاولة وبين عكس تغيير مطبق.
- لا استعادة عامة لقاعدة بيانات أو خدمات خارجية بزر واحد.

**معيار الإغلاق:**

- لا تكتب مهمة في مساحة مهمة أخرى.
- لا يتقدم Candidate على base revision تغير دون إعادة دمج وإعادة تحقق.
- لا يكتب عامل قديم أو Attempt قديم إيصالًا أو يحذف مساحة محاولة جديدة.
- استعادة التنفيذ لا تدعي إعادة حالة كل المشروع.
- كل تعارض يظهر قبل التطبيق، وله نتيجة مراجعة وإعادة تحقق.

**الاختبارات:** crash/restart، lease expiry، worker replacement، محاولة قديمة، تعارض ملفات، تعارض Schema، قتل عامل، استعادة Candidate، دمج ثم تحقق من البصمة، تأكيد عدم المساس ببيانات خارج النطاق.

## 12. خطة الاختبار والقبول الشامل

### 12.1 الرحلات الإلزامية

| الرحلة                 | الثابت الذي يجب إثباته                                                           |
| ---------------------- | -------------------------------------------------------------------------------- |
| First Run              | يبدأ المستخدم هدفًا حتى مع فشل Dashboard Work Summary.                           |
| Existing Project       | سياق المشروع والصلاحية وإصدار الملفات واضح قبل الإجراء.                          |
| Goal to Preview        | الهدف يظل مرتبطًا بالجسلة والمرشح الذي يظهر في Canvas.                           |
| Preview to Review      | المعاينة وDiff والتحقق متطابقة في بصمة Candidate.                                |
| Review to Apply        | لا يمكن تطبيق مرشح تغير بعد مراجعته دون إعادة التحقق.                            |
| Apply to Evidence      | يظهر ما طبق وما لوحظ فقط من الاستجابة/الدليل المعتمد.                            |
| Apply to Delivery      | لا تُخلط نتيجة التطبيق المحلي بتسليم GitHub.                                     |
| Recovery               | Reload وانقطاع الشبكة يعيدان الحالة الصحيحة من الخادم دون إرسال أو تطبيق تلقائي. |
| Conflict               | يتوقف التعارض قبل أثر غير قابل للتراجع، ويعرض الخيارات والنتيجة.                 |
| Cross-project security | لا يستطيع المستخدم قراءة/عرض جلسة مشروع آخر بتغيير معرّف أو رابط.                |

### 12.2 مستويات الاختبار

1. **Unit:** تحويل Snapshot إلى العرض، والتغطية الجزئية، حالة `unknown`, ترجمة status، الروابط العميقة.
2. **Contract:** مخططات API، enums، IDs، revisions، الحقول nullable، ومخرجات الأخطاء.
3. **Integration:** تجميع مصادر المشروع/المحادثة/المهمة/التنفيذ/Proposal من قاعدة اختبار معزولة.
4. **State/replay:** تكرار الأحداث، انقطاع وإعادة اتصال، ترتيب قديم، cursor منتهي، محاولات متعددة.
5. **Browser security:** الوصول بين المشاريع، انتهاء الجلسة، Host/Origin، WebSocket، الشبكات الداخلية، تنقيح السر.
6. **Playwright:** رحلة كاملة من الهدف حتى مراجعة نتيجة واحدة، على Desktop وMobile وعلى RTL.
7. **Manual accessibility:** قارئ شاشة، لوحة مفاتيح، focus return، Escape، تمييز بصري، zoom وviewport ضيق.

### 12.3 معايير قياس تجربة الاستخدام

يُسجل خط أساس قبل تحديد أهداف رقمية:

- Time to First Preview.
- Time to First Accepted Outcome.
- Human Intervention Rate.
- Context Switches.
- Preview Revision Mismatch.
- Candidate Rejection Rate وأسباب الرفض.
- Recovery Success Rate.
- Unintended Mutation Count.

حد غير قابل للتفاوض: `Unintended Mutation Count = 0` في المسارات التي تتطلب موافقة صريحة. لا يستخدم عدد الاختبارات الخضراء بديلًا عن نجاح الرحلة أو صحة الإثبات.

### 12.4 شروط الإطلاق العام

- إغلاق معايير كل حزمة سابقة في مخطط التبعيات.
- اجتياز رحلة Playwright كاملة على النسخة نفسها.
- نجاح فحوص الوصول والتفويض للقراءات والأوامر وPreview.
- لا توجد شاشة تعرض `Applied`, `Proven`, أو `Delivered` بلا مصدر خادمي مطابق.
- لا توجد حالة فقد سياق أو إرجاع لمحاولة قديمة.
- تبقى حالات عدم التوفر/القدم مرئية وصادقة.
- عدم وجود تراجع غير مقبول في تجربة الهاتف أو RTL أو لوحة المفاتيح.
- كل تغيير UX مرتبط بحزمة UXW ومعيار إغلاق، لا بمجرد تحسين شكلي.

## 13. الأمان والخصوصية

- مصادقة Clerk الحالية لا تستبدل تفويض المشروع؛ تحقق الخادم مطلوب لكل endpoint.
- تخزين Query Cache ينظف عند تبدل المستخدم، وتظل Snapshot/Events مرتبطة بالمالك الحالي.
- لا يرسل الخادم إلى الواجهة بيانات اعتماد Git أو متغيرات سرية أو محتوى ملفات غير مطلوب.
- الوصول إلى Preview capability قصيرة الأجل ومقيدة بالجلسة والهدف والإصدار.
- يمنع Preview Gateway SSRF وloopback وmetadata وcross-tenant routing.
- لا يحتوي Event Stream على أسرار أو محتوى غير منقح.
- لا يصبح intent أو branch أو session من العميل حدًا للتفويض.
- لا يؤدي إدخال المستخدم إلى تغيير صلاحيات الأداة أو مستوى الخطر تلقائيًا.
- إجراءات التطبيق أو التسليم تتطلب إعادة فحص الصلاحية والـrevision والسياسة في لحظة التنفيذ.
- الإلغاء أو انتهاء الجلسة لا يمنح العامل صلاحية الاستمرار في الخلفية دون عقد/Lease صحيح.
- قيود الاستعادة والتسليم الخارجية يجب توضيحها؛ لا نعرض Undo شاملًا حين لا يوجد.

## 14. التوطين والإتاحة

- الواجهة الأساسية بالعربية RTL، مع أسماء إجراءات مباشرة.
- القيم التقنية مثل `projectId`, commit SHA، المسار، command، branch وevidence ref تظهر LTR وفي عنصر مخصص.
- لا تدمج تسمية الحالة العربية والرمز التقني في عقدة وصول واحدة غير قابلة للتمييز.
- لكل إجراء اسم Accessible يحدد العنصر أو النتيجة، حتى لا تتكرر أسماء عامة مثل «إغلاق».
- حالات Loading/Error/Empty/Partial/Stale لها دلالات منفصلة.
- لا يكون اللون وحده مؤشر حالة أو موافقة.
- لوحة العمل قابلة للاستخدام دون سحب أفقي على الهاتف.
- تظهر حاجة المستخدم ومخاطر القرار قبل الضغط، ويحافظ الرفض على البيانات.
- التنقل بالتبويب يوضح موضع التركيز، ويعيده بعد إغلاق Dialog/Drawer.

## 15. قرارات ثابتة وأسئلة مؤجلة

### 15.1 قرارات ثابتة في الإصدار 1.0

1. المساحة الرئيسية واحدة مرتبطة بمشروع، لا صفحة مستقلة لكل قدرة.
2. Snapshot طبقة قراءة؛ لا جدول حالة موحدًا كمصدر حقيقة.
3. حالات التنفيذ والتحقق والقبول والتطبيق والتسليم منفصلة.
4. Browser Preview Verification غير Preview التفاعلية.
5. Candidate والPreview والأدلة والإيصالات ملزمة ببصمة وملكية ومحاولة واضحة.
6. لا توازٍ كتابي قبل إثبات عزل التنفيذ.
7. لا استعادة عامة للبيانات الخارجية ضمن زر Rollback موحد.
8. لا يُبنى أي جزء على كيان أو مسار غير مدعوم.

### 15.2 أسئلة يجب حسمها في UXW-00 أو بوابة الحزمة المعنية

- ما المصادر الفعلية ومعايير freshness التي يجب أن يجمعها Snapshot لكل بطاقة؟
- كيف يبنى cursor قابل للاستعادة فوق الأحداث الدائمة الحالية من دون ترتيب مصطنع؟
- ما النطاق ووسيلة التبادل الآمن لتذكرة HTTPS، وما سياسة النطاقات وملفات الارتباط في المتصفح؟
- كيف تُبنى صورة Vite/React الثابتة من Candidate دون تشغيل سكربتات غير موثوقة أو نقلها قبل الموافقة؟
- ما منطقة AWS وسقف الإنفاق وحدود التزامن والموارد لكل جلسة؟
- حُسم موقع المنسق: Gateway داخل AWS، وAPI يرسل أوامر تحكم Ed25519 قصيرة العمر؛ يبقى تحديد إصدار/تدوير المفتاح الخاص في Replit والمفتاح العام في Gateway.
- حُسم عقد النقل: POST HTTPS إلى مسار ثابت؛ DynamoDB conditional fence يرفض نسخة Start أقدم بعد Stop أحدث. يبقى بناء Gateway HTTP runtime وجدول الـfence الفعلي في AWS.
- ما آلية التنظيف المرتبطة بانتهاء الجلسة دون حذف صورة ما زالت مستخدمة؟
- هل يبقى Intent Brief مسودة مرتبطة بالرسالة، أم يحتاج عقدًا دائمًا جديدًا؟ لا ينشأ كيان جديد قبل قرار موثق.
- ما قواعد الكشف الآمن عن مصدر عنصر بصري إلى ملف/مكون؟ لا تخمين مسار من DOM وحده.
- ما خط أساس مؤشرات تجربة المستخدم قبل تعيين أهداف؟
- أي مسارات قديمة تصبح تحويلًا، وأيها تبقى تفاصيل متقدمة؟

لا تؤجل الإجابة عن سؤال أمني إلى مرحلة الواجهة؛ تُغلق قبل تشغيل Preview أو التوازي.

## 17. شروط كل طلب تنفيذ لاحق

على كل طلب أو PR متعلق بـUX Workspace أن يذكر:

1. رقم الحزمة UXW ومعيار الإغلاق الذي يعالجه.
2. مصدر الحقيقة الحالي الذي يعتمد عليه.
3. الملفات أو العقود التي يعاد استخدامها، وما الذي لا يعاد استخدامه.
4. هويات `projectId`, `sessionId`, `taskId`, `executionId`, `attempt`, `proposalId`, `operationId`, revisions ذات الصلة.
5. حالات الفشل/القدم/التعذر التي ستظهر للمستخدم.
6. اختبار السلوك والثابت الذي يثبته، لا مجرد عدد الاختبارات.
7. دليل أن الإجراء لم يتجاوز صلاحية أو موافقة أو قيد عزل.

إذا لم يستطع الطلب تحديد هذه النقاط، فهو غير جاهز للتنفيذ في Workspace.

## 18. تعريف النجاح النهائي

يُعتبر EngineeringOS Studio قد حقق هدف هذه الوثيقة عندما يستطيع مستخدم غير تقني تنفيذ الرحلة الرأسية على مشروع مدعوم، من وصف الهدف إلى مراجعة وتطبيق نتيجة متحقق منها، داخل مساحة عمل واحدة، من دون فقد السياق أو تضليل الحالة أو تجاوز الموافقة.

والاختبار الحاسم ليس أن كل صفحة تعمل منفردة؛ بل أن:

```text
الهدف + المشروع + التنفيذ + Candidate + Preview + Verification
+ Acceptance + Apply + Delivery
```

تبقى مربوطة بالهويات والإصدارات الصحيحة عبر القراءة الحية، Reload، إعادة الاتصال، المحاولة والفشل، ولا تعلن الواجهة أكثر مما أثبته النظام.
