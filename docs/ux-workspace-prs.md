## 0. سلطة الوثيقة وطريقة استخدامها

هذه الوثيقة هي المرجع الواحد لتنفيذ تجربة UX Workspace. وهي تجمع المتطلبات المستهدفة، والحدود المعمارية، والعقود المقترحة، وإعادة الاستخدام المسموح، وترتيب حزم العمل، واختبارات القبول.

كل ادعاء عن الموجود الآن موسوم ضمنيًا أو صراحةً بأنه **موجود** أو **جزئي** أو **مقترح**. ذكر واجهة أو مسار في قسم «الموجود» لا يعني أنه يحقق تجربة Workspace كاملة.

ترتيب السلطة عند التعارض:

1. صلاحيات الخادم وعقود القبول والإثبات والتسليم الحالية.
2. هذه الوثيقة لمتطلبات UX Workspace وقرارات تنفيذها.
3. ملاحظات التصميم والاستراتيجية السابقة، وهي سياق وليست تفويضًا لتجاوز هذه الوثيقة.

إذا كشف التنفيذ أن عقدًا حاليًا أو بوابة أمان لا يطابق هذا التصميم، يتوقف التنفيذ عند الحزمة المتأثرة. تُحدّث هذه الوثيقة ونتائج التدقيق أولًا؛ لا يُنشأ مسار بديل أو حالة واجهة توحي بنجاح غير مثبت.

لا تعني هذه الوثيقة أن جميع الحزم معتمدة للتنفيذ بالتوازي. لكل حزمة شروط دخول وإغلاق، والبوابات الأمنية والاعتمادية تتقدم على الجدول.

## 1. الملخص التنفيذي

يبني EngineeringOS تجربة **Intent-to-Outcome Workspace**: يصف المستخدم نتيجة يريدها، ويحافظ النظام على سياق المشروع والطلب، ويعرض العمل الجاري ونسخته المرشحة والتحقق والقرار والأثر في مساحة واحدة.

الهدف ليس إعادة بناء Agent Core أو نقل الجداول إلى مخطط موحد. الهدف هو وضع طبقة UX وقراءة موحدة فوق مصادر الحقيقة القائمة، مع إبقاء المحادثة والمهام والتنفيذ والقبول والتطبيق والتسليم مفاهيم منفصلة.

التميّز المطلوب:

- **بدء من الهدف:** لا يُطلب من المستخدم غير المتخصص اختيار أداة أو كيان داخلي قبل شرح النتيجة.
- **استقلالية مرئية:** يرى المستخدم ما يفعله الوكيل، وما ينتظره، وما يحتاجه منه.
- **نتائج تحمل دليلها:** لا تُعرض «مكتملة» على أنها «متحقق منها» أو «مطبقة» أو «مسلمة».
- **معاينة مرتبطة بالنسخة:** لا يراجع المستخدم نسخة قديمة على أنها المرشح الحالي.
- **موافقة ذات أثر واضح:** القبول والتطبيق والتسليم إجراءات منفصلة، وكل إجراء يعاد التحقق منه على الخادم.

تُبنى أولًا شريحة رأسية واحدة:

> الهدف → فهم قابل للمراجعة → عمل في مرشح معزول → معاينة للمرشح نفسه → تحقق ومراجعة → موافقة وتطبيق → سجل نتيجة يوضح الأثر المثبت.

لا تُفعّل المعاينة التفاعلية لمرشح أو التوازي الكتابي قبل إثبات عزل مساحة المرشح، وربط التنفيذ والأدلة والمعاينة والتطبيق بالنسخة نفسها.

## 2. المستخدم والوعد المنتجّي

### 2.1 المستخدم الأساسي

مستخدم عربي لا يلزم أن يعرف البرمجة أو المصطلحات الهندسية. يريد وصف ما يريد، وفهم التقدم والقرارات المهمة، ثم مراجعة نتيجة حقيقية قبل اعتمادها.

المستخدم المتمرس يجب أن يستطيع فتح التفاصيل التقنية عند الحاجة، من دون أن تصبح تلك التفاصيل الطريق الإلزامي للمستخدم العادي.

### 2.2 وعد المنتج

يستطيع المستخدم الإجابة من مساحة العمل على الأسئلة التالية:

1. ماذا فهم النظام من طلبي؟
2. ما الذي يعمل الآن، وما الذي ينتظرني؟
3. أي مشروع ونسخة ومرشح يعرضهم النظام؟
4. ماذا تغيّر وما الذي اختُبر؟
5. ماذا ثبت بالدليل، وما الذي لم يثبت؟
6. ما القرار المطلوب مني، وما عاقبة كل خيار؟
7. هل طُبق التغيير؟ وهل سُلّم إلى GitHub فعلًا؟

### 2.3 مبادئ UX ملزمة

- المحادثة وسيلة تحكم وليست المنتج كله.
- إظهار الحالة بحسب الحاجة؛ التفاصيل التقنية قابلة للكشف التدريجي.
- المصطلحات العربية تشرح الهدف والخطوة والتنفيذ ولا تخلط بينها.
- لا يُستبدل غياب البيانات بعبارة «لا يوجد عمل»؛ تُعرض حالة عدم التوفر أو نقص التغطية.
- لا يعرض الربع الأخضر أو اكتمال التنفيذ ما لم تثبت الاستجابة المعنية ذلك.
- تبقى اللغة العربية RTL؛ مسارات الملفات والمعرّفات والأوامر والقيم اللاتينية معزولة باتجاه LTR.
- القيم المعروضة في الواجهة لا تمنح صلاحية، ولا تصبح بديلًا عن تحقق الخادم.

## 3. النطاق والاستبعادات

### 3.1 داخل النطاق

- مدخل هدف واضح لمسار مشروع جديد أو مشروع قائم.
- غلاف Workspace متمحور حول المشروع والطلب.
- ملخص قراءة يجمع حالة مصادر العمل المدعومة من دون نسخ مصادر الحقيقة.
- حالة محادثة وتقدم وإجراءات موحدة قابلة للاستعادة بعد إعادة التحميل أو انقطاع الاتصال.
- معاينة تفاعلية للمشروع أو المرشح عبر بوابة مصادق عليها، إذا اجتازت بوابة العزل والأمان.
- مراجعة المرشح وربط Diff ونتائج التحقق والقبول والتطبيق والتسليم بهويته.
- إدارة Release ونشر التطبيق ومتابعة صحته واستعادته بعد قبول وتطبيق التغيير؛ مسار مستقل وموافقة نشر منفصلة ضمن UXW-08.
- عرض مهام العمل المدعومة والتخطيط لطلب آخر مع منع التوازي الكتابي غير المعزول.
- Canvas بصري محدود ومربوط بمصدر تغيير قابل للمراجعة.
- استعادة تشغيل العمل داخل حدوده، مع تمييزها عن استرجاع ملفات المشروع أو البيانات الخارجية.

### 3.2 خارج النطاق

- إعادة بناء Agent Core أو موفري الذكاء الاصطناعي أو محرك التنفيذ.
- توحيد كل أنواع السجلات في كيان أو حالة واحدة.
- اعتماد شاشات أو حقول أو حالات أو مسارات تعتمد على كيان Mission؛ هذه الوثيقة تخص القدرات المدعومة فقط.
- تعديل سياسات الإذن أو القبول أو إثبات Canonical Proof أو حواجز التطبيق والتسليم بغرض تبسيط الواجهة.
- تشغيل كتابي متوازٍ قبل إثبات ملكية وعزل كل مساحة مرشح وقاعدة فض التعارض.
- Infinite Canvas، أو محرر بصري عام، أو عدة أنواع مخرجات قبل نجاح الشريحة الرأسية.
- اعتبار الاستعادة العامة للمشروع أو استعادة قاعدة بيانات أو خدمة خارجية زرًا واحدًا غير مقيّد.
- نشر Production تلقائيًا أو تسليم التغيير إلى GitHub تلقائيًا بعد المعاينة؛ UXW-08 يصف نشرًا منفصلًا يتطلب موافقة صريحة.
- إعادة تصميم الصفحات التقنية كلها. تبقى التفاصيل المتقدمة متاحة، لكنها ليست الطريق الرئيسي.

### 4.1 نتائج الفحص المعمارية

1. توجد القدرات الأساسية في مسارات منفصلة؛ لا يوجد بعد عقد Workspace واحد أو شاشة واحدة تجمعها.
2. لا يوجد حاليًا `WorkspaceSnapshot` أو Workspace Event Stream موحد في واجهة API.
3. المعاينة التفاعلية للمستخدم ليست هي Browser Preview Verification.
4. لوحة Runtime الحالية لا تثبت أن النسخة المعروضة هي Candidate محدد.
5. إعادة استخدام Delivery Workspace لا تثبت وحدها عزل كل تنفيذ من بدايته.
6. ملخص العمل الحالي جزئي وذو نطاق تغطية معلوم، لذلك لا يجوز استخدام غياب عنصر منه كدليل على غياب العمل.

## 5. التصميم المستهدف

### 5.1 سطح الوصول والمسارات

المسار الأساسي المقترح:

```text
/projects/:projectId/workspace
```

أسباب الاختيار:

- يبقي Workspace تحت هوية المشروع الحالي.
- يسمح بروابط عميقة قابلة للمشاركة وفق صلاحيات المشروع.
- لا يتطلب تغيير artifact أو تغيير المسارات التقنية القديمة دفعة واحدة.

تبقى `/ai` و`/projects/:id` و`/tasks` تفاصيل متقدمة أو مداخل توافقية. أي تحويل لها يكون صريحًا ويحفظ `projectId` و`sessionId` ومعرّفات العنصر المستهدف؛ لا يحذف سياقًا ولا يختار مشروعًا آخر بصمت.

### 5.2 مناطق Workspace

#### أ. Agent Panel

المسؤولية: الهدف، الحوار، أسئلة التوضيح، ملخص الفهم، القرارات التي تحتاج المستخدم.

يعرض:

- وصف الهدف الحالي ومصدره.
- ما فهمه النظام كنطاق وقيود ومعايير مقترحة، مع تمييز ما أكده المستخدم عما استنتجه النظام.
- رسائل المحادثة والتقدم والطلب الذي يعمل عليه.
- أسئلة وقرارات لها سبب وأثر لكل اختيار.
- استعادة الجلسة بعد Reload أو انقطاع الاتصال.

لا يعرض التخمين على أنه مواصفة مؤكدة، ولا يخفي أن إجراءً ينتظر موافقة أو مدخلًا بشريًا.

#### ب. Project Canvas

المسؤولية: عرض النتيجة التي تخص نسخة محددة، والتفاعل معها، لا تقديم iframe عام بلا هوية أو حماية.

الإصدارات المتدرجة:

1. Preview للمشروع الحالي، إذا كان تشغيل المشروع متاحًا.
2. Preview مرشح معزول، بعد نجاح بوابة العزل.
3. أوضاع عرض Desktop / Tablet / Mobile.
4. تحديد عنصر مرئي وربطه بمصدره، بعد إثبات مصدر الربط.
5. مقارنة بدائل بصرية قابلة للمراجعة.

كل معاينة تعرض نوع الهدف (مشروع حالي أو Candidate)، بصمة النسخة، حالة التشغيل، وقت آخر تحديث، وحالة القِدم. عند عدم توفر Preview يعرض السبب أو الإجراء الممكن، ولا يعرض Preview قديمًا على أنه حي.

#### ج. Work & Trust Panel

المسؤولية: العمل النشط، حالة التنفيذ، التحقق، المراجعة والقبول والتطبيق والتسليم.

يعرض الأقسام الوظيفية:

- يعمل الآن.
- ينتظر قرارًا أو معلومة.
- جاهز للمراجعة.
- نتائج مسجلة مؤخرًا.

تظل مصادر الحالة منفصلة خلف العرض. لا تُسقط `failed verification` أو `pending acceptance` بسبب `completed execution`.

### 5.3 السلوك حسب الجهاز

| الجهاز  | السلوك المستهدف                                                                                                                 |
| ------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Desktop | المناطق الثلاث مرئية، مع مساحة أكبر للمعاينة وإمكانية تغيير حجم اللوحات أو طيّها.                                               |
| Tablet  | منطقتان ظاهرتان؛ يمكن إظهار اللوحة الثالثة كدرج أو تبويب مع بقاء المشروع والطلب المحددين.                                       |
| Mobile  | تبويبات أو خطوات واضحة للوكيل والمعاينة والعمل والمراجعة. لا تُخفى حالة الانتظار أو زر الموافقة في لوحة أفقية غير قابلة للوصول. |

المقاسات النهائية تُحسم بالاختبارات البصرية الفعلية. لا تُفرض ثلاث أعمدة على الهاتف.

### 5.4 الهيكل الوظيفي المقترح

```text
Project identity + current revision
├── Agent Panel
│   ├── Intent Brief
│   ├── Conversation / streamed progress
│   └── Decision Inbox
├── Project Canvas
│   ├── Current-project preview or Candidate preview
│   ├── Viewport modes
│   └── Revision / freshness indicator
└── Work & Trust
    ├── Task and execution progress
    ├── Candidate diff
    ├── Verification evidence
    ├── Human review and acceptance
    ├── Apply receipt
    └── Delivery receipt
```

هذا تقسيم للمسؤوليات، وليس إلزامًا بأن تظهر كل التفاصيل في آن واحد.

## 6. دورة المستخدم المستهدفة

### 6.1 بدء مشروع جديد

1. يختار المستخدم «إنشاء مشروع جديد» ويصف ما يريد إنجازه.
2. يعرض النظام فهمًا مختصرًا، والأسئلة الضرورية فقط، وحدود ما سيبدأ به.
3. يراجع المستخدم النطاق قبل أي تغيير مؤثر.
4. ينشأ المشروع أو العملية عبر المسارات الحالية المخولة.
5. ينتقل المستخدم إلى Workspace من دون فقد وصفه أو رسائله.

### 6.2 العمل على مشروع قائم

1. يختار المستخدم مشروعًا يملك صلاحية الوصول إليه.
2. يقرأ النظام سياق المشروع والإصدار الفعلي.
3. يصف المستخدم النتيجة أو يختار هدفًا من مسودته.
4. تعرض بطاقة Intent Brief: الهدف، ما فُهم، النطاق، القيود، ومعيار النجاح المقترح.
5. يوضح النظام المعلومات الناقصة أو يواصل ضمن النطاق المؤكد.

### 6.3 من الهدف إلى نتيجة متحقق منها

```text
Describe
  → Understand
  → Plan
  → Build in Candidate
  → Candidate Preview
  → Verify
  → Review
  → Apply
  → Verify applied effect
  → Deliver (separate, explicit operation)
```

قواعد الدورة:

- لا يكتب بناء Candidate إلى النسخة الأساسية مباشرة.
- Preview وVerification يرتبطان ببصمة Candidate نفسها.
- إذا تغيرت بصمة الأساس بعد التحقق، يتوقف التطبيق حتى يعاد التحقق.
- موافقة المستخدم على Proposal ليست إثباتًا أن التطبيق نجح.
- نجاح التطبيق ليس إثباتًا أن GitHub استلم التغيير.
- يكون لكل خطوة فاشلة تفسير واضح وإجراء استعادة آمن، لا نجاحًا بصريًا متفائلًا.

### 6.4 Decision Inbox

كل قرار معروض يجيب:

1. ما المطلوب؟
2. لماذا لا يستطيع النظام المتابعة من دونه؟
3. ما أثر كل اختيار؟

أمثلة: توضيح نطاق، اختيار بديلين، مراجعة Candidate، قبول تطبيق، قرار تسليم إلى GitHub، أو إقرار خطر محدد.

لا تتحول كل الأحداث الداخلية إلى إشعار. تجمع الواجهة فقط ما يحتاج انتباه المستخدم، مع رابط إلى السجل التقني عند الطلب.

## 7. عقد قراءة Workspace المقترح

### 7.1 قواعد العقد

- `WorkspaceSnapshot` **Read Model** تجميعي، وليس مصدر حقيقة جديدًا ولا سجلًا بديلًا.
- يقرأ الحالة من مصادرها الحالية: المشروع، المحادثة، المهمة، التنفيذ، Proposal/Candidate، التحقق، القبول، التطبيق، Runtime والتسليم.
- لا يخزن حالة تنفيذ مكررة لمجرد أن الواجهة تحتاج تجميعها.
- لا يضمّن أي حقل أو كيان غير مدعوم ليبدو العقد شاملًا.
- لا يختزل الحالات المستقلة إلى `completed`.
- أي استجابة جزئية أو قديمة أو غير متاحة تصف ذلك صراحةً.
- معرّفات الإجراء والقيم المقدمة من العميل لا تمنح صلاحية؛ يعاد التحقق عند كل أمر.

### 7.2 واجهة TypeScript المقترحة

هذا عقد تصميمي جديد، وليس نوعًا موجودًا حاليًا. يجب تحويله إلى مخطط Zod موحد في مصدر العقود المعتمد وتوليد عميل API منه؛ لا تُكتب نسخة مستقلة داخل الواجهة.

### 7.3 أحكام العقد

- `rawStatus` قيمة مصدرية معروفة؛ الترجمة والعرض منفصلان.
- `nextActions` اقتراحات واجهة، وليست قائمة صلاحيات. كل أمر يعاد فحصه خادميًا.
- `intentBrief` ملخص قابل للمراجعة؛ المعايير المقترحة ليست عقد قبول حتى يؤسسها المسار الخادمي المعتمد.
- `candidateRevision` و`changeSetHash` قد يكونان `null` قبل وجود Candidate؛ لا يخترع العميل بصمة.
- `acceptance.status = "proven"` لا يصدره النموذج أو المتصفح؛ يصدر فقط بعد تحميل دليل القبول المعتمد والتحقق من هويته.
- `application.status = "applied"` يتطلب إيصالًا أو حالة خادمية تثبت التطبيق.
- `delivery.status = "delivered"` يتطلب إيصال التسليم الخارجي ومرجعه البعيد.
- `sources` و`freshness` تمنعان تحويل عطل مصدر القراءة إلى شاشة فارغة أو حالة نجاح.
- يجب إسقاط الحقول غير المدعومة أو إظهارها `unknown`؛ لا نستنتج حالة من النص أو لون Badge.

### 7.4 مسارات القراءة والأحداث

#### Snapshot

```http
GET /api/projects/:projectId/workspace
```

**مقترح، غير موجود حاليًا.** يتطلب مصادقة وحاجز صلاحية المشروع. يعيد `WorkspaceSnapshotV1` في قراءة متماسكة قدر الإمكان، أو يحدد المصادر التي تعذر قراءتها. لا يكتب بيانات تشغيلية جديدة ولا ينفذ إجراءً.

#### Workspace Event Stream

```http
GET /api/projects/:projectId/workspace/events
Accept: text/event-stream
Last-Event-ID: <opaque-cursor>
```

غرضه تنبيه العميل إلى تغير حالة المشروع، ثم إعادة قراءة Snapshot موثوقة. عند أول اتصال يرسل `workspace.resync` لإغلاق الفجوة بين جلب Snapshot وبدء الاشتراك؛ وعند إعادة الاتصال يستخدم الخادم `Last-Event-ID` لإعادة تشغيل الأحداث ضمن نافذة محدودة. لا يستبدل:

- تدفق رسائل AI Chat الحالي.
- تدفق سجلات مهمة بعينها.
- سجل الأحداث التاريخي `/api/events`.

صيغة الحدث المقترحة:

```json
{
  "eventVersion": 1,
  "projectId": "…",
  "entityKind": "project",
  "entityId": "…",
  "eventId": "…",
  "occurredAt": "…",
  "snapshotCursor": "opaque"
}
```

الشروط:

- `id`/cursor معتم ومعرّف من الخادم؛ يستخدم فقط لإعادة تشغيل سجل الأحداث الحالي ولا يمنح صلاحية قراءة.
- يعاد فحص صلاحية المشروع عند إنشاء البث، مع إغلاقه عند انتهاء الجلسة أو صلاحية الوصول.
- تُرسل بيانات إبطال محدودة فقط؛ لا يُكشف `message` أو `payload` أو السجلات أو مخرجات المزود.
- التكرار مسموح؛ الحدث لا يغيّر حالة الواجهة مباشرة، بل يبطل Snapshot ويُعاد قراءته.
- عند انتهاء نافذة الاستعادة يرسل الخادم حدث إعادة مزامنة ويعيد العميل قراءة Snapshot كامل.
- لا يحمل الحدث نصوص ملفات أو أسرارًا أو سجلات خامًا أو مخرجات مزود غير منقحة.
- لا يُبنى استدلال «لا تغيير» من غياب حدث؛ إعادة اتصال ناجحة تعيد قراءة Snapshot.
- يظل Snapshot هو مصدر الحقيقة؛ إعادة قراءة دورية محدودة تعالج التغييرات التي لا ينتج عنها حدث محفوظ أو التي تُكتب بطابع زمني خارج ترتيب الإدراج.

### 7.5 أوامر UX مقابل API

لا يقدم الإصدار الأول سطح أوامر عامًّا جديدًا. يربط محول الواجهة الأوامر الواضحة بمساراتها الحالية، ويضيف مسارات جديدة فقط إذا أثبت التدقيق عدم كفاية العقد الحالي.

| نية المستخدم            | السطح الحالي المرشح لإعادة الاستخدام                                  | قاعدة التنفيذ                                                                        |
| ----------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| إرسال طلب ومتابعته      | `POST /api/ai/chat/stream`                                            | الحفاظ على `sessionId` وملكية الطلب وسياق المشروع، مع استمرار قيود التنفيذ الخادمية. |
| إعادة قراءة رسائل وجلسة | `/api/ai/chat/sessions` و`/api/ai/chat/:sessionId/messages`           | لا تعتمد الاستعادة على التخزين المحلي وحده.                                          |
| قراءة العمل             | `/api/tasks`, `/api/tasks/:taskId`, `/api/ai/executions/:executionId` | كل نوع يعرض مصدره وحالته ومحاولته؛ لا تخلط Task مع Execution.                        |
| قراءة اختلاف Candidate  | `/api/ai/executions/:executionId/diff` ومسار Proposal المرتبط         | يجب أن يطابق الطلب `projectId`, `operationId`, الإصدار والمرشح المقروء.              |
| مراجعة أو رفض Proposal  | `POST /api/ai/chat/proposals/:proposalId/approve` ومسار الرفض الحالي  | المراجعة لا تعني تطبيق التغيير.                                                      |
| تطبيق تغيير             | `POST /api/ai/chat/apply-changes`                                     | يستخدم موافقة المستخدم وبوابات الصلاحية وبصمة المرشح والتحقق الحالية.                |
| تشغيل Runtime الحالي    | `/api/projects/:projectId/runtime` و`/start`, `/restart`, `/stop`     | لا يعاد تعريف هذا كـ Candidate Preview.                                              |
| سجل مهمة                | `/api/tasks/:taskId/logs` و`/logs/stream`                             | يستخدم للتفاصيل عند الطلب، ولا يصبح الحالة العامة للWorkspace.                       |
| تسليم إلى GitHub        | مسارات Git Delivery الحالية                                           | يظل قرارًا منفصلًا وصريحًا ويتطلب إيصالًا خارجيًا.                                   |

أي خريطة نهائية للمسارات يجب تأكيدها في UXW-00 من OpenAPI/المخطط المولد قبل التنفيذ؛ الأسماء أعلاه توضح سطح إعادة الاستخدام الموجود في مصدر المشروع الحالي.

#### شروط أوامر التغيير

كل أمر يغيّر حالة أو ملفات أو Runtime أو وجهة خارجية يجب أن يربط، بحسب عقد ذلك المسار:

- المستخدم والمشروع المستهدفين.
- معرّف العملية أو Proposal أو التنفيذ والمحاولة.
- `expectedSourceRevision` أو `candidateRevision` عندما يكون الإجراء معتمدًا على نسخة.
- مفتاح idempotency ثابت لإعادة المحاولة للطلب نفسه، ومختلف للقرار الجديد.
- إيصالًا أو حالة خادمية قابلة لإعادة القراءة بعد انقطاع الاتصال.

هذه شروط تصميم للعقود الجديدة؛ لا تفترض أن كل مسار قائم يدعم الحقول نفسها. في UXW-00 يُدقق العقد الفعلي لكل مسار، ثم تُضاف حماية خادمية لازمة قبل أن تعرض الواجهة زرًا يعيد تنفيذ أثر غير idempotent. إعادة المحاولة لا تعيد استعمال مفتاح مع محتوى أو نسخة مختلفة.

## 8. Candidate وPreview: عقد الثقة

### 8.1 هوية المرشح

هوية المرشح في العرض مرتبطة على الأقل بـ:

```text
projectId
proposalId
operationId
executionId
attempt
baseRevision
candidateRevision
changeSetHash
```

لا يُقبل Diff أو دليل أو Preview أو إيصال إذا لم تتفق الهويات التي يتطلبها مسار المصدر. ليست هناك قيمة «مرشح نشط» عالمية تكفي وحدها.

### 8.2 Candidate Preview

عقد الجلسة المقترح:

```ts
type PreviewSessionRequest = {
  target: "project" | "candidate";
  expectedSourceRevision: string;
  proposalId?: string;
  operationId?: string;
  candidateRevision?: string;
};

type PreviewSessionResponse = {
  sessionId: string;
  target: "project" | "candidate";
  sourceRevision: string;
  candidateRevision: string | null;
  status: "starting" | "ready" | "failed";

```

المسارات التالية **مقترحة فقط**، ولا تُنشأ قبل إغلاق بوابة الأمان في UXW-03:

```http
POST   /api/projects/:projectId/preview-sessions
GET    /api/projects/:projectId/preview-sessions/:sessionId
DELETE /api/projects/:projectId/preview-sessions/:sessionId
```

### 8.3 سجل Gateway السابق — تفاصيل AWS مؤرشفة

المسارات التالية تفاصيل لنموذج AWS السابق وليست قرارات تشغيلية حالية. الترتيب المعتمد هو UXW-03.1–03.6 في قسم حزم التنفيذ؛ تُنقل الوظائف القائمة إلى adapters فقط بعد تثبيت العقود المحايدة، ولا ينشأ تنفيذ موازٍ.
- أضيف مخطط سجل جلسات في PostgreSQL الحالي: يربط `proposalId` ونسخته وهاش Candidate وهاش التغييرات وهاش صورة OCI ونسخة Task Definition بالمالك والحالة وموعد الانتهاء ومرجع ECS Task ARN. يرفض بدء الجلسة إذا لم تعد Proposal مملوكة للمستخدم وبحالة Candidate معزول أو متحقق وبالبصمات نفسها.
- انتقالات الجلسة تستخدم `stateVersion` لمنع كتابة عامل قديم فوق حالة أحدث؛ لا يقبل الانتقال إلى `ready` إلا قبل الانتهاء ومع بقاء Candidate وملكيته مطابقين. على المُنسّق ألا يكتب `ready` قبل نجاح فحص صحة المهمة من Gateway. حد العمر الأولي للجلسة 30 دقيقة.
- اختير أن يعمل ECS Gateway داخل AWS، وأن يبقى PostgreSQL تحت ملكية API الحالي. يرسل API أوامر Start/Stop موقعة بـEd25519 قصيرة العمر؛ يحتفظ API بالمفتاح الخاص، ويحمل Gateway المفتاح العام فقط، فلا يحتاج Gateway بيانات اتصال PostgreSQL أو سرًا مشتركًا لأوامر التحكم.
- نُفذت نواة تنسيق محلية: أمر Start يثبت Candidate والـimage digest وTask Definition، ويطلق مهمة واحدة في private subnets مع `assignPublicIp=DISABLED` و`clientToken=sessionId`. لا يقبل Runner إلا صورة مطابقة للهاش، وTask Definition بلا `taskRole`, بلا أسرار أو environment أو volumes، وبمستخدم غير root وfilesystem للقراءة فقط وإسقاط كل Linux capabilities.
- أضيف عقد DynamoDB مساعد لا يمثل حالة المنتج: قيد ذري يحفظ أعلى `stateVersion` وبصمة الأمر لكل جلسة، مع TTL بعد انتهاء الجلسة. يرفض Gateway Start قديمًا بعد Stop، ويتحقق مرة أخرى بعد RunTask ويوقف المهمة إذا سبقها Stop. يسجل API ARN الناتج عبر CAS على `stateVersion`; وإذا خسر تحديث الربط، يرسل Stop للمهمة نفسها.
- إذا فُقد رد الإطلاق قبل معرفة ARN تبقى الجلسة `starting` قابلة لإعادة المحاولة بمفتاح idempotency نفسه. ما زال عامل المصالحة الدوري غير موصول، ولا يكتب Gateway `ready`؛ يلزم إثبات صحة المهمة عبر بوابة البيانات قبل قبول تذكرة Preview.
- أضيفت نواة تذكرة موقعة قصيرة العمر (30 ثانية) وسجل منع إعادة الاستخدام في PostgreSQL الحالي. تُشتق مفتاحيتها بنطاق مستقل من `SESSION_SECRET`؛ يخزن السجل بصمة `ticketId` لا التذكرة نفسها، ويربط الاستهلاك ذريًا بالمستخدم والمشروع والجلسة و`proposalId` ونسختها و`candidateRevision` و`changeSetHash` والانتهاء. الإصدار والاستهلاك يتطلبان جلسة `ready` ومهمة ECS مسجلة وCandidate ما زال مطابقًا. لا تُمرر التذكرة في URL أو السجلات.
- أصبح لـGateway HTTP runtime مستقل داخل حزمة API، بمسار تحكم محدود وفحص صحة ومسار رفع ZIP موقّع. يخزن الرفع في S3 عبر Task Role، مع حد حجم وتزامن وبصمة SHA-256؛ لا يستخدم مفاتيح AWS ثابتة أو بيانات PostgreSQL.
- قوالب Terraform المحلية تضيف ECS private endpoint وجدول DynamoDB للـfence ومخزن S3 خاصًا ببادئات `build-inputs/` و`preview-build-outputs/` و`builder-job-envelopes/` بعمر يوم واحد، مع فصل أدوار Gateway/Runner/Builder Execution. يبقى تفعيلها `false` افتراضيًا؛ لا يوجد Load Balancer أو Gateway ECS service أو صورة Gateway أو Candidate Task Definition منشورة.
- طُبّق مخطط الجلسات والتذاكر على قاعدة التطوير فقط، واجتاز `schema:check`. بقيت الجداول بلا سجلات، ولم تُنشأ موارد AWS.
- أضيف مُجهّز محلي لمدخلات Builder يقرأ Candidate المثبتة ببصمتها، ويرفض الروابط الرمزية والملفات الحساسة ويفحص أنماطًا معروفة للأسرار ضمن حدود الحجم. هذا الفحص استدلالي وليس ضمانًا شاملًا؛ لا يقبل أي مسار من العميل، ولا يشغّل كود المشروع أو ينقل الملفات إلى AWS.
- أضيف عقد مهمة بناء موقّع قصير العمر من API بـEd25519. يتحقق Builder من التوقيع والمهلة والحقول الدقيقة قبل أي طلب S3، ويستمد هوية المشروع وCandidate و`sourceRoot` وبصمة المصدر والمدخل والمخرج وصورة Builder من المطالبات الموقّعة بدل متغيرات بيئة يختارها المستدعي. اختبارات API وBuilder تتحقق من التوافق بين التنفيذين.
- يأتي مفتاح التحقق من إعداد ثابت في تعريف مهمة Builder؛ يتحقق Gateway من تطابق المفتاح والبيئة الثابتة والصورة وExecution Role، ولا يسمح بتمرير المفتاح عبر overrides. يقبل مسار `POST /internal/v1/preview/builds` التذكرة الموقعة فقط، ويشتق مفاتيح النقل منها، ثم ينشئ روابط S3 قصيرة العمر. لتجنب وضع التذكرة وروابط النقل في حقول بيئة طلب ECS، يحفظها Gateway في ملف بيئة فريد مشفر بـSSE-S3 ومقيّد ببادئة IAM، ويمرر إلى `RunTask` ARN الملف فقط. يسمح Execution Role لـBuilder بقراءة هذه البادئة لتجهيز البيئة، ولا يملك Builder Task Role. يحجز Gateway `jobId` بقيد DynamoDB ذري؛ ولا يسمح باستئناف الطلب إلا إذا أثبتت قراءة قوية تطابق البصمة وإعداد الإطلاق وبيانات الملف. عندها يعيد طلب ECS نفسه بـ`clientToken` نفسه ليحصل على المهمة الأصلية عند ضياع الرد، لا لإنشاء بناء آخر. يرفض أي بصمة مختلفة أو مهمة منتهية أو ملف غير مطابق.
- لا يثبت هذا العقد وحده أن المهمة المنشورة استخدمت الصورة المتوقعة أو أن الخرج سليم. تعريف Builder الثابت والصورة لم يُنشرا بعد؛ وما زال يلزم عامل مصالحة، وفحص هوية المهمة من AWS، وAttestor مستقل يتحقق من الخرج قبل قبول الإيصال.
- أضيف مصدر مستقل `preview_build_jobs` لدورة حياة البناء، بدل وضع حالات البناء في سجل الجلسة الذي لا يُنشأ إلا بعد إيصال موثّق. يربط الطلب بمفتاح idempotency و`jobId/buildId` ومالك المشروع ونسخة Candidate وبصمات المصدر والأرشيف، مع حالات `queued → launching → running → builder_succeeded → verified` والحالات النهائية للفشل/الإلغاء/الانتهاء. لا يخزن التذكرة الموقعة أو روابط S3 الموقعة؛ وتبقى `builder_succeeded` غير كافية لإنشاء جلسة Preview، ولا تتحقق `verified` إلا مع إيصال مستقل. يربط `preview_sessions.build_job_id` جلسة واحدة فقط بمهمة بناء موثقة.
- أضيف مسار API لبدء بناء Candidate عبر `POST /projects/:projectId/proposals/:proposalId/preview-builds`، مع `clientRequestId` ثابت لإعادة المحاولة، ومسار قراءة حالة مقيّد بمالك المشروع عبر `GET /projects/:projectId/preview-builds/:jobId`. يقرأ الخادم `sourceRoot` وبصمة صورة Builder من إعداداته، ويرفض Candidate غير الحالي أو وجود بناء نشط آخر قبل نقل الملفات متى أمكن؛ ويعيد فحص النسخة والمالك داخل معاملة إنشاء السجل. ينقل API الأرشيف المقيّد إلى Gateway ثم يحفظ سجل البناء، وينقل حالته بـCAS قبل إرسال المطالبة الموقعة. إذا ضاع رد Gateway، تبقى الحالة `launching` ويعيد الطلب نفسه المطالبة نفسها ضمن مهلة صلاحيتها؛ بعد انتهاء المهلة لا يعيد إطلاق ECS تخمينًا، وتبقى المصالحة المستقلة مطلوبة. إسقاط الاستجابة لا يكشف مفاتيح التوقيع أو روابط S3 أو مفاتيح الأرشيف. يتطلب التشغيل إعداد `PREVIEW_GATEWAY_URL` ومفاتيح API الخاصة وبصمة Builder و`PREVIEW_BUILD_SOURCE_ROOT`؛ إن غابت الإعدادات يفشل المسار مغلقًا. اختبارات API والخدمة تثبت رفض الطلب غير الصحيح، وعزل الحالة حسب المالك، ومنع بناءين نشطين، وإعادة المحاولة بنفس الهوية بعد غموض النقل.
- أضيف callback خادمي `POST /api/internal/preview-build-jobs/:jobId/receipt` يقبل إيصالًا قصير العمر موقّعًا بمفتاح Attestor العام المنفصل. لا يثق في `status` أو digest من المستدعي، ويرفض الإيصال إلا إذا كانت المهمة `builder_succeeded` وكان digest يطابق سجل البناء. قبل `verified` يقفل المشروع وCandidate ثم يعيد التحقق من المالك والعملية والمراجعة والبصمات والحالة الحالية داخل المعاملة، وبعدها ينفّذ انتقالًا بإصدار حالة متوقع. يبقى المسار غير مهيأ ما لم يتوفر `PREVIEW_BUILD_RECEIPT_PUBLIC_KEY_PEM`؛ ولم يُنشأ أو يُنشر Attestor مستقل بعد، لذا لا يستطيع هذا callback وحده إثبات نجاح البناء أو استعادة مهام ECS.
- أضيفت مصالحة دورية محدودة لمهام ECS: يوقّع API استعلامًا قصير العمر ومقيدًا بهوية البناء، ويتحقق Gateway من توقيعه ثم يعيد المهمة الوحيدة ذات `startedBy` المطابق. يستعيد API حالة `launching → running` بعد ضياع رد البدء، ويسجل فشل الخروج غير الصفري، ولا يسجل `builder_succeeded` إلا بعد خروج صفر وحساب SHA-256 فعليًا لخرج S3 المشفر والمحدود الحجم. غياب الخرج أو هويته يبقي المهمة غير معتمدة؛ هذا لا ينتج إيصال Attestor ولا يجيز Preview. لم يُنشر Gateway أو Builder على AWS.
- أضيف مخطط Drizzle وحارس انتقالات لـ`preview_build_jobs` وربطه بجلسة المعاينة، وطُبّق المخطط الإضافي على قاعدة التطوير واجتاز فحص التطبيق الكامل للمخطط. أضيف مخزن لإنشاء السجل ونقل حالاته والتحقق من الإيصال؛ لكنه لا يثبت وحده نجاح Builder أو سلامة الخرج. لا توجد بعد API لإيقاف جلسة Preview أو إصدار تذكرة للمستخدم، ولا Builder معزول/Attestor أو عامل reconciler يراقب ECS ويصدر أثر البناء. لا ينشئ Candidate صورة OCI أو يسجّل Task Definition.
- أصبح عقد إيصال Builder يفرض توقيع Ed25519 مستقلًا، وبصمة صورة Builder موثوقة، وربط Candidate ومدخلات الأرشيف وهاش ومفتاح ناتج `dist`. لا يتضمن الإيصال صورة التشغيل أو Task Definition؛ تختارهما API من `PREVIEW_ECR_REPOSITORY_URI` و`PREVIEW_RUNTIME_IMAGE_DIGEST` و`PREVIEW_TASK_DEFINITION_ARN` المثبتة خادميًا. تحفظ الجلسة `buildReceiptId` بقيد uniqueness لمنع إعادة استعماله، ويجب الاحتفاظ بصف الجلسة كأثر منع إعادة التشغيل. لم توجد بعد خدمة Attestor أو نقل ناتج إلى Runtime تُصدر هذه الإيصالات وتستهلكها.
- ارتبط مفتاح ناتج البناء وبصمة SHA-256 في سجل الجلسة وأمر Start الموقّع حتى يصلان إلى ECS كقيمتين ثابتتين لا يختارهما Candidate. يرفض المنسّق جلسة قديمة بلا هذا الربط؛ لكنه لا يثبت أن صورة Runtime مبنية أو منشورة أو شغّلت الأثر فعليًا.
- يتحقق Gateway من وجود ناتج S3 وحد الحجم وبصمة SHA-256 المخزنة قبل الإطلاق، ثم يوقّع رابط GET قصيرًا (5 دقائق) للكائن نفسه ويمرره كـoverride للحاوية. كما أضيف مزود نقل يتحقق من أثر الإدخال المشفر وبصمته، ويصدر رابط GET للإدخال ورابط PUT شرطيًا لمرة واحدة إلى مفتاح خرج فريد. تمر هذه الروابط إلى Builder عبر ملف بيئة S3 قصير العمر؛ أما طلب ECS فيحمل ARN الملف فقط. يسمح S3 endpoint وIAM بالنقل ضمن بادئات الإدخال والخرج وملف البيئة، وتنتهي الكائنات بعد يوم. مصدر صورة Runtime الثابتة موجود: ينزّل الرابط دون تحويلات، يتحقق من SHA-256، يرفض أرشيفات غير POSIX ustar والروابط والمسارات المتجاوزة والملفات الزائدة، ثم يخدم ملفات ثابتة من الذاكرة فقط. لم تُبنَ الصورة أو تُنشر، ولم يوجد بعد Builder ينشئ المخرجات.
- أضيفت حقول `build_receipt_id` و`build_output_artifact_key` و`build_output_digest` إلى مصدر Drizzle ومدقق المخطط، مع فهرس uniqueness لـ`build_receipt_id`، وطُبّق المخطط الإضافي على قاعدة التطوير فقط مع فحوص الجاهزية والعلاقات والفهارس. لا توجد تغييرات على الإنتاج.
- لم يُثبت الاتصال الفعلي بـAWS بعد: لا توجد خدمة Gateway عامة منشورة أو إعدادات تشغيل API مُتحقق منها في بيئة نشر. لا يستطيع المسار بدء بناء فعلي حتى تتوفر بوابة TLS وإعدادات التوقيع والصورة ومسار المصدر؛ كما لا توجد بعد مصالحة ECS أو Attestor أو تذكرة/عرض Preview تفاعلي. يجب إبقاء الواجهة مغلقة حتى تكتمل هذه الحدود وتتحقق من Host/Origin والإلغاء وعزل الشبكة.
- يتحقق الخادم من المشروع والمستخدم ومرجع Candidate والإصدار المتوقع.
- كل جلسة مقيدة بمشروع ونسخة ووقت انتهاء وحدود موارد.
- لا يُعرض المنفذ الداخلي الخام أو PID أو مسار نظام الملفات في رابط المستخدم.
- تمر حركة Preview عبر بوابة مصادق عليها ومقيدة؛ لا يختار العميل أصلًا أو عنوان IP أو منفذًا اعتباطيًا.
- يحظر الوصول إلى loopback وعناوين الشبكات الداخلية والخدمات الإدارية وواجهات metadata.
- تُراجع حماية WebSocket وOrigin وHost وCSRF بحسب طريقة البوابة.
- لا تُمرر أسرار تطبيق الخادم أو بيانات اعتماد Git إلى Preview.
- تنتهي الجلسة ويوقف العامل المملوك لها بعد انتهاء TTL أو الإلغاء؛ لا يوقف عامل مشروع آخر.
- تكون سجلات المستخدم منقحة ولا تكشف متغيرات بيئة أو ملفات خاصة.
- معاينة Candidate لا تقع تلقائيًا إلى Runtime المشروع الأساسي عند تعذر Candidate.
- إذا تغيرت ملفات Candidate، توسم الجلسة `stale` ويمنع اعتبارها المعاينة الحالية حتى إنشاء جلسة مرتبطة بالبصمة الجديدة.

### 8.4 الفصل عن Browser Preview Verification

| المستخدم التفاعلي                            | التحقق الآلي                                            |
| -------------------------------------------- | ------------------------------------------------------- |
| يشاهد النتيجة ويتفاعل معها ويختار عنصرًا.    | ينفذ سيناريو تحقق محددًا على بيئة اختبار.               |
| جلسة لها هوية مستخدم وصلاحية وعمر وصول.      | تشغيل آلي محدود بالملف الشخصي والنسخة والإجراء.         |
| لا يثبت النجاح الهندسي بمجرد أن الصفحة فتحت. | ينتج دليلًا يربط محاولة تحقق ونسخة ومخرجات مسموحًا بها. |

يمكن للاثنين تشغيل Candidate واحد فقط إذا اتفقت هوية المصدر والبصمة؛ أحدهما لا يحل محل الآخر.

## 9. فصل الحالات والمصادر

### 9.1 أبعاد الحالة المستقلة

| البعد        | السؤال الذي يجيب عنه                       | ما لا يعنيه                                    |
| ------------ | ------------------------------------------ | ---------------------------------------------- |
| Work / Task  | ما حالة العمل الذي طلبه المستخدم؟          | لا يثبت أن محاولة تنفيذ بعينها نجحت.           |
| Execution    | هل جرى التنفيذ، وبأي محاولة؟               | `completed` لا يعني نجاح التحقق أو القبول.     |
| Verification | هل اجتاز المرشح الاختبار المطلوب؟          | لا يعني أن المستخدم وافق أو أن التغيير طُبق.   |
| Acceptance   | هل استوفى العقد وقُبل بالدليل المطلوب؟     | لا يعني أن التغيير وصل إلى المشروع الحي.       |
| Application  | هل طُبق التغيير على النسخة المستهدفة؟      | لا يعني أن GitHub استلم Commit.                |
| Delivery     | هل استلمت الوجهة الخارجية الإصدار المقصود؟ | لا تستنتج من نجاح Commit محلي أو HTTP بدأ فقط. |
| Preview      | أي إصدار معروض وهل هو حديث؟                | العرض المرئي ليس دليلًا على الصحة.             |

### 9.2 قواعد الحالة

- الحالة المجهولة ليست «معلقة» ولا «ناجحة».
- العطل في مصدر القراءة لا يتحول إلى قائمة فارغة.
- حدث قديم أو محاولة سابقة لا يحدّث الحالة الحالية.
- المستخدم يرى «مسجل كمنتهٍ» عند غياب إثبات مستقل، لا «تم التحقق».
- `Applied` و`Delivered` لا يظهران قبل استجابة أو إيصال موثوق للخطوة نفسها.
- إذا اختلفت `candidateRevision` عن `verification.candidateRevision` فالنتيجة `stale` أو `unknown`، لا `passed`.
- لا تعرض الواجهة ضمانًا كليًا من تجميع حالات جزئية.

### 10.2 إعادة استخدام ممنوعة أو مشروطة

- لا تعتمد على أي شاشة أو مسار قديم خارج النطاق المدعوم كمصدر لWork Board.

- لا تعِد استخدام مخطط التحقق الآلي باعتباره قائمة تفاعل مستخدم.
- لا تنفذ Visual Editing بتغيير DOM مؤقت فقط.
- لا تجعل `nextActions` أو صلاحية زر في React تصريحًا خادميًا.
- لا تعيد كتابة محادثة AI أو الاستعادة قبل اختبار إمكان تركيبها في Workspace.

### 10.3 الحد بين UX وAgent Core

طبقة Workspace مسؤولة عن:

- العرض والتجميع وإعادة القراءة وحالات التحميل والتعذر.
- توجيه المستخدم إلى الأمر الحالي المناسب.
- حفظ اختيار سطح العمل غير السلطوي واستعادة السياق.
- عرض التفريق بين الحقيقة والدليل والاقتراح.

طبقة Workspace غير مسؤولة عن:

- إنشاء إثبات قبول من كلام النموذج.
- تخفيف صلاحية أو Lease أو قفل أو حارس تنفيذ.
- اختيار عملية كتابة من نص واجهة فقط.
- استنتاج التسليم من رسالة ناجحة.
- إعادة تفسير فشل مصدر الحقيقة على أنه عدم وجود عنصر.

### UXW-02 — Workspace Shell وقراءة موحدة

**التبعيات:** UXW-01.

**النطاق:**

- Snapshot API وZod/عميل مولدان.
- تجميع القراءة من المصادر الموجودة مع تحديد النقص والقدم.

- Workspace Event Stream للإبطال/إعادة القراءة بعد تثبيت cursor قابل للاستعادة.

**المخرجات:** غلاف Workspace يقرأ حقيقة واحدة من مصادرها، ولا يكتب حالة تنفيذ موازية.

**معيار الإغلاق:**

- يبقى التنقل من التفاصيل والعودة محافظًا على `projectId` و`sessionId` والهدف.

**الاختبارات:** مخطط Zod، اختبارات Snapshot/ownership/partial source، إعادة تشغيل/replay للحدث، out-of-order/duplicate events، Playwright للانتقال والعودة وإعادة التحميل.

**التنفيذ الأولي — 2026-11-10:**

### UXW-03 — Preview محليًا أولًا، ومزودون اختياريون

**هذا هو ترتيب التنفيذ المعتمد حاليًا.** لا تنشر أو تنشئ موارد AWS/Cloudflare أثناء حزم 03.1–03.5. لا تغيّر أي حزمة قواعد إثبات Candidate أو قبولها: تظل هوية المشروع والعملية والمحاولة والنسخ والبصمات والأدلة محكومة بالعقود الحالية. التخزين يحفظ بايتات ولا يصنع إثباتًا؛ Builder ينفذ ولا يقبل؛ Attestor مستقل يفحص الناتج؛ والخادم الحالي وحده يقرر صلاحية الإيصال والقبول.

**ما وُجد في التدقيق:** Builder وAttestor وGateway وTerraform الحالية متمحورة حول AWS/S3/ECS، وليست طبقة محايدة. توجد صورتا Builder وAttestor محليًا؛ صورة Runtime غير مبنية. Terraform يحتوي ECR وتعريفَي Builder وAttestor، لكنه لا يحتوي تعريف ECS للـRuntime. لا توجد موارد AWS منشورة، ولا Store محلي محايد. تُعامل الشيفرة القائمة كـadapter/مرجع قابل لإعادة الاستخدام بعد فصل العقود؛ لا ننشئ Builder أو receipt أو جلسات Candidate موازية.

#### UXW-03 target architecture — Preview Fabric

المستهدف خمس حدود منطقية، وليست خمسة خدمات أو قواعد بيانات جديدة:

1. **Control Plane:** API وPostgreSQL الحاليان يظلان مصدر الحقيقة للملكية وJobs وSessions والقرارات؛ Workspace Snapshot إسقاط قراءة فقط.
2. **Execution Plane:** منفذ محلي أولًا، ومنافذ Cloud اختيارية؛ جميعها تعمل عبر Job/Attempt/Lease/Fencing الخادمية نفسها.
3. **Artifact Plane:** Local CAS Store وRemote Store اختياري، مع `ArtifactRef` وبصمة وManifest ثابتة.
4. **Trust Plane:** فحص Attestor ثم تحقق الإيصال في API؛ لا يتخذ Builder أو Artifact أو Preview قرار قبول.
5. **Preview Delivery Plane:** Local/Cloud Gateway أو ناشر Static اختياري؛ الجلسة والتذكرة والإلغاء وTTL مرتبطة بهوية Candidate نفسها.

لا نبني `PreviewProvider` عملاقًا أو framework عامًا للبنية التحتية. العقود صغيرة ومحددة، ولا تُنشأ خدمة أو جدول إضافي قبل أن يثبت UXW-03.0 عدم وجود مصدر قائم مناسب.
الرؤية طويلة الأمد يمكن أن تشمل Local، وSelf-hosted، وCloud execution، وStatic publishing بموافقة المستخدم؛ هذا لا يعني دعم كل الأنماط في الإصدار الأول.

**فصل Preview عن Release:** Builder وArtifact Store وAttestation وReceipt Verifier وRuntime Profiles وقدرات Job/Lease/Fencing مشتركة عبر عقود محددة. أما Preview Session والتذكرة والـExposure Gateway فمؤقتة ومقيدة بالنسخة؛ Release وEnvironment وDeployment وHealth وTraffic Promotion وRollback دورة منفصلة. لا تتحول Preview Session إلى Production Deployment، ولا يُنسخ Builder أو CAS أو Attestor إلى نظام موازٍ لمجرد إضافة النشر.

#### تدقيق مرفق Preview Fabric (2026-11-12)

رُوجع المرفق كاملًا، مع فصل الموجود عن المقترح:

- **مؤكد:** Builder الحالي Static لـVite/React، والاسم المثبت في `preview-build-job.ts` وعقود API/الصورة هو `vite-react-static-v1`. `vite-static-v1` في المقترح اسم مستقبلي غير متوافق تلقائيًا؛ لا يُعاد تسمية العقد الحالي من دون إصدار/ترحيل واضح.
- **مؤكد مع تصحيح نطاق:** `preview-runtime-profile.ts` يثبت إعداد ECR/ECS وصورة/Task Definition مملوكتين للخادم؛ ليس عقد Runtime محايدًا متعدد Profiles. `preview_sessions` في `preview-session-store.ts` تخزن `taskDefinitionArn` و`runnerTaskArn`، لذا اقتران AWS في دورة الجلسة حقيقي.
- **مؤكد:** `preview-session-store.ts` يحد العمر الأقصى للجلسة بـ30 دقيقة ويفرض تفرد `buildReceiptId`، ويقفل Candidate وBuild Job ويتحقق من المالك والنسخة. `preview-access-ticket.ts` يحدد عمر التذكرة بـ30 ثانية؛ يخزن `preview-access-tickets.ts` digest في PostgreSQL ويستهلكه مرة واحدة.
- **مؤكد:** `preview-gateway-server.ts` يقدم الصحة والتحكم الداخلي ورفع مدخلات البناء وبدء البناء/المصالحة/Attestation؛ لم يظهر فيه مسار عرض عام للمستخدم يستهلك Preview Ticket ويوجه طلب المتصفح إلى Session.
- **مؤكد مع تضييق العبارة:** يوجد `deployment` كنوع هدف/إيصال تحقق عام في `task-objective-contract.ts` و`task-objective-receipts.ts` مرتبط بدليل صحة نشر، لكن لا يوجد مسار منتجي متكامل لإدارة Release وEnvironment وDeployment Provider وDomains وTraffic Promotion وRollback. لا يصح وصف المشروع بأنه خالٍ من أي مفهوم deployment.
- **غير قابل للتثبيت من الملف وحده:** بيانات CI وحالة Commit الواردة في المرفق وقتية؛ لا تُعامل كحالة CI راهنة ولا كمعيار إغلاق دون فحص مباشر للفرع وPR والـchecks وقت التنفيذ.

Backend Preview وUXW-08 أدناه **توسعة معمارية مستهدفة** وليسا قدرات منفذة أو إذنًا بتشغيل Candidate أو إنشاء موارد سحابية. كل Profile يبقى غير مدعوم للمستخدم حتى يجتاز بوابة العزل والرحلة المحددة له.

#### UXW-03.0-B — Backend Runtime Threat Model & Isolation Qualification

**التبعية:** UXW-03.0. بوابة تصميم وتأهيل تسبق عقد Backend أو تنفيذ Candidate؛ لا تؤخرها إلى ما بعد إطلاق Backend.

- عرّف `node-express-managed-v1` ونموذج التهديد والملفات المسموح بها، نقطة الدخول، الاعتماديات المدمجة، الشبكة، الهوية، الملفات، الموارد، العمليات، TTL، وسجل الإيقاف.
- قبل التنفيذ، وثّق ADR يختار آلية العزل والأنظمة المدعومة وحدودها؛ لا يُفترض وجود Runner Linux مؤهل أو صلاحيات إضافية من دون إثبات.
- **قرار العزل المعتمد:** يجب أن يكون حد Runner أقوى من `runc` القياسي الذي يشارك نواة المضيف؛ أمثلة مرشحة `gVisor/runsc` أو VM/microVM بعد تأهيلها، وليس مجرد non-root/rootless أو namespaces أو seccomp. لا يتوفر حاليًا Runner بهذه الأهلية في البيئة المفحوصة، لذا Backend Preview غير مدعوم فيها.
- عقد رسائل Runner وقياس قدراته وحدود إعادة الاستخدام موثقة في [UXW-03 Runner Contract V1](uxw-03-runner-contract.md). يظل التصميم غير منفذ؛ لا تُوسّع `PreviewControlCommand` الحالي أو `VerifiedPreviewRuntimeProfile` الـAWS-specific بصمت، ولا يُنشأ مصدر حالة ثانٍ.
- قيّم كل نظام تشغيل وRunner منفردًا؛ لا يُعلن دعم Linux/macOS/Windows بالتعميم. Rootless أو non-root أو `spawn()` وحدها ليست عزلًا مثبتًا.
- يجب أن يرفض Runtime التشغيل إذا لم يستطع إثبات حدود الملفات والشبكة/العمليات/الموارد. لا fallback إلى تشغيل Candidate على Host أو داخل عملية API.
- اختبر منع قراءة Host وDocker Socket والأسرار وPostgreSQL/metadata/private networks، منع المنافذ الإضافية والعمليات الشاردة، وإنهاء شجرة العمليات عند TTL أو الإلغاء.
- حدّد سياسة Egress المغلقة افتراضيًا؛ أي استثناء لاحق يحتاج قائمة سماح قابلة للتدقيق وحماية فعلية من SSRF وDNS rebinding عند نقطة الاتصال.
- **إغلاق الحزمة:** نموذج تهديد مُراجع، Runtime Profile ونطاق دعم صريحان، واختبارات مستقلة تثبت العزل والتعافي. إذا لم تتأهل بيئة محلية، تُرفض عليها Backend Preview بدل تخفيض الحد الأمني.

**نتيجة التأهيل الأولية (2026-11-12):** اجتاز Docker المحلي فحصًا آمنًا لقيود الحاوية الأساسية، ونجحت اختبارات العزل القائمة (43/43). وأثبت نموذج ثابت وصول HTTP عبر مقبس Unix خاص مع بقاء شبكة الحاوية مغلقة، لكن لم يُشغّل Candidate ولم يُربط Gateway المنتج، واستخدم النموذج مجلدًا واحدًا قابلًا للكتابة، كما أن `runc` يشارك نواة المضيف ولا يحقق حد العزل المعتمد. لذلك لم تُغلق البوابة ولا يُعلن دعم Backend؛ تفاصيل الدليل والقيود في [ADR عزل Backend](adr/uxw-03-backend-runtime-isolation.md).

#### UXW-03.1 — Provider-Neutral Preview Contracts

**تنفيذ أولي (2026-11-12):** أُنشئت مكتبة مشتركة لأوامر Runner الموقّعة ورسائل `start/stop/observe` الموقّعة. ترفض `shared_kernel` والحقول الإضافية، وتربط الرسائل بهوية الجلسة والمرشح والإيصال والملف التعريفي وجيل الـfencing، وتتحقق من تطابق بصمات الملف المطبّق وحداثة الملاحظة. التوقيع يثبت هوية المفتاح المُرسل ولا يثبت وحده صحة العزل؛ كما أن النقل، وسجل replay الدائم، والتحقق المستقل من دليل العزل، وتنفيذ Agent لم تُنجز. مخزن الجلسات الحالي ما زال ECS-specific، لذلك لم أضع `executionRef` المحلي في أعمدة ARN ولم أطبّق ترحيل قاعدة بيانات. هذا لا يغلق UXW-03.1 ولا يسمح بتشغيل Backend Candidate.

- افصل المسؤوليات بعقود صغيرة لا تسرّب تفاصيل AWS/Cloudflare: `PreviewBuildExecutor`, `PreviewArtifactStore`, `PreviewAttestationService`, `PreviewReceiptVerifier`, `PreviewSessionRuntime`, `PreviewRunnerAgent`, `PreviewExposureGateway`, `PreviewNodeRegistry`, و`PreviewPlacementPolicy`. `PreviewRunnerAgent` بروتوكول موثّق لعامل العقدة يطبّق أوامر Runtime موقعة، وليس مصدر حالة أو نظام تنفيذ مكررًا. لا تجمعها في provider واحد ضخم، ولا تُنشئ تنفيذًا موازيًا لوظائف موجودة.
- افصل `PreviewBuildProfile` عن `PreviewRuntimeProfile` وعن `PreviewTopologyProfile`: الأول يحدد إعداد إنتاج Artifact، والثاني الصورة والـLauncher وسياسات التشغيل، والثالث عدد الخدمات وعلاقاتها وموارد بياناتها. لا تجعل `previewProfile` واحدًا يحدد هذه المسؤوليات معًا.
- حافظ على العقد الفعلي `builderProfile: "vite-react-static-v1"` أثناء التحويل؛ أضف `buildProfileId` بإصدار/ترحيل صريح. لا تستخدم الاسم المقترح `vite-static-v1` كمرادف صامت. ملفات Runtime الحالية AWS-specific وليست دليلًا على اكتمال هذه العقود المحايدة.

| Build Profile | Runtime Profile | Topology | الدعم المقصود |
|---|---|---|---|
| `vite-react-static-v1` | `static-files-v1` | `single-service-v1` | أول رحلة Static؛ هي الوحيدة الموجودة حاليًا كعقد Builder |
| `node-express-source-v1` | `node-express-managed-v1` | `single-service-v1` | Backend مقيد بعد اجتياز 03.0-B و03.4-B |
| الأول + الثاني | static + managed backend | `full-stack-ephemeral-db-v1` | تجميع لاحق بعد 03.4-C |

عقد Runtime المستهدف يحمل `profileId/version`, و`imageDigest`, و`launcherDigest`, و`entrypoint/port/filesystem/network/resource policies`, و`statePolicy`, و`requiredAssuranceLevel`. هذه حقول تصميم لا تُنسب إلى `preview-runtime-profile.ts` الحالي.

- اجعل كل عقد يمرر هوية Candidate الحالية نفسها: `projectId`, `operationId`, `candidateRevision`, `baseRevision`, `changeSetHash`، مراجع الأدلة والمحاولة. لا يقبل العقد أوامر shell أو صورة/وجهة يختارها Candidate.
- `SignedPreviewBuildJob` يربط `projectId`, `proposalId`, `operationId`, `executionId`, `attempt`, revisions, `changeSetHash`, `buildProfileId`, `builderPolicyDigest`, `idempotencyKey`, `dispatchGeneration`, و`jobId`; ويحتوي `nodeId/executorRef`, `leaseOwner`, `leaseExpiresAt`, `issuedAt`, `expiresAt` عند الحاجة. يتحقق API من كل حقل مقابل السجل الحالي.
- `ArtifactRef` غير قابل للتغيير يصف بصمة المحتوى وحجمه وManifest ومصدره ونسخته وسياسة الاحتفاظ. `BuildExecutionRef` يربط Job والمنفذ والمحاولة والـLease. `AttestationReceipt` يثبت فحص الناتج، لكنه ليس Canonical Proof أو قبولًا.
- استخدم مخططات Zod/أنواع المشروع المشتركة للعقود المتبادلة بين API وDashboard وAgent، مع توليد العملاء من OpenAPI؛ تبقى تفاصيل المنافذ الداخلية والعامل خارج واجهة HTTP العامة.
- افصل دورة بناء Job عن دورة Preview Session. استخدم `preview_build_jobs` و`preview_sessions` الحاليين وأعد فحص المخطط في 03.0؛ لا تسمح بإنشاء Session قبل `verified` حسب مستوى الثقة المسموح. لا تعِد تعريف حالة `verified` أو مصدر إثباتها.
- أعد المحاولة بنفس idempotency key للطلب نفسه؛ تغيير Candidate أو Attempt/dispatch generation ينشئ هوية جديدة. لا يقبل أي كتابة إلا Lease/Fencing generation الحالي. استخدم Outbox/Inbox أو الآلية القائمة المكافئة لمنع فقد الإرسال بين PostgreSQL والمنفذ، ولا تدّعِ exactly-once.
- أعد استخدام Candidate/Execution/Validation/Acceptance الحالية. انقل AWS إلى adapter لاحقًا ولا تكرر المنطق أو الجداول.
- **إغلاق الحزمة:** contract tests على fake/local providers وعلى AWS adapter بعد لف الوظائف الحالية به؛ تبقى اختبارات AWS الحالية ناجحة ولا يتطلب الإغلاق AWS حيًا. اختبر round-trip للعقود، فقدان رد submit وإعادته بالهوية نفسها، أمرًا مكررًا، عاملًا قديمًا بعد انتهاء Lease، فشلًا بين تسجيل Job وإرساله، ورفض إيصال لمشروع/مرشح/محاولة مختلفة؛ وأثبت بقاء Candidate/receipt/acceptance identities دون تغيير.

**سياسة اختيار المنفذ:** القرار خادمي وحتمي وقابل للتفسير، لا يقرره نموذج AI. يقيّم `previewProfile`, `requiredAssuranceLevel`, `localNodeId/capabilities`, `networkPolicy`, `costPolicy`, موافقة المستخدم وحداثة Candidate. Local هو الأول عند الأهلية؛ إذا لم يسمح المستخدم/السياسة بـCloud يبقى الطلب منتظرًا أو ينتهي بسبب واضح، ولا يحدث تحويل صامت مدفوع. سجّل سبب الاختيار ونسخة السياسة ضمن Job الحالية لا في مصدر حقيقة موازٍ. أي تغير في Candidate يبطل قرار placement. السياسات الممكنة لاحقًا: `local_only`, `local_preferred`, `cloud_allowed`.

#### UXW-03.2 — Local Artifact Store

**تنفيذ أولي (2026-11-12):** أضيف محوّل Linux محليًا لمخزن مدخلات البناء الموقّعة الحالي. يشترط مسارًا صريحًا خارج `workspaceRoot`، ويرفض الجذر الرمزي أو واسع الصلاحيات، ويوفر `putStream` محدودًا إلى staging خاص مع حساب SHA-256 ثم نشر Blob/مرجع ذري بلا استبدال عبر `link` وحذف اسم staging. واجهة Gateway الحالية ما زالت تمرر `Buffer`، لذا لم يُوصل الرفع الشبكي بالبث بعد. اخترت النشر بلا استبدال لأن `rename` العادي على POSIX قد يستبدل ملفًا موجودًا عند التزامن. هذا لا يفعّل المسار محليًا في API ولا يوصله بـAWS Builder؛ و`0700` لا يعزل عن عملية Candidate تعمل بالـUID نفسه، لذلك لا يستخدم قبل فصل التنفيذ بهوية مستقلة.

**حاجز GC الجاري:** أضيفت حالات `active/eligible_for_gc/deleting/deleted` لمراجع مدخل ومخرج البناء، مع مزوّد صريح لكل مرجع (`local` أو `s3`) و`inputArtifactReadyAt`. سجلات البناء الحالية تُوسم `s3`؛ عامل التنظيف لا يلمسها. صار سجل Build يُنشأ قبل الرفع، ولا ينتقل إلى الإرسال حتى ينجح الرفع ويُسجل الاستعداد؛ كما أصبحت جلسة Preview ترفض مخرجًا في حالة تقاعد. اكتشف الاختبار أيضًا أن سجل Build كان يستخدم مفتاحًا لا يطابق مفتاح الرفع المرتبط بهوية Candidate، ووُحّد الاشتقاق.

أضيفت إزالة محلية idempotent تحفظ Blob المشترك حتى تختفي آخر إحالة، وعامل pass واحد لمدخلات `local`: يؤهل بعد 24 ساعة من انتهاء Build، بما في ذلك الرفع الذي ربما اكتمل دون وصول إقرار الجاهزية، ينتظر مهلة ساعة، ثم يحجز المرجع بمهلة عامل 15 دقيقة كي يستطيع عامل آخر الاستعادة بعد انقطاعه. كل انتقال في قاعدة البيانات يقفل بصمة المحتوى ويعيد فحص السجلات؛ وحالة `deleting` تمنع إنشاء مرجع متزامن أثناء الحذف. فشل الحذف يبقي الحالة `deleting` للمحاولة التالية.

**لا تُشغّل الجدولة بعد:** قاعدة البيانات موجودة في API، لكن مسار الرفع الحالي يعمل داخل Gateway منفصل ويكتب إلى S3؛ والـGateway يمنع إعدادات اتصال قاعدة البيانات. لا يوجد حاليًا تدفق يُنشئ Artifact محليًا ولا معرّف يحدد أي عقدة/Agent تملك ملف CAS. جدولة العامل داخل API قد تحدّث صفًا يخص ملفًا موجودًا على مضيف آخر، أو تحذف الملف من عقدة غير مالكته. لذلك لن أفعّل Timer قبل وجود مالك تخزين موثوق ومسار حذف موجّه إليه. المخرجات الحالية تظل على قاعدة S3 ذات دورة حياة يوم واحد. لم يُطبّق المخطط على قاعدة التطوير، ولم تُحذف ملفات من مخزن حقيقي؛ لذلك تبقى UXW-03.2 مفتوحة.

- أنشئ مخزنًا محليًا خاصًا خارج جذر المشروع، مرتبطًا ببصمة المحتوى؛ كتابة مؤقتة ثم flush/sync ونشر ذري بلا استبدال (`rename` بشرط no-replace أو `link` ثم حذف اسم staging)، ورفض استبدال بصمة موجودة بمحتوى مختلف.
- خزّن CAS بواسطة IDs مولدة من الخادم مع Manifest غير قابل للتغيير يربط Artifact بـJob وCandidate والسياسة و`digest/sizeBytes/manifestDigest/retentionPolicy`. الموقع الفعلي لا يظهر في API؛ العميل لا يرسل مسارًا محليًا لـAPI أو Gateway لقراءته.
- عرّف أنواعًا محددة مثل `static_bundle` و`backend_source_bundle`; لا تخلط Artifact المصدر بصورة Runtime مثبتة. إذا أضيف `database_seed_snapshot` فيجب أن يكون اصطناعيًا/مؤقتًا ومربوطًا بالجلسة، لا نسخة من بيانات Production ولا مخزن أسرار.
- استقبل الملفات داخل staging محدود الحجم، واحسب البصمة أثناء التدفق، ثم تحقق من العدد/الحجم/النوع والمسارات قبل الكتابة، ونفّذ `fsync` ثم rename ذري. لا تربط المرجع بسجل Job قبل اكتمال الكتابة والتحقق؛ ضياع الرد يعيد نفس Artifact identity.
- ارفض absolute/traversal، الروابط الرمزية والصلبة غير المسموحة، الملفات الخاصة، التكرار المتعارض، Unicode-normalization collisions، ZIP/TAR bombs، وعدد الملفات والأحجام المتجاوزة. لا تكتب خارج root مخصص ولا تمنح Candidate وصولًا مباشرًا للمخزن.
- نظّف بجمع مرحلتين: mark كـ`eligible_for_gc` بعد فحص مراجع Jobs/Receipts/Sessions، ثم مهلة وحساب المراجع مجددًا مباشرة قبل sweep. تتضمن حالات الاحتفاظ `temporary/active/retained/eligible_for_gc/deleted`؛ لا تحذف الأثر عند فشل فحص الملكية/المراجع.
- ضع حصصًا لكل مستخدم/جهاز/مشروع/Job: الحجم الإجمالي، الملف، عدد الملفات، عمليات الرفع، المدة والمساحة. الموارد المحدودة جزء من الأمان، لا تحسين أداء لاحق.
- **إغلاق الحزمة:** قتل العملية قبل/أثناء/بعد `fsync/rename`، restart/readback، تكرار الكتابة وتعارض البصمة وتلف البايتات، طلبان متزامنان، فشل بعد الكتابة وقبل تسجيل المرجع، أرشيفات عدائية، سباق GC مع Session جديدة، quota exhaustion، وعدم حذف Artifact حي.

#### UXW-03.3 — Local Builder + Independent Attestor

- شغّل Builder الحالي فوق Local Artifact Store باستعمال job موقّع قصير العمر من الخادم وCandidate مثبتة؛ لا lifecycle scripts ولا مفاتيح/أسرار ولا وصول شبكي غير لازم.
- ابدأ بملف البناء الحالي `vite-react-static-v1` فقط: Node/Corepack/Vite والاعتماديات مثبتة، إعداد البناء يختاره EngineeringOS، ولا تُقرأ Candidate `package.json` scripts أو Vite/PostCSS config أو lockfile، ولا تثبّت اعتمادياتها. لا يُستبدل اسم الملف القائم بـ`vite-static-v1` دون إصدار/ترحيل. ملف `node-express-source-v1` المقترح لا يُفعّل إلا بعد UXW-03.0-B و03.4-B؛ لا يضيف تثبيتًا حرًا أو سكربتات Candidate.
- اعزل Builder بهوية غير إدارية، ومدخلات قراءة فقط، ومساحة مؤقتة وناتج منفصل، وحدود CPU/Memory/I/O/القرص/العمليات/الوقت/السجل. امنع أسرار Host وGit/Cloud credentials وDocker socket؛ الشبكة ممنوعة افتراضيًا ولا تُفتح إلا بقائمة مصادر محددة. Rootless container طبقة إضافية وليس ضمانًا للعزل؛ ملف الدعم الأول يحدد Linux/البيئة التي أثبتت حدودها.
- شغّل Attestor بهوية/عملية منفصلة عن Builder؛ أعد قراءة bytes النهائية، واحسب digest مستقلًا، وتحقق من job والعامل وصورة التشغيل وCandidate قبل توقيع receipt قصير العمر.
- اجعل Receipt يعلن Subject/Profile وسياسة الفحص بوضوح (`static_bundle` أو `backend_source_bundle` لاحقًا)؛ وسّع الخدمة المشتركة بدل Attestor ثانٍ. Receipt ليس Canonical Proof أو Acceptance أو تصريح تشغيل.
- لا يستطيع Builder قراءة مفتاح Attestor أو تعديل مدخلاته أو ناتجه بعد التسليم. Attestor لا يقرأ Candidate الأصلية، ويعيد فحص bytes والسياسة والهوية بدل قبول claims من Builder؛ ولا يملك صلاحية بدء Session أو تغيير Acceptance.
- **حد الثقة المحلي:** فصل العمليتين والهوية المحلية يقلل أخطاء/اختراق Builder، لكنه لا يثبت استقلالًا بعيدًا إذا كان مالك الجهاز أو مسؤول النظام يستطيع تعديل العمليتين أو مفاتيحهما. يجب ألا تُعرض شهادة محلية على أنها `remote_attested` أو `hardware_backed` دون نطاق تحقق مستقل فعلي.
- أظهر `assuranceLevel` كبيان provenance محدود المعنى: `local_observed` (ملاحظة على عقدة محلية مسجلة)، `locally_isolated` (ملف عزل محدد ومتحقق)، `remote_attested` (مراجع مستقل في نطاق تشغيل منفصل)، `hardware_backed` (فقط عند وجود مفتاح/جذر ثقة عتادي مدعوم). لا يرتقي المستوى لمجرد نجاح العملية، ولا يغير أيًا من Canonical Proof أو Acceptance.
- لا يستطيع Builder إصدار receipt أو تقرير القبول، ولا يصبح نجاح الخروج دليلًا على قبول Candidate.
- **إغلاق الحزمة:** فقدان الرد وإعادة المحاولة دون تنفيذ مكرر؛ قتل Builder/Attestor واستعادة Job/Lease؛ رفض Candidate قديمة أو بصمة مختلفة؛ منع إعادة استخدام receipt أو نقله بين Job/عامل/Node؛ رفض digest أو توقيع أو مفتاح منتهي/ملغى؛ نفاد الموارد؛ وتغيير Artifact بعد الفحص.

#### UXW-03.4 — Local Preview Runtime + Exposure Gateway

- قدّم Vite/React ثابتًا فقط من ArtifactRef موثق؛ لا تستخدم `dev server` أو أوامر Candidate. لا تعرض منفذًا داخليًا أو وجهة يختارها المتصفح.
- ميّز Exposure Gateway الذي يستهلك المتصفح Preview Ticket ويوجه الطلب إلى Session عن `Preview Gateway` الحالي ذي مسارات التحكم الداخلية. أعد استخدامه كـControl Plane Adapter فقط؛ لا تعتبر وجوده دليلًا على بوابة عرض للمستخدم.
- اربط Session بـ`sessionId/userId/projectId/proposalId/operationId/candidateRevision/changeSetHash/buildReceiptId/outputDigest/runtimeRef/expiresAt/stateVersion`. قبل إصدار تذكرة، يتحقق API من المالك وCandidate الحالية والإيصال ومستوى الضمان المسموح؛ Gateway يستمد Runtime من سجل الجلسة فقط. لا أصل أو IP أو منفذ يختاره المتصفح، ولا token في URL/log/analytics.
- اجعل لكل Preview Origin معزولًا؛ لا مشاركة cookies أو auth tokens مع التطبيق الرئيسي، وقيّد iframe sandbox وCSP وفتح النوافذ والتنزيلات والصلاحيات. اختبر CSRF وHost/Origin. عند تشغيل EngineeringOS مستضافًا، لا تفترض أن المتصفح يستطيع الوصول إلى `localhost`؛ افصل نمط Local/Desktop عن نمط Hosted+Agent واختبر أذونات Local Network Access.
- لا تسمح بميزة arbitrary `targetUrl` أو Reverse Proxy. لا يوجد server-side fetch في الملف الأول؛ إن أضيف لاحقًا، فحص العنوان عند الاتصال نفسه ويثبت الوجهة بعد DNS، ويتعامل مع redirect وIPv4/IPv6 وprivate/link-local/metadata وIPv4-mapped/NAT64 وDNS rebinding.
- ابدأ دورة الجلسة `requested → provisioning → ready → stale → stopping → stopped/expired/failed` مع مطابقة انتقالات `preview_sessions` الفعلية بعد 03.0؛ لا تضف حالة بلا حاجة. لا تسجل `stopped` بمجرد إرسال أمر الإيقاف، واستخدم حالة انتظار/مجهولة عند تعذر الملاحظة. أعد فحص Candidate عند التمديد وعلّم Preview القديمة `stale` عند تغيّرها.
- اعزل الملفات والشبكة والهوية؛ لا وصول إلى جذر المشروع الحي أو الأسرار أو PostgreSQL أو metadata/internal networks. عند TTL/الإلغاء، ارفض الطلبات الجديدة وأوقف العامل المملوك للجلسة وحده.
- **إغلاق الحزمة:** صلاحيات الجلسة والعبور بين المستخدمين/المشروعات، ticket replay، TTL والخمول والإلغاء، قتل عامل جلسة دون التأثير على أخرى، رفض Candidate قديمة، عزل الملفات والأسرار، رفض loopback/private/link-local/metadata وIPv4/IPv6/DNS rebinding عند وجود fetch، Host/Origin/CSRF، فشل Stop واستعادة حالة Runtime، ورحلة Playwright لمستخدم مسموح وآخر مرفوض.

#### UXW-03.4-B — Managed Backend Preview: Node.js/Express

**التبعية:** UXW-03.0-B و03.1–03.4. هذه إضافة إلى أول ملف Static، ولا تجعل Backend مدعومًا قبل تأهيل Runtime على بيئة التشغيل المختارة.

- عرّف Runtime Profile ثابتًا `node-express-managed-v1` وصورة مثبتة بالبصمة، مستخدمًا غير Root، وLauncher خادميًا ثابتًا، ومنفذًا داخليًا واحدًا وموارد/وقت/خمول محدودة.
- اسمح بمنطق Routes وMiddleware داخل عقد ملفات موثق ونقطة دخول ثابتة؛ تُضمّن Node.js وExpress والاعتماديات المعتمدة داخل Runtime. لا `npm install` حر، ولا `package.json` scripts، ولا أمر Shell أو صورة أو port أو متغير تشغيل يختاره Candidate.
- اعتبر كل ملف Candidate كودًا غير موثوق حتى لو كان Runtime موثوقًا. اقرأ الملفات من Artifact مربوط ببصمة النسخة، واجعل المصدر read-only، وامنع الوصول إلى Host وDocker Socket ومشاريع أخرى وأسرار أو خدمات EngineeringOS.
- الشبكة Deny-by-default بلا Egress في الإصدار الأول. لا يسمح Candidate باختيار وجهة Gateway أو فتح منفذ إضافي؛ الوصول يمر عبر Exposure Gateway وسياق Session المحدد خادميًا.
- لا تسمح باستخدام `WorkspaceRuntime` الحالي لتشغيل Candidate: تشغيل `pnpm run dev` من `projectRoot` الحي لا يثبت عزلًا ولا تشغيلًا من Artifact مثبت.
- **إغلاق الحزمة:** تشغيل Backend حقيقي من Artifact محدد، وإثبات هوية/بصمة Candidate وRuntime، ورفض الوصول للملفات والأسرار والشبكات الداخلية والمنافذ الأخرى؛ إيقاف شجرة العمليات عند TTL/الإلغاء؛ استعادة فقد الرد/قتل العامل بلا تشغيل مكرر؛ رفض Candidate قديمة؛ ورحلة متصفح مصادق عليها. لا تكفي استجابة `/health` أو نجاح وحدة منفردة.

#### UXW-03.4-C — Full-Stack Routing + Ephemeral Database

**التبعية:** UXW-03.4-B. نطاق لاحق مستقل؛ لا يُفترض وجوده عند إغلاق Static أو Managed Backend.

- اربط Frontend وBackend منفصلين داخل Topology موثوقة واحدة، مع أسماء خدمات ومسارات Gateway داخلية يحددها الخادم؛ لا عنوان أو DNS أو port من Candidate أو المتصفح.
- خصص لكل Preview Session قاعدة بيانات مؤقتة منفصلة، ولا تصلها بـProduction أو بيانات مشروع آخر. ابدأ بـSQLite أو Mock Services حيث تكفي؛ أي PostgreSQL مؤقتة تحتاج Provider/isolated instance وتأهيلًا مستقلًا.
- Migrations مقيدة بملف Profile ومهمة قصيرة العمر ونسخة Candidate، وتعمل على DB الخاصة بالجلسة فقط. لا تعتبر Snapshot أو Seed Artifact دليل قبول؛ يمنع إدخال أسرار أو بيانات Production.
- لا تضف Egress أو Redis أو خدمات إضافية ضمن هذه الحزمة من دون تبرير وملف Topology مُراجع.
- **إغلاق الحزمة:** عزل قواعد البيانات بين جلستين، رفض وصول Preview إلى Production/metadata/private networks، توجيه Frontend إلى Backend المقيد فقط، تنظيف DB والخدمات عند انتهاء TTL، ومنع عامل قديم من إعادة إحياء Topology أو تسجيل نتيجة.

#### UXW-03.5 — Local Agent Integration

- صمّم طريقة وصل Agent على جهاز المستخدم بـWorkspace عندما يكون EngineeringOS مستضافًا سحابيًا. تسبق التنفيذ وثيقة ADR تحدد pairing والقناة وإبطال الجهاز وتجديد الهوية.
- التسجيل بموافقة المستخدم ورمز pairing قصير العمر؛ ينشئ Agent مفتاحه الخاص داخل OS keystore قدر الإمكان، ويسجل API `nodeId`, نسخة البرنامج، النظام، capabilities، حالة المفتاح والإلغاء. اختيار المشروع والجذر المحلي صريح لكل جهاز، ولا يمنح التسجيل وصولًا تلقائيًا لمجلدات أخرى.
- لا تفتح منفذ inbound عامًا. يبدأ Agent اتصالًا صادرًا موثقًا بـTLS إلى Control Plane؛ كل Job موقعة ومحدودة العمر ومقيدة بـnode/job/attempt/dispatchGeneration/Lease. يستخدم Heartbeat وSequence/Cursor للانقطاع والاستئناف، بلا مفاتيح خاصة أو بيانات دخول داخل Job.
- لا shell عام ولا مسار filesystem حر. يقبل Agent أنواع مهمات مسماة وسياسات server-owned فقط، يحل الروابط الرمزية ثم يعيد التحقق من أن المسار داخل الجذر المصرح به، ولا يصل إلى Docker socket أو أسرار Host أو مشاريع أخرى.
- عند الانقطاع لا يعد Agent النجاح؛ يوقف العمل عند انتهاء Lease وفق watchdog، ويطابق الحالة الخادمية عند reconnect، ويرفض النتيجة القديمة أو الملغاة بدل رفعها. لا يبدأ Attempt جديدة تلقائيًا. يعرض Workspace حالات node: متصل/مشغول/غير متاح/يحتاج تحديثًا/ملغى.
- الخصوصية الافتراضية: Candidate وبياناتها ومخرجاتها محلية؛ يرسل Agent بصمات وإيصالات وملخص سجل منقح فقط. لا ينقل ملفات للمضيف/السحابة إلا بموافقة وسياسة نقل واضحة، ولا يرسل الأسرار مطلقًا.
- **إغلاق الحزمة:** pairing منتهي/ملغى/معاد؛ جهاز/مستخدم آخر؛ تدوير/إلغاء المفتاح؛ root خارج النطاق وروابط رمزية؛ shell أو Docker Socket؛ ملفات سرية؛ فصل أثناء البناء وإعادة اتصال وLease منتهية؛ Worker قديم؛ ومحاولة تسريب Candidate دون موافقة.

#### UXW-03.6 — Optional Cloud Providers

- أضف AWS وCloudflare كـadapters اختيارية للعقود ذاتها؛ لا يحتاج المسار المحلي إلى حساب أو موارد cloud، ولا يغيّر provider قواعد إثبات Candidate.
- **AWS Adapter:** أبقِ `ECS Build Executor / S3 Artifact Store / Attestor / DynamoDB Fencing / ECS Runtime / Gateway` وراء ports فقط؛ تظل `Task ARN`, `Object Key`, وFence خارج حالات Workspace. أبقِ `enable_foundation_resources=false` حتى تُراجع الموارد والتكلفة وتُعتمد خطة النشر صراحةً. لا نعيد كتابة AWS بالتزامن مع تغيير معنى الإيصال؛ أولًا نثبت contract compatibility.
- **Cloudflare Adapter:** دوره الاختياري نشر Static Preview ومشاركة رابط مؤقت/عام بموافقة صريحة؛ لا يبني ولا يتحقق ولا يشغّل كود Candidate ولا يستبدل Local Runtime. يميّز المنتج بين `Preview Ready Locally` و`Published Static Preview` حتى لا توحي المشاركة بنوع عزل غير موجود.
- سياسات اختيار التنفيذ محددة خادميًا وقابلة للمراجعة: `local_only` يمنع Cloud، `local_preferred` يفضّل Local ولا ينتقل إلى Cloud إلا إذا كانت السياسة والموافقة والسقف تسمح، و`cloud_allowed` يجيز Cloud ضمن التكلفة والحصة المعتمدتين. لا تحويل صامت، ولا اعتماد على AI في قرار الأمان/التكلفة.
- نفّذ contract suite نفسها لكل adapter، مع digest ثابت للصورة والأثر، وقيود owner/session/TTL والإلغاء والإيصال ذاتها. لا تسمح لأي مزود بتجاوز API أو التوقيع أو Attestor، ولا تعتمد Workspace على provider-specific status.
- راجع قائمة الموارد وخطة التكلفة والمنطقة وحدود الاستخدام قبل أي إنشاء؛ لا `apply` دون موافقة مستقلة. فشل مزود أو حذف حسابه لا يغيّر Candidate/Acceptance ولا يفسد السجلات المحلية؛ `terraform validate` أو local image build ليس دليل تشغيل cloud.
- **إغلاق الحزمة:** إثبات أن المسار المحلي يعمل دون إعداد cloud وأن واجهات providers لا تتسرب إلى Candidate proof. تُشغّل contract suite نفسها لأي adapter عند اختياره؛ لا يلزم تفعيل AWS أو Cloudflare لإغلاق الحزمة. نشر adapter بعينه يحتاج قرارًا وخطة موارد/تكلفة وموافقة مستقلة.

#### متطلبات أمنية وتشغيلية عابرة لكل الحزم

لا تؤجل هذه invariants إلى مرحلة الإغلاق: ربط كل Job/Artifact/Receipt/Session بالمستخدم والمشروع وCandidate/Operation/Attempt؛ Lease/Fencing تمنع العامل القديم؛ idempotency تمنع آثارًا مكررة بعد فقد الرد؛ الخصوصية تمنع تسريب الأسرار والسجلات الخام؛ الهوية ترفض stale Candidate؛ حدود موارد تمنع الاستنزاف؛ ومستوى الثقة لا يُستنتج من نجاح البرنامج.

| مجموعة تحقق | السيناريو | الثابت المطلوب |
|---|---|---|
| عقد المزود | تشغيل Local وAWS وfake adapter على العقود نفسها | لا تسرب لتفاصيل المزود إلى المجال/Workspace |
| Candidate identity | تغيير Proposal أو Revision أو Hash أو Attempt | رفض عدم التطابق |
| التكرار | فقد رد Upload/Start/Receipt ثم إعادة المحاولة | نفس الهوية ولا آثار مكررة |
| التعافي | قتل Builder/Gateway/Agent أثناء التنفيذ | استعادة موثوقة أو فشل صريح؛ لا نجاح مفترض |
| Lease/Fencing | عودة عامل بعد انتهاء Lease | لا يكتب الحالة أو Artifact/Receipt متأخرًا |
| سلامة Artifact | تغيير/تلف البايتات بعد البناء | رفض digest mismatch |
| استقلال Attestor | Builder يعدل مدخل التحقق أو يحاول استخدام المفتاح | لا receipt موثوق بلا فحص مستقل |
| أمان الإيصال | Receipt مكرر/قديم أو مفتاح/Node مُلغى | رفضه مع ربطه بالـJob الحالية |
| الملكية | مستخدم آخر يطلب Artifact أو Session | رفض الوصول وعدم كشف بيانات |
| Gateway | تبديل Session/Ticket/Host/Origin أو CSRF | رفض التفويض غير المطابق |
| الشبكة | loopback/private/link-local/metadata | منع الاتصال الداخلي؛ واختبار DNS/redirect عند وجود fetch فقط |
| الموارد | تجاوز CPU/ذاكرة/قرص/عدد عمليات/زمن | إيقاف آمن ضمن الحدود |
| دورة الحياة | TTL/خمول/إلغاء/تغيير Candidate | إبطال Session وإيقاف Runtime المملوك لها |
| GC | الحذف بالتزامن مع Session أو مرجع جديد | لا حذف لأثر له مرجع نشط |
| Local Agent | pairing/revocation/offline/reconnect | لا صلاحية أو نتيجة قديمة بعد الإلغاء |
| Browser E2E | فتح Preview حقيقية من Workspace | الصفحة تطابق Candidate/Artifact المحددين |

#### Preview Security Abuse Suite

تشمل اختبارات الملفات العدائية (traversal، symlink، أسماء متعارضة، أحجام/أعداد مفرطة)، وسلوك البناء غير الموثوق (محاولة شبكة/أسرار/عمليات غير محدودة)، ومحاولات تزييف Artifact/Receipt، والتباس Host/Origin/Session، وحدود الشبكة، والعامل القديم بعد Attempt أحدث، ومحاولات تحويل Agent إلى shell أو تجاوز الجذر. تُنفذ الاختبارات داخل بيئة اختبار معزولة وبحدود وقت/موارد، ولا تخفف بوابات الأمان عند تعذر Runner مناسب.

#### Preview Evidence Graph — إسقاط لا مصدر حقيقة جديد

اعرض سلسلة Candidate → Build Job → Artifact → Attestation → Preview Session → Browser Observation بهويات opaque وبصمات ومراجع خادمية فقط. أعد استخدام مصادر `preview_build_jobs`, `preview_sessions`, إيصالاتها، وطبقة Shared Evidence Graph/الإسقاط الحالي؛ لا تنشئ Preview Evidence Graph أو Acceptance Ledger موازيًا. لا تحفظ source bodies أو provider payloads أو raw logs أو مسارات داخلية في الرسم. وجود الرسم/السجل لا يثبت قبولًا؛ يظل القرار من Acceptance الحالي، وBrowser Verification يبقى منفصلًا عن Canonical Proof.

#### UXW-03.7 — End-to-End Qualification Gate

بوابة إغلاق بعد .0–.6؛ نجاح كل Adapter/اختبار منعزل لا يغلق الرحلة. يُؤهل كل Build/Runtime/Topology Profile على حدة، ولا تعني نتيجة Static جاهزية Backend أو Full-Stack. ينفذها مستخدم حقيقي من Workspace: فتح مشروع، طلب تعديل عبر المسار الحالي، إنشاء Candidate، اختيار سياسة Local، التأكد من أهلية Node، إنشاء Job موقعة، تشغيل Builder، إنتاج Artifact، تحقق Attestor، تحقق API، إنشاء Session للنسخة نفسها، فتح Preview والتفاعل، ثم تعديل Candidate وإظهار القديمة `stale` وإنشاء Session جديدة ومراجعة Diff/Evidence.

تكون الرحلة الأولى لـ`vite-react-static-v1`. لا يعلن `node-express-managed-v1` مدعومًا حتى اجتياز عزل 03.0-B وإغلاق 03.4-B. ولا يعلن Full-Stack/DB مدعومًا حتى إغلاق 03.4-C واختبار عزل خدمات وبيانات مستقل.

أعد كل رحلة مؤهلة مع قتل Builder/Attestor/Runtime قبل الاكتمال، وفقد الرد بعد الحفظ ثم إعادة المحاولة، وفصل Agent، وانتهاء Lease، وإعادة Start بعد فقد الرد، وانتهاء TTL أثناء المشاهدة، وتغيير Candidate، وإلغاء Node وله Session نشطة. Backend يضيف رفض الشبكات الداخلية/الأسرار/المنافذ الإضافية وقتل شجرة العملية؛ Full-Stack يضيف فصل قواعد البيانات والخدمات.

| البوابة | معيار الإغلاق |
|---|---|
| G1 Identity | Candidate identity ثابت عبر المراحل |
| G2 Execution | لا Job دون توقيع وLease/Fencing صالحين |
| G3 Artifact | bytes قابلة لإعادة القراءة وdigest مطابق |
| G4 Trust | Receipt مستقل وفق assurance المسموح ومتحقق في API |
| G5 Runtime | Session تخدم Artifact المتحقق منه فقط |
| G6 Isolation | Candidate لا تصل إلى Host أو مشروع آخر |
| G7 Lifecycle | TTL/الإلغاء/stale/التنظيف مثبتة فعليًا |
| G8 User Journey | المستخدم يرى النتيجة ويراجعها من Workspace |
| G9 Portability | الرحلة المحلية تعمل دون AWS؛ تغيير adapter لا يغير العقد |
| G10 Recovery | الفشل وإعادة المحاولة لا يخلقان تكرارًا أو نجاحًا زائفًا |

**معيار إغلاق UXW-03:** سجل رحلة منقح يربط Job/Artifact/Receipt/Session والاختبارات بنفس الهويات، مع إثبات أن ما عرضه المتصفح هو Artifact المتوقع. لا يُسجل نجاح عند غياب ملاحظة موثوقة، ولا يُرفع مستوى assurance بسبب نجاح HTTP أو عملية محلية فقط.

**توازي آمن محدود:** يمكن إعداد جرد التبعيات ومصفوفة الاختبار في 03.0 بالتوازي مع تصميم contracts دون دمج تغيير تنفيذي قبل اجتياز 03.0؛ ويمكن تحضير ملفات Artifact العدائية مع تصميم 03.2 واختبارات الموارد مع 03.3. يمكن تصميم ADR/تجربة pairing للـAgent أثناء 03.4، لكن لا يربط بالإنتاج قبل جاهزية العقود والجلسات. لا توجد تغييرات كتابة متوازية على Candidate أو Runtime أو Session دون ملكية وLease وعزل مثبت.

#### حدود الإصدار الأول

- يبدأ التأهيل بـVite/React Static، ثم يضيف Managed Node.js/Express فقط بعد إغلاق UXW-03.0-B و03.4-B؛ لا ادعاء بدعم Backend على جهاز/نظام غير مؤهل.
- لا بيئة تطوير عامة أو shell أو تثبيت اعتماديات يختارها Candidate؛ Full-Stack وقاعدة البيانات المؤقتة مرحلة 03.4-C مستقلة.
- لا Builder ثانٍ من الصفر، ولا مشاركة لمفتاح Attestor مع Builder، ولا قبول بناء من نتيجة خروج فقط.
- لا جعل AWS شرطًا، ولا نقل ملفات إلى Cloud لمجرد سهولة التنفيذ، ولا fallback مدفوع صامت.
- لا تسمية Local Preview على أنها Public Preview؛ النشر الثابت ومشاركة الرابط مسار منفصل بموافقة صريحة.
- لا خفض Canonical Proof/Acceptance، ولا إنشاء Preview Evidence Graph أو جدول مصدر حقيقة موازٍ.

#### سجل خطة AWS السابقة (مؤرشف وغير حاكم)

**تنبيه:** البنود أدناه تصف التصميم السابق المتمحور حول AWS. استُبدل ترتيبها بحزم UXW-03.0 إلى UXW-03.7 أعلاه؛ لا تبدأ من AWS ولا تعتبره شرطًا للمسار المحلي.

**التبعيات:** UXW-02.

**بوابة دخول إلزامية:** توثيق وإثبات عزل Preview عن المشروع الآخر، والخدمات الداخلية، والأسرار، ومساحة المشروع الأساسية. لا يبدأ العرض التفاعلي للمرشح قبل إغلاقها.

**فحص أمان التنفيذ الحالي — 2026-11-10:** لا يمكن فتح Preview تفاعلية اعتمادًا على Runtime الحالي. الـAPI والمشرف يشغّلان `pnpm run dev` مباشرة داخل `projectRoot`؛ تصفية متغيرات البيئة تقلل الأسرار الموروثة، لكنها لا تنشئ عزلاً للملفات أو الشبكة أو هوية نظام منفصلة. منفذ Runtime من النطاق المحلي ليس حدودًا أمنية، والعملية تستطيع الوصول إلى موارد المضيف التي يسمح بها مستخدم Replit. كذلك يبدأ Runtime من جذر المشروع الحي، ولا يثبت أن العملية تشغّل Candidate محددًا ببصمتي `candidateRevision` و`changeSetHash`. لا يوجد حاليًا Preview Gateway أو جلسة مقيّدة بـTTL أو فصل Origin/Host. لذلك لا نضيف route/proxy ولا نعرض المنفذ الخام؛ فهذا سيعرض الخدمة دون إثبات بوابة UXW-03. يلزم أولًا Runner فعلي بعزل ملفات وشبكة وهوية للمشروع، يشغّل نسخة Candidate غير قابلة للتغيير بلا أسرار أو وصول للخدمات الداخلية، ثم Gateway مصادق يربط كل طلب بالمالك والمشروع والجلسة والنسخة ومدة الصلاحية.
**تنفيذ الشريحة الأولى — 2026-11-11 إلى 2026-11-12 (محلي غير منشور):**

- أول نوع مدعوم هو واجهة Vite/React ثابتة: تُبنى مخرجات `dist` من Candidate محدد وتُقدّم كملفات ثابتة من صورة غير قابلة للتغيير؛ لا يُشغّل `npm run dev` ولا lifecycle scripts داخل Preview.
- أصبح لـBuilder تنفيذ محلي أولي: جذر التطبيق مسار نسبي صريح يحدده الخادم لكل مشروع، وتدخل قيمة `sourceRoot` في بصمة المصدر والعقد المتوقع؛ لا يختار Candidate ملف إعداد Vite أو PostCSS.
- قائمة الاعتماديات مثبتة ومحصورة في الحزم التي يستوردها Dashboard مع إضافات CSS المسموحة صراحة؛ لا يقرأ Builder سكربتات `package.json` ولا يثبت اعتماديات Candidate. يشغّل فقط Vite وإعداداته الثابتة، ويفحص ZIP والملفات وبصماتها قبل البناء.
- يخرج Builder أرشيف USTAR/Gzip محدودًا يقبله محلل Runtime الحالي، ويرفعه عبر رابط S3 قصير لكتابة شرطية لمرة واحدة. بُنيت عينة React/Vite فعلية محليًا واجتازت بوابة الاختبارات؛ هذا لا يثبت عزل ECS أو AWS أو توقيع Attestor.
- اخترنا بوابة HTTPS عامة بتذكرة موقعة قصيرة العمر. يربط الخادم التذكرة بالمستخدم والمشروع والجلسة و`candidateRevision` و`changeSetHash` والانتهاء؛ يشتق Gateway الوجهة من سجل خادمي ولا يقبل IP أو منفذًا من المتصفح.
- يكون لكل جلسة Fargate task خاص بلا عنوان عام أو NAT؛ يقبل منفذ التطبيق الثابت من Gateway فقط، ولا يحصل Candidate على `taskRole` أو أسرار.
 - قوالب `infra/aws-preview` تشمل شبكة خاصة وEndpoints وECS Cluster وECR وS3 وDynamoDB والأدوار، مع `enable_foundation_resources=false` افتراضيًا. لا تنشئ ALB أو Listener عام أو خدمة Gateway. تسجّل تعريفَي Builder وAttestor اختياريًا فقط عند تزويد بصمات الصور المثبتة ومفتاح التحقق المطابق؛ ولم يُشغّل plan أو apply.
- لا تُفتح معاينة حية حتى يُبنى Builder وRuntime من صور مثبتة بالبصمة، ويُوصل Builder بمصدر أمر خادمي موثوق وAttestor مستقل، وتُثبت مصادقة الخدمة والتحقق من التذكرة وHost/Origin وTTL والإلغاء وعزل الشبكة.

**حدود التنفيذ المحلي:** توجد شيفرة API وGateway وBuilder وAttestor، وبُنيت صورتا Builder وAttestor واختُبرتا محليًا. لم تُنشر الصور إلى ECR، ولم تُنشأ خدمة Gateway أو مهام/Endpoints على AWS. لذلك لا تزال معاينة المرشح غير متاحة للمستخدم حتى تُنشر الصور وتُطبّق البنية وتُثبت مفاتيح التوقيع.

**النطاق:**

- جلسة Preview معرّفة بنوع الهدف والإصدار ووقت الانتهاء.
- بوابة وصول مصادق عليها؛ لا منفذ داخلي خام.
- عرض Desktop/Tablet/Mobile.
- إيقاف الجلسة بعد انتهاء المدة أو الإلغاء.
- علامة واضحة إذا أصبحت النسخة قديمة.
- استخدام تحقق المتصفح الآلي في مساره المنفصل فقط.

**المخرجات:** Preview تفاعلي لمشروع/مرشح معزول، وإظهار نسخة المصدر وحالتها.

**معيار الإغلاق:**

- Candidate Preview لا يخدم المشروع الأساسي عند فشل العزل.
- الوصول عبر تغيير `sessionId` أو رابط لا يسمح بعبور مشروع/مستخدم.
- لا تُسرب الأسرار أو المسارات الداخلية أو سجلات غير منقحة.
- يوقف العامل المملوك للجلسة وحده.
- يرفض المراجع أو التطبيق Preview قديمًا على أنه النسخة الحالية.

**الاختبارات:** اختبارات حدود الشبكة وHost/Origin وWebSocket إن وجد وTTL والإلغاء وcross-project access وcandidate revision mismatch؛ اختبار متصفح تفاعلي للمستخدم مع اختبار تحقق آلي منفصل.

### UXW-08 — Application Release & Deployment Lifecycle

**الغرض:** بعد UXW-03.7 وUXW-04، تمكين المستخدم من إصدار نسخة مقبولة ونشرها ومتابعة صحتها واستعادتها من Workspace. هذا ليس امتدادًا لـPreview Session، ولا يعني أن النشر أو AWS أصبح منفذًا أو معتمدًا.

المسار المستهدف:

```text
Candidate → Accept → Apply → Release → Build → Attest → Deploy
          → Health Qualification → Promote → Operate / Rollback
```

القبول والتطبيق وتسليم GitHub والنشر قرارات ومراحل منفصلة. يتطلب نشر Production موافقة مستقلة تحدد Release وEnvironment وProvider والأثر؛ لا يسببه قبول Candidate تلقائيًا.

#### حدود إعادة الاستخدام وعدم التكرار

| القدرة | Preview (UXW-03) | Release (UXW-08) | القاعدة |
|---|---|---|---|
| Builder | Artifact للمعاينة | Artifact للإصدار | محرك واحد متعدد Build Profiles وسياسات موثوقة |
| Artifact Store | أثر مؤقت | أثر يحتفظ به للرجوع | Store/CAS واحد؛ namespaces وRetention مختلفة |
| Attestor/Verifier | Subject للمعاينة | Subject للإصدار | خدمة تحقق واحدة؛ نوع Subject وسياسة ثقة مرتبطان بالسياق |
| Jobs | Build/Session Jobs | Release/Deployment Jobs | نمط Job/Attempt/Lease/Fencing/idempotency مشترك |
| Runtime Profile | تشغيل Preview معزول | Runtime موافق للإصدار | تعريف Profile مشترك مع قيود Production مستقلة |
| Gateway | وصول Preview مؤقت | حركة مرور تطبيق منشور | لا Preview ticket/session في Production، ولا تحويل Exposure Gateway إلى بوابة إنتاج |
| حالة التشغيل | Session ذات TTL | Deployment دائم مرتبط ببيئة | لا تمديد Preview Session لتصبح Deployment |

كل إعادة استخدام يجب أن تُثبت بتوافق العقد؛ لا يُنسخ Builder أو CAS أو Attestor، ولا تدمج مسؤوليات Exposure Gateway وProduction Traffic Controller.

#### UXW-08.0 — Deployment Forensic Baseline

- جرد Candidate/Apply/Git Delivery، مصادر Release الممكنة، الجداول والمسارات الحالية، صور البناء والتشغيل، التخزين والإثبات، البيئات والأسرار وقواعد البيانات، Terraform، الـProviders واختبارات التعافي.
- اكتب مصفوفة `Existing Capability → Owner → Source of Truth → Reusable Contract → Provider Coupling → Missing Invariant → Test → Migration Risk`.
- ميّز عقد `deployment` العام وإيصال صحة المهمة عن نظام Release/Deployment للمستخدم؛ لا تعتبر الاسم أو النوع العام تنفيذًا.
- **إغلاق الحزمة:** تثبيت فجوات مصدرية، وإثبات عدم وجود Builder/Store/Attestor/Deployment Lifecycle مكرر قبل كتابة تنفيذ جديد. لا تنشئ موارد أو تنفذ Migration.

#### UXW-08.1 — Release, Environment & Deployment Contracts

- عرّف سجلات مستقلة لـ`Release` (نسخة غير قابلة للتغيير)، و`ReleaseArtifactRef`, و`Environment`, و`Deployment`, و`DeploymentAttempt`, و`HealthObservation`, و`TrafficPromotion`, و`RollbackAction`. لا تضع هذه الحالات في `preview_sessions`.
- اربط Release بمصدر ثابت: إما Candidate مطبقة بهوية `projectId/operationId/proposalId/candidateRevision/changeSetHash` وإيصال قبول/تطبيق، أو Git commit محدد مع Delivery Receipt. لا تبنِ من مجلد حي أو اسم Branch متحرك.
- اربط الهوية بـ`releaseId`, `source`, `acceptedEvidenceRef`, `buildProfileId`, `runtimeProfileId`, `policyDigest`, وidempotency key؛ كل Deployment يضيف `environmentId`, `providerRef`, `attempt`, `lease/fence`, ونتيجة ملاحظة مستقلة.
- قبول Candidate لا يمنح إذن النشر. سجّل موافقة منفصلة على البيئة والـProvider والتكلفة/الأثر، وأعد التحقق منها لحظة التنفيذ.
- **إغلاق الحزمة:** اختبارات اختلاف المصدر/البصمة/البيئة والمحاولة، رفض Branch المتحرك، وفقد الرد وإعادة الطلب دون إنشاء Release أو Deployment مكرر.

#### UXW-08.2 — Shared Build & Artifact Pipeline

- وسّع `PreviewBuildExecutor` و`PreviewArtifactStore` المثبتين بدل إنشاء Release Builder أو مخزن ثانٍ؛ افصل Build Profile وسياسة الاحتفاظ ومراجع Artifact عن Preview.
- ثبّت Builder Image وBuild Policy بالبصمة، واربط Artifact بمصدر Release و`artifactDigest` وRuntime Profile. لا تعدّل Artifact بعد الفحص.
- ابنِ Artifact مرة واحدة ثم رقِّ نفس البايتات بين Staging وProduction؛ إذا اختلف إعداد الواجهة حسب البيئة فليكن Config عامًا وقت التشغيل أو مرجع إعداد منفصلًا، لا إعادة بناء خفية.
- لا تمرر أسرار Production إلى Builder أو Artifact. احتفظ بأثر Release طوال نافذة الرجوع، ولا يحذفه GC بسبب انتهاء Preview TTL.
- **إغلاق الحزمة:** استعادة Artifact مطابق بعد restart، إثبات digest واحد عبر البيئات، وسباق GC/Deployment لا يحذف Artifact مستخدمًا.

#### UXW-08.3 — Shared Release Attestation

- أعد استخدام خدمة Attestation وReceipt Verifier المشتركتين، مع Subject صريح مثل `release_artifact` وربط Receipt بـRelease ومصدره وArtifact وBuild/Runtime Profile والسياسة والصورة المثبتة.
- لا يصدر Builder شهادة ولا يبدأ نشرًا. نجاح Attestation يثبت فحص Artifact المحدد فقط؛ لا يثبت سلامة التشغيل بعد النشر ولا يحل محل Acceptance أو Canonical Proof.
- افصل `Production Health Qualification` عن Receipt، واحتفظ بمصدر الملاحظة ووقتِها وارتباطها بـDeployment.
- **إغلاق الحزمة:** رفض Receipt قديم/مكرر/مختلف البصمة أو المصدر أو السياسة، وإثبات عدم قدرة Receipt وحده على Promotion.

#### UXW-08.4 — Deployment Provider Contracts

- عرّف واجهة Provider محدودة للتحضير والنشر والملاحظة والترويج والاستعادة والإيقاف. لا تدّعِ Blue/Green أو Canary أو Rollback فوريًا إلا عند إثباته واختباره للمزود المحدد.
- اجعل `Self-hosted Node`, وCloudflare Static، وAWS خيارات مستقبلية منفصلة؛ لا اعتماد إجباري ولا نقل Candidate أو تكلفة Cloud دون اختيار وموافقة المستخدم.
- اجعل فشل Provider لا يغير Candidate/Acceptance ولا يفسد حالة Release المحلية. لا تُسرب Task ARN أو Object Key أو provider status إلى عقد المجال العام.
- **إغلاق الحزمة:** Contract suite واحدة للمزود المختار، مع فشل/إعادة محاولة/ملاحظة غير مؤكدة؛ لا يلزم تفعيل AWS أو Cloudflare لإغلاق العقد. أي Terraform plan/apply أو تكلفة يحتاج موافقة مستقلة.

#### UXW-08.5 — Environments, Secrets & Database Binding

- افصل `development`, `staging`, و`production` في الهوية والصلاحيات والإعدادات والبيانات؛ لا تعتمد على `NODE_ENV` كحد أمني.
- خزن قيم الأسرار في Secret Manager يختاره المستخدم/Provider؛ اربط `SecretRef` وإصدارها بـDeployment ولا تحفظ القيمة داخل Release/Artifact/Build/Attestation/Logs. Runtime يأخذ أقل صلاحية، وPreview لا يرث أسرار Production.
- افصل Preview DB المؤقتة عن Staging وProduction. كل Migration مرتبطة بـRelease/Environment/Attempt/Lease وتعمل على DB المقصودة فقط.
- قبل Migration Production، استخدم Backup/Snapshot حسب قدرات المزود، واختبر Staging، وأوقف الترويج عند الفشل. لا تفترض أن Rollback للكود يعكس Migration؛ صمم Expand/Contract أو استعادة بيانات منفصلة.
- **إغلاق الحزمة:** اختبارات منع عبور الأسرار وقواعد البيانات بين البيئات، إخفاء السر من الواجهة والسجلات، وتوقف صريح عند Migration فاشلة أو Backup غير متحقق.

#### UXW-08.6 — Static ثم Managed Backend Release

- ابدأ بـStatic Release من Build Profile مدعوم وArtifact ثابت، ونقطة وصول عامة موثقة وإصدارات محفوظة للاستعادة. إعدادات Frontend لا تحمل أسرارًا.
- أضف Managed Backend فقط بعد تأهيل `node-express-managed-v1` في UXW-03؛ Runtime إنتاج مستقل عن Preview Session، مرتبط بصورة مثبتة وإصدار Release وأسرار وقت التشغيل وقاعدة بيانات Production محددة.
- امنع التطبيق المنشور من وراثة صلاحيات EngineeringOS API أو Builder أو Attestor أو Gateway. لا تسمح بأوامر/صور/منافذ غير موثوقة.
- **إغلاق الحزمة:** اختبار نشر Static فعلي؛ ثم Backend وفق ملف منفصل، مع فحص المالك والصلاحيات والشبكة والأسرار وHealth. نجاح `terraform validate` أو بناء محلي وحده لا يغلق نشرًا.

#### UXW-08.7 — Domains, Health, Traffic Promotion & Rollback

- إثبات ملكية النطاق وإدارة DNS/TLS وتجديد الشهادة؛ منع Domain Takeover بعد حذف Deployment أو حساب Provider؛ فصل نطاق Preview عن Production.
- لا تعتبر `RUNNING` أو HTTP 200 منفردًا صحة. اجمع ملاحظات موثوقة عن بدء العملية، نقطة صحة محددة، الوصول من مسار المستخدم، اعتماديات التشغيل، Crash loops، ونافذة الاستقرار.
- لا تحول الحركة إلى إصدار جديد قبل Health Qualification. وضح الانقطاع الممكن عند Providers التي لا تدعم Rolling/Blue-Green.
- افصل Rollback التطبيق والمرور والبيانات والأسرار/الإعدادات؛ لا يظهر نجاحًا نهائيًا إلا بعد ملاحظة أن الإصدار السابق يخدم الطلبات. استعادة قاعدة البيانات إجراء مستقل.
- **إغلاق الحزمة:** فشل DNS/TLS/Health لا يعلن التطبيق حيًا؛ ترويج غير المؤهل مرفوض؛ Rollback يؤكد هوية الإصدار المستعاد ومصير قاعدة البيانات بصورة منفصلة.

#### UXW-08.8 — End-to-End Release Qualification

يجب إثبات رحلة متصفح حقيقية: إنشاء Candidate → Preview للنسخة نفسها → قبول وتطبيق → اختيار نشر ومراجعة المصدر/البيئة/Provider/الأثر → موافقة صريحة → Build/Attestation → Deployment → Health → Promotion → زيارة النطاق → Release جديد مع بقاء الحالي → Rollback مؤكد.

| الفشل | الثابت المطلوب |
|---|---|
| فقد رد Build/Deploy | retry بنفس الهوية ولا آثار مكررة |
| قتل العامل أو انتهاء Lease | العامل القديم لا يكتب ولا يعلن نجاحًا |
| Candidate/Artifact قديم أو متغير | رفض النشر/الإيصال |
| فشل Health أو Migration | لا Promotion |
| سر منتهٍ أو خطأ إعداد | خطأ ظاهر دون تسريب السر |
| DNS/TLS غير جاهز | لا ادعاء بأن التطبيق Public/Live |
| فشل Rollback | الحالة تبقى غير مؤكدة؛ لا نجاح مفترض |
| تبديل Environment أو Project | لا وصول متقاطع للأسرار/البيانات |

**بوابات الإغلاق:** Release Source، Build، Attestation، Authorization، Provider/Environment، Isolation، Health، Traffic، Recovery، Rollback، ثم رحلة مستخدم كاملة. الاختبارات المجمعة لا تعوض غياب مشاهدة تشغيل فعلية.

**التبعية:** UXW-03.7 وUXW-04. يمكن تصميم العقود بعد تثبيت Build/Artifact/Runtime/Attestation في UXW-03، لكن لا يبدأ نشر تطبيق حقيقي قبلها. لا يتطلب UXW-08 إغلاق UXW-05/06/07 ولا يغيّر صلاحياتها.

#### مؤشرات UXW-08 بعد تثبيت خط الأساس

تُسجل المقاييس بعد وجود تشغيل مؤهل؛ لا تُستخدم لإلغاء موافقة أو لتجاوز بوابة:

| المؤشر | ما يقيسه |
|---|---|
| Time to First Published App | الزمن من موافقة النشر إلى وصول المستخدم للتطبيق |
| Release Build Success Rate | نجاح بناء Release وفق Profile معروف |
| Attestation Rejection Rate | رفض الإيصالات وأسبابه |
| Deployment Success Rate | النشر المؤكد من Provider، لا مجرد قبول الطلب |
| First-attempt Health Qualification | تأهيل صحة التشغيل من المحاولة الأولى |
| Time to Recovery / Rollback Success | زمن الاستعادة ونسبة الرجوع المؤكد |
| Configuration / Migration Failure Rate | إخفاقات الإعداد والأسرار وMigrations |
| Cost per Deployment | التكلفة الفعلية لكل نشر عند Provider مدفوع |
| Human Intervention Rate | النشرات التي احتاجت قرارًا أو تدخلًا يدويًا |

## 12. خطة الاختبار والقبول الشامل

### 12.1 الرحلات الإلزامية

| الرحلة                 | الثابت الذي يجب إثباته                                                           |
| ---------------------- | -------------------------------------------------------------------------------- |
| First Run              | يبدأ المستخدم هدفًا حتى مع فشل Dashboard Work Summary.                           |
| Existing Project       | سياق المشروع والصلاحية وإصدار الملفات واضح قبل الإجراء.                          |
| Goal to Preview        | الهدف يظل مرتبطًا بالجسلة والمرشح الذي يظهر في Canvas.                           |
| Preview to Review      | المعاينة وDiff والتحقق متطابقة في بصمة Candidate.                                |
| Review to Apply        | لا يمكن تطبيق مرشح تغير بعد مراجعته دون إعادة التحقق.                            |
| Apply to Evidence      | يظهر ما طبق وما لوحظ فقط من الاستجابة/الدليل المعتمد.                            |
| Apply to Delivery      | لا تُخلط نتيجة التطبيق المحلي بتسليم GitHub.                                     |
| Recovery               | Reload وانقطاع الشبكة يعيدان الحالة الصحيحة من الخادم دون إرسال أو تطبيق تلقائي. |
| Conflict               | يتوقف التعارض قبل أثر غير قابل للتراجع، ويعرض الخيارات والنتيجة.                 |
| Cross-project security | لا يستطيع المستخدم قراءة/عرض جلسة مشروع آخر بتغيير معرّف أو رابط.                |

### 12.2 مستويات الاختبار

1. **Unit:** تحويل Snapshot إلى العرض، والتغطية الجزئية، حالة `unknown`, ترجمة status، الروابط العميقة.
2. **Contract:** مخططات API، enums، IDs، revisions، الحقول nullable، ومخرجات الأخطاء.
3. **Integration:** تجميع مصادر المشروع/المحادثة/المهمة/التنفيذ/Proposal من قاعدة اختبار معزولة.
4. **State/replay:** تكرار الأحداث، انقطاع وإعادة اتصال، ترتيب قديم، cursor منتهي، محاولات متعددة.
5. **Browser security:** الوصول بين المشاريع، انتهاء الجلسة، Host/Origin، WebSocket، الشبكات الداخلية، تنقيح السر.
6. **Playwright:** رحلة كاملة من الهدف حتى مراجعة نتيجة واحدة، على Desktop وMobile وعلى RTL.
7. **Manual accessibility:** قارئ شاشة، لوحة مفاتيح، focus return، Escape، تمييز بصري، zoom وviewport ضيق.

### 12.3 معايير قياس تجربة الاستخدام

يُسجل خط أساس قبل تحديد أهداف رقمية:

- Time to First Preview.
- Time to First Accepted Outcome.
- Human Intervention Rate.
- Context Switches.
- Preview Revision Mismatch.
- Candidate Rejection Rate وأسباب الرفض.
- Recovery Success Rate.
- Unintended Mutation Count.

حد غير قابل للتفاوض: `Unintended Mutation Count = 0` في المسارات التي تتطلب موافقة صريحة. لا يستخدم عدد الاختبارات الخضراء بديلًا عن نجاح الرحلة أو صحة الإثبات.

### 12.4 شروط الإطلاق العام

- إغلاق معايير كل حزمة سابقة في مخطط التبعيات.
- اجتياز رحلة Playwright كاملة على النسخة نفسها.
- نجاح فحوص الوصول والتفويض للقراءات والأوامر وPreview.
- لا توجد شاشة تعرض `Applied`, `Proven`, أو `Delivered` بلا مصدر خادمي مطابق.
- لا توجد حالة فقد سياق أو إرجاع لمحاولة قديمة.
- تبقى حالات عدم التوفر/القدم مرئية وصادقة.
- عدم وجود تراجع غير مقبول في تجربة الهاتف أو RTL أو لوحة المفاتيح.
- كل تغيير UX مرتبط بحزمة UXW ومعيار إغلاق، لا بمجرد تحسين شكلي.

## 13. الأمان والخصوصية

- مصادقة Clerk الحالية لا تستبدل تفويض المشروع؛ تحقق الخادم مطلوب لكل endpoint.
- تخزين Query Cache ينظف عند تبدل المستخدم، وتظل Snapshot/Events مرتبطة بالمالك الحالي.
- لا يرسل الخادم إلى الواجهة بيانات اعتماد Git أو متغيرات سرية أو محتوى ملفات غير مطلوب.
- الوصول إلى Preview capability قصيرة الأجل ومقيدة بالجلسة والهدف والإصدار.
- يمنع Preview Gateway SSRF وloopback وmetadata وcross-tenant routing.
- لا يحتوي Event Stream على أسرار أو محتوى غير منقح.
- لا يصبح intent أو branch أو session من العميل حدًا للتفويض.
- لا يؤدي إدخال المستخدم إلى تغيير صلاحيات الأداة أو مستوى الخطر تلقائيًا.
- إجراءات التطبيق أو التسليم تتطلب إعادة فحص الصلاحية والـrevision والسياسة في لحظة التنفيذ.
- الإلغاء أو انتهاء الجلسة لا يمنح العامل صلاحية الاستمرار في الخلفية دون عقد/Lease صحيح.
- قيود الاستعادة والتسليم الخارجية يجب توضيحها؛ لا نعرض Undo شاملًا حين لا يوجد.

## 14. التوطين والإتاحة

- الواجهة الأساسية بالعربية RTL، مع أسماء إجراءات مباشرة.
- القيم التقنية مثل `projectId`, commit SHA، المسار، command، branch وevidence ref تظهر LTR وفي عنصر مخصص.
- لا تدمج تسمية الحالة العربية والرمز التقني في عقدة وصول واحدة غير قابلة للتمييز.
- لكل إجراء اسم Accessible يحدد العنصر أو النتيجة، حتى لا تتكرر أسماء عامة مثل «إغلاق».
- حالات Loading/Error/Empty/Partial/Stale لها دلالات منفصلة.
- لا يكون اللون وحده مؤشر حالة أو موافقة.
- لوحة العمل قابلة للاستخدام دون سحب أفقي على الهاتف.
- تظهر حاجة المستخدم ومخاطر القرار قبل الضغط، ويحافظ الرفض على البيانات.
- التنقل بالتبويب يوضح موضع التركيز، ويعيده بعد إغلاق Dialog/Drawer.

## 15. قرارات ثابتة وأسئلة مؤجلة

### 15.1 قرارات ثابتة في الإصدار 1.0

1. المساحة الرئيسية واحدة مرتبطة بمشروع، لا صفحة مستقلة لكل قدرة.
2. Snapshot طبقة قراءة؛ لا جدول حالة موحدًا كمصدر حقيقة.
3. حالات التنفيذ والتحقق والقبول والتطبيق والتسليم منفصلة.
4. Browser Preview Verification غير Preview التفاعلية.
5. Candidate والPreview والأدلة والإيصالات ملزمة ببصمة وملكية ومحاولة واضحة.
6. لا توازٍ كتابي قبل إثبات عزل التنفيذ.
7. لا استعادة عامة للبيانات الخارجية ضمن زر Rollback موحد.
8. لا يُبنى أي جزء على كيان أو مسار غير مدعوم.
9. Local-first هو الاختيار المفضل المؤهل؛ لا تحويل سحابي أو مدفوع صامت.
10. طبقات Preview Fabric حدود منطقية، لا إذن بإنشاء خدمات/جداول/مصادر حقيقة موازية.
11. Preview/Browser evidence ومستوى assurance لا يغيران Canonical Proof أو Acceptance.
12. Preview Evidence View إسقاط من السجلات والـShared Evidence Graph القائم، لا Graph مخزنًا أو Ledger جديدًا.
13. Managed Backend Preview يضاف كـProfile محدد فقط بعد تأهيل عزل Runtime لكل بيئة مدعومة؛ لا تشغيل Candidate على Host كبديل.
14. Preview وProduction Release يشتركان في Build/Artifact/Attestation بعقود متعددة Profiles، لكن Session وTicket وGateway والترويج الإنتاجي لا تُدمج.
15. UXW-08 يتطلب موافقة نشر منفصلة، وHealth Qualification وملاحظة Rollback؛ قبول Candidate أو Terraform validation لا يطلق نشرًا.

### 15.2 أسئلة يجب حسمها في UXW-00 أو بوابة الحزمة المعنية

- ما المصادر الفعلية ومعايير freshness التي يجب أن يجمعها Snapshot لكل بطاقة؟
- كيف يبنى cursor قابل للاستعادة فوق الأحداث الدائمة الحالية من دون ترتيب مصطنع؟
- ما النطاق ووسيلة التبادل الآمن لتذكرة HTTPS، وما سياسة النطاقات وملفات الارتباط في المتصفح؟
- كيف تُبنى صورة Vite/React الثابتة من Candidate دون تشغيل سكربتات غير موثوقة أو نقلها قبل الموافقة؟
- ما آلية عزل `node-express-managed-v1` التي اجتازت تهديدات الشبكة والملفات والعمليات والموارد على كل نظام/Runner مدعوم؟ وما الحد الأدنى من الاعتماديات المدمجة؟
- أي قاعدة بيانات مؤقتة تلائم Full-Stack، وما حدود Seed/Migration والبيانات التي يمنع نسخها من Production؟
- ما حدود عزل Local Agent على filesystem والشبكة، وما pairing والتدوير والإلغاء الآمن للهوية؟
- ما سياسة تنظيف Local Artifact Store عند انتهاء TTL مع الاحتفاظ بالمراجع النشطة؟
- كيف يُعرّف كل `assuranceLevel` ومصدر الثقة وإلغاء المفتاح، وما الذي يجوز أن يدعيه المنتج دون خلطه بالقبول؟
- ما قيم Placement Policy الافتراضية وحدود أهلية Node وNetwork، وكيف يطلب المستخدم نقل Artifact أو الموافقة على Cloud؟
- إذا اختير AWS/Cloudflare لاحقًا: ما المنطقة وسقف الإنفاق وحدود التزامن والموارد لكل Session، وما موافقة المشاركة العامة؟
- كيف يُعرض Preview Evidence View من السجلات الحالية والـShared Evidence Graph دون إنشاء مصدر حقيقة أو تخزين raw logs؟
- ما الأنظمة وملفات العزل المدعومة فعليًا لـLocal Agent؟ لا توحّد Linux/macOS/Windows قبل إثبات تكافؤ الحدود.
- ما نموذج اتصال المتصفح إلى Local Gateway عند استضافة Control Plane سحابيًا، وكيف تختبر أذونات المتصفح دون افتراض وصول `localhost`؟
- ما آلية إيقاف Session وتنظيف ملفات Runtime عند انتهاء المهلة دون حذف Artifact ما زال مستخدمًا؟
- ما مصدر Release المسموح أولًا: Candidate مطبقة أم Git commit بإيصال Delivery؟ وكيف ترتبط الموافقة المنفصلة بالبيئة والأثر؟
- ما Providers والـRegions وسقف التكلفة وحدود الاستخدام التي يختارها المستخدم؟ لا يُعتمد AWS/Cloudflare أو يُنشأ مورد قبل ذلك.
- ما Secret Manager ونموذج ربط الأسرار؟ وما خطة Backup/Migration/Health/DNS/TLS/Traffic Promotion/Rollback لكل Provider؟
- هل يبقى Intent Brief مسودة مرتبطة بالرسالة، أم يحتاج عقدًا دائمًا جديدًا؟ لا ينشأ كيان جديد قبل قرار موثق.
- ما قواعد الكشف الآمن عن مصدر عنصر بصري إلى ملف/مكون؟ لا تخمين مسار من DOM وحده.
- ما خط أساس مؤشرات تجربة المستخدم قبل تعيين أهداف؟
- أي مسارات قديمة تصبح تحويلًا، وأيها تبقى تفاصيل متقدمة؟

لا تؤجل الإجابة عن سؤال أمني إلى مرحلة الواجهة؛ تُغلق قبل تشغيل Preview أو التوازي.

| Preview عبر Exposure Gateway وتذكرة قصيرة | الوصول التفاعلي لا يكشف عنوان Runtime ولا يفتح Session عامة | المتصفح لا يختار المنبع؛ Control Gateway ليس بوابة عرض، وCloud Runtime اختياري. |
| Terraform محلي ومغلق افتراضيًا            | إعداد أساس آمن قبل اعتماد النشر والتكلفة                   | لا `plan` أو `apply` ولا نقل Candidate ضمن هذه الحزمة.                        |
| Release وDeployment منفصلان عن Preview    | مؤقتية Session تختلف عن استمرارية Production               | مشاركة محرك البناء/المخزن/الإثبات؛ لا مشاركة Ticket أو Session أو Gateway.      |
| النشر يتطلب تفويضًا وملاحظة مستقلة        | القبول لا يساوي الإذن بالإطلاق، وطلب Provider ليس نتيجة نشر | موافقة Environment صريحة، وHealth ثم Promotion، وRollback مؤكد بالملاحظة.       |
| اعتماد الشريحة الرأسية قبل التوازي        | اختبار الربط بين goal، runtime، candidate، evidence، apply | لا لوحة توحّد بطاقات غير معزولة.                                              |
| احترام مصدر الحقيقة لكل حالة              | «اكتمل التنفيذ» لا يعني «نجح أو سُلّم»                     | العرض يبقي status dimensions منفصلة.                                          |
| منع التحسينات الشكلية غير المرتبطة بحزمة  | الهدف إغلاق فجوة التكامل وليس إعادة تلوين الصفحات          | كل PR يذكر UXW ومعيار الإغلاق ودليل الرحلة.                                   |

## 17. شروط كل طلب تنفيذ لاحق

على كل طلب أو PR متعلق بـUX Workspace أن يذكر:

1. رقم الحزمة UXW ومعيار الإغلاق الذي يعالجه.
2. مصدر الحقيقة الحالي الذي يعتمد عليه.
3. الملفات أو العقود التي يعاد استخدامها، وما الذي لا يعاد استخدامه.
4. هويات `projectId`, `sessionId`, `taskId`, `executionId`, `attempt`, `proposalId`, `operationId`, `candidateRevision`, `changeSetHash`; وفي UXW-08 يضاف `releaseId`, `environmentId`, `deploymentId` ونسخة الإعداد/السر ذات الصلة.
5. حالات الفشل/القدم/التعذر التي ستظهر للمستخدم.
6. اختبار السلوك والثابت الذي يثبته، لا مجرد عدد الاختبارات.
7. دليل أن الإجراء لم يتجاوز صلاحية أو موافقة أو قيد عزل.

إذا لم يستطع الطلب تحديد هذه النقاط، فهو غير جاهز للتنفيذ في Workspace.

## 18. تعريف النجاح النهائي

يُعتبر EngineeringOS Studio قد حقق هدف هذه الوثيقة عندما يستطيع مستخدم غير تقني تنفيذ الرحلة الرأسية على مشروع مدعوم، من وصف الهدف إلى مراجعة وتطبيق نتيجة متحقق منها، داخل مساحة عمل واحدة، من دون فقد السياق أو تضليل الحالة أو تجاوز الموافقة.

ويُعتبر مسار إدارة التطبيقات قد اكتمل فقط عند إغلاق UXW-08 منفصلًا: يختار المستخدم Release وEnvironment ويوافق صراحة، ثم يثبت النظام البناء والإيصال والنشر والصحة والترويج والاستعادة. لا يغير هذا المسار تعريف اكتمال Workspace الأساسي ولا يدمج Deployment مع Acceptance أو Preview Session.

والاختبار الحاسم ليس أن كل صفحة تعمل منفردة؛ بل أن:

```text
الهدف + المشروع + التنفيذ + Candidate + Preview + Verification
+ Acceptance + Apply + Delivery
```

تبقى مربوطة بالهويات والإصدارات الصحيحة عبر القراءة الحية، Reload، إعادة الاتصال، المحاولة والفشل، ولا تعلن الواجهة أكثر مما أثبته النظام.

بعدها فقط يبدأ مسار اختياري منفصل:

```text
Release + Environment + explicit approval
→ Deployment + Health → Promotion / verified rollback
```

لا يُشترط النشر لإغلاق Workspace الأساسي، ولا يُعلن اكتمال النشر دون ملاحظة فعلية من Provider ومسار المستخدم.
