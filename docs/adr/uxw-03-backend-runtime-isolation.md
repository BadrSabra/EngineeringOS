# ADR: UXW-03.0-B Backend Runtime Isolation

**Status:** Isolation requirement accepted; Backend Preview remains blocked

**Date:** 2026-11-12

## Context

UXW-03.0-B must qualify an execution boundary before EngineeringOS accepts
Candidate-controlled Node.js/Express code. The source is untrusted regardless
of whether it was written by a user or generated by an Agent. It must not
inherit the API process, live project root, host credentials, Docker control
socket, or internal network access.

The user selected stronger isolation than a standard shared-kernel `runc`
container before any Backend Preview can be enabled.

The current `WorkspaceRuntime` starts `pnpm run dev` from the live
`projectRoot`; it is a project development runner, not a Candidate sandbox. The
current Preview Runtime serves static files and is not a Node/Express execution
profile.

## Decision

1. Do not execute Backend Candidates through `WorkspaceRuntime`, a direct
   `spawn()` from the API, or a Node-only egress guard.
2. Keep Backend Preview unavailable unless a server-owned Runtime Profile and
   the selected runner both prove the required file, network, identity, process,
   and resource boundaries. Never fall back to host execution.
3. Treat a disposable OCI container with `--network none`, read-only root,
   non-root identity, dropped capabilities, `no-new-privileges`, no host bind
   mounts, and bounded resources as a **qualification baseline only**. Standard
   `runc` shares the host kernel and does not meet the selected minimum for
   Backend Candidate execution.
4. Do not use that no-network profile as the final interactive topology by
   itself. It denies the Preview Gateway any IP route to the Candidate service.
   A local proof-of-concept showed a fixed HTTP handler can be reached through
   one per-session Unix-domain-socket mount while the container has no network
   and no published TCP ports. This is the preferred transport to qualify next,
   not an implemented Gateway integration or an approved production transport.
5. Keep the execution contract provider-neutral. Require a sandbox boundary
   stronger than standard shared-kernel `runc` (for example, a qualified
   gVisor/runsc or VM/microVM profile, or an equivalently evidenced boundary).
   A runner that cannot meet the profile reports an explicit unsupported/
   blocked result; it cannot weaken isolation or silently switch providers.

## Evidence from the initial local qualification

The current workspace has Docker Engine 27.5.1 with the standard `runc`
runtime, built-in seccomp, and cgroup namespaces. `runsc`, Firecracker,
Kata-runtime, `bwrap`, and Podman were not found in the PATH. This describes
the inspected workspace, not every user device or supported deployment.

A harmless probe used the already-built `engineeringos-preview-builder:local`
image. It did not receive a project mount and did not execute Candidate code.
The resulting disposable container was verified to have:

- a non-root UID and network namespace distinct from the host;
- only `lo` in Node's process-visible interface list, no IPv4 routes, and an
  unavailable IPv6 route table for which a local `::1` bind returned
  `EAFNOSUPPORT` (the existing network guard accepts missing IPv6 routes only
  with that explicit unsupported-kernel result);
- read-only root filesystem, no host bind mounts, no Linux capabilities, and
  `no-new-privileges`;
- explicit PID, memory, and CPU limits.

The existing isolation contract suite passed: `pnpm run test:api-only-smoke`
(43 tests). These are API-smoke, policy, and guard tests; they do not run a
Backend Candidate and do not close this ADR.

### Unix-domain-socket feasibility probe

A second harmless probe ran a fixed HTTP health handler in the same prebuilt
Builder image with `--network none`, no published ports, and a single
per-session read/write bind mount at `/preview`. A host-side HTTP client
received the expected `200` response through `/preview/app.sock`. Docker
inspection confirmed that this was the only bind mount and that the container
retained the non-root, read-only-root, dropped-capability, no-new-privilege,
and CPU/memory/PID settings.

This establishes a possible local Gateway-to-service path without opening an IP
interface. It does not prove the product Gateway, signed-ticket flow,
Candidate-controlled handler, socket ownership/race protections,
cross-session isolation, remote Local Agent transport, or cleanup. In
particular, the probe's read/write bind mount is not accepted as a production
policy until the Gateway owns and constrains the per-session socket lifecycle.

The local Backend Runtime image `engineeringos-preview-runtime:local` was not
present. The probe therefore establishes only that this Docker host can apply
the listed controls to a harmless container. It does not qualify a real
Candidate Runtime or prove resistance to kernel escape.

### Probe failures and their boundaries

| Observation | Boundary and resolution |
|---|---|
| The first Docker inspection assertion failed while looking for the container user under `HostConfig`. | This was a probe bug: Docker reports it under `Config.User`. The assertion was corrected and the container configuration then passed. |
| The first network probe stopped because `/proc/net/ipv6_route` was absent. | This was insufficient evidence, so the probe failed closed. A separate local bind check returned `EAFNOSUPPORT`; only then was the absent IPv6 route table accepted under the existing guard contract. |
| A probe using `require()` plus top-level `await` stopped in Node 24. | This was invalid probe syntax, not a container result. The probe was changed to consistent ESM and rerun. |
| `/sys/class/net` exposed `sit0`. | That sysfs view did not match the process-visible network namespace. The project guard uses `os.networkInterfaces()`; it reported only `lo`, and the route table had no IPv4 routes. The corrected check passed. |

No failure above involved Candidate execution; no Candidate code was run.

### Dedicated Linux host inventory

`infra/local-preview-runner/host-preflight.mjs` provides a read-only inventory
for the separately selected Linux host. Run it as the intended unprivileged
Agent account. It records basic kernel/cgroup support, current-user access to
`/dev/kvm`, and whether stronger runtime binaries are present on `PATH`; it
does not execute those binaries, install packages, alter permissions, use the
network, or run Candidate code. Its output is always diagnostic and never
qualifies a Runner. Independent policy and isolation tests remain required.

Running the preflight in the current Replit shell reported Linux x64 and cgroup
v2, but no accessible `/dev/kvm` and no `runsc`, Firecracker, Jailer, or `runc`
binary on `PATH`. This is evidence only about the Replit shell, not the separate
Linux host the user selected.

## Remaining security gates

Backend Preview remains blocked until all of the following have evidence:

1. **Supported runner and assurance:** select and qualify a runner whose
   isolation boundary is stronger than standard shared-kernel `runc`. Record
   and independently verify the provider/runtime version and policy actually
   used for each execution. Rootless mode, namespaces, seccomp, or a container
   image alone do not satisfy this requirement. The host preflight is an
   inventory only and cannot close this gate.
2. **Runtime identity:** build and pin a dedicated `node-express-managed-v1`
   image and fixed launcher. Candidate input is an immutable, digest-bound
   Artifact; no Candidate-selected image, shell, install step, entrypoint, or
   port.
3. **No host authority:** no host project mounts, Docker socket, credentials,
   database access, metadata service, or other session's files. Enforce
   read-only inputs, isolated writable scratch space, and CPU, memory, disk,
   PID, and wall-clock limits.
4. **Gateway path:** integrate the real session-bound Gateway over a
   per-session channel, preferably the Unix-domain-socket path, and prove
   socket ownership, no path/symlink race, no cross-session access, and cleanup.
   Apart from that exact channel, the Candidate must not reach host files or
   services, private networks, metadata endpoints, or arbitrary Internet
   destinations. The local probe alone cannot satisfy this.
5. **Lifecycle and replay:** test lost responses, worker termination/recovery,
   TTL and cancellation, process-tree cleanup, stale Candidate rejection,
   receipt replay rejection, and isolation between simultaneous sessions.
6. **Fail-closed behavior:** absent, stale, or unverifiable runner
   capabilities reject the request with a clear unsupported state; no host
   fallback.

## Consequences

- Static Vite/React Preview is not blocked by this ADR.
- Backend source artifacts and provider-neutral contracts may be designed, but
  no Backend Candidate may be started until the gates above are closed.
- The inspected local workspace has only the standard `runc` runtime and does
  not currently qualify for Backend Preview. Its successful Docker and UDS
  probes do not override the stronger-isolation requirement.
- The provider-neutral command, evidence, lifecycle, and reuse contract is
  specified in [UXW-03 Runner Contract V1](../uxw-03-runner-contract.md).
- The next implementation step is to turn the UDS feasibility probe into a
  session-owned, race-safe Gateway contract and qualify it with a stronger
  runner, not to add another application-level network guard.
