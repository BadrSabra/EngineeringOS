# P7.5 — مراجعة جدوى عينة `runtime.start` قبل اختيار مصدر الدليل

**الحالة:** مراجعة شيفرة وتصميم فقط، 2026-09-30؛ لم تُشغَّل
Missions أو reset أو قياسات، ولم تُفحص بيانات إنتاج أو مصدر خارجي.
**النتيجة:** التشغيل المتسلسل في مشروع واحد ممكن من حيث آلية الإيقاف
والبدء، لكن **جدوى 30 وحدة مستقلة داخل نطاق واحد غير مثبتة**.
لا يُستنتج `GO` للجمع، ولا يُعيّن مصدر، ولا تتغير
`NO_QUALIFIED_SOURCE` للشرطين أو شروط runtime السبعة `MISSING`
أو `collectionAuthorized=false` أو `fixed_safe_probe`.

## ما تسمح به الشيفرة وما لا تثبته

| المسألة | نتيجة المراجعة | الحد |
|---|---|---|
| إعادة `running → stopped` | يوجد `POST /projects/:projectId/runtime/stop` محمي بحق كتابة المشروع، وينفذ recipe له هوية وreceipt وفحص قبل/بعد تحت Gate C (`artifacts/api-server/src/routes/runtime.ts:152-175`؛ `artifacts/api-server/src/lib/recipe-operation-runner.ts:763-863`). ويمكن بدء جلسة جديدة بعد الإيقاف (`artifacts/api-server/src/lib/workspace-runtime.ts:1256-1293,1455-1485`). | حق الكتابة وreceipt ناجح لا يعيّنان مشغّل reset مستقلًا ولا يثبتان تكراريته أو استقلال الوحدات، ولا يربطان تلقائيًا الإيقاف بـMission التالية كدليل P7.5. |
| نطاق القياس | `calibrationScopeRef` يتضمن `projectId` ومراجعة المشروع والبيئة وإصدارات السياسة واسم partition (`artifacts/api-server/src/lib/agent-state/runtime-start-hypothesis-experiment.ts:398-416`). مسارا البدء والإيقاف يقرآن مراجعة المشروع الحالية (`artifacts/api-server/src/routes/runtime.ts:86-95,152-165`). | إذا لم تتغير مراجعة المشروع وأعادت attestation مراجعة البيئة نفسها، فقد يبقى النطاق نفسه؛ المسار العام لا يضمن ذلك مسبقًا. تغيير أي منها يمنع خلط النتائج. |
| شكل الوحدات | runtime durable واحد لكل مشروع بفهرس فريد (`lib/db/src/schema/workspace_runtime.ts:25-51`)؛ المدير يوقف الجلسة القائمة قبل جلسة جديدة (`artifacts/api-server/src/lib/workspace-runtime.ts:1256-1293`). | لا توجد نسخ runtime متزامنة مستقلة بنفس `projectId` في v1؛ مشاريع مستنسخة بمعرّفات مختلفة تقع في نطاقات مختلفة. البدء المتسلسل بعد reset للوحدة نفسها ليس عينة مستقلة بحكم الهوية. |
| بصمة البيئة | attestation تربط profile والمنصة وإصدارات/بصمات manifests وتنتج `env-v1` (`artifacts/api-server/src/lib/agent-state/environment-attestation.ts:228-244`). | لا تشمل لقطة كاملة لحالة العملية أو المستمعين أو الخدمات الخارجية أو تاريخ reset؛ تساوي البصمة لا يثبت تماثل الظروف أو استقلالها. |
| التسجيل والنتيجة | P7.5 يسجل تجربة Mission `runtime.start` المؤهلة فقط عندما توجد هويات Goal والخطة والتنفيذ وEpisode وأدلة قبلية (`artifacts/api-server/src/lib/recipe-operation-runner.ts:1443-1594`). يستخرج استمرار القياس نتيجة من قراءة `runtime.status` لاحقة، لا من تشغيل start جديد (`artifacts/api-server/src/lib/agent-state/runtime-start-hypothesis-measurement-continuation-runner.ts:629-662`). | مسار `runtime/stop` العام ليس P7.5 registration. مجرد Mission جديدة أو receipt reset لا يثبت وحدة مستقلة أو نسبها إلى التجربة أو عدم استخدام نتيجتها في الضبط. |

**حكم تقني محدود:** تسلسل `stop → stopped` تحت جهة مخولة ثم
Mission جديدة ببدء حقيقي قد يكون قابلًا للتنفيذ في مشروع واحد مع
ثبات مراجعاته؛ لم نثبت الربط التشغيلي بين دورات reset والتسجيل
والنتيجة أو استقلال الدوريات. لا نزعم استحالة 30 تجربة من الشيفرة
وحدها، ولا ندّعي جاهزيتها.

## حاجز عددي مستقل عن جدوى العينة

التوقع الثابت قبل النتيجة يعطي للمخرجات الأربع على الترتيب
`runtime_running=4/9`، و`runtime_not_running=4/9`،
و`runtime_other=1/9`، و`runtime_unexpected=0`
(`artifacts/api-server/src/lib/agent-state/runtime-start-hypothesis-experiment.ts:419-455,485-499`).
مقيس ECE الحالي يساوي متوسط أخطاء الفئات الأربع؛ ومع هذا
التوقع الثابت لكل تسجيل يكون ربع مجموع فروق الاحتمالات المطلقة
عن تكرارات النتائج (`artifacts/api-server/src/lib/agent-state/runtime-start-hypothesis-calibration.ts:171-199`).

- إذا كانت **كل** النتائج الكاملة `runtime_running`، فإن
  `ECE = (5/9 + 4/9 + 1/9 + 0)/4 = 5/18 ≈ 0.278`،
  أعلى من حد `0.15`. إعادة أخذ عينات bootstrap من مجموعة كلها
  نجاحات لا تخفض هذا الفارق.
- لأي عدد من النتائج الكاملة، إذا تجاوزت نسبة `runtime_running`
  `67/90 ≈ 74.4%`، فـ`ECE > 0.15` **مهما وُزّعت بقية الفئات**:
  فروق الفئات الأخرى مجتمعة لا تقل عن فرق فئة النجاح. في 30 نتيجة
  كاملة، `23` نجاحًا أو أكثر تمنع اجتياز عتبة ECE النقطية.
- الفشل ليس تلقائيًا نتيجة مفقودة: قراءة حالة `failed` مع عملية
  ميتة قد تنتج `runtime_not_running`، ومع عملية حية
  `runtime_unexpected` إذا بقيت القراءة جديدة ومطابقة للنطاق.
  الحالة `runtime_other` مدعومة في المخطط والتوقع لكن مسار
  الاستمرار الحالي لا يصدرها (`artifacts/api-server/src/lib/agent-state/runtime-start-hypothesis-measurement-continuation-runner.ts:629-662`).
  الغياب أو القراءات القديمة/غير المصنفة لا تُستبدل بفشل اصطناعي،
  بل تُبقي التسجيل غير مكتمل.

هذه ملاحظة عن **سياسة توقع v1 لا توصية بتوليد فشل** لتحسين
المقياس. لا بيانات هنا عن توزيع نتائج تشغيل حقيقي؛ اجتياز ECE
والحد الأعلى 95% ممكن حسابيًا لبعض التوزيعات لكنه غير مثبت
تشغيليًا، واجتيازه لا يثبت الاستقلال أو held-out. المقيم يتطلب
30 Mission ID صالحة ولا يقبل التسجيلات غير المحسومة، ثم يصدر
`thresholds_met_unverified` عند اجتياز العتبات دون مصدر مؤهل
(`artifacts/api-server/src/lib/agent-state/runtime-start-hypothesis-calibration.ts:325-353`).
إذا رأى المالك أن المجتمع المستهدف نجاحات البدء المعتادة، فلا
يُعدّل forecast بعد مشاهدة نتائج held-out لهذا النطاق؛ يحتاج
أي تغيير سياسة/نطاقًا جديدين وتقييمًا مستقبلًا مستقلًا.

## قرار جدوى التصميم وما ينقصه

| المرشح | الحكم الآن |
|---|---|
| تشغيلات متسلسلة للمشروع نفسه بعد إيقاف محكوم | **ممكنة آليًا، استقلالها غير مثبت.** يلزم تعريف وحدة لا تساوي Mission ID، وإطار اختيار مسبق، وعلاقة كل reset بالجلسة والحالة والبيئة والنتيجة، وحدود اعتماد التشغيلات المتكررة. |
| نسخ مشروع مستقل لكل تشغيل | **لا تُجمع في نطاق v1 واحد** لأن `projectId` جزء من بصمة النطاق. يتطلب هذا سياسة/نطاقًا ومراجعة جديدة، لا حيلة لبلوغ 30. |
| نتائج قديمة أو تجارب fixture أو اختيار نجاحات لاحقًا | **غير مؤهلة** لإثبات held-out/استقلال مستقبلي. لا يعالج توقيع لاحق تاريخًا غير مسجل. |

## مرشح وحدة محلية قابل للدحض — غير معتمد

إذا اختار المالك لاحقًا هدف **موثوقية البدء داخل مشروع واحد ومراجعة
مشروع وبيئة ثابتتين**، فالمرشح هو *فرصة تشغيل محددة مسبقًا* في دورة
تشغيل مستقلة سببيًا عن غيرها، لا Mission ID ولا مجرد إعادة
`stop → start`. لا يمتد ادعاؤها إلى مشاريع أو بيئات أخرى، ولا
يُعد هذا النص اعتمادًا من المالك لذلك الهدف.

لكل فرصة مرشحة مستقبلًا، يلزم ربط يمكن مراجعته بين: قاعدة إدراج
الفرصة وجدولها السابق للنتيجة، هوية الوحدة ومصدر اختلافها الحقيقي
عن الدورات السابقة، دليل إيقاف الجلسة السابقة وحالة `stopped`
المباشرة، أي حالة مشتركة باقية في جذر المشروع أو قاعدة البيانات
أو الخدمات الخارجية أو cache/منافذ التشغيل، ومراجعة المشروع
والبيئة والسياسة، ثم Mission/Goal/التنفيذ/المحاولة وEpisode
والتوقع المسجل والنتيجة. الربط المطلوب مفهوم إثبات **لا مخطط
جدول أو writer جديد**؛ أي `runtime/stop` receipt لا يثبت وحده
إزالة آثار الدورات السابقة أو فصل النتائج. لا يُستعمل تغير عشوائي
مصطنع أو توليد فشل لادعاء الاستقلال أو تحسين ECE.

| فحص قابل للتكذيب قبل احتساب أي وحدة | سبب الحجب إذا فشل |
|---|---|
| قاعدة اختيار الفرص وحدود الأهلية والاستبعاد مثبتة قبل نتائجها، ولا يتغير توقيت السحب أو عدد المحاولات بعد رؤية الفشل/النجاح | انتقاء لاحق أو اعتماد القرار على نتيجة سابقة |
| لكل دورة إثبات إيقاف سابق وحالة `stopped` مباشرة، مع جلسة جديدة وملاحظة `runtime.status` قبل/بعد مرتبطة بالتسجيل نفسه | `running → running`، أو جلسة/ملاحظة لا تخص التجربة |
| تدقيق الحالة المشتركة بين الدورات: ملفات المشروع، البيانات المستمرة، العمليات، الخدمات والموارد الخارجية؛ تفسير مسبق لسبب استقلال مصدر الاختلاف بين الفرص | مشاركة عامل خفي أو بقاء حالة لا يغطيها reset؛ لا يصح اعتبارها 30 وحدات بمجرد تعدد Missions |
| تطابق `projectId` ومراجعة المشروع والبيئة والإصدارات المثبتة، مع فحص سبب اختلاف World State أو الأثر التشغيلي دون استنتاج الاستقلال من hash | تغير النطاق؛ لا تُدمج النتائج في معايرة v1 |
| حفظ جميع التسجيلات غير المحسومة والتداخل والتعرض للنتائج في سجل الفحص؛ نسخة التوقع لا تُضبط بمخرجات النطاق | استبعاد انتقائي أو تسرب held-out أو استعمال النتائج في السياسة |

لا يمكن لاختبار ترابط لاحق على نتائج قليلة أن يخلق استقلالًا
لم يكن في التصميم؛ bootstrap المجمّع حسب Mission يفترض
ما لم يثبته عن العلاقة **بين** Missions. إذا لم يسمِّ المالك
ومراجع منهجي مستقل مصدرًا معقولًا لفرص جديدة غير مترابطة
ويحددا كيف يُضبط أثر الحالة المشتركة، يبقى هذا المرشح
`UNPROVEN` و`NO-GO` لجمع v1. إن كان الاستقلال يتطلب مشاريع
مستقلة، فذلك خيار بروتوكول/نطاق جديد، لا توسيع معنى v1
بالاستنتاج.

**GO للانتقال إلى قرار مصدر تصميمي فقط** يتطلب من المالك ومراجع
المنهج وصفًا مكتوبًا لمجتمع الاستدلال ووحدة استقلال قابلة للدفاع،
وتفسيرًا لعدم جعل دورات reset مجرد إعادة للحالة نفسها، وإجراء
مشغّل متكرر يحفظ مراجعات النطاق ويربط إثبات الإيقاف بالملاحظة
القبلية للـMission التالية، ومراجعة حدود تقدير ECE والـbootstrap
في هذا المجتمع. يمكن جرد مصادر قائمة بالتوازي، لكن لا يُؤهل
أيٌّ منها ولا يُبنى مصدر جديد اعتمادًا على هذه المذكرة.

إذا تعذر ذلك، يبقى `NO-GO` لجمع P7.5 في v1؛ لا تُوسّع سلطة
الوكيل إلى `stop` أو `restart` ولا يُغيّر forecast لتجاوز العتبة.
هذه المذكرة لا تختبر reset فعليًا: أي اختبار تشغيلي لاحق يحتاج
تفويضًا مستقلًا وخطة تمنع إدخال نتائجه في held-out وتراعي أن
Mission `runtime.start` المؤهلة قد تسجل P7.5 تلقائيًا. وبعد
الجدوى تبقى سلطة المصدر وفصل الواجبات والادعاءات السبعة وموافقة
الجمع قرارات مستقلة وفق
`docs/p75-sampling-heldout-governance-procedure.md`.
