# P7.5 — مسودة بروتوكول بديل لمعايرة `runtime.start` عبر مشاريع مستقلة

**الحالة (2026-09-30): تصميم للمراجعة فقط، غير معتمد وغير منفذ.**
هذه ليست نسخة v1 جديدة ولا تشغيلًا لـP11. لم يحدد المالك مجتمعًا مستهدفًا
أو جهة تصدر دليل استقلال المشاريع أو منشأ held-out؛ لم يُفوض اختبار تشغيلي
أو جمع. تبقى قرارات المصدرين `NO_QUALIFIED_SOURCE`، وشروط الثقة السبعة
`MISSING`، و`collectionAuthorized=false`، والاختيار `fixed_safe_probe`.
لا تنشئ هذه المسودة cohort أو evaluator أو writer أو صلاحية جديدة للوكيل.

## 1. الادعاء المقترح وحدوده

**السؤال المرشح:** هل forecast مسجل **قبل** تنفيذ `runtime.start` من
`stopped` يتنبأ بتوزيع نتائج `runtime.status` الملاحظة حديثًا في *مشاريع
مستقبلية مستقلة المنشأ* ضمن عائلة مهمة وبيئات محددة مسبقًا؟
هذا سؤال معايرة/قابلية نقل **للتوقع**، لا إثبات أن strategy تعلمت أو
تحسنت؛ اختبار تحسن strategy مقارنة بـbaseline وقرار ترقيتها يبقيان في
P11 و§25.4. نجاح تقني لـstart أو Gate C أو Canonical Proof ليس
outcome معايرة مستقلة ولا يمنح `PROVEN` لهذا الادعاء.

يحدد المالك والمراجع المنهجي قبل أي outcome: مجتمع المشاريع المستهدف،
توزيع بيئاتها وظروف البدء، task stratum، الفئات الأربع للنتيجة،
الـforecast المجمد وخط الأساس، وما إذا كانت النتيجة المطلوبة صلاحية
على مستوى **المجتمع** أم داخل مشروع بعينه. النتيجة المجمعة، إن
اعتمد بروتوكولها لاحقًا، لا تثبت صلاحية forecast في كل مشروع.
إذا كان المطلوب صلاحية محلية لمشروع واحد، فهذه المسودة لا تحل
مشكلة 30 وحدة مستقلة داخل `calibrationScopeRef` الخاص بـv1.
الفئات الأربع الحالية نقطة مراجعة لا مسلّمة صلاحية: مسار
measurement continuation لا يصدر `runtime_other` حاليًا رغم
إسناد forecast v1 احتمالًا لها. يجب مراجعة قابلية رصد كل فئة
ومعنى النتيجة وخط الأساس **قبل** تجميد أي بروتوكول بديل؛ أي
تعديل outcome schema أو forecast يتطلب نسخة جديدة ونتائج
مستقبلية محجوبة، لا إعادة حساب نتائج v1 بعد مشاهدتها.

## 2. وحدة الاستقلال وفصل النطاقات

- **وحدة الاستدلال العليا المرشحة:** عائلة منشأ مشروع مستقلة، لا
  `projectId` ولا Mission ID. المشاريع المستنسخة من seed أو repository
  أو fixture/بيانات أو trajectories مشتركة، والمتأثرة بسبب تشغيلي
  مشترك، تُعامل كعائلة واحدة أو تُحجب؛ مجرد اختلاف الهويات أو
  environment hash لا يثبت الاستقلال. يلزم تعريف قابل للدحض
  لمعيار القرابة والتداخل، ومصدر مؤهل لمنشأ كل عائلة وظروفها.
- **الوحدة الداخلية:** فرصة `runtime.start` مؤهلة تسجلها Mission
  مع Goal والخطة والتنفيذ والمحاولة وEpisode، وتوقع ونتيجة
  مرتبطين. الفرص المتكررة داخل العائلة مترابطة ولا تتحول إلى
  مشاريع مستقلة؛ يعالج تصميم القياس ارتباطها صراحة.
- تبقى registration وresult داخل نطاق المشروع ومراجعة المشروع
  والبيئة والسياسة الأصلية. يقترح **مرجع تقييم خارجي جديد بإصدار
  مستقل** لربط ملخصات العائلات المسموح بها؛ لا يُصنع
  `calibrationScopeRef` واحد لعدة مشاريع ولا يعاد وسم نتائج v1
  أو continuation القديمة. هذا مرجع مفاهيمي لا حقل منفذ.

## 3. التجميد والحجب قبل النتائج

1. يوافق المالك والمراجع المنهجي أولًا على مجتمع الأهلية ومعيار
   عائلة المنشأ، مصدر وسلطة إثبات الاستقلال، قواعد إدراج/استبعاد
   الفرص، ومجالات البيئة، وفصل واجبات اختيار الوحدات عن ضبط
   forecast/policy/evaluator. غياب مصدر مؤهل = **NO-GO**.
2. قبل أول outcome مؤهل، يجمد مصدر زمني موثوق نسخة
   البروتوكول والتوقع وخط الأساس وoutcome schema وطريقة
   ECE/Brier وعدم اليقين وخطة الحجم/الإيقاف وإطار عائلات
   المنشأ وقاعدة تخصيصها إلى تطوير/معايرة/تقييم نهائي. للعائلات
   المستقبلية غير المعروفة مسبقًا، تجمد قاعدة التخصيص قبل
   وصولها ثم تثبت عضوية **العائلة كاملة** قبل أول forecast
   لها، وعضوية كل فرصة قبل forecast الخاص بها؛ لا تؤثر
   النتائج السابقة في تخصيص عائلة لاحقة، ولا تُنقل عائلة
   أو trajectory مشتقة منها بين الأقسام.
3. يحفظ حارس held-out مصدر كل عائلة/فرصة وتاريخ تعرضها
   للتطوير أو الضبط والوصول إلى نتائجها، منذ بدء الحجب وطوال
   التقييم. لا يثبت partition label أو hash وحده عدم التسرب،
   ولا يعالج اعتماد لاحق تاريخًا مجهولًا. تعديل أي نسخة بعد كشف
   نتائج التقييم يحتاج بروتوكولًا جديدًا وحجبًا مستقبلًا مستقلًا؛
   لا يُعاد استخدام تلك النتائج لتقييم النسخة المعدلة.
4. تصميم فصل داخل العائلة وتكرار start أو reset لا يُطبق من
   هذه المسودة. أي تشغيل مستقبلي يحتاج تفويضًا منفصلًا ومشغّلًا
   محكومًا؛ لا يمنح الوكيل `stop`/`restart`، ولا يُحتسب
   اختبار جاف أو fixture بيانات held-out.

## 4. القياس المقترح إذا اعتُمد ونُفذ لاحقًا

- يحمل كل forecast نسخة مجمدة وزمنًا سابقًا للفعل؛ ترصد النتيجة
  من `runtime.status` حديثة ومطابقة للنطاق ومربوطة بنفس التجربة.
  تبقى نتيجة بلا ربط صحيح أو قياس حديث أو مع تغيير المراجعة
  **غير محسومة**، لا تُحوّل إلى `runtime_not_running` ولا تُحذف
  لتحسين ECE. يعرض التقرير جميع الفرص المسحوبة، والمكتملة،
  وغير المحسومة وأسبابها بحسب العائلة وtask stratum.
- تظل نتائج measurement continuation خارج معايرة v1؛
  لا تدخل البروتوكول البديل افتراضيًا. أي أهلية مستقبلية لها
  تحتاج policy ونطاقًا ومقيمًا مجمدين مسبقًا، بلا ترقية رجعية.
- تقارن forecast وخط الأساس على **نفس** عائلات التقييم،
  outcome schema، ومعاملة النقص وطريقة الحساب. تسجل
  Brier لكل فرصة، وECE محددة مسبقًا للفئات والـbins،
  مع نتائج per-project/per-stratum وملخص مجتمع مستقل.
  يحدد المراجع مسبقًا هل تُوزن العائلات بالتساوي أم بحسب
  فرصها ولماذا، وكيف يحسب فاصل عدم اليقين على مستوى
  عائلات المنشأ مع الارتباط الداخلي؛ لا تكفي bootstrap
  المجمعة حسب Mission عبر مشاريع مستنسخة.
- تقرر مراجعة قوة التقدير قبل السحب عدد **العائلات المستقلة**
  والفرص اللازمة والفئات النادرة وقاعدة توقف ثابتة. حدود
  `>=30` held-out و`>=3` transfer fixtures في §25.4
  حدان أدنى لترقية strategy وليسا تصميم حجم عينة صالحًا
  لمعايرة مجتمع مشاريع. أي طلب ترقية لاحق يظل ملزمًا
  بحد ECE والحد الأعلى `<=0.15` **في كل scope/task stratum
  يجري الترويج له** وبقية §25.4؛ لا تُخفّض العتبة أو يُنتقى
  stratum ناجح بعد النتائج. لا يحول اجتياز مجتمع إجمالي
  إلى اجتياز stratum ضعيف أو إلى صلاحية محلية تلقائية.

## 5. قرار المراجعة، الإبطال، وما ليس مخرجًا

| مدخل القرار المطلوب | سبب الحجب إذا غاب أو تعارض |
|---|---|
| تعريف مجتمع الاستدلال والعائلات، وجهة مؤهلة لإصدار سلسلة نسب كل مشروع/فرصة وفحص التداخل | معرّفات منفصلة بلا مصدر استقلال موثوق |
| موافقة مالك ومراجع مستقلين على البروتوكول والحجم والمقيم وملاءمة الاستدلال | قوة غير كافية أو مراجعة ذاتية أو سلطة غير مثبتة |
| مصدر زمن التجميد، عضوية held-out السابقة للتوقع، وسجل استعمال مستمر | تسرب أو تاريخ مجهول لا يصلحه توقيع متأخر |
| مصدر نتيجة `runtime.status` مربوط بـEpisode والنطاق والمراجعة مع حفظ غير المحسوم | نجاح تقني/قبول أو نتيجة ناقصة تُستعمل بديلًا عن القياس |
| تفويض لاحق منفصل للفحص التشغيلي ثم للجمع، ومراجعة تعارض/إبطال المصدر | صلاحية تصميمية تتحول خطأً إلى إذن تشغيل |

حالات الغياب أو المصدر الموجود بلا سلطة أو التعارض أو التسرب
تبقى محجوبة وفق `MISSING`/`UNVERIFIABLE`/`CONFLICTING`،
ولا تصبح `HUMAN_REVIEW_REQUIRED` بمجرد وجود سجل. مراجعة
المقترح لا تغير `validated_for_scope` ولا تمنح وضع
`calibrated_decision_value`. عند اعتماد بروتوكول جديد مستقبلًا،
يلزم عقد نسخة/نطاق ومدقق خادمي منفصلان قبل أي استنتاج runtime؛
هذه الوثيقة لا تُعرّف حالة قبول جديدة أو تنفذ أيًا منهما.

**مخرجات هذه المسودة:** أسئلة قابلة للرفض، لا cohort ولا نتائج
ولا قرار `GO`. الخطوة التي يمكن طلبها من المالك الآن هي مراجعة
الادعاء ووحدة العائلة ومصدرها وجدوى حجم العينة؛ إن تعذر إثبات
أي منها، يبقى P7.5 محجوبًا، ولا يبدأ P11.
