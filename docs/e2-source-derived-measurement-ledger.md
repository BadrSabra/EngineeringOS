# E2 Source-Derived Measurement Ledger

- **Updated:** 2026-10-07
- **Stage:** E2 only; E3 remains stopped. E4 remains under its existing gates.
- **Purpose:** Make E2 coverage measurable from source-discovered surfaces and invariants without deriving a denominator from test totals, `PROVEN` row counts, or a new Runtime catalog.
- **Current result:** Source-family completeness is `UNKNOWN`; no total denominator, percentage, or overall score is valid yet.

## Measurement rules

1. **Inventory completeness is independent from invariant evidence.** A source family is `CLOSED` only after its entrypoints, writers, consumers, and recovery paths have been enumerated and reviewed. Any family still `UNKNOWN` blocks a project-wide ratio.
2. **An evidence unit is one surface × one invariant.** Keep independently testable behaviors in separate rows. Do not award fractional credit to a mixed `PARTIAL` row.
3. **`PASS` is boundary-specific.** It requires source-linked evidence that tests the stated condition and scope. A test file's existence, a stored status, or an adjacent invariant is not enough.
4. **`FAIL` means a tested counterexample to that exact invariant.** `UNKNOWN` means evidence or inventory closure is missing; it does not mean the behavior is broken.
5. **No weights or aggregate score.** The number of rows and the number of passing rows are not a percentage.
6. **Stage state is not a coverage score.** `0/4` means zero of the four architectural layers is fully closed. It is not a progress fraction.

#### 2026-10-07 bounded source recheck

Read-only searches covered the workspace for retained-body references and the API-server production source for `EvidenceSnapshotInput`, `normalizeEvidenceSnapshot`, `loadCanonicalProof`, `loadReusableEvidenceReads`, finalizer calls, and acceptance-table references; test files were excluded for production counts and reviewed separately. The source confirms one production retained-body query, in `loadReusableEvidenceReads`; two chat recovery/resume callers use it. It filters complete, non-truncated source reads by execution/project/attempt and optional operation/revision, but does not recompute the stored hash/length or require a successful acceptance link. A separate integration-test file reads stored bodies for assertions. Neither read path contributes private bodies to Canonical Proof.

The recheck also confirms that the `loadCanonicalProof` production callsite set is 11 files and that direct acceptance-table references span the modules listed above. It does not classify every direct acceptance read/write by decision authority or verify all indirect client, queue, replay, and out-of-workspace consumers. Evidence-source family closure therefore remains `UNKNOWN`; this observation does not change any E2 gate or ratio.

Two non-display consumers were inspected as decision-edge samples:

- `agent-state/effect-observer.ts::linkAcceptance` locks the specified acceptance by acceptance/execution identity, checks project and attempt, rejects conflicting effect-bundle links, and rejects linking a non-observed effect to a successful acceptance. It can attach an effect-bundle ID but does not upgrade outcome or proof.
- `agent-state/runtime-start-transition.ts` transition finalizers require a successful acceptance for the bound execution/attempt and compare its effect-bundle or operation identity with the transition binding. They separately validate transition and observation evidence before materialization; the acceptance row alone is not the World State transition proof. Variant parity and recovery paths remain unclassified.

The next consumer sample distinguishes four additional roles:

- `mission-runtime.ts::evaluateRuntimeStartTransitionGate` joins successful acceptances to completed source-Goal executions by execution and attempt, requires the matching effect bundle on a materialized transition, and checks transition freshness, project scope, World Revision, and environment revision before allowing the dependent Goal to proceed. This is a dependency-release gate; a successful acceptance by itself is insufficient.
- `routes/ai/missions.ts` checks execution, project, assistant-message, successful/completed outcome, evidence snapshot/completeness, source revision, and accepted claim references for generic project-query claims, then requires a matching `PROVEN` Canonical Proof. Skill-candidate binding and replay routes use acceptance IDs to locate executions, then reload Canonical Proof under project/operation/revision/candidate and, for replay, completed Goal/plan bindings. An acceptance ID alone does not authorize those actions.
- `ai-recovery-coordinator.ts` selects current-attempt `FAILED` acceptances with bounded recovery action codes; retry/resume eligibility also checks execution/task status, `recoveryState`, retry time, resumability, and revision. `routes/ai/tasks.ts` independently rejects manual resume unless the current acceptance says `RESUME_ALLOWED`, is resumable, and has `recoveryState: REQUIRED`. These rows authorize failure recovery, not successful completion.
- `structured-task-execution.ts` reads failed rate-limit acceptances to compute cooldown/adaptive retry delay, while `task-progress.ts` permits a terminal progress event only when a matching execution/attempt acceptance exists with the same terminal outcome. These affect retry timing and progress consistency, not Canonical Proof.
- `routes/ai/analysis.ts` turns current-attempt acceptance fields into a terminal SSE projection; `routes/ai/benchmark.ts` attaches the bounded acceptance projection to Mission Control execution output. These are status surfaces, not independent acceptance decisions.
- `apply-change-reconciliation.ts::hasAcceptedApplyProof` uses a succeeded, completed acceptance bound to execution/project/attempt, operation, candidate, source revision, and effect bundle, then independently verifies the Apply episode/action, observed effect bundle/effects, before/after tree observations, and matching applied event before releasing the accepted Apply projection. | External effect | Whether it can create or report an external effect, and the observed effect boundary |
| Execution outcome | Whether it can terminalize an execution; distinguish successful authority-bearing completion from failure, cancellation, abandonment, and informational status |
| World State | Whether it reserves, materializes, or only reads/projects a World Transition |
| Decision use | Whether the value can authorize completion, dependency release, dispatch, approval, promotion, or is display-only |
| Required authority | The exact acceptance, Canonical Proof, effect observation, approval, or other server-owned check required for that operation |
| Identity binding | The project, operation, execution, attempt, objective/plan revision, candidate, and evidence identities actually required at that boundary |

A surface can have more than one disposition. Split distinct reads, writes, projections, and decision edges into separate rows when they have different authority or failure behavior. A terminal failure or cancellation is not successful completion; its correct classification does not by itself satisfy a dependent Goal or authorize promotion. Likewise, a status projection is not an acceptance writer merely because it displays `completed` or `PROVEN`.

These dispositions refine source review only. They do not create a new runtime catalog, change permission, or replace the atomic `surface × invariant` evidence register. If a disposition or identity requirement cannot be established from reviewed source and bounded evidence, keep it `UNKNOWN`.
