# خطة تنفيذ مسارات ذكاء اصطناعي بلا استدعاءات مدفوعة

**الحالة (1 نوفمبر 2026):** سياسة OpenRouter المجاني وحواجز PR-1 مثبتة محليًا باختبارات بلا egress. أصلح هذا التحديث ازدواج احتساب عينات جودة المهمة كطلبات فعلية، وأعاد تشغيل الـbuild المعزول على PostgreSQL مؤقتة؛ PR-2 ما زال يفتقر إلى خط أساس موثوق لـ«المهام المقبولة لكل رمز». قياس PR-3 وجد 4 vCPU و8 GiB ذاكرة، لكن لا runtime أو أوزان محلية ولا اختبار جودة/كمون. لا يوجد استدلال حي أو إثبات توفر الحصة الخارجية، ولا push أو deploy. لذلك لا تزال الخطة الأوسع غير مكتملة، ولا يجوز وصف RATE_LIMITED بأنه حُلّ جذريًا.
**الهدف:** منع الإنفاق على استدعاءات الذكاء الاصطناعي تصميميًا، وتقليل الاعتماد على حصة سحابية واحدة، مع حفظ المهام واستئنافها دون فقد الأدلة أو تكرار الآثار.
**المرجع التشغيلي الحالي:** يبقى توجيه المنتج إلى نماذج OpenRouter المجانية فقط إلى أن تجتاز أي وجهة إضافية بوابات الأهلية والخصوصية والقدرة المحددة هنا.

## القرار التنفيذي

لا يمكن للكود إزالة قيود حصة مزود سحابي أو ضمان استمرار أي Free Tier. ما يمكن ضمانه هو:

1. لا يرسل مسار المنتج طلبًا مدفوعًا أو إلى مسار مجهول الأهلية.
2. لا يحول 429 أو QUOTA إلى عاصفة محاولات أو تبديل غير منضبط.
3. لا يفقد المهمة عند نفاد المسارات المؤهلة؛ يوقفها ويحفظ نقطة استئنافها.
4. لا يعلن النجاح قبل قبول النتيجة وفق عقد المهمة وأدلتها.
5. يتيح لاحقًا إضافة استدلال محلي أو مزود مجاني آخر، لكن بعد إثبات صلاحية كل مسار للبيئة والحساب والمهمة.

**حدود معنى «صفر تكلفة»:** المقصود صفر إنفاق على واجهات AI المدفوعة. لا يعني أن الحوسبة المحلية أو الكهرباء أو التخزين أو الاستضافة بلا تكلفة، ولا أن حصة الخدمات السحابية المجانية مضمونة.

## حالة التنفيذ والتحقق الحالية

بدأ تنفيذ PR-0 محليًا لتثبيت سياسة OpenRouter المجاني فقط:

- قائمة مزودي المنتج منفصلة عن ترتيب registry الداخلي، والاختيار التلقائي والمرشح الاحتياطي في API يبقيان OpenRouter حتى عند غياب مفتاحه؛ لا تُقرأ مفاتيح بديلة ولا تُرسل طلبات إليها.
- طبقة نقل OpenRouter ترفض أي نموذج غير موجود بالمعرّف الدقيق في كتالوج النماذج المجانية قبل طلب الاستدلال. كما يرفض مسار الاستراتيجية قيمة `OPENROUTER_MODEL` غير المثبتة قبل تحديث الكتالوج.
- مسار استرداد القدرة الذي يبدأ من OpenRouter لا يعبر إلى مزود آخر، حتى عند غياب اعتماد OpenRouter.
- رسائل API وحالات التوافر لم تعد تقترح إضافة رصيد أو إعداد مزود بديل عند 429 أو الحصة أو النموذج المفقود/غير المتاح.
- إضافة مفتاح لمزود غير مفعّل ترفضه الواجهة قبل التخزين، وحملتا empirical quality وlive review محصورتان في OpenRouter ونماذج الكتالوج المجاني.
- واجهة مفاتيح المزودين الآخرين تعرضها كغير مفعّلة، وتسمح بإزالة مفتاح قديم فقط؛ قراءة حالة المفتاح لا تجري فحص كتالوج أو اتصالًا خارجيًا، وسجلات تنبيه Groq القديمة تُعرض كسجل تاريخي لا كإرشاد لتفعيلها.
- هذه التغييرات محلية وغير منشورة. لا تثبت أن الحصة المجانية متاحة، ولا تحل حدود 429 أو الاستجابات الفارغة عند المزود.

**أدلة تحقق محلية:** اجتازت 174 حالة للمحوّل والاختيار المجاني، و33 حالة لمساعدات مسار API، و4 حالات رفض لحملة الجودة قبل إنشاء مساحة عمل (تُركت 24 حالة خارج مرشح هذا التشغيل)، و252 حالة لواجهة المحادثة، و16 حالة للوحة التحكم. في هذه الجولة اجتازت اختبارات 429/التبريد المحاكية 24 حالة من عميل OpenAI-compatible و7 حالات من موثوقية OpenRouter (142 حالة أخرى متخطاة عمدًا بمرشح الاختبار)، مع `AI_PROVIDER_EGRESS_DISABLED=1`. نجحت فحوص TypeScript لخدمات API والمنسّق والواجهة و`git diff --check`. واختبارات الواجهة تستخدم mocks.

**حدود التحقق:** لم يُشغّل طلب استدلال حي إلى OpenRouter، ولا benchmark أو رحلة Mission. سجلت خدمة API القائمة تحديثًا دوريًا لكتالوج OpenRouter كل خمس دقائق (17 نموذجًا مجانيًا و0 مدفوع ضمن الكتالوج وقت السجل)؛ هذا طلب كتالوج تحكمي، وليس اختبار استدلال ولا دليلًا على توافر الحصة. لم يثبت السجل إن كان طلب الكتالوج يشارك حدًا منفصلًا مع حد الاستدلال. فحوص مسارات API التي تكتب بيانات لم يُعَد تشغيلها لأن إعدادها لم يثبت قاعدة مؤقتة صريحة. كما أن تشغيلًا سابقًا لاختبارات API أعطى 6 إخفاقات ضمن 249 حالة، ولا يُعتمد دليلًا على سلامة المسار أو قاعدة البيانات؛ وجهة قاعدة ذلك التشغيل لم تُثبت كقاعدة مؤقتة. لذلك لا يمكن تأكيد أن Development/Production لم يتأثرا من ذلك التشغيل، ولا يجوز إجراء فحوص DB أخرى قبل تجهيز عزل مثبت.

**تتبّع Workflow API (1 نوفمبر 2026):** أظهر السجل أولًا بدء الـartifact المُدار على `0.0.0.0:8080`، ونجاح فحص المزود وتحديث كتالوج OpenRouter (17 مجانيًا و0 مدفوع)، ثم إعادة تحميل سجل التدقيق؛ بعدها فشل الاستماع بـ`EADDRINUSE`. يبين ترتيب `src/index.ts` أن المصالحة والتنظيف/الحذف الدوري تُستدعى قبل ربط المنفذ. فحص `ss` و`fuser` بعد الفشل لم يجد مستمعًا على 8080، ولم تُثبت هوية مالك المنفذ وقت الخطأ. أوقفنا عندها ولم نقتل عملية. بعد تأكيد المالك أن وجهة الـWorkflow هي Development والموافقة على الصيانة، أُعيد تشغيله مرة واحدة ونجح الاستماع على 8080؛ أعاد `/api/healthz` و`/api/readiness` حالة 200، وظهر في السجل `Server listening`. فحص الصحة سجل صفر صفوف محذوفة في عدّادي تنظيف تشخيصات AI وسجلات تنفيذ المهام، لكنه لا يعرض عدد صفوف `pruneExpiredAiUsage`؛ لذلك لا ندعي أن كل صيانة كانت بلا أثر. جرى تحديث الكتالوج الخارجي مرة أخرى؛ لا يظهر طلب استدلال حي. تأكيد Development مصدره المالك، وليس قراءة مستقلة لعنوان الاتصال. لم ننشر إلى Production.

**فشل P0 المسجل قبل الإصلاح:** اختبار حدّ جديد استدعى `agentComplete()` مباشرة مع كل من Groq وGemini وDeepSeek ومفتاح اصطناعي و`fetch` محاكى. فشل رفض المزود في الحالات الثلاث (3 فشل، 9 نجاح)؛ وصل التنفيذ إلى عملاء النقل بدل رفضه قبل الشبكة. كان `assertProductProviderEnabled` موجودًا في فحص المفتاح فقط، لا عند بداية `agentComplete`. لم يُرسل أي طلب خارجي في هذا الاختبار، ولا يثبت هذا وحده وجود مسار HTTP عام قابل للاستغلال؛ لكنه يثبت تجاوزًا داخل واجهة المنسّق يحتاج إصلاحًا واختبارًا مستقلًا قبل إغلاق P0.

**فشل 429 المسجل قبل الإصلاح:** اختبار محلي بـ`fetch` محاكى مرر خيار `waitOnRateLimit: true` إلى `openrouterCompleteWithFallback`، مع `Retry-After: 1` ونطاق مصنّف `unknown`. أظهر السجل انتظارًا ثانية ثم استدعاءً ثانيًا؛ وفشل الشرط 1 مرة (كان المتوقع طلبًا واحدًا، والفعل وقع طلبان). لم يحدث اتصال خارجي. الخيار كان متاحًا عبر نوع خيارات `agentComplete` أيضًا، رغم عدم وجود مستدعٍ حالي يفعّله. هذا يخالف سياسة التوقف عند النطاق المجهول، ويجب ألا يصبح إعادة طلب داخل العملية مسارًا لمنتج.

**فشل التحقق الأول بعد تغيير سياسة 429:** اجتازت اختبارات السلوك 184 حالة، لكن فحص TypeScript أوقف الإغلاق بثلاثة أخطاء: تمرير `waitOnRateLimit` إلى نوع خيارات أُزيل منه الحقل، وبقاء استيراد غير مستخدم، ومقارنة `"model"` بقيم لا تتضمنها الأنواع الحالية لنطاق الحد. هذه أخطاء تكامل في التغيير الحالي، لا إخفاقات مزود أو قاعدة بيانات؛ يجب تصحيحها ثم إعادة typecheck والاختبارات.

**فشل تحقق TypeScript التالي:** بعد تصحيح أخطاء الواجهة الثلاثة، بقي خطأ واحد: دالة `sleep` لم تعد مستخدمة بعد إزالة إعادة محاولة 429 داخل الطلب. اختبارات السلوك ما زالت 184/184 ناجحة؛ الخطأ محصور في تنظيف الكود الناتج عن التغيير.

**نتائج الإصلاح والتحقق الحالي (محلي، دون مزود حي):**

- أضيف رفض صريح في `agentComplete()` قبل تحميل المفتاح أو فحص دورة حياة المزود أو استدعاء العميل؛ بعد الإصلاح نجح اختبار حدّ الرفض `12/12`. اختبارات اختيارات API ذات الصلة نجحت `33/33`.
- أزيلت آلية `waitOnRateLimit` من المسارات عالية المستوى ومن عميل النقل: 429 لا ينتظر ثم يعيد الطلب داخل الاستدعاء نفسه، و429 مجهول النطاق يفشل مغلقًا. اختبارات المنسّق والعميل والتبريد والحارة: `184/184`.
- نجح `typecheck` للمنسّق وخادم API و`git diff --check`.
- أُنشئ PostgreSQL مؤقت جديد تحت `/tmp` بعنوان Loopback صريح؛ طُبق مخطط الكود الحالي عليه فقط، ونجحت اختبارات cursor/lease الثلاثة `3/3`، ومنها حجز النموذج نفسه من عمليتين مستقلتين. أُوقف العنقود بـ`pg_ctl` وأُزيل جذر الاختبار؛ لا عملية مطابقة بقيت. لم يستخدم هذا الاختبار Development أو Production.
- شُغّلت الاختبارات مع `AI_PROVIDER_EGRESS_DISABLED=1` ومفاتيح المزودين غير موجودة في بيئة الأمر؛ لم يُرسل استدلال حي ولم يُتصل بأي مزود خارجي.
- لم يُعَد تشغيل خدمة API: سجلها يثبت وجود تحديث دوري قائم لكتالوج OpenRouter كل خمس دقائق؛ تجنبنا إعادة تشغيل قد تطلق طلب كتالوج إضافيًا. لذلك هذه نتائج source/tests، وليست تأكيدًا بأن عملية API الحالية حمّلت الملفات المعدّلة.

**الحدود التي كانت قائمة قبل منسّق الحجز الحالي:** كان الحجز يخص النموذج وحده، ولم يكن يثبت منع التزامن بين موديلات مختلفة للاعتماد نفسه أو بين بيانات اعتماد مختلفة لناشر واحد. لم يُنفذ اختبار Mission لاستئناف مهمة بعد 429 دون تكرار آثار الأدوات، ولم يوجد قياس baseline لمعدل القبول لكل استدعاء أو benchmark لاستدلال محلي. حجز الناشر الذي أضيف لاحقًا يقلل التوازي المحلي ولا يثبت نطاق الحصة عند upstream.

**فشل اختبار المرحلة 3 قبل الإصلاح:** اختبار محلي حاكى ردّين فارغين ثم نجاحًا؛ مع عدم تحديد `maxFallbackModels` انتقل التنفيذ إلى النموذج الثالث بدل التوقف بعد الأساسي والبديل. الفشل متوقع وفق السياسة المحافظة، وناتج عن غياب حد افتراضي؛ كل الردود كانت من `fetch` محاكى ولم يحدث اتصال خارجي.

**فشل التحقق النوعي أثناء توصيل القبول:** أول `typecheck` رفض تمرير خيارات fallback إلى دالة القبول لأنها كانت معرفة كخيارات نقل كاملة، مع أن fallback يحذف عمدًا `baseUrl` و`providerName`. لم يبدأ أي طلب؛ الإصلاح هو تضييق نوع مدخل القبول إلى حقول السياسة/الحجز المطلوبة فقط.

**فشل الجولة التالية من التحقق:** بعد تضييق النوع، بقي خطأان نوعيان لأن سياق القبول لا يضمّ `model`، وفشلت 4 من 94 حالة نقل لأن fixtures استخدمت معرفات نماذج غير موجودة في الكتالوج المجاني؛ الحارس رفضها قبل `fetch` كما ينبغي. لم يحدث أي اتصال خارجي. الإصلاح المقصود إضافة `model` إلى مدخل القبول وتحديث fixtures فقط إلى معرفات مجانية حقيقية من الكتالوج، دون استثناءات اختبارية في كود الإنتاج.

**مراجعة بوابة اختيار المزود:** كشف اختبار الحدّ أن فرض allowlist داخل `resolveExecutionProvider()` يخلط اختيار المحاكي بحدّ إرسال المنتج. أُبقي قرار الاختيار عامًا، ووُضعت الحماية عند حدود اعتماد واستدلال المنتج الفعلية؛ لا يُعاد توجيه تفضيل غير مؤهل إلى مزود آخر بصمت.

**مراجعة بوابة benchmark:** ظهر أن فرض allowlist المنتج داخل `probeProviderHealth()` يمنع قياس adapters المعزولة ويخلط بين مسار المنتج وأداة benchmark. أزيل ذلك الحارس؛ تظل الحماية إلزامية عند حدود استدلال المنتج الفعلية، لا في كل أداة قياس عامة.

**نتيجة التحقق الشامل الأولى بعد تجميع القبول:** نجح typecheck للـorchestrator والـAPI واختبار API route helpers (33/33)، لكن تشغيلًا كاملًا مبكرًا انتهى بـ2622 نجاحًا و63 فشلًا من 2685 عبر 12 ملفًا. لم تُستخدم خدمة حية. صُنفت الإخفاقات لاحقًا؛ هذه نتيجة تاريخية لا تمثل الحالة النهائية.

**تصنيف أولي للإخفاقات:** معظم حالات `FREE_ROUTE_NOT_VERIFIED` نتجت عن فرض allowlist داخل `resolveExecutionProvider()`، وهو دالة اختيار مشتركة تُستخدم أيضًا في اختبارات ومحاكيات `chat-agent`، وليست حد إرسال HTTP ولا نقطة تحميل credential لواجهة المنتج. هذا كان تغييرًا أوسع من اللازم؛ يُعاد القرار إلى وظيفة الاختيار، وتبقى الحماية عند حدود المنتج/الاعتماد/النقل الفعلية. بقية إخفاقات OpenRouter تتطلب fixtures بعقود نماذج حقيقية، بينما timeout وفرق ترتيب scorecard لم يثبت بعد أنهما سببهما التعديل.

**فشل scorecard تاريخي:** فشل اختبار منفردًا في ترتيب fallback بعد انتهاء rolling window، لكن اختباراته اجتازت تشغيل الحزمة النهائي أدناه. لم يجرِ أي إرسال في التشخيص الأول؛ لا يُسجل كعيب حالي مثبت.

**سجل تشخيصي سابق لقاطع الاعتماد:** ظهرت توقعات اختبار قديمة تسمح بمحاولة تالية بعد غياب `Retry-After` أو تتوقع تبريد النموذج بدل الاعتماد. عُدّلت fixtures والعقود، ثم اجتازت الاختبارات النهائية المجموعة الكاملة أدناه؛ لم يحدث اتصال خارجي في أي تشغيل.

**إعادة قياس تاريخية بعد تحديث توقعات 429:** ظهرت حالتا اختبار بسبب مقارنة زمنية حرفية ورسالة stream قديمة؛ أصلحتا قبل التحقق النهائي أدناه.

**تشغيل الحزمة قبل إصلاح fixtures والمهلات:** `vitest run` اكتمل بـ2,924 نجاحًا و15 فشلًا و4 تخطّيات من 2,943 اختبارًا عبر 180 ملفًا. عُدلت fixtures لتتوافق مع عقد الأدوات والكتالوج، وأزيل الخلط بين probe المنتج وprobe benchmark؛ ثم اجتازت الحزمة نهائيًا في قاعدة مؤقتة موثقة أدناه.

**تشغيل بلا `DATABASE_URL` (غير صالح كدليل حزمة):** فشل 159 اختبارًا لأن استيراد `@workspace/db` يرفض غياب المتغير، بينما اجتاز 2,230 اختبارًا. لم يصل هذا التشغيل إلى قاعدة بيانات؛ لا تُستخدم هذه النتيجة كحكم على سلوك المنتج.

## تحديث منسّق الحصة والإثبات

كل طلب استدلال OpenRouter يمر الآن ببوابة admission قبل الإرسال: أهلية النموذج المجاني وقدرته أولًا، ثم حالة التبريد، ثم حجز متسلسل لهوية اعتماد مشتقة غير سرية وnamespace الناشر والنموذج الدقيق. الحجز يعيد استخدام lease PostgreSQL المشترك؛ فشل التخزين أو انشغال الحارة يمنع الإرسال، وتُحرر الحجوزات بترتيب عكسي أو تنتهي بمدة محدودة. تُعاد قراءة التبريد بعد الحجز لتفادي سباق عامل آخر.

هوية حجز الاعتماد مشتقة من SHA-256 ولا تحتوي المفتاح الخام. سجل تبريد الاعتماد المستديم يستخدم HMAC عند ضبط مفتاح التشفير؛ عند غيابه لا يوجد ضمان تبريد اعتماد مستديم عبر العمليات، رغم بقاء lease الحجز المشترك فعالًا. يجب اعتبار هذا نقص إعداد/مراقبة، لا تخمين أن الحالة مشتركة.

حجز namespace الناشر إجراء محلي محافظ لتقليل تزامن موديلاته؛ لا يثبت أن OpenRouter يوجهها إلى مجموعة upstream واحدة أو أن حصة متبقية متاحة. نطاق المجموعة يُعامل كمؤكد فقط عندما يطابق اسم upstream الذي أرسله المزود namespace معروفًا؛ النطاق غير المعروف أو غير القابل للربط يوقف الاعتماد بدل تجربة موجة بدائل.

على 429 لا يعاد الطلب داخل العملية ولا يحدث fallback في المحاولة نفسها. `Retry-After` الإيجابي يُحفظ للنطاق الذي أثبته المزود فقط؛ النطاق المجهول أو حد الحساب/الاعتماد يمنح hold على الاعتماد. عند غياب المهلة يستخدم القاطع المحلي تدرجًا محدودًا يبدأ بـ30 ثانية ويتضاعف حتى 10 دقائق بعد فشل حديث، ولا يمثل موعدًا من المزود. `EMPTY_RESPONSE` حالة منفصلة ولا تسمح إلا بالأساسي وبديل مجاني واحد مؤهل للعقد؛ لا تُقبل كدليل نجاح.

**التحقق النهائي:** اجتاز typecheck للـorchestrator وAPI؛ واجتازت الحزمة 180/180 ملفًا و2,945 اختبارًا، مع تخطٍ واحد من 2,946. شُغّلت على PostgreSQL مؤقتة loopback فقط بعد تطبيق `schema:apply`، مع `AI_PROVIDER_EGRESS_DISABLED=1` ومفاتيح المزودين غير موجودة. اجتاز اختبار cursor/lease الحقيقي على القاعدة المؤقتة 3/3. ظهر تحذير Node واحد عن عدد AbortSignal listeners لكنه لم يفشل أي اختبار.

**إغلاق فجوة استئناف Task بعد 429:** صُنّف `RATE_LIMITED` و`QUOTA` كفشل مزود مميز، مع تمرير نطاق التحديد ومصدر المهلة الآمن فقط إلى قبول التنفيذ. تُسجل المهلة المحلية التكيفية بوصفها `adaptive_default`، ورفض الحارة المحلي بوصفه `local_admission`، ولا يُحوّل أي منهما إلى مهلة مزود. داخل معاملة التنفيذ، وبعد قفل Task والتنفيذ والقبول المطابق للمحاولة، يُفحص `retryAt` قبل استعادة/تدوير رمز الاستئناف أو حجز المحاولة. الموعد المفقود يسمح بتوافق السجلات القديمة؛ الموعد المشوه يوقف المسار مغلقًا. واجهة `/ai/tasks/:taskId/resume` تفحص الموعد قبل حل بيانات اعتماد المزود وتعيد 429 مع `Retry-After` عند الانتظار، أو 503 عندما يتعذر إثبات الموعد.

**توافق Chat الموجود مسبقًا:** المسار لا يستخدم زر الاستئناف العام؛ لديه `retry-capability` خاصًا للتنفيذات المؤهلة، مربوطًا بالقبول الحالي و`retryAt`. اختبار تكامل المسار يثبت رفض طلب مبكر قبل موعد المهلة ثم إصدار القدرة بعد انتهائها، وواجهة Chat تعرض مؤقتًا لحالات PROJECT_QUERY المؤهلة. لذلك لا تُسجل هذه الجزئية كفجوة جديدة؛ التغيير الحالي يضيف فقط عرض انتظار مماثل في لوحة Tasks.

**سجل فشل التحقق قبل إصلاح fixture:** اختبار `does not retry an upstream shared-pool 429 within the request` أُعيد توجيهه لتأكيد وسم التبريد المحلي، لكنه ظل يرسل رأس `Retry-After: 120` ولم يحدد اسم upstream مطابقًا لـnamespace النموذج. لذلك رفض الاختبار توقع `LOCAL_ADAPTIVE_MODEL_COOLDOWN`؛ كانت بيانات الاختبار تمثل مهلة مزود صريحة/مجموعة غير مربوطة، لا تبريدًا محليًا لمجموعة معروفة. لم يدل ذلك على فشل التنفيذ، ولم تبدأ بعده اختبارات API في ذلك التشغيل.

**إعادة المحاولة بعد تصحيح المهلة فقط:** أزيل رأس `Retry-After` وأضيف `provider_name: "Liquid"`، لكن الاختبار ما زال لا يرى `LOCAL_ADAPTIVE_MODEL_COOLDOWN`؛ السجل أكد تصنيف scope فقط ولم يكشف هوية مجموعة upstream المستخدمة. هذا يعني أن fixture لم يثبت بعد تطابق namespace الفعلي، وليس نجاحًا للفرع المحلي. أوقفنا مجموعة الاختبارات عند أول فشل؛ لم تبدأ اختبارات API في هذا التشغيل أيضًا.

**سبب الفشل الثاني:** الاختبار كان يستدعي `oacCompleteRaw()` مباشرةً، وهي طبقة النقل التي تصنف 429 فقط؛ تسجيل القاطع التكيّفي موجود في غلاف `openrouterCompleteWithFallback()`. تغيير بيانات الـfixture وحده لا يمكن أن يختبر هذا السلوك في الطبقة الخطأ. سيُبقى اختبار النقل الخام على توقعه الأصلي، ويضاف اختبار مستقل للغلاف الذي يملك منطق التبريد.

**التحقق المركّز من حاجز Task وChat والواجهة:** اجتاز typecheck API وDashboard. على PostgreSQL مؤقتة محصورة بـ`127.0.0.1` وبـ`AI_PROVIDER_EGRESS_DISABLED=1`: اختبارات OpenRouter المركزة 3/3، اختبارات API الخاصة بـTask 10/10، واختبار Chat للتأخير وإصدار retry capability بعد انتهاء الموعد 1/1. اجتاز ملف Tasks في Dashboard 37/37، بما فيها الانتظار المتناقص، إخفاء زر الاستئناف أثناء المهلة، إظهاره بعد انتهائها، والإغلاق عند موعد مشوه. كما اجتازت اختبارات حدود المزود المجاني 14/14. المرشحات تخطت اختبارات غير مستهدفة (97 في OpenRouter و90 في API Task و123 في تكامل Chat)؛ لا تمثل هذه نجاحًا أو فشلًا لتلك الحالات.

**إثبات lease بين العمليات:** اختبار `model-lane-cursor-store.db.test.ts` اجتاز 3/3 على PostgreSQL مؤقتة loopback بعد تطبيق مخططها؛ من بينها عملية فرعية مستقلة لا تحصل على lease النموذج نفسه أثناء امتلاك العملية الأولى له، ثم تحصل عليه بعد تحريره. هذا يثبت قفل PostgreSQL المشترك لمسار lease، ولا يساوي اختبار طلبين حيين كاملين أو قياس حصة OpenRouter. أُغلقت القاعدة المؤقتة بعد الاختبار.

**حالة خدمة التطوير وحدود الإغلاق:** بعد تعارض أولي على المنفذ 8080، استُعيدت خدمة API المُدارة مرة واحدة؛ انتهى الـworkflow بحالة `RUNNING`، وأعاد `/api/healthz` الرمز 200 و`jobRecovery: healthy`. جلب بدء التشغيل 17 نموذجًا مجانيًا و0 مدفوع، ولم يحدث استدلال حي. المنسق لا يخلق سعة جديدة لدى OpenRouter ولا يضمن اختفاء `RATE_LIMITED` أو `EMPTY_RESPONSE`. لا يوجد مسار استدلال محلي معتمد، ولا ينبغي ادعاء حل جذري لحصة المزود.

## نموذج الأهلية للمسار

لا تكفي قيمة `free: true` أو لاحقة `:free` لإثبات صلاحية أي مسار لكل حساب ولكل وقت. يجب أن يصف كل مرشح:

- المزود والنموذج وقدراتهما المطلوبة: chat، الأدوات، JSON، البث والسياق.
- حالة السعر: `verified_free` أو `free_quota` أو `unknown` أو `paid`.
- نطاق التحقق: المزود، الحساب/بيانات الاعتماد، النموذج، المنطقة ونمط endpoint عند توفرها.
- مصدر التحقق ووقته ومدة صلاحيته، مع رفض الحالة المنتهية أو المجهولة.
- سياسة الدفع الخاصة بالحساب، بما فيها أي تعبئة تلقائية أو تجاوز للحصة إن كان المزود يدعمها.
- تصنيف الخصوصية: ما البيانات التي يجوز إرسالها إلى الوجهة.

المساران `verified_free` و`free_quota` لا يصبحان مؤهلين إلا إذا كان التحقق حديثًا ومطابقًا للحساب. `unknown` و`paid` مرفوضان افتراضيًا. استجابة كتالوج عامة لا تثبت حالة الفوترة في حساب المستخدم.

## مسار التنفيذ المستهدف

1. **حساب حتمي أولًا:** استخدم قواعد التطبيق، الأدلة المقبولة، القراءات الموجودة، والفحوص المحلية قبل طلب نموذج.
2. **تحضير سياق محدود:** استرجع الملفات اللازمة فقط، واربط كل cache بمراجعة المستودع وعقد المهمة وإصدارات الموجّه/النموذج؛ لا تعتبر cache دليلًا جديدًا.
3. **Admission قبل الشبكة:** احجز محاولة وميزانية رموز متحفظة وهوية طلب مادية فريدة، ثم امنع الازدواج أو تجاوز التوازي ضمن الحساب/النموذج/مجموعة المزود.
4. **اختيار مؤهل:** اختر من المسارات المجانية المثبتة التي تحقق عقد المهمة. ترتيب القدرة والجودة لا يستطيع تجاوز سياسة السعر أو الخصوصية.
5. **تصنيف الفشل عند حد HTTP:** احتفظ بنوع الخطأ ونطاقه ومدة `Retry-After` الإيجابية فقط، من دون أجسام الطلب/الاستجابة أو بيانات الاعتماد في السجلات.
6. **قبول مستقل:** مرّر المحتوى إلى تحقق البنية والدلالة والاستشهاد والأدلة وقبول المهمة. نجاح HTTP أو نص النموذج ليس نجاحًا نهائيًا.
7. **توقف واستئناف:** إذا لم يوجد مسار مؤهل، احفظ checkpoint وحالة انتظار قابلة للاستئناف. عند الاستئناف لا تعاود الآثار الجانبية المكتملة ولا تصطنع receipt.

## سياسة الفشل

| الحالة | السلوك المطلوب |
|---|---|
| نموذج مدفوع أو `unknown` | رفض قبل أي طلب للشبكة؛ لا fallback تلقائي |
| `RATE_LIMITED` مع `Retry-After` إيجابي | اعتبره حدًا منسوبًا للمزود؛ لا تعِد الطلب في العملية نفسها. احفظ التبريد للنطاق المؤكد، ولا تعممه على أشقاء غير مثبتين |
| `RATE_LIMITED` بلا مهلة | استخدم التبريد المحلي المحدود: model/pool للنطاق upstream المثبت، والاعتماد للحساب أو النطاق المجهول. لا تعرضه كموعد من المزود |
| 429 بنطاق حساب/اعتماد أو مجموعة upstream | أوقف العملية دون fallback داخلها؛ لا تبرد إلا النطاق المثبت. إذا لم يمكن ربط المجموعة بمرشحيها، أوقف الاعتماد بدل تخمين أشقاء المجموعة |
| 429 بنطاق مجهول | credential hold fail-closed؛ لا تخمّن أن نموذجًا آخر يتجاوز الحصة نفسها |
| `QUOTA` | أوقف المسار المؤهل؛ لا تنشئ مهلة اصطناعية على أنها من المزود ولا تنتقل إلى دفع |
| `EMPTY_RESPONSE` | صنّفه فشل توافر/عقد للنموذج، لا نجاحًا ولا 429. يسمح بمرشح مجاني آخر فقط ضمن السلسلة المصرح بها وبنفس عقد القدرة والميزانية |
| timeout أو 5xx أو محتوى غير صالح | طبّق سياسة كل خطأ الحالية بحدودها؛ لا تعمم سياسة 429 عليها |
| فشل التخزين أو منسق الحجز | لا تتجاوز بوابة الإنفاق ولا ترسل محاولة مكررة؛ أعد خطأ محليًا واضحًا أو أوقف المهمة حسب العقد |

التبريد المحلي يحد من الطلبات التي يتحكم بها التطبيق فقط. انتهاء المدة يسمح بمحاولة مستقبلية عادية عبر lease الحجز، لكنه لا يثبت عودة المزود ولا يضمن نجاح المحاولة؛ تكرار الفشل يبدأ التدرج من جديد.

## خطة PR المحدثة

### PR-0 — إثبات منع الإنفاق المدفوع

**النطاق:** جرد جميع نقاط إرسال الطلب، إعدادات البيئة، مسارات benchmark/review، والعملاء المباشرين. اجعل سياسة الوضع المجاني مركزية وغير قابلة للتجاوز بإعداد بيئي أو اختيار نموذج من المستخدم. تنطبق على تشغيل المنتج والاختبارات الحية/الحملات التي يملكها المشروع؛ يسمح الاختبار بمحاكاة نموذج مدفوع بfixture محلي فقط، لا بطلب حي مدفوع.

**القبول:**
- لا يستطيع أي مسار للمنتج أو حملة حية إرسال نموذج مدفوع أو مجهول السعر.
- الاختبارات تفعّل متغيرات الدفع عمدًا وتثبت رفض الطلب قبل الشبكة عبر كل نقاط الدخول، بما فيها scripts/campaigns.
- الاستثناء الوحيد هو fixture اصطناعي لا يتصل بمزود؛ لا يوجد استثناء حي مدفوع داخل وضع صفر إنفاق.
- لا يُدّعى أن سجل الإنفاق يثبت وحده فاتورة صفرية؛ تُفصل محاولات الطلب عن المصالحة مع بيانات الحساب.

**ما ثبت حتى الآن:** جرد المسارات الحالية وجد أن `PROVIDER_PRIORITY` يحصر المنتج في OpenRouter، و`collectAvailableProviders` يستبعد البقية، ومسارا chat/fallback يبنيان مرشحيهما من هذا المصدر؛ `agentComplete()` يرفض المزود غير المفعّل قبل النقل. مسار حفظ المفتاح يرفضه قبل validator أو التخزين. أدوات benchmark الحية تتطلب opt-in ووضع المجاني فقط ومزوّد OpenRouter، وحملة empirical تتحقق من المزود والنموذج عند مدخلها. موصل الصحة عام عمدًا، لكن مستهلك المنتج يأخذ مزوده من resolver المحصور. اجتازت الأدلة المحلية: حدود المزود 14/14، مسار حفظ المفتاح 1/1، حواجز benchmark smoke بـ`node:test` 17/17، رفض المزود غير المفعّل بحملة empirical 3/3، واختبار سياسة fallback بالـAPI 2/2.
**ما لم يثبت:** لم يحدث استدلال حي مجاني أو تحقق من بيانات فوترة OpenRouter؛ لذلك لا نثبت أن الحصة المشتركة متاحة أو أن حساب المزود لم يسجل أي استخدام من خارج التطبيق. هذه حدود خارجية لا يستطيع اختبار محلي إزالتها. لا يُدّعى نجاح الرحلة الحية أو حل `RATE_LIMITED` جذريًا.

### PR-1 — تدقيق وتقوية Admission والتعافي الموجودين

**النطاق:** إعادة استخدام نموذج محاولات الطلب والميزانية والـlease والـcursor والتبريد الحالي. أضف التغييرات فقط حيث تكشف اختبارات الاستدعاءات المتزامنة أو إعادة التشغيل فجوة حقيقية.

**القبول:**
- في سباق عبر عمليتي API، لا يرسل النظام طلبين متطابقين غير محجوزين للنطاق نفسه.
- يحافظ فشل قاعدة الحجز أو انتهاء lease على منع الإرسال المكرر.
- تبقى 429/QUOTA نهائية للعملية نفسها ولا تدخل مسار الإصلاح أو إعادة تشغيل العقدة أو استدعاء النموذج نفسه.
- يظل التبريد المحلي بلا مهلة منفصلًا عن `Retry-After` المزود، ويختبر التصعيد والانتهاء والمحو عند النجاح.
- لا يلزم migration جديد إلا إذا أثبتت مراجعة المخطط وجود نقص ملموس.

**إثبات محلي مضاف:** على PostgreSQL مؤقتة مربوطة بـ`127.0.0.1`، يثبت اختبار عبر عمليتين مستقلتين أن حجز النموذج نفسه يمنع العامل المنافس حتى التحرير، وأن نموذجين مختلفين من namespace الناشر نفسه يتنافسان على حجز واحد قبل الإرسال. يكمّل ذلك اختبار عميل OpenRouter الذي يتحقق من ترتيب حجز الاعتماد ثم الناشر ثم النموذج، وفشل الإرسال مغلقًا عند تعطل مخزن الحجز. وفي تشغيل مركّز بلا egress اجتاز 24 اختبارًا من `openai-compatible-client.test.ts` و7 من `openrouter-reliability.test.ts` حالات 429/Retry-After/التبريد/التوازي؛ لم يحدث اتصال حي. لا تثبت هذه الحواجز مقدار حصة OpenRouter ولا تنسق بين حسابات مختلفة خارج التطبيق.

### PR-2 — تقليل استهلاك AI دون إضعاف القبول

**النطاق:** تحديد مواضع الاستدعاء الحتمي، تقليل السياق إلى الملفات المطلوبة، deduplication، cache آمن ومحدود، وقياس tokens ومحاولات كل نتيجة مقبولة.

**فشل انحداري قبل الإصلاح وحدوده:** بعد إنشاء قاعدة `runner` صراحةً وتطبيق المخطط على PostgreSQL المؤقتة، فشل اختبار الميزانية لأن العينة الموسومة بعقد المهمة استهلكت خانة محاولة إضافية، فرُفض الطلب الفيزيائي التالي بـ`AI_BUDGET_EXHAUSTED`. وفشل اختبار التليمترية لأن `totalAttempts` بلغ 2 بينما يوجد طلب HTTP واحد وعينة جودة واحدة. شُغّلت حالة مستهدفة واحدة من كل ملف (6 و12 حالة أخرى متخطاة بالمرشح)؛ هذا يثبت ازدواج العد في هذه الحالة فقط، ولا يحكم على بقية الملفين أو توافر OpenRouter. لم يحدث استدلال حي أو تعديل في قاعدة مشتركة، وأُزيلت قاعدة الاختبار المؤقتة بعد التشغيل.

**الإصلاح والتحقق بعده:** استُخدم `model_task_contract IS NULL` للفصل بين أحداث HTTP الفعلية وعينات جودة المهمة في ميزانية المشروع (المحاولات والرموز)، وملخص الاستخدام، وتشخيص التنفيذ، وعدّاد تنبيه الاستخدام اليومي. بقيت عينات العقد محفوظة لاستعمال سجل جودة النموذج؛ لم يتغير المخطط ولم تُضف migration. بعد الإصلاح نجحت اختبارات `ai-budget.test.ts` و`ai-telemetry.test.ts` كاملة: 21/21؛ شمل ذلك اختبارًا يضبط حد التنبيه إلى محاولتين ويثبت أن عينة الجودة لا تفتح تنبيهًا زائفًا. نُفذت الاختبارات على مخطط مطبق في قاعدة مؤقتة مربوطة بـ`127.0.0.1` فقط، مع `AI_PROVIDER_EGRESS_DISABLED=1` ومفاتيح مزود غير متاحة للعملية. نجح `typecheck` و`build` لخادم API. كما بدأ الـbuild المعزول على قاعدة مؤقتة أخرى وأعاد `/api/readiness` حالة `ready`؛ أُوقفت عمليتا الاختبار ونُظف جذر القاعدة المؤقتة. وبعد تأكيد المالك أن Workflow يستخدم Development والسماح بالصيانة، أُعيد تشغيل الـWorkflow المُدار مرة واحدة؛ أرجع `/api/healthz` و`/api/readiness` 200، وأعاد build الخدمة من المصدر الحالي. حدث تحديث كتالوج OpenRouter فقط، لا استدلال حي. هذا الإصلاح يغلق ازدواج العد فقط، ولا يثبت معيار قبول لكل مهمة/رمز ولا يزيل قيود حصة OpenRouter.

**فشل واجهة مسجل قبل مواءمة الاختبارات:** تشغيل `AiChat.authenticated.test.tsx` أعاد 249 نجاحًا و3 إخفاقات من 252. اثنان في حالتي `refreshing` و`empty` لأن الاختبارين ما زالا يتوقعان نصي الحالة السابقين اللذين تغيرا لتوضيح مصدر القياس. الثالث في اختبار بوابة Mission لم يجد زر START عند المحدد `button-chat-mission-action-start`؛ لا يطابق التغيير المرئي للتليمتري، لذلك لم يُنسب إليه قبل إعادة تشغيل مستقلة. تحذيرات React `act(...)` ظهرت أيضًا لكنها ليست إخفاقات تأكيد. لا تعتبر هذه النتيجة نجاحًا كاملًا للواجهة قبل معالجة الثلاثة وإعادة التحقق.

**إعادة عزل إخفاق Mission قبل الإصلاح:** تشغيل الاختبار نفسه منفردًا بـ`-t` أعاد إخفاقًا واحدًا و251 حالة متخطاة؛ فشل `findByTestId('button-chat-mission-action-start')` عند السطر 768. لذلك ليس إخفاق ترتيب بين الاختبارات. لم يُحدد السبب بعد، ولم يُجرَ إصلاح لهذا الفشل حتى تسجيله.

**القبول:**
- تحسن نسبة المهام المقبولة لكل محاولة/رمز مقارنة بخط أساس محفوظ.
- لا تعاد نتيجة cache بعد تغير المصدر أو عقد القبول أو إعداد النموذج دون تحقق freshness.
- يبقى التحقق server-owned، ولا تصبح الذاكرة المخزنة proof.

### PR-3 — دراسة جدوى الاستدلال المحلي

**النطاق:** قياس RAM/CPU/GPU/storage ووقت البدء والكمون على بيئة التشغيل المستهدفة، ثم تجربة نموذج محلي واحد لمهمة واحدة محددة. لا يُفترض أن Ollama أو vLLM مناسبان تلقائيًا لبيئة Replit الحالية.

**قياس تمهيدي للبيئة الحالية (2026-11-01):** حدّ CPU الظاهر 4 وحدات (`cpu.max=400000 100000`)، وحد الذاكرة cgroup هو 8 GiB مع نحو 2.62 GiB مستخدمة وقت القياس، و`MemAvailable` نحو 3.38 GiB؛ التخزين المتاح 249 GiB في workspace و4 GiB في `/tmp`. لم يظهر GPU أو `nvidia-smi`، ولم يوجد Ollama أو llama.cpp runtime أو ملف وزن محلي من الأنواع المفحوصة. هذا قياس لحظي لهذه العملية، لا ضمان موارد لبقية أحمال Replit أو وقت بدء/جودة نموذج. لم يُنزّل نموذج ولم يُجر اختبار استدلال؛ لذلك **لا يوجد إثبات حالي بأن تشغيلًا محليًا يحقق عقد مهمة بجودة أو كمون مقبولين**. تبقى تجربة النموذج مشروطة بتحديد عقد المهمة ومجموعة قبول ثابتة، وموافقة منفصلة على مصدر/حجم النموذج والـruntime، ثم قياس offline قابل للتكرار.

**القبول:**
- إثبات الموارد والكمون والجودة لعقد المهمة باختبار offline reproducible.
- لا يقبل عنوان endpoint محلي من المستخدم، مع منع SSRF والاتصال بمضيفين غير مصرحين.
- يظل إيقاف المسار واستئناف المهمة صحيحًا عند غياب العتاد أو نفاد موارده.

### PR-4 — اتحاد المسارات المجانية المؤهلة (مؤجل ومشروط)

**النطاق:** يمكن دراسة مزود سحابي مجاني آخر فقط إذا قرر مالك المنتج توسيع النطاق، وتوفرت بيانات اعتماد مناسبة عبر آلية الأسرار، وأُثبتت أهلية الحساب المجانية وعقد المهمة والخصوصية.

**القبول:**
- الحالة غير المعروفة أو المنتهية ترفض قبل الشبكة.
- اختبارات egress لكل مزود تمنع أي وجهة أخرى ولا تمرر أسرارًا إلى logs.
- لا يحدث failover بعد 429 إلا إذا كان نطاق الفشل ومجموعة المزودين يثبتان استقلال الوجهة البديلة.
- لا يغير المزود الإضافي دليل القبول أو يكرر أثر أداة مكتملًا.

### PR-5 — قياس وتشغيل موثوق

**النطاق:** إظهار بيانات ناتجة من سجل المحاولات المقبولة والتبريد والانتظار، لا مؤشرات ثابتة. لا تبنَ لوحة قبل توحيد مصدر بياناتها.

**القبول:**
- تمييز 429، QUOTA، EMPTY_RESPONSE، timeout، قبول العقد، قبول المهمة، والانتظار.
- توضيح أن قيمة التبريد المحلي تقدير admission داخلي وليست ETA من المزود.
- «الإنفاق صفر» يظهر كسياسة ومحاولات ممنوعة؛ ولا يعرض كحقيقة محاسبية ما لم تتوفر مصالحة مستقلة للحساب.

## بوابات التحقق

1. **بوابة static:** جرد الاستدعاءات والإعدادات، وفحوص السياسة والـtypes و`git diff --check` دون طلبات خارجية.
2. **بوابة تكامل محلية:** PostgreSQL مؤقت عند الحاجة، محاكاة مزود دقيقة ببنية أخطاء إنتاجية، واختبارات التزامن/الـlease/الإيصالات؛ لا Development ولا Production.
3. **بوابة جودة:** benchmark معزول مربوط بمراجعة مصدر وعقد قبول؛ النتائج غير المقبولة لا تتحول إلى نجاح تجميعي.
4. **بوابة محلية:** اختبار offline للنموذج المحلي والقدرات المطلوبة فقط.
5. **بوابة حيّة منفصلة:** تحتاج إذنًا مستقلًا في كل مرة، وتتطلب نموذجًا مجانيًا محددًا، وexplicit opt-in، وحد طلبات واضحًا، وإيصالًا معقمًا. لا تثبت استمرارية الحصة المستقبلية.

## المخاطر والقرارات المفتوحة

- **الحصة الخارجية:** لا يمكن ضمان توافرها أو معرفة المتبقي منها إذا لم يكشف المزود ذلك.
- **مجانية الحساب:** أسماء المزودين أو أرقام الكتالوج لا تكفي؛ يجب تحقق حسابي حديث لكل مسار.
- **خصوصية البيانات:** أي federation يوسع الوجهات التي قد تستقبل شيفرة أو بيانات مشروع؛ يلزم تصنيف بيانات وسياسة لكل مزود.
- **الموارد المحلية:** لا نعرف بعد عتاد البيئة التي يجب أن يستهدفها النموذج المحلي. هذا شرط لاختيار النموذج، وليس تفصيلًا لاحقًا.
- **التكلفة الكلية:** هذه السياسة تمنع رسوم AI API وفق حدودها؛ لا تصف الاستضافة والطاقة والموارد المحلية بأنها مجانية.
- **النطاق الحالي:** المنتج يظل OpenRouter المجاني فقط إلى أن تكتمل PR-0 وPR-1 ويصدر قرار منفصل بتفعيل مسار آخر. وجود strategy أو secret لا يفعّله تلقائيًا.

## خارج النطاق

- تجاوز أو تدوير مفاتيح الوصول لتفادي حدود المزود.
- تكرار الطلبات حتى ينجح عدد غير محدود من المحاولات.
- إخفاء فشل النموذج عبر قبول نص فارغ أو اصطناع receipt.
- تطبيق schema أو تعديل بيانات Development/Production ضمن هذه الخطة.
- اعتبار اختبار وحدات أو اتصال كتالوج أو smoke واحد دليلًا على توافر مجاني مستمر.
