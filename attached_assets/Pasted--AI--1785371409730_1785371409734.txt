 هذه **الخريطة الأولى الدقيقة لطبقة الـ AI فقط** كما تظهر من الكود الحالي، مقسّمة إلى **ملفات → وظائف → تدفقات**.

# 1) صورة الطبقة كاملة

```text
HTTP Routes
  └─ artifacts/api-server/src/routes/ai/*
       ├─ providers.ts
       ├─ chat.ts
       ├─ analysis.ts
       ├─ workflows.ts
       └─ tasks.ts
            ↓
Shared AI Runtime
  └─ lib/ai-orchestrator/src/*
       ├─ context-builder.ts
       ├─ prompts/*
       ├─ agents/*
       ├─ provider-registry.ts
       ├─ agent-complete.ts
       ├─ parsing.ts
       ├─ tool-policy.ts
       └─ tools/*
            ↓
Providers
  └─ groq / openrouter / gemini / deepseek
            ↓
DB / Events / Audit / Cache Invalidation
```

# 3) التدفق الأعلى: من HTTP إلى النموذج ثم الرجوع

```text
Request
  ↓
Route handler
  ↓
requireProjectAccess / requireProvider / rate limit checks
  ↓
buildProjectContext()
  ↓
prompt composer
  ↓
agent (chat / task / workflow / scan / review)
  ↓
provider-registry → agent-complete → provider
  ↓
raw model output
  ↓
parseAgentResponse()
  ↓
route-level guards
  ↓
DB write / events / audit / cache invalidation
  ↓
HTTP response
```

# 4) خريطة طبقة الـ Context

هذه أهم طبقة لأنها ما يراه النموذج فعليًا.

## الملف

`lib/ai-orchestrator/src/context-builder.ts`

## الوظيفة

يبني `ProjectContext` من بيانات قاعدة البيانات، ثم يقدمه كنص منظم للـ prompt.

## الحقول التي تُدخل عادةً إلى السياق

* `project`
* `latestMetrics`
* `graphSummary`
* `recentTasks`
* `recentEvents`
* `workflows`

## نقاط مهمة في هذه الطبقة

* يوجد **TTL cache** داخل الذاكرة لمدة 30 ثانية.
* يوجد **cross-process invalidation** عبر `pg_notify`.
* يوجد **sections selection**، أي أن السياق ليس دائمًا كاملًا؛ يمكن طلب أجزاء محددة فقط.
* `graphSummary` هنا **نصي** وليس graph object خام.

## التدفق الداخلي

```text
DB queries
  ↓
structured objects
  ↓
string sections
  ↓
AgentContext schema
  ↓
ProjectContext
```

# 5) خريطة الـ Prompt Layer

## الملف

`lib/ai-orchestrator/src/prompts/prompt-composer.ts`

## الوظيفة

تحويل `ProjectContext` إلى sections قابلة للإدخال في prompt.

## أهم وظيفة

`promptContextOverview(context, profile)`

والـ profiles الحالية:

* `full`
* `chat`
* `task`
* `scan`
* `review`
* `workflow`

## معنى ذلك

النظام لا يرسل كل شيء دائمًا للنموذج.
كل agent يرى **subset** مختلفًا من السياق.

---

## ملف المحادثة

`lib/ai-orchestrator/src/prompts/chat.prompt.ts`

### ماذا يفعل؟

* يبني system prompt للمحادثة.
* يشرح حدود الأدوات.
* يفرض قواعد:

  * نفس لغة المستخدم
  * عدم ترجمة أسماء الملفات والدوال
  * عدم اختراع معلومات
  * التعامل الصارم مع source discipline

### نقطة مهمة جدًا

في هذا الملف يوجد نص صريح يقول إن **Knowledge Graph pre-extracted index** و**not guaranteed to be exhaustive**.

هذا يعني أن النموذج **ليس مع الجراف الكامل**، بل مع **لقطة/فهرس مختصر**.

# 6) خريطة الـ Agent Layer

## 6.1 `BaseAgent`

### الملف

`lib/ai-orchestrator/src/agents/base-agent.ts`

### دوره

القالب المشترك للمهام ذات المرة الواحدة:

1. build messages
2. call provider
3. parse output
4. fallback عند الفشل

### النتيجة

هذا هو الأساس الذي تستخدمه agents مثل:

* `task-agent`
* `scan-analyst`
* `code-reviewer`

---

## 6.2 `chat-agent.ts`

### الملف

`lib/ai-orchestrator/src/agents/chat-agent.ts`

### دوره

هذا هو **أكثر agent تعقيدًا** لأنه يدير:

* المحادثة
* tool loop
* read/list/search
* pendingChanges
* streaming
* source sanitation

### ما يميزه

* `MAX_TOOL_ITERATIONS`
* `MAX_TOOL_CALLS`
* dedup cache للأوامر المتكررة
* `write_file` لا يكتب فعليًا على القرص، بل يبني `pendingChanges`
* `toolSources` تُجمع من أدوات القراءة الفعلية

### التدفق الداخلي

```text
chat message
  ↓
build prompt + tools policy
  ↓
provider call
  ↓
tool calls? → execute tools → append results → loop
  ↓
parse result
  ↓
sanitize sources
  ↓
return response + sources + pendingChanges
```

---

## 6.3 `task-agent.ts`

### الملف

`lib/ai-orchestrator/src/agents/task-agent.ts`

### دوره

إخراج structured recommendation لمهمة واحدة.

### المخرجات المتوقعة

* `summary`
* `steps`
* `result`
* `confidence`
* `needsHumanReview`

---

## 6.4 `workflow-orchestrator.ts`

### الملف

`lib/ai-orchestrator/src/agents/workflow-orchestrator.ts`

### دوره

اتخاذ قرار workflow ثم التحقق منه.

### الوظائف

* `decide()`
* `validateDecision()`
* `orchestrateWorkflow()`

### الميزة الأساسية

حتى لو اقترح النموذج `advance` أو `complete`:

* يتم تطبيق **metrics gate**
* ثم **validation**
* ثم فقط يخرج القرار النهائي

### التدفق

```text
workflow state + projectContext
  ↓
LLM proposal
  ↓
parseAgentResponse
  ↓
metrics gate
  ↓
validateWorkflowDecision
  ↓
final decision
```

# 8) خريطة الـ Parsing Layer

## الملف

`lib/ai-orchestrator/src/parsing.ts`

### دوره

* استخراج JSON من النص
* محاولة إصلاح/فهم الرد
* التحقق عبر schema
* إنتاج fallback عند اللزوم

### التدفق

```text
raw model text
  ↓
extract JSON
  ↓
validate schema
  ↓
ok? → return parsed
  ↓
fail? → fallback + _parseError
```

### لماذا هذه الطبقة مهمة؟

لأنها نقطة الفصل بين:

* نص النموذج الخام
* وبين مخرجات منضبطة يمكن للراوتات حفظها أو رفضها

## 9.4 `chat.ts`

### الملف

`artifacts/api-server/src/routes/ai/chat.ts`

### هذا هو المسار الأكثر تعقيدًا

لأنه يجمع:

* جلسات chat
* streaming
* pending changes
* apply changes
* advisory lock
* parse handling
* cache invalidation
* transaction on message persistence

### التدفق المبسط

```text
request
  ↓
load project + access
  ↓
rate limit
  ↓
resolve rootPath
  ↓
provider resolution
  ↓
advisory lock (apply)
  ↓
buildProjectContext
  ↓
chatWithFallback
  ↓
parse error handling
  ↓
invalidateContextCache
  ↓
persist session/messages in transaction
  ↓
return response / SSE stream
```

### نقطة مهمة

في `stream` يوجد SSE path مستقل، لكنه ما يزال يمر بنفس منطق:

* context
* provider fallback
* parse handling
* cache invalidation
* persistence

# 11) أين تقع نقاط الحساسية في هذه الطبقة؟

## أ) `buildProjectContext()`

أهم نقطة لأنها تحدد ما الذي يراه الـ AI.

## ب) `promptContextOverview()`

تحدد كيف تُصاغ هذه البيانات.

## ج) `chat-agent.ts`

لأنه الوحيد تقريبًا الذي يدير loop أدوات + pending changes + sources.

## د) `parseAgentResponse()`

لأنه نقطة الفصل بين الرد الخام والرد المعتمد.

## هـ) `provider-registry.ts`

لأنه يحدد من ينفذ الطلب أصلًا.

## و) الراوتات

لأنها تقرر:

* هل نرفض؟
* هل نُسجل؟
* هل نُبطل الكاش؟
* هل نحفظ 422 أم 200؟

# 12) الخلاصة الأولية

الآن يمكننا وصف طبقة الـ AI في هذا المشروع بهذه الجملة:

**هي بنية Agent-based, context-snapshot-driven, schema-validated, provider-abstracted، مع guard rails في الراوتات، لكنها تعتمد بشدة على جودة `buildProjectContext()` وصياغة الـ prompt وحدود الـ sample المرسل للنموذج.**
