## Root Cause

`pCode` is assumed to be a string, but it is sourced from `extractProviderError(body)` without runtime validation. In `extractProviderError`, `parsed.error.code` / `parsed.error.type` are returned directly from parsed JSON, so a provider response like `code: 404`, `code: { ... }`, or `code: null` can flow through. Then `classifyStatus()` reaches `pCode.includes(...)` and crashes because `.includes()` only exists on strings.

## Evidence

Exact fault path in `lib/ai-orchestrator/src/openai-compatible-client.ts`:

1. `extractProviderError(body)` returns `code: parsed.error.code ?? parsed.error.type` without checking the type.
2. `classifyStatus()` copies that value into `pCode`.
3. The crash happens here:

   ```ts
   pCode.includes("model_not_found")
   pCode.includes("invalid_model")
   pCode.includes("model_unavailable")
   ```

   This is the only `pCode.includes` use in the file.

So the issue is a runtime type mismatch from provider JSON parsing, not the `body` string itself.

## Fix

Harden both layers, but keep the behavior unchanged:

1. In `extractProviderError`, only accept real strings for `code` and `message`.
2. In `classifyStatus`, add a local `providerCode` string guard and use optional chaining before `.includes()`.

That stops the crash while preserving:

* `looksLikeMissingModel`
* 404/402/410/422 fallback behavior
* existing classification rules

## Risk of regression

Low. The change is narrowly scoped to error classification:

* no request payload changes
* no fallback-chain changes
* no model selection changes
* no behavioral change for valid string provider codes

The only functional difference is that malformed provider error payloads can no longer crash the orchestration path. The safer fix is both `classifyStatus()` and `extractProviderError()` together; `classifyStatus()` alone would stop the crash, but `extractProviderError()` also needs hardening so invalid provider data does not leak into error context.
