---
name: OpenRouter throttling and campaign checkpoints
description: Durable policy for model-scoped throttling, Retry-After waits, and empirical campaign persistence.
---

Model-scoped throttling must remain separate from the provider circuit. An OpenRouter 429 identified as an upstream shared-pool or credential/window limit must not trigger generic same-model retries, stream model advancement, or the tool loop's same-provider `powerModel` fallback. A shared-pool 429 cools only the exact failed model in shared PostgreSQL state; the current fallback starts at 15 minutes, honors a valid Retry-After up to six hours, and escalates repeated failures up to six hours. A successful response clears that model's persisted failure history so later throttling starts a fresh escalation streak. Clearing is best-effort and must not turn a successful provider response into a failed AI operation. This is not a pool-wide quarantine and says nothing about other models' upstream routing. Opt-in automatic Retry-After sleeps remain capped at 60 seconds and must leave recovery reserve instead of consuming the full request deadline.

**Why:** Provider-wide opening on one model's 429 unnecessarily removes healthy fallback candidates, while unbounded waiting caused live campaigns to outlast their request budget. Process-local cooldowns also allow the next request routed to another API instance to hit the same throttled model. Escalating only failures since the last successful response avoids carrying stale backoff across recovery. The September 22, 2026 disposable run confirmed that OpenRouter candidates can independently return upstream shared-pool 429s even when catalog startup is healthy. September 30, 2026 project logs showed the generic transient retry replaying a shared-pool 429 against the same model and receiving a second 429; code-path review also found the outer tool loop could retry the same provider through `powerModel`.

**How to apply:** Classify the 429 once at the HTTP boundary where headers and provider metadata exist, carry only the bounded scope through health/telemetry, and let the Airlock or empirical campaign quarantine all remaining lanes/cases for a shared provider-pool hit. Shared-pool and credential limits must fail before generic transient retries, Retry-After replays, paid same-provider fallback, or the tool loop's same-provider model fallback. For shared-pool scope, persist a cooldown for only the exact failed OpenRouter model; on a successful response, clear that model's persisted failure history as well as its process-local state. Do not infer a model-to-upstream mapping or quarantine other model IDs. Keep provider-credential limits separate because they apply beyond one model. Retain a process-local cache only as a best-effort fallback if the shared store is unavailable. Test behavior across independent clients, escalation after repeated failures, reset after success, and stream paths. Keep same-provider fallback ownership in the OpenRouter strategy/client, and route cross-provider recovery only through an existing caller-owned, authorized candidate list. Do not add a parallel retry chain or persistent pool quarantine; the existing provider circuit remains a separate policy. Preserve bounded probe candidate iteration only for model/capability failures, and persist empirical scorecards after every completed case. JSON repair must remain structural and bounded; schema validation stays authoritative.
