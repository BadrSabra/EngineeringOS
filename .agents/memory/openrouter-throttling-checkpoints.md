---
name: OpenRouter throttling and campaign checkpoints
description: Durable policy for model-scoped throttling, Retry-After waits, and empirical campaign persistence.
---

Model-scoped throttling must remain separate from the provider circuit. Any OpenRouter 429, including one whose scope is `unknown`, must stop automatic same-provider retries, stream model advancement, and the tool loop's same-provider `powerModel` fallback; only an existing authorized different-provider route may continue. Explicit shared-pool and credential/window limits also must not trigger the provider-wide circuit; rate limits and quota exhaustion are admission signals, not endpoint-health failures. A positive provider-supplied Retry-After remains authoritative and is capped at six hours as a safety bound. With a missing/zero Retry-After, only `RATE_LIMITED` may create a local adaptive cooldown, scoped to the exact model that failed: 30 seconds initially, doubled after a repeated recent failure, capped at 10 minutes, with history expiring after one hour. This is local admission protection, not a provider recovery estimate; do not expose it as a provider Retry-After or extend it to sibling models, the shared pool, credential, or account. `QUOTA` never receives a synthetic cooldown. Legacy structured-task rows tagged with invented server/adaptive defaults are not live cooldown evidence. An opt-in wait must honor the full provider window only when it fits within the remaining request budget and recovery reserve; otherwise fail without sleeping or retrying early. A successful response clears that model's persisted cooldown and adaptive history. This is not a pool-wide quarantine and says nothing about other models' upstream routing.

**Why:** Provider-wide opening on one model's 429 unnecessarily removes healthy fallback candidates. Repeated manual attempts against the same free model can also keep hitting a pool limit when OpenRouter omits Retry-After; a model-only adaptive gate reduces that traffic without claiming the provider has recovered or blocking sibling free lanes. Its exact scope and labeled local source distinguish this from provider evidence. Process-local cooldowns alone would let another API instance hit the same model, so the adaptive window is persisted separately under a reserved model key. The September 22, 2026 disposable run confirmed that OpenRouter candidates can independently return upstream shared-pool 429s even when catalog startup is healthy. September 30, 2026 project logs showed the generic transient retry replaying a shared-pool 429 against the same model and receiving a second 429; code-path review also found the outer tool loop could retry the same provider through `powerModel`. An October 28, 2026 one-case live benchmark observed two shared-pool 429 responses for the pinned model followed by successful responses, yet produced no source evidence and ended U. An October 29, 2026 multi-file live case showed a different integration gap: the execution-node coordinator treated a thrown 429 like a repairable failed node, retried the node, and exhausted the case budget. This confirms transport and tool-loop guards alone do not stop request-level recovery. A local regression fixture also showed that missing scope metadata is classified as `unknown` and previously allowed both transport retry and tool-loop same-provider fallback; fail closed on the 429 code rather than assuming unknown means model-local. In multi-step proof-required queries, earlier successful reads do not excuse a later 429 or grant partial Canonical Proof. A later one-shot health probe also wrote a cooldown row to Development and its generic cleanup could delete unrelated expired cooldown rows.

**How to apply:** Classify the 429 once at the HTTP boundary where headers and provider metadata exist, carry only the bounded scope through health/telemetry, and let production routing and each pinned empirical scorecard quarantine their own remaining lanes/cases for a shared provider-pool hit. A request-level test must also prove that after the first 429, including an `unknown` scope, nested planning, tool, repair, synthesis, and execution-node retry paths do not issue another same-provider call in that request; a client-only retry test is insufficient. The execution-node coordinator must treat `RATE_LIMITED` and `QUOTA` as terminal blocked outcomes, cancel active peer work, and block queued nodes rather than feeding provider failures into validation-repair retries. If the user explicitly requests a multi-model empirical campaign, start the next eligible registered OpenRouter model as a separate exact-model scorecard; this campaign-level progression does not permit same-request fallback or change production lane/circuit behavior. Shared-pool, credential, and unknown-scope limits must fail before generic transient retries, Retry-After replays without explicit opt-in, paid same-provider fallback, or the tool loop's same-provider model fallback. Durable automatic `RETRY_AFTER_RATE_LIMIT` recovery also requires a valid persisted `retryAt` backed by a positive limiter window; missing, malformed, or zero delay must not enqueue an immediate retry. For shared-pool scope, persist only a positive provider Retry-After for the exact failed model and share it with siblings only when provider metadata exactly matches the model namespace. If Retry-After is absent/zero and the code is `RATE_LIMITED`, persist a local adaptive cooldown under a reserved exact-model key; use 30s base, 2x repeat steps, a 10-minute cap, and one-hour history. Do not expose the local window as provider Retry-After, infer a pool mapping, quarantine sibling models, or synthesize cooldowns for `QUOTA`. On success, clear that model's provider and local cooldown state. Never truncate a longer provider wait and retry before the provider's deadline. Keep provider-credential limits separate because they apply beyond one model. Retain a process-local cache as a best-effort fallback if the shared store is unavailable. Test exact provider durations, local escalation and expiry, sibling-lane availability, success clearing, waits beyond the caller budget, and stream paths. Keep same-provider fallback ownership in the OpenRouter strategy/client, and route cross-provider recovery only through an existing caller-owned, authorized candidate list. Do not add a parallel retry chain or persistent pool quarantine; the existing provider circuit remains a separate policy. Preserve bounded probe candidate iteration only for model/capability failures, and persist empirical scorecards after every completed case. Standalone smoke and diagnostic probes must inject isolated model and credential cooldown stores instead of reading or writing the application's shared database; keep expired-row cleanup out of probe execution. JSON repair must remain structural and bounded; schema validation stays authoritative. In composition tests, count the exact operation's provider calls rather than every chat call or ledger event: planning and lifecycle transitions add legitimate entries that are not retries.

Controlled live-run diagnostics may correlate provider-attempt sequence, execution, operation, model, result, and rate-limit scope only when explicitly enabled. They must exclude prompt/response bodies, credentials, and raw provider messages; keep the trace disabled by default.

**Projection check:** A correctly typed provider error does not guarantee durable scope or Retry-After telemetry. Test the full chain from HTTP classification through the final ledger event and persistence projection, since explicit ledger completion builders can drop added fields; persist only positive safe-integer Retry-After values on classified rate-limit failures.

An `EMPTY_RESPONSE` may advance to the next distinct model already present in the caller's eligible free chain, but every candidate must still satisfy the same capability and response-format contract. This does not permit a retry after `RATE_LIMITED`/`QUOTA`, nor does it treat malformed or unaccepted content as success.

**Why:** Free models can return an empty completion even when another eligible free model is available, while a 429 may apply to a shared pool or credential and must remain terminal for that request.

**How to apply:** Bound the empty-response recovery by the existing candidate chain and request budget; preserve the attempted-model list. Keep provider-supplied cooldowns for later requests and keep rate-limit failures terminal.
