---
name: OpenRouter throttling and campaign checkpoints
description: Durable policy for model-scoped throttling, Retry-After waits, and empirical campaign persistence.
---

Model-scoped throttling must remain separate from the provider circuit. Any OpenRouter 429, including one whose scope is `unknown`, must stop automatic same-provider retries, stream model advancement, and the tool loop's same-provider `powerModel` fallback; only an existing authorized different-provider route may continue. Explicit shared-pool and credential/window limits also must not trigger the provider-wide circuit; rate limits and quota exhaustion are admission signals, not endpoint-health failures. A model cooldown is created only from a positive provider-supplied Retry-After, capped at six hours as a safety bound; missing or zero values create no local or durable cooldown, and repeated failures do not synthesize or escalate a delay. Legacy structured-task rows tagged with invented server/adaptive defaults are not live cooldown evidence. An opt-in wait must honor the full provider window only when it fits within the remaining request budget and recovery reserve; otherwise fail without sleeping or retrying early. A successful response clears that model's persisted cooldown. This is not a pool-wide quarantine and says nothing about other models' upstream routing.

**Why:** Provider-wide opening on one model's 429 unnecessarily removes healthy fallback candidates, while invented waits can block testing even when the provider supplies no Retry-After value. Process-local cooldowns also allow the next request routed to another API instance to hit the same throttled model. The September 22, 2026 disposable run confirmed that OpenRouter candidates can independently return upstream shared-pool 429s even when catalog startup is healthy. September 30, 2026 project logs showed the generic transient retry replaying a shared-pool 429 against the same model and receiving a second 429; code-path review also found the outer tool loop could retry the same provider through `powerModel`. An October 28, 2026 one-case live benchmark observed two shared-pool 429 responses for the pinned model followed by successful responses, yet produced no source evidence and ended U. An October 29, 2026 multi-file live case showed a different integration gap: the execution-node coordinator treated a thrown 429 like a repairable failed node, retried the node, and exhausted the case budget. This confirms transport and tool-loop guards alone do not stop request-level recovery. A local regression fixture also showed that missing scope metadata is classified as `unknown` and previously allowed both transport retry and tool-loop same-provider fallback; fail closed on the 429 code rather than assuming unknown means model-local. In multi-step proof-required queries, earlier successful reads do not excuse a later 429 or grant partial Canonical Proof. A later one-shot health probe also wrote a cooldown row to Development and its generic cleanup could delete unrelated expired cooldown rows.

**How to apply:** Classify the 429 once at the HTTP boundary where headers and provider metadata exist, carry only the bounded scope through health/telemetry, and let production routing and each pinned empirical scorecard quarantine their own remaining lanes/cases for a shared provider-pool hit. A request-level test must also prove that after the first 429, including an `unknown` scope, nested planning, tool, repair, synthesis, and execution-node retry paths do not issue another same-provider call in that request; a client-only retry test is insufficient. The execution-node coordinator must treat `RATE_LIMITED` and `QUOTA` as terminal blocked outcomes, cancel active peer work, and block queued nodes rather than feeding provider failures into validation-repair retries. If the user explicitly requests a multi-model empirical campaign, start the next eligible registered OpenRouter model as a separate exact-model scorecard; this campaign-level progression does not permit same-request fallback or change production lane/circuit behavior. Shared-pool, credential, and unknown-scope limits must fail before generic transient retries, Retry-After replays without explicit opt-in, paid same-provider fallback, or the tool loop's same-provider model fallback. Durable automatic `RETRY_AFTER_RATE_LIMIT` recovery also requires a valid persisted `retryAt` backed by a positive limiter window; missing, malformed, or zero delay must not enqueue an immediate retry. For shared-pool scope, persist only a positive Retry-After for the exact failed OpenRouter model; on success, clear that model's persisted cooldown. Do not synthesize or exponentially escalate a duration when the provider omits Retry-After. Never truncate a longer provider wait and retry before the provider's deadline. Do not infer a model-to-upstream mapping or quarantine other model IDs. Keep provider-credential limits separate because they apply beyond one model. Retain a process-local cache only as a best-effort fallback if the shared store is unavailable. Test exact provider durations, missing/zero headers, waits beyond the caller budget, success clearing, and stream paths. Keep same-provider fallback ownership in the OpenRouter strategy/client, and route cross-provider recovery only through an existing caller-owned, authorized candidate list. Do not add a parallel retry chain or persistent pool quarantine; the existing provider circuit remains a separate policy. Preserve bounded probe candidate iteration only for model/capability failures, and persist empirical scorecards after every completed case. Standalone smoke and diagnostic probes must inject isolated model and credential cooldown stores instead of reading or writing the application's shared database; keep expired-row cleanup out of probe execution. JSON repair must remain structural and bounded; schema validation stays authoritative. In composition tests, count the exact operation's provider calls rather than every chat call or ledger event: planning and lifecycle transitions add legitimate entries that are not retries.

Controlled live-run diagnostics may correlate provider-attempt sequence, execution, operation, model, result, and rate-limit scope only when explicitly enabled. They must exclude prompt/response bodies, credentials, and raw provider messages; keep the trace disabled by default.

**Projection check:** A correctly typed provider error does not guarantee durable scope or Retry-After telemetry. Test the full chain from HTTP classification through the final ledger event and persistence projection, since explicit ledger completion builders can drop added fields; persist only positive safe-integer Retry-After values on classified rate-limit failures.
