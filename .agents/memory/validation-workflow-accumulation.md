---
name: Validation workflow accumulation
description: Environment guidance for validation workflows that can interfere with normal app startup or artifact services.
---

Generated `.engineeringos-delivery/...` validation workflows can remain registered or running after a validation campaign. They may consume process/thread slots, collide with the real artifact ports, and cause unrelated pnpm, Vite, esbuild, or Node startup failures. Validation sandboxes must use a fixed host temp base such as `/tmp`, not `os.tmpdir()`, because `TMPDIR` can be redirected into the registered delivery tree. Also, updating a named `isValidation=true` command may append a `workflow.run` entry to the normal `Project` startup workflow, causing a long-running validation to run whenever the app starts.

**Why:** During imported-project startup, the application failures were initially masked by missing dependencies and then by resource exhaustion from stale validation copies. Stopping only the stale generated workflows restored reliable startup while preserving the real artifact services. A release-journey command update also inserted a startup task for the validation workflow; removing only that link kept the check available without running it on app startup.

**How to apply:** Before retrying a failed setup or restart, inspect workflow state and stop/remove only `.engineeringos-delivery/...` copies. Leave `artifacts/...` services running; do not replace their managed workflows. After updating a named validation command, inspect `.replit` and ensure it is not also a `workflow.run` task under `Project` unless startup execution is intended. The workflow registry may remain stale after removal, so verify real listeners and process counts before retrying. Treat a running workflow whose open port differs from its configured port as registration failure, not health. For a very large tracked tree, remove approved roots directly and run one `git add -u`; verify no Git process owns `.git/index.lock` before removing a stale lock.
