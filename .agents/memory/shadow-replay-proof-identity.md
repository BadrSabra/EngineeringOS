---
name: Shadow replay proof identity
description: Shadow replay rows distinguish source proof acceptance from replay proof acceptance.
---

Shadow Replay must persist source and replay Canonical Proof acceptance IDs separately. Any consumer that recovers a receipt or uses it for completion or promotion must match every source/case/replay identity in the receipt to the current case definition and replay row, then reload Canonical Proof from the current execution attempt's durable acceptance and evidence rows; a receipt's `PROVEN` label is never authoritative. The receipt ID, replay row's `replayCanonicalAcceptanceId`, and freshly loaded acceptance ID must agree, and the loaded trajectory must match the receipt. After successful expired-lease recovery, preserve the complete validated durable replay receipt; a generic execution recipe receipt is not a substitute.

**Why:** Reusing the source acceptance or trusting a stored `PROVEN` projection could let stale receipt data complete an expired replay or promote a skill after its proof no longer matches the current attempt. Reloading proof alone also does not validate source identity claims copied into the stored receipt; those claims must match the current case definition. Replacing the validated replay receipt with the execution's generic recipe receipt strips proof and paired-baseline data needed by later consumers.

**How to apply:** Keep source and replay acceptance IDs in separate durable fields. Bind all stored source/case fields to the current definition, and bind the reloaded proof to the replay execution, current attempt, operation, project/Mission/Goal, active plan revision, source revision, and candidate identity. Recovery and promotion must check the receipt ID and trajectory before marking completed or promoted. Recovery should preserve the already-validated full receipt, including its proof, validator, and paired-baseline fields.
