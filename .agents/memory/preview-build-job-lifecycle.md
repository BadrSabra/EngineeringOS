---
name: Preview build-job lifecycle
description: Keep build attempts separate from Preview sessions and require independent verification before session creation.
---

**Rule:** Persist a Preview build attempt in its own `preview_build_jobs` record, bound to owner, project, proposal revision, candidate digest, idempotency key, and artifact identities. A Builder's successful exit is only an execution result; only an independently verified receipt may move a job to `verified` or authorize creation of a Preview session. The Attestor must independently verify the exact stopped ECS task and hash the exact bounded S3 output bytes before signing; its private signing key is available only to the Attestor process, never to the Builder, Gateway, or API task. The Gateway may transport receipt objects but must not accept them as proof; API verification and current Candidate rechecks remain authoritative. If reconciliation needs an output digest, have a trusted service hash actual object bytes rather than relying on a Builder digest or optional S3 checksum metadata. Never persist signed job bearer tokens or presigned transfer URLs.

**Why:** A Preview session is created only after a verified build receipt exists. Reusing the session table for queued/running attempts would make an unbuilt or unverified Candidate look like an active Preview and would blur operational state with accepted evidence. A presigned Builder upload may not establish a full-object checksum in S3 metadata, and the Builder is not an independent attestor. Keeping the signing capability in a separate one-off task prevents a compromised builder or orchestration service from fabricating accepted evidence.

**How to apply:** Use the build-job row as the durable request/recovery identity, keep transitions versioned and terminal states closed, and recheck current Candidate ownership/revision at admission and receipt acceptance. Keep the build-job registry separate from Workspace Snapshot state. Reconciliation may record `builder_succeeded` only after matching the exact ECS identity, successful exit, encrypted bounded artifact, and observed object digest; retain independent receipt verification as the only `verified` gate. Give Attestor execution and task roles separate permissions: only execution role loads the receipt key, while the task role can inspect its bound ECS task, read build outputs, and write receipt objects. Use a distinct, deterministic `startedBy` value for Attestor tasks; reusing the Builder's job ID would make Builder reconciliation discover two tasks and reject the identity. The API never gives database credentials to Gateway or Attestor.

**Artifact-reference rule:** The content-addressed blob is shared by digest, but each Preview Job and artifact role needs its own stable, job-owned `artifactRefId`. Manifest and GC operations must address that exact `jobId + artifactRefId`; retries of the same job reuse the reference, while another job gets a separate reference even for the same key and bytes.

**Why:** Input object keys can be reused for the same Candidate across separate build attempts. A key-derived reference conflates those owners; treating each job ref as separate allows safe per-job lifecycle while preserving blob deduplication.

**How to apply:** Allocate the reference from the server-owned job identity and role, bind it into signed transfer claims and the immutable manifest, persist the matching identity in the existing Build row, and let GC delete only that reference. Do not enable local admission until the DB row, paired Agent owner, and actual store metadata agree; never authorize cleanup from the manifest alone.
