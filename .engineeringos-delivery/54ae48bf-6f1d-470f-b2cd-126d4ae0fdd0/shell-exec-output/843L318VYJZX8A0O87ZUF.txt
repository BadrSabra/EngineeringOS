# Task #104: Catch dashboard freshness drift after reconnect

# Catch dashboard freshness drift

## What & Why
Prevent an older dashboard response from overwriting newer project or task data after reconnect, reload, or concurrent changes from another session. Operators must see the latest readiness state and available recovery action.

## Done looks like
- Two authenticated dashboard sessions can use distinct project summaries.
- A project or task summary changed in one session remains current in the other after refresh or reconnect.
- A delayed older response cannot overwrite the newer rendered readiness or data state.
- Browser assertions verify visible values and available recovery actions rather than relying only on network request counts.
- The provider-free test path remains deterministic and bounded.

## Out of scope
- Redesigning dashboard project management.
- Changing server-side project authorization or persistence semantics.
- Live-provider campaigns or deployment validation.

## Steps
1. **Map freshness ownership** — Identify the dashboard queries, reconnect handlers, and state transitions that can receive responses out of order, then define the server or client freshness identity used to reject older results.
2. **Guard stale responses** — Ensure delayed responses cannot replace newer project, task, readiness, or recovery state after a reconnect or concurrent update.
3. **Add the multi-session browser journey** — Exercise a changed visible dataset across two authenticated sessions with bounded delays and reconnect behavior.
4. **Assert rendered convergence** — Verify the browser displays the newest project summary, readiness state, and safe action after stale responses arrive.
5. **Preserve isolation and determinism** — Keep fixtures provider-free, use request-identity-based concurrency barriers, and avoid unbounded polling or assumptions about request order.
