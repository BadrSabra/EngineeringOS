# Stop repeated AI retries from multiplying latency

## What & Why

The AI layer now has a request-owned execution ledger, but provider backoff and several response-recovery calls still use local retry rules. This can make one logical request spend more time and model calls than the operator expects. Consolidating those retries around one deadline and one admission rule gives the largest reliability improvement with a narrow implementation surface.

## Done looks like

- Groq and OpenAI-compatible retry/backoff attempts stop when the shared request deadline, cancellation signal, or attempt budget is reached.
- Empty-response, truncated-response, JSON-correction, and forensic-recovery attempts use explicit bounded recovery categories.
- A provider fallback cannot start after the request budget is exhausted.
- Completed evidence is preserved when a retry or recovery is refused.
- Existing provider-specific behavior remains unchanged when no request ledger is supplied.
- Deterministic tests cover cancellation during backoff, deadline exhaustion, provider fallback exhaustion, and evidence preservation.

## Minimal implementation plan

1. Add one small adapter around provider calls that admits an attempt, clamps timeout to remaining request time, and records completion/failure.
2. Route client-level retry/backoff through the adapter without changing provider selection or error classification.
3. Thread the existing ledger into all direct chat-agent recovery calls and remove duplicated local deadline ownership only where it conflicts with the request deadline.
4. Keep evidence and terminal-result construction unchanged; only change whether a new attempt may start.
5. Add focused unit tests before touching release/browser validation.

## Out of scope

- Changing model quality, prompts, or provider priority.
- Replacing the evidence RunLedger.
- Adding dashboard UI; that is covered by Task #11.
- Groq catalog outage behavior; covered by Tasks #8 and #10.

## Dependencies

- Depends on Task #9 (completed): use its ExecutionLedger contract.

# Prevent long investigations from looping without progress

## What & Why

Long investigations can still spend several model turns repeating reads, searches, or planning without producing new evidence or closing a claim. Existing duplicate and soft-limit guards help, but a small explicit progress policy would make broad investigations terminate earlier and produce a truthful partial result instead of consuming the full budget.

## Done looks like

- Each investigation turn is classified as new evidence, new dependency, claim closure, useful edit/validation, or no progress.
- A bounded consecutive no-progress streak forces synthesis or a safe incomplete result.
- Repeated cached reads and searches cannot reset the progress streak.
- Hierarchical children report progress and exhaustion consistently to the parent aggregate.
- No-progress termination preserves collected evidence and uses the existing incomplete/verdict semantics.
- Deterministic tests cover repeated reads, repeated searches, a productive turn after a stall, hierarchical child exhaustion, and cancellation.

## Minimal implementation plan

1. Reuse existing source-retrieval telemetry, duplicate detection, and objective claim state rather than adding a second evidence tracker.
2. Define one small progress predicate at the tool-loop boundary.
3. Make the existing no-progress/force-primary/synthesis guards consume that predicate.
4. Pass only the resulting status to hierarchical receipts; do not redesign scheduling.
5. Add focused tests for the transition boundaries and verify that ordinary chat remains unaffected.

## Out of scope

- New planning algorithms or recursive task decomposition.
- Changes to evidence acceptance rules.
- Provider retry/backoff behavior; covered by the retry task.
- Operator UI; covered by Task #11.

- Should follow the retry consolidation task to avoid conflating provider failure with no-progress behavior.
