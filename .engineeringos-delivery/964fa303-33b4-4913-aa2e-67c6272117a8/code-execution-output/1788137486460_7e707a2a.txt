Findings for task #24:

Current capability contract/registry:
- `lib/ai-orchestrator/src/capability-contract.ts:48-55` defines scope kinds (`none|project|paths|file|workspace`), while catalog metadata (`:87-140`) carries `defaultScope`/`supportedScopes` and policy (`:142-173`) carries allowed operations and approved command-profile names.
- Adapter shape is registration descriptor + runtime schemas + `execute(input, context)` (`:253-257`). Runtime context currently has only server `rootPath`, `operation`, optional approved profile set, approval state, and signal (`:241-251`); it has no invocation scope/path field.
- `CapabilityRegistry` stores cloned/frozen adapters in a Map, rejects malformed/duplicate IDs, lists descriptor-only entries sorted by ID (`:409-444`), validates recipe version, JSON size, reserved controls and input schema (`:446-482`), then checks approval/operation/profile requirements before execute and validates/bounds output (`:484-531`). It does not validate scope at invocation time. Existing failure union has no runtime scope failure (`:259-271`).
- `recipe-capabilities.ts:24-60` currently registers exactly one adapter, `project.read_file`. Its input is `{path}` with traversal-rejecting schema; execute resolves against `context.rootPath` and prevents filesystem escape (`:50-58`). Its catalog supports only `file` (`:32-46`), but it does not check that the requested file is within an approved invocation path list.

Recipe/compile shape:
- Recipe nodes contain business `capabilityId`, version, input, dependencies and declared outputs only (`lib/ai-orchestrator/src/recipe-contract.ts:142-166`); execution controls are intentionally absent.
- Server-owned `RecipeContext` does already contain `projectId`, nullable `rootPath`, revision, operation and `{kind, paths}` scope (`recipe-contract.ts:215-225`). Compiled execution nodes persist it (`task-session-state.ts:85-110`).
- Compiler context accepts operation/scope, approved files, authorization, approval, approved command profiles, risk and validation profile (`recipe-compiler.ts:89-104`). It validates operation/approval/profiles/authorization/risk and only checks `adapter.catalog.supportedScopes.includes(scope.kind)` (`recipe-compiler.ts:454-481`); it does not validate scope paths against node inputs or adapter semantics.
- `prepareRecipeOperation` establishes approved paths and scope (`artifacts/api-server/src/lib/recipe-operation-runner.ts:38-55`), but runtime `registry.invoke` drops the compiled node execution context and invokes with only `{rootPath, operation, signal}` (`:119-132`). Thus compile-time scope checks are not carried into execution.

Execution/validation profiles:
- `lib/ai-orchestrator/src/tools/execution-tools.ts:25-44` defines a `CommandProfile` with server-owned name/command/args/timeout/output/cwd and optional `allowedOperations`/`allowedPaths`; runner receives profile, root, signal, operation ID, revision and target paths. `executeCommandTool` selects only by registered name and checks operation/path equality (`:255-301`), but profile lists are caller-supplied, not a central registry.
- Validation profiles are a hard-coded four-value enum (`lib/ai-orchestrator/src/schemas/chat.schema.ts:15-22`), with actual bounded definitions in API server `ai-repair-validation.ts:53-97`: `ai-orchestrator-tests`, `knowledge-engine-tests`, `api-ai-tests`, `workspace-typecheck`. Scope is checked by profile predicate and nonempty paths (`:289-304`) before bounded isolated execution (`:306-355`).
- Browser verification has a declarative registered profile shape (`artifacts/api-server/src/lib/browser-preview-verification.ts:43-58`), strict safety validation (loopback:4300 origin, steps/timeouts/selectors) (`:67-100`), revision/origin/session checks (`:196-210`, `:332-370`), and bounded evidence. Project DB routes own registration and revision binding (`artifacts/api-server/src/routes/projects.ts:124-169`); AI chat loads exactly one project/revision-matching profile and rejects other/stale names (`artifacts/api-server/src/routes/ai/chat.ts:3760-3817`). This is a separate project profile store, not a capability registry.

Smallest safe design:
1. Extend `CapabilityExecutionContext` with a required server-owned invocation scope (reuse the existing `RecipeContext.scope` shape, ideally `{kind, paths}`), and add a distinct fail-closed capability failure such as `CAPABILITY_SCOPE_NOT_APPROVED` (retain `CAPABILITY_SCOPE_UNSUPPORTED` for catalog/compiler diagnostics). Centralize runtime validation in `CapabilityRegistry.invoke`: validate scope shape, require the adapter catalog to support `scope.kind`, normalize paths, and reject paths outside the server-approved set. Do not accept scope in recipe input.
2. For file-scoped adapters, make the adapter contract express the target path (smallest practical option: add an adapter-owned `validateScope(input, scope)` hook, or a narrow `scopePaths` callback). `project.read_file` must reject unless `input.path` is exactly one approved path (normalized), in addition to root containment. Avoid generic guesses about arbitrary adapter inputs.
3. Pass `node.executionContext.scope`, `revision`, and the server approved profile set into the `registry.invoke` call in `recipe-operation-runner.ts:126-131`; use the durable binding’s approved paths as the final authority and re-run `assertRecipeNodeBinding` immediately before invocation. This closes the current compile/runtime scope gap without changing recipe schemas.
4. Keep profile ownership separated: do not make model input or recipe nodes carry command/browser definitions. Add a small immutable server-side profile registration map only where recipe adapters need profiles; each entry should use existing `CommandProfile`/browser profile shapes and be selected by opaque name, with operation/path/revision checks. Reuse existing API validation profile definitions and project browser DB profiles rather than creating parallel ad hoc names. `project.read_file` needs no execution profile.
5. Add focused regression tests: registry invoke rejects unsupported scope and unapproved path before `execute`; read-file accepts an approved exact path but rejects another; recipe runner forwards scope/profile context; compile/runtime mismatch is blocked; profile registration rejects duplicate/invalid/stale registrations. Existing command/browser/repair tests should remain unchanged except for explicit context assertions.

Important boundary: existing `assertRecipeNodeBinding` already checks node allowed files and execution-context paths against durable approved paths (`artifacts/api-server/src/lib/ai-execution-state.ts:278-296`), but this is preparation/checkpoint validation only. It does not replace an invocation-time scope check, and the current runner bypasses the node execution context entirely.
