# Prevent Schema Drift Failures

## What & Why
Make PostgreSQL schema delivery reviewable, repeatable, and fail closed for the task/remediation contract. The TypeScript and API layers already use nullable `tasks.remediation_plan` and related task-log fields, but the project currently relies on imperative Drizzle push and a preflight that checks only a few column names; a release can therefore reach startup with a missing or incompatible application schema.

## Done looks like
- The committed task and task-log schema declarations are checked against the runtime PostgreSQL contract, including required columns, types, nullability, defaults, foreign keys where applicable, and required indexes; `tasks.remediation_plan` is explicitly covered as nullable JSONB.
- A narrow, reviewable schema-delivery path exists for both fresh databases and upgrades, including an upgrade fixture with existing tasks whose `remediation_plan` is NULL. Existing rows remain intact, and populated remediation plans round-trip with evidence, verification steps, source, and status unchanged.
- Reapplying schema delivery is safe and idempotent: it does not duplicate objects, rewrite task data, or silently omit required columns. If Drizzle push remains supported, its ownership, environment, and repeatability are explicit.
- Startup performs a read-only, fail-closed application-schema preflight before `app.listen`; missing or incompatible task/task-log contract details identify the safe delivery command and prevent public traffic. DDL remains outside `startup-migrations.ts`, and the audit-outbox check remains a separate check.
- Task GET/list/execute and verification flows, task-log REST/SSE, discovery and scan remediation-plan persistence, dashboard task summaries, and owner-scoped access continue to work for both NULL and populated plans.
- CI and release ordering apply or verify the schema before release validation and before server traffic; failures are nonzero and retain sanitized, actionable diagnostics without being confused with OpenAPI/codegen drift.

## Out of scope
- Redesigning remediation-plan semantics, task verification behavior, discovery/scan behavior, task-log behavior, or dashboard UX.
- Rebuilding browser recovery, controlled journeys, quality-baseline governance, aggregate readiness, or autonomous-loop integration.
- Replacing PostgreSQL, Drizzle, Clerk, or the existing application architecture.
- Client fallbacks, weakened authorization, allowing traffic against a partially validated database, or DDL inside startup migrations.
- Conflating database schema drift with generated API codegen drift; existing codegen checks remain a separate release concern.

## Steps
1. **Inventory the authoritative contract** — Compare the Drizzle task and task-log declarations with the database package exports, existing audit-schema checker, API query/write paths, discovery and scan persistence, and dashboard consumers. Define the smallest release-critical contract and distinguish nullable fields such as `remediation_plan` from non-null fields, defaults, indexes, and relationships.
2. **Add reviewable schema delivery** — Introduce the narrowest committed migration or equivalent controlled delivery artifact supported by the current Drizzle setup, covering the complete required task/task-log contract on a fresh PostgreSQL database and an existing database missing `tasks.remediation_plan`. Keep data preservation explicit, avoid DDL in startup migrations, and document/test the supported role of any remaining `drizzle-kit push` command.
3. **Build a complete read-only preflight** — Extend the reusable database schema check so it validates the selected task/task-log contract rather than only table/column presence, with actionable typed diagnostics for missing tables, columns, incompatible nullability/defaults/types, indexes, or relationships. Run it before the listener opens, preserve the separate pending-audit outbox check, and ensure connection or contract failures terminate startup with a nonzero result.
4. **Add fresh, upgrade, and repeatability fixtures** — Exercise delivery against a clean database and an upgrade fixture containing existing tasks with NULL and populated remediation plans. Apply the delivery repeatedly, assert object definitions and row contents remain stable, and retain bounded sanitized evidence for both successful and failing cases.
5. **Regress application behavior across plan states** — Extend focused API, discovery/scan, task-log, and dashboard tests so NULL plans remain valid while populated plans preserve all structured fields through task reads, lists, execution/verification, persistence, REST/SSE logs, summaries, and owner-scoped authorization. Assert unrelated task data is unchanged by schema delivery.
6. **Wire release ordering and verification** — Replace the release-critical reliance on the audit-only schema command with the complete schema delivery/preflight sequence in package scripts and CI, before release validation and any server process or traffic. Add ordering/failure assertions, run the focused checks in the normal validation path, and retain actionable release diagnostics while keeping codegen validation independent.
