- `<|tool_call_start|>` / matching end markers and `plan(...)` / `write_file(...)` are not present in source and are not recognized by `parseXmlToolCalls`, SSE buffering, or any other parser. A response containing them in `message.content` has `toolCalls === null`; the engine therefore treats the entire session as a final response. `plan(...)` cannot execute because no `plan` tool exists. Even if `write_file(...)` is parsed, it must be mapped to the actual registered function and validated against the active tool scope; arbitrary textual calls must not bypass repair-plan/approval policy.

1) Required tool failure is fail-closed only in SSE route. `lib/ai-orchestrator/src/tool-execution-engine.ts:1252-1261,2300-2336` returns `{kind:"failed", tool, failureKind, diagnosticCode}` and emits `tool_result(resultKind failed/unavailable/cancelled)` plus `done.stopReason:"tool_failure"`. `lib/ai-orchestrator/src/agents/chat-agent.ts:5920-5929` converts that into a blocked response, but does not return a failure/status field.

2) Streaming `/api/ai/chat/stream` compensates by inspecting the trace at `artifacts/api-server/src/routes/ai/chat.ts:3604-3670`: finds `done.stopReason === "tool_failure"`, emits SSE `error`, calls `persistFailedChatTurn` with FAILED/INTERRUPTED, calls `failAiExecution`, sets `executionTerminal`, ends without `done`. Caveat: SSE error omits `executionId`, `sessionId`, `outcome`, and `failureKind` (`:3633-3639`) even though `AiStreamErrorEvent` supports them (`lib/api-client-react/src/use-ai-chat-stream.ts:200-219`); immediate UI can only identify the execution from its local ref, and wire consumers cannot reliably correlate the failure.

3) Non-streaming `/api/ai/chat` has no equivalent trace inspection. After `chatWithFallback` (`artifacts/api-server/src/routes/ai/chat.ts:1993-2043`), it always inserts user and assistant rows with `outcome:"SUCCEEDED"` (`:2153-2179`), returns JSON `outcome:"SUCCEEDED"` (`:2223-2252`), and has no AI execution row. Thus a required tool failure becomes a persisted successful assistant message containing blocked prose, and reload/UI will not render the failure card. The UI gates failure display exclusively on `msg.outcome === FAILED|INTERRUPTED` (`artifacts/dashboard/src/pages/AiChat.tsx:4314-4317,4407-4467`). This is the clearest focused fix: share/duplicate the SSE terminal-tool-failure detection in JSON, persist via `persistFailedChatTurn`, and return a structured JSON failure (likely HTTP 200 contract with `outcome:FAILED`, or define an explicit HTTP status—current JSON route has no such contract).

4) Recovery failure is a separate seam. `chat-agent.ts:8056-8170` deliberately catches provider recovery failures, retains evidence, and may produce deterministic evidence-only/NO_FINDING output; final decision trace encodes `finalState` as `FAILED` or `RECOVERY_REQUIRED` at `:9251-9271`, with `recoveryFailureKind` and diagnostics. There is no status field on chat output, so both routes infer success from return completion. SSE persists the assistant as SUCCEEDED and can call `completeAiExecution` (`chat.ts:4003-4071,4208-4221`) even when trace says recovery failed; if acceptance rejects it, execution is failed but assistant message and `done` still remain success-shaped (`:4222-4241,4285-4324`). This creates execution/message/UI inconsistency: Flight Deck can show failed execution while chat history shows a normal assistant success. The existing recovery-rejected test intentionally expects `done`/report success (`artifacts/api-server/src/routes/ai-stream-integration.test.ts:3760-3861`), so distinguish recoverable evidence-only fallback (safe valid response) from terminal recovery failure (`decision_trace.finalState:FAILED` / unrecovered `FORENSIC_CONTRACT_RECOVERY_FAILED`) before changing semantics.

5) The same recovery-status ambiguity exists more severely in JSON: it persists `outcome:"SUCCEEDED"` regardless of `finalState:FAILED`/recovery-failure diagnostics. If product contract treats terminal recovery failure as failed/incomplete (rather than valid evidence-only fallback), JSON and SSE need a shared terminal classification and failed persistence. `persistFailedChatTurn` is at `chat.ts:836-895`.
