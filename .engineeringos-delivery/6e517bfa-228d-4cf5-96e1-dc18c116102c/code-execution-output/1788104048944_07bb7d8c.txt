--- loop-state-audit ---
Findings against Task #80 (no files changed):

- `executeToolLoop` has no explicit goal/claim contract input. `ToolLoopOpts` starts with `messages`/provider config and only has `requiresEvidence`, scope policy, and `firstEvidenceTargetPath` (`lib/ai-orchestrator/src/tool-execution-engine.ts:978-1010, 1171-1183`). A goal is therefore implicit in prompt text; a target path is not a goal, and required claims/evidence edges are absent. `AgentStep` has only free-form `plan_activity` fields (`:1369-1381`) and read “reasoning” text (`:1393-1399`), not typed goal, claim ID, evidence IDs, or claim transitions. Recommended: add server-owned `AgentGoal`/`RequiredClaim`/evidence-edge state to opts and every checkpoint/step; require tool results/accepted model findings to transition claims only when linked to retained evidence.

- Phase is a single optional static string, not loop state. `phase?: ExecutionPhase` merely caps tools/budget (`:1056-1057`, `:1632-1639`); `AgentStep.plan_activity.stage` is never emitted by this engine (only its type exists; emitted events are `iteration_start`, `model_call`, tool events, etc. at `:2391-2399`). The richer `ExecutionPhaseState` and transition rules live separately in `quality/execution-phases.ts:24-33,72-138` and are not accepted, advanced, or returned by `executeToolLoop`. Recommended: pass a mutable/server-owned phase state, emit phase enter/exit with transition rejection, and persist it atomically with claims/evidence.

- Terminal reasons remain lossy and success can be returned before objective completion. `ToolLoopResult` has `response`, `partial`, `exhausted`, `failed`, `stopped`, `cancelled` (`:1213-1283`); only `stopped` has a specific reason (`repeated_tool_call`). `done.stopReason` is limited to response/iteration_budget/soft_limit/repeated_tool_call/empty_response/provider_timeout/tool_failure/cancelled (`:1538-1568`). There is no `goal_met`, `claim_unclosed`, `evidence_incomplete`, `no_progress`, `phase_blocked`, or `validation_incomplete`, nor a terminal state payload. Normal no-tool output returns `kind: response` immediately (`:3013-3033`) regardless of required claims. The engine declares `EVIDENCE_AVAILABLE_BUT_CLAIM_UNCLOSED` and `OBJECTIVE_BLOCKED` diagnostic codes (`:1353-1360`) but does not emit them; post-hoc classification is delegated to `chat-agent.ts:2254-2324`, making loop semantics dependent on report parsing. Recommended: centralize an authoritative terminal evaluator in the loop; return `kind: incomplete`/`kind:completed` with explicit reason, goal status, missing claims, evidence count, and phase.

- No-progress handling forces evidence, but does not have a terminal no-progress outcome. The streak threshold is two (`:2220-2231`); it activates forced dispatch and later sets `forceSynthesisNext` after another forced no-progress pair (`:4190-4228`). Synthesis/no-text then becomes `partial`/`empty_response` or generic budget exhaustion (`:3036-3073`, `:4303-4347`), losing the fact that the cause was no progress. Recommended: track per-iteration progress tokens (new evidence, claim closure, state transition, patch/validation delta), emit `no_progress` with streak and last progress checkpoint, and terminate as incomplete after bounded recovery rather than treating synthesis/response as success.

- Incomplete outcomes are only partially represented. Zero source reads set telemetry `incompleteBeforeEvidence` and emit a diagnostic (`:2301-2329`), but evidence-present/claim-missing, phase-stalled, partial patch, and validation-without-passed-proof have no `ToolLoopResult` representation. A response can thus carry evidence but no closed claim and still be `response`; `sourceRetrieval` is telemetry, not an enforceable completion contract (`:1218-1224`). Existing tests cover zero-read and repeated-tool mechanics (`lib/ai-orchestrator/src/__tests__/tool-execution-engine.test.ts:3060-3253, 3254-3346`) but no test asserts goal/claim gating of a response or a distinct no-progress/incomplete result. Recommended tests: response with missing claim => incomplete; evidence with unclosed claim => claim_unclosed; forced streak exhaustion => no_progress; validation/phase stop => explicit incomplete reason.

- Resumability is outside the loop and insufficient for mid-loop continuation. `ToolLoopOpts` has no checkpoint/resume token, run ID, sequence, or serialized cursor (`:978-1211`); `messages` is explicitly mutated in memory (`:981-985`), and `cancelled` only returns retained in-memory maps (`:2330-2350`). `ToolLoopResult` likewise has no checkpoint or resume metadata (`:1213-1283`). `task-session-state.ts` persists bounded paths and an execution plan/current step (`:112-140`, `:142-160`), and continuation reconstructs classification (`:569-602`), but not current message/tool-call cursor, no-progress streak, phase, claim statuses, budgets, or terminal reason. Tests only round-trip the separate state and plan (`lib/ai-orchestrator/src/__tests__/task-session-state.test.ts:22-72,114-169`). Recommended: define versioned `AgentLoopCheckpoint` containing goal, phase, claims, evidence refs (not bodies), messages/tool-call cursor, iteration/tool budgets, no-progress counters, pending changes fingerprint, and last terminal status; accept `resumeFrom` plus an idempotent `onCheckpoint`, and return a durable resume token/checkpoint on cancellation, timeout, provider failure, and incomplete stops.

- Additional observability gap: `done.diagnosticCodes` is often hard-coded to `[]` even after zero-read/forced behavior (`:3016-3031`, `:4319-4344`), and `done.iterations` is hard-coded to `0` in tool-failure helper (`:2352-2388`). Recommended: derive terminal diagnostics/reason from the same state snapshot and report actual iteration/tool counts.

--- planner-contract-audit ---
Inspected `lib/ai-orchestrator/src/agents/query-planner.ts` and `lib/ai-orchestrator/src/__tests__/query-planner.test.ts`; Task #80’s documented contract is also in `docs/ai-agent-improvement-plan.md:131-179`.

Concrete gaps:
- Runtime parser is permissive sanitization, not validation (`query-planner.ts:164-220`). Invalid/missing `scopeEstimate` silently becomes `medium`; arbitrary `suggestedIterations` is rounded/clamped, but scope-specific ranges (narrow 5–16, medium 18–35, broad 40–60) are not enforced. `NaN` can survive as `suggestedIterations` (`Math.min/Math.max` yields NaN).
- `requiresToolUse` is effectively truthy-defaulted (`parsed[...] !== false`), so strings/numbers/null are accepted as booleans. `originalIntent` may be absent/empty and is backfilled only later; FALLBACK_PLAN has `originalIntent: ""` (`110-119`), violating the type comment that it retains the original intent verbatim. The prompt’s “exact shape” omits `originalIntent` while its rule requires it (`138-159`).
- Counts/shape are not contract-checked: targetFiles/entities/subQueries accept blank strings and duplicates; only array length slices are applied (files 10, entities 10, subqueries 5). Broad plans are not required to have 2–5 subQueries, and narrow/medium plans are not required to have none (`185-198`). `compoundParts` silently drops malformed entries, caps at 8, permits blank/duplicate IDs/questions, accepts arbitrary/NaN/Infinity/decimal `requiredCount`, and treats any non-boolean citation value as true (`199-215`).
- No target-file/entity validity check against graph/context. Model-provided paths are passed to prefetch (`chat-agent.ts:4805-4818`); only explicit file mentions get deterministic direct-neighbour restriction. Graph enrichment is bounded at 15 total, but paths are not normalized/deduplicated before the initial plan and entity names are not verified (`516-592`).
- `inferCompoundParts` is heuristic and only recognizes English/limited Arabic terms; it can produce no parts or false positives (`223-240`). The normalization then fabricates `subQueries` from compound parts when model returned fewer than 2 (`683-691`), even for non-broad scopes; it does not ensure broad plans have 2–5 focused queries.
- Fallback/valid/invalid telemetry is incomplete. Timeout/model errors collapse into `TIMEOUT_OR_ERROR` (`653-657`), parse failure emits `PARSE_FAILED` (`660-671`), but semantic-invalid plans are converted and emitted as `PLAN_READY` (`698-708`). There is no explicit `planStatus`/fallback reason, validation failure details, target-entity/compound-part counts, or distinction between valid plan and sanitized/invalid plan. Graph timeout/enrichment telemetry is separate and does not identify whether final plan was valid (`578-592`).
- Existing tests cover only graph enrichment, graph timeout, metrics skip, empty entities, 15-file cap, and explicit-file guidance (`query-planner.test.ts:65-307`). They do not exercise malformed JSON, wrong field types, invalid scopes, iteration bounds/NaN, count/blank/duplicate handling, broad subQuery rules, compoundParts, originalIntent, requiresToolUse, target validity, or telemetry. `makeMockStrategy` itself omits originalIntent/compoundParts (`34-49`).

Minimal safe implementation/testing plan (no edits made):
1. Add a small pure runtime validator/normalizer (prefer Zod if already standard; otherwise explicit predicates) invoked immediately after JSON parse. Require object and all fields’ types; reject semantic-invalid plans to FALLBACK rather than silently coercing. Preserve `message` as fallback `originalIntent`.
2. Enforce/deduplicate bounded counts: files ≤10 from model/≤15 after enrichment, entities ≤10, subQueries 0 for narrow/medium and 2–5 for broad, compoundParts bounded with nonblank unique IDs/questions; `requiredCount` finite positive integer (and only 3 for explicit top-three); citation strictly boolean. Normalize paths safely and reject/omit blank/untrusted entries according to existing prefetch policy, without broadening explicit-file scope.
3. Enforce scope-to-iteration ranges (or deterministically derive the default/range value); explicitly reject non-finite numbers. Keep graph enrichment as a post-validation bounded operation and revalidate merged file count.
4. Emit structured telemetry for `PLAN_VALID`/`PLAN_INVALID`/`PLAN_FALLBACK` with reason (`timeout`, `model_error`, `json_parse`, `schema`), plus counts and scope; avoid logging raw model output except carefully redacted/truncated diagnostics. Preserve separate graph timeout/enrichment events.
5. Extend focused tests through `planQuery`: valid full-shape plan; each invalid type/semantic case falls back with exact safe shape and originalIntent; scope/count/duplicate/blank rules; broad subquery cardinality; compound-part validation/inference; NaN/Infinity iterations; target-file/entity handling; model rejection/timeout/parse fallback. Spy on `console.info/warn` and assert valid vs invalid/fallback telemetry and reasons. Retain existing enrichment tests and add an assertion that enrichment never exceeds 15 or changes validated non-file fields.

--- hierarchical-receipts-audit ---
Findings (read-only):

- `lib/ai-orchestrator/src/agents/hierarchical-executor.ts:110-115` defines `SubResult` with only intent/text/toolSources/sourceEvidence; `HierarchicalResult:90-98` is aggregate-only. There is no exported per-subtask receipt, task ID/index, terminal status, reason, or completion metadata. Thus Task #80's explicit receipts/statuses (`complete`, `partial`, `failed`, `cancelled`) cannot be returned or audited.
- `runSubTask:154-157` only preserves model text for `response`/`partial`; every other engine kind (`exhausted`, `failed`, `stopped`, `cancelled`) is collapsed to the same text claiming iteration-budget exhaustion. A tool failure/cancellation/repeated-call stop is therefore misreported as budget exhaustion, with no status/reason. `runSubTask:173-187` catches thrown failures and emits generic `[...encountered an error]`, again losing failure classification and any result metadata.
- The engine explicitly supplies distinct kinds and cancellation/evidence semantics (`tool-execution-engine.ts:1213-1283`): `failed`, `cancelled`, and `partial` are not interchangeable. Hierarchical executor does not propagate those distinctions.
- Synthesis gets raw/generic statusless text (`buildSynthesisUserTurn:255-282`). The prompt says classify claims, but error/placeholder text is presented in the same `Sub-analysis` channel as findings and there is no hard boundary/structured status or post-synthesis provenance guard. `executeHierarchical:414-437` falls back to concatenating those placeholders verbatim when synthesis fails, so error text can become caller-visible answer content. `validateCompoundSynthesis:293-328` checks part names/cited file membership only; it does not reject unsupported facts, error-derived claims, or claims sourced from failed/cancelled subtasks.
- Cancellation is not terminal at hierarchical level: `executeHierarchical:363-387` continues scheduling pending waves regardless of `opts.signal.aborted`, and `:398-423` always attempts synthesis after cancellation. The engine's cancelled result does preserve `fileContents`, but hierarchical status is lost; synthesis may be attempted with an aborted signal and then fallback output is produced. There is no guarantee no new subtask starts after cancellation.
- Evidence is partially preserved: `:159-172` maps `fileContents` for all loop kinds, and `:390-396` aggregates it, including failed/cancelled results. However thrown exceptions lose any evidence because catch returns empty arrays (`:182-187`), and evidence line ranges are fabricated as `startLine:1` (`:165-170`) with excerpts truncated to 4,000 chars, so exact citation/evidence preservation is not reliable. Evidence is not bound to a subtask receipt/status.
- Existing tests in `hierarchical-executor.test.ts` cover happy path/waves/tools (`:74-276`), exhausted + successful synthesis (`:284-320`), synthesis failure fallback (`:322-351`), thrown subtask resilience (`:353-381`), and basic evidence citation validation (`:403-445`). They do not assert any per-subtask status/receipt, failed/cancelled distinction, cancellation scheduling, evidence retention on failed/cancelled/throw paths, or synthesis safety against error text.

Concrete tests to add:
1. Mock `executeToolLoop` once each as response, partial, failed, cancelled; assert result exposes four receipts in task order with statuses exactly `complete`, `partial`, `failed`, `cancelled`, reasons/tool diagnostic metadata, and per-receipt sources/evidence.
2. Failed result with `tool:'read_file'`, diagnostic and `fileContents` should retain source evidence but synthesis input must label it failed/unverified; synthesized `FACT` based only on its error text must be rejected/converted to NOT PROVEN.
3. Cancelled result with `fileContents`/toolSources should retain both in output, status cancelled, and must never be reported as exhausted or complete.
4. Abort signal already aborted before execution: assert zero `executeToolLoop` calls, no synthesis call, terminal cancelled aggregate/receipts.
5. Abort during first wave: resolve first task cancelled, assert pending second-wave task never starts and synthesis is skipped (or explicitly returns a cancellation receipt, never a normal synthesis).
6. A thrown error after a mocked loop has evidence (or an error object carrying result metadata) should preserve evidence and emit failed, not generic text/empty evidence.
7. Make synthesis throw; assert fallback contains only explicitly marked subtask outcomes and cannot present failed/cancelled/error placeholders as findings/facts.
8. Synthesis returns an unsupported claim citing a file mentioned only in a failed/cancelled subtask; assert compound validation fails. Also test a valid cited file from a partial subtask remains retained but is marked partial/unproven.
9. Assert evidence line ranges reflect actual multiline content and long content does not silently lose the cited tail; current fixed `1..excerpt line count`/4K truncation should fail this test.
10. Assert `stopped` is represented distinctly (or deliberately mapped to failed with reason), rather than the current iteration-budget placeholder.
