# Prevent Schema Drift Failures

## What & Why
Make PostgreSQL schema delivery reviewable, repeatable, and fail closed for the task/remediation contract. The TypeScript and API layers already use nullable `tasks.remediation_plan` and related task-log fields, but the project currently relies on imperative Drizzle push and a preflight that checks only a few column names; a release can therefore reach startup with a missing or incompatible application schema.

## Done looks like
- The committed task and task-log schema declarations are checked against the runtime PostgreSQL contract, including required columns, types, nullability, defaults, foreign keys where applicable, and required indexes; `tasks.remediation_plan` is explicitly covered as nullable JSONB.
- A narrow, reviewable schema-delivery path exists for both fresh databases and upgrades, including an upgrade fixture with existing tasks whose `remediation_plan` is NULL. Existing rows remain intact, and populated remediation plans round-trip with evidence, verification steps, source, and status unchanged.
- Reapplying schema delivery is safe and idempotent: it does not duplicate objects, rewrite task data, or silently omit required columns. If Drizzle push remains supported, its ownership, environment, and repeatability are explicit.
- Startup performs a read-only, fail-closed application-schema preflight before `app.listen`; missing or incompatible task/task-log contract details identify the safe delivery command and prevent public traffic. DDL remains outside `startup-migrations.ts`, and the audit-outbox check remains a separate check.
- Task GET/list/execute and verification flows, task-log REST/SSE, discovery and scan remediation-plan persistence, dashboard task summaries, and owner-scoped access continue to work for both NULL and populated plans.
- CI and release ordering apply or verify the schema before release validation and before server traffic; failures are nonzero and retain sanitized, actionable diagnostics without being confused with OpenAPI/codegen drift.

## Out of scope
- Redesigning remediation-plan semantics, task verification behavior, discovery/scan behavior, task-log behavior, or dashboard UX.
- Rebuilding browser recovery, controlled journeys, quality-baseline governance, aggregate readiness, or autonomous-loop integration.
- Replacing PostgreSQL, Drizzle, Clerk, or the existing application architecture.
- Client fallbacks, weakened authorization, allowing traffic against a partially validated database, or DDL inside startup migrations.
- Conflating database schema drift with generated API codegen drift; existing codegen checks remain a separate release concern.

## Steps
1. **Inventory the authoritative contract** — Compare the Drizzle task and task-log declarations with the database package exports, existing audit-schema checker, API query/write paths, discovery and scan persistence, and dashboard consumers. Define the smallest release-critical contract and distinguish nullable fields such as `remediation_plan` from non-null fields, defaults, indexes, and relationships.
2. **Add reviewable schema delivery** — Introduce the narrowest committed migration or equivalent controlled delivery artifact supported by the current Drizzle setup, covering the complete required task/task-log contract on a fresh PostgreSQL database and an existing database missing `tasks.remediation_plan`. Keep data preservation explicit, avoid DDL in startup migrations, and document/test the supported role of any remaining `drizzle-kit push` command.
3. **Build a complete read-only preflight** — Extend the reusable database schema check so it validates the selected task/task-log contract rather than only table/column presence, with actionable typed diagnostics for missing tables, columns, incompatible nullability/defaults/types, indexes, or relationships. Run it before the listener opens, preserve the separate pending-audit outbox check, and ensure connection or contract failures terminate startup with a nonzero result.
4. **Add fresh, upgrade, and repeatability fixtures** — Exercise delivery against a clean database and an upgrade fixture containing existing tasks with NULL and populated remediation plans. Apply the delivery repeatedly, assert object definitions and row contents remain stable, and retain bounded sanitized evidence for both successful and failing cases.
5. **Regress application behavior across plan states** — Extend focused API, discovery/scan, task-log, and dashboard tests so NULL plans remain valid while populated plans preserve all structured fields through task reads, lists, execution/verification, persistence, REST/SSE logs, summaries, and owner-scoped authorization. Assert unrelated task data is unchanged by schema delivery.
6. **Wire release ordering and verification** — Replace the release-critical reliance on the audit-only schema command with the complete schema delivery/preflight sequence in package scripts and CI, before release validation and any server process or traffic. Add ordering/failure assertions, run the focused checks in the normal validation path, and retain actionable release diagnostics while keeping codegen validation independent.

# Normalize Provider Tool Calls

## What & Why
Harden the OpenAI-compatible provider boundary against models that serialize executable requests as ordinary text, including marker dialects such as `<|tool_call_start|>`, `plan(...)`, and `write_file(...)`. The current client handles native `tool_calls` and one legacy XML form, but its textual parser accepts arbitrary names, uses nondeterministic IDs, strips complete XML blocks even when they are not valid calls, and the content-only stream can surface executable-looking text as trusted assistant content.

The normalization boundary should produce canonical calls only for a documented strict grammar and tools present in the request manifest. Unsupported, malformed, partial, pseudo-tool, or mixed-invalid output must fail closed through the existing provider/incomplete diagnostics rather than becoming a successful final answer.

## Done looks like
- Native OpenAI-compatible `tool_calls` remain compatible, while their arguments are canonical safe JSON objects before they enter replayable message history.
- The supported legacy `<tool_call>` form and the newly documented marker forms are parsed only when their complete syntax, object arguments, and function name match a tool actually registered for that request.
- Unknown names such as planning pseudo-tools, unresolved placeholders, malformed or nested-invalid arguments, partial markers, and mixed valid/invalid responses cannot execute, create pending changes, bypass root/scope/approval checks, or be presented as a successful answer.
- Recognized textual call blocks are removed only after successful normalization; surrounding legitimate content is preserved, and invalid executable-looking content is reported as incomplete/invalid rather than silently emitted.
- Normalized calls flow through the existing tool loop, manifest authorization, phase policy, project-root containment, repair-plan scope, and approval-gated pending-change behavior without a second execution path.
- Content-only streaming has an explicit no-tool contract: marker syntax is buffered across chunks and either safely treated as invalid/incomplete or rejected, never emitted as verified assistant content and never executed from the stream.
- Deterministic provider-free tests cover native/XML compatibility, marker whitespace and newlines, nested JSON/string values, multiple and mixed calls, malformed/partial/unknown pseudo-tools, content stripping, stream chunk boundaries, and execution-policy preservation.

## Out of scope
- Redesigning forensic recovery, evidence gates, provider fallback, or ordinary response parsing beyond the provider-result failure signal needed to fail closed.
- Adding unrestricted shell access, arbitrary tool names, or a new execution route.
- Making the content-only provider stream execute tools; it remains a no-tool stream and must stay observable and fail closed when it receives executable-looking markers.
- Changes to database schema, discovery/scan behavior, dashboard layout, aggregate release validation, or generated API codegen.

## Steps
1. **Define the provider protocol boundary** — Document the accepted native, legacy XML, and strict marker grammars, including complete-call requirements, safe object-argument rules, deterministic textual-call IDs, registration checks against the request's tool definitions, and the classification of ignored planning metadata versus malformed executable output. Keep provider-derived diagnostics bounded and safe for user-facing surfaces.
2. **Normalize or reject non-streaming responses** — Refactor the OpenAI-compatible response ingestion path so native calls retain their existing behavior while textual forms are parsed deterministically, including multiple calls, whitespace/newline variation, nested JSON, and mixed native/text output. Strip only successfully recognized call blocks; preserve surrounding content, and return the existing typed provider/incomplete outcome for unknown, malformed, partial, unresolved, or otherwise unsafe markers instead of returning them as final content.
3. **Preserve the existing execution policy** — Ensure every normalized call uses the same tool manifest and enters `executeToolLoop` and its server-owned authorization gates. Verify that pseudo-tools and placeholder paths cannot become executable capabilities, and that root containment, phase restrictions, approved repair-plan paths, validation profiles, and write approval/pending-change flow remain authoritative.
4. **Make content-only streaming fail closed** — Update the OpenAI-compatible stream handling and its OpenRouter strategy contract so marker detection works across SSE/chunk boundaries, does not leak recognized or unsupported executable syntax as assistant prose, and cannot dispatch tools. Preserve normal plain-text streaming and make incomplete/invalid marker termination observable through the existing bounded error path.
5. **Add deterministic protocol and policy regression coverage** — Extend the OpenAI-compatible and provider reliability tests with native/XML compatibility, strict marker acceptance/rejection, multiple and mixed calls, nested/escaped arguments, malformed and partial input, unknown planning pseudo-tools, selective content stripping, and streaming boundary cases. Extend tool-loop and chat execution-handoff coverage to prove normalized calls still obey manifests, scope/root checks, and approval-gated writes, with all provider turns injected and no live-provider dependency.
