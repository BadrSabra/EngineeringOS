    42## Bounded live-provider correlation run
    43
    44The live-provider path is opt-in and never runs as part of the normal smoke
    45journey. It uses the isolated Clerk user, a disposable project already owned
    46by that user, and the configured provider without printing keys or model
    47responses:
    48
    49```sh
    50DASHBOARD_E2E_LIVE_PROVIDER=1 \
    51DASHBOARD_E2E_LIVE_CAMPAIGN=1 \
    52DASHBOARD_E2E_LIVE_SCENARIO=delivery-success \
    53DASHBOARD_E2E_LIVE_DISPOSABLE=1 \
    54DASHBOARD_E2E_LIVE_PROJECT_ID=<disposable-project-id> \
    55DASHBOARD_E2E_LIVE_REPORT_PATH=test-results/dashboard-journey/live-mission-correlation.json \
    56RUN_CONTROLLED_RELEASE_VALIDATION=1 \
    57pnpm run validate:dashboard-journey
    58```
    59
    60The run is bounded by `DASHBOARD_E2E_LIVE_TIMEOUT_MS` (default 120 seconds)
    61and the live browser test allows an additional five seconds for Playwright
    62cleanup and report collection. The normal journey remains non-executing: the
    63provider-backed path is skipped unless `DASHBOARD_E2E_LIVE_PROVIDER=1` is set.
    64The fast `test:dashboard-journey-contract` and
    65`test:mission-correlation-report` checks run before release validation. Together
    66they verify the timeout relationship, provider opt-in guard, and the report
    67boundary. The correlation report contract requires redacted identity
    68(`operationId`, `projectId`, `sessionId`, and `workspaceRevision`), one
    69supported terminal state, and execution, message, SSE, checkpoint, and
    70dashboard surfaces. It explicitly classifies successful terminals separately
    71from blocked, cancelled, failed, and unavailable terminals, so an incomplete
    72report fails with the missing surface named before a live provider run.
    73When enabled, it exports a redacted report keyed by the provider-backed `operationId` and
    74the latest Git `workspaceRevision`. The report verifies persisted messages,
    75SSE events, execution checkpoints, evidence, proposals, validation, and
    76Mission Control state. `COMPLETED`-class states are success; provider
    77failover, unavailable, failed, and cancelled terminals are retained as
    78explicit non-success outcomes rather than being treated as passing runs.
    79The live objective is an explicit, bounded forensic review of
    80`scripts/mission-correlation-report.mjs`, requiring at least one accepted
    81evidence item and one validation checkpoint. A successful `COMPLETED` report
    82is rejected if either proof surface is empty; provider-unavailable, blocked,
    83cancelled, failed, and otherwise incomplete outcomes remain non-success.
    84For the disposable campaign, run the same command once per scenario:
    85`provider-outage`, `malformed-output`, and `delivery-success`. The first
    86records OpenRouter rate-limit/provider-exhaustion as a current non-success
    87operation; the second records malformed live output as non-success; the third
    88requires candidate-bound evidence before apply, commit, or push can count as
    89delivery proof. Reports include operation ID, project revision, and candidate
    90identity/revision, and explicitly label any retained result. A failed current
    91operation cannot reuse an older or cached analysis as a fresh success.
    92The release log also prints a redacted one-line result with the terminal,
    93outcome class, accepted evidence count, and validation checkpoint count. It
    94does not print prompts, source contents, provider credentials, or model
    95responses; non-success terminals are labeled `outcome=non-success`.
