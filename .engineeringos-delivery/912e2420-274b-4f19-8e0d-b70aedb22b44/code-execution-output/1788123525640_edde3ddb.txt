## Verified state and flow

- Durable “session memory” is `aiSessionMemoriesTable` in `lib/db/src/schema/ai_chats.ts:105-129`: rows are project/session scoped, typed (`file_summary`, `entity_fact`, `session_summary`, `key_finding`), with `content`, optional `sourcePath`, scalar `relevance`, created/expiry timestamps. In practice the writer only emits `file_summary` and `session_summary` (`lib/ai-orchestrator/src/session-memory.ts:104-152`).
- `writeSessionMemories()` is called only after a successful non-streaming turn (`artifacts/api-server/src/routes/ai/chat.ts:2518-2525`) and streaming turn (`artifacts/api-server/src/routes/ai/chat.ts:4562-4569`), fire-and-forget. It receives `result.sources` and response text, not the user question, tool outcomes, validation result, correction/acceptance, or explicit feedback.
- File memories retain no analysis: each row has the identical content `Previously accessed and analyzed in a chat session.` and only the path (`session-memory.ts:106-125`). At most 8 paths are written per turn (`:35`, `:109-115`). Session memory is only the first 400 chars of the response after code-block stripping (`:128-147`); it is not an LLM-generated/structured finding and does not preserve the associated question or evidence.
- Retrieval is `fetchSessionMemories(projectId, 20)` ordered solely by `relevance DESC`, with expiry filtering (`session-memory.ts:51-77`); there is no query/keyword/semantic/session recency filter. `enrichContextWithMemories()` mutates the already-built context after cache retrieval (`:206-223`), which correctly avoids putting memory into the 30-second project-context cache (`context-builder.ts:104-118`, `:170-184`).
- The injected text explicitly calls memory a navigation hint and stale/non-current evidence, requiring current reads/telemetry (`session-memory.ts:198-203`). It is marked untrusted (`formatUntrustedContent`). The prompt includes it once through `promptContextOverview()` (`lib/ai-orchestrator/src/prompts/prompt-composer.ts:62-80`) and again as a dedicated `Prior session memory` section (`lib/ai-orchestrator/src/prompts/chat.prompt.ts:330-365`). This duplication consumes prompt budget and increases stale-hint exposure.

## What is actually remembered/retrieved

- The route fetches up to 48 prior chat messages (`CONVERSATION_HISTORY_FETCH_MESSAGES = 24*2`) from the current session (`artifacts/api-server/src/routes/ai/chat.ts:2150-2163`), reverses them into chronological user/assistant-only history (`:2224-2233`).
- `buildConversationHistoryWindow()` retains 12 complete turns verbatim and summarizes all older messages, role-aware, bounded to 12,000 chars (`lib/ai-orchestrator/src/agents/chat-agent.ts:231-235`, `:246-285`). Tests verify both-role summary and intentional zero-turn behavior (`lib/ai-orchestrator/src/__tests__/conversation-history.test.ts:11-51`). Thus conversational state is substantially stronger than durable session memory, but only within the fetched 24-turn bound.
- Repair-plan state is separately persisted in `aiChatSessions.activeTaskState` and recovered for execution handoffs; the route computes `persistedActiveTaskState`/`resumableStateForTurn` (`artifacts/api-server/src/routes/ai/chat.ts:2104-2124`) and passes it into `chatWithFallback` (`:2234-2238`). The agent injects a resumed evidence ledger and prior repair-plan message (`lib/ai-orchestrator/src/agents/chat-agent.ts:4497-4521`, `:4561-4567`). This is structured task continuity, not feedback learning.

## Feedback loop assessment: weak/stale

1. **No closed feedback loop.** Writes happen after successful provider execution, but there is no update/reweight path when a memory is reused, found wrong, superseded by a new scan, contradicted by a tool read, or accepted/rejected by the user. `relevance` is initialized to 1.0 for every file row and .85 for summaries (`session-memory.ts:115-147`), then only decays globally by 10% during sweep (`:225-264`). There is no reinforcement, deduplication, replacement, or per-query relevance.
2. **Memory can misrepresent results.** `result.sources` can include prefetched/read paths, but every path becomes “analyzed”; no content, symbol, claim, or successful validation is retained (`session-memory.ts:109-125`). The summary is merely the assistant’s first paragraph, so future turns cannot reliably recover what was decided or why.
3. **Staleness is time-based only.** Rows expire after 30 days (`session-memory.ts:37-43`, `:99-102`) and sweep is scheduled every 6 hours (`:284-301`), but source edits/scans do not invalidate memory rows. Context cache invalidation exists for DB context (`lib/ai-orchestrator/src/context-cache-manager.ts:97-115`), not session memories.
4. **Policy fields are not wired to runtime retrieval.** `buildExecutionPlan()` computes `memoryDepth`, `historyDepth`, graph budgets/modes (`lib/ai-orchestrator/src/quality/quality-planner.ts:53-62`, `:85-98`), but repository references show no consumer of `executionPlan.memoryDepth` or `.historyDepth`. Runtime instead always fetches 20 memories in the route (`chat.ts:2188-2192` / `session-memory.ts:218`) and uses fixed 12 turns (`chat-agent.ts:4150-4155`). The task profile says workflow/analysis/code-review memory should be `none` or varies by mode (`lib/ai-orchestrator/src/quality/task-profile.ts:30-37`), but route-level enrichment is unconditional; only evidence/forensic/capability paths suppress it (`chat-agent.ts:4080-4082`).
5. **Memory prefetch is broad and stale-prone.** For ordinary tool turns, paths are parsed from memory bullets and eagerly reread, up to the prefetch budget (`chat-agent.ts:4707-4761`). This does improve latency if the path remains relevant, but it treats historical paths as current candidates. It is disabled for graph-guided requests, forensic/single-file modes, repair execution, and evidence queries (`:4714-4723`), so it cannot consistently improve all future turns.

## Context loading/building

- `loadProjectContext()` reads a repeatable-read snapshot (`lib/ai-orchestrator/src/context-loader.ts:297-313`, `:442-443`): project, up to 10 priority/recency-sorted tasks (`:181-191`), one latest metric (`:194-205`), graph entities up to 60 and projected relationships up to 40 (`:208-244`), 10 events (`:247-257`), 20 workflows (`:260-270`), and latest scan job (`:273-293`). Non-project query failures degrade to empty values (`:135-159`).
- Serialization is lossy by design: task descriptions 100 chars, graph entity descriptions 60 chars, max 50 displayed entities and 40 relationships (`lib/ai-orchestrator/src/context-serializer.ts:60-87`, `:138-195`, `:224-227`). The graph context is an index, not source evidence; the prompt states it is not exhaustive (`lib/ai-orchestrator/src/prompts/chat.prompt.ts:337-339`).
- Context sections are admitted under plan budgets with explicit ADMIT/REFERENCE/DEFER/DROP decisions and cached for 30 seconds (`lib/ai-orchestrator/src/context-builder.ts:138-184`; cache TTL `context-cache-manager.ts:5-6`). This is robust budgeting, but admission does not rank based on the current user query; profile-selected sections and plan budgets determine inclusion.

## Graph-guided prefetch

- Explicit mentioned files are resolved against graph file entities, then only the mentioned roots plus depth-1 direct neighbors are admitted (`lib/ai-orchestrator/src/agents/query-planner.ts:473-487`, `:494-609`). It has bounded roots/neighbors/files, produces prompt hints and optional source-grounded cross-file traces.
- The runtime requires a completed verified scan (`projectContext.metricsVerified`) before graph guidance or generic graph enrichment (`lib/ai-orchestrator/src/agents/chat-agent.ts:4455-4462`; `query-planner.ts:825-829`). Guidance prefetch supersedes generic speculative prefetch (`chat-agent.ts:4618-4660`), and explicit graph target files replace the model planner’s target files (`:4795-4803`). This prevents unrelated expansion and is a real improvement over random exploration.
- Generic planner enrichment searches target entities, traverses depth-2 neighborhoods for top 5 matches, merges paths up to its cap, and races a hard timeout (`query-planner.ts:636-729`; invoked `:856-859`). Planner failures return a fallback plan (`:733-739`, `:789-823`), so graph guidance is opportunistic, not guaranteed.
- Prefetched content is injected as synthetic assistant/tool messages and seeds the tool dedup cache (`speculative-prefetch.ts:16-24`, `:259-306`; plan list `:321-416`). Reads are capped/truncated unless complete (`:45-50`, `:235-249`). This improves future-turn latency only indirectly: it improves the current turn and then records only paths, not durable content/findings.

## Bottom line

The system remembers recent conversational messages, structured repair/task state, recently accessed file paths, and a short first-paragraph response snippet. It retrieves those project-wide by fixed relevance/limits and uses paths to seed future prefetches. It does not learn from future correctness, user feedback, validation outcomes, source changes, or query-specific usefulness. Graph-guided prefetch is bounded and source-read-backed, but it is a navigation accelerator rather than a memory-learning loop. The strongest verified weaknesses are the unconsumed `memoryDepth/historyDepth` policy, unconditional route enrichment despite memory modes, duplicate prompt injection, generic path-only file memories, and decay-only relevance with no stale/source-change feedback.

Aggregate latency/duplicate-work conclusions:
- Worst-case logical task call compounds outer provider fallback (up to 4 providers), provider-owned model fallback (OpenRouter chain), provider transport retries (Groq 4 attempts/OpenRouter 2), then BaseAgent quality retries (up to 3 logical calls), plus later node/reconciliation retries. Without a shared deadline, aggregate latency is multiplicative rather than additive/bounded globally.
- Duplicate work is concrete: BaseAgent NON_200 repeats an already internally completed `agentComplete`; OpenRouter JSON-mode retry repeats same model/request; chat stream failure can resend full synthesis non-stream; JSON correction and forensic/behavior/capability corrections resend retained context; provider fallback repeats full agent/tool prompt on another provider; task/node recovery replays it again.
- Cancellation is threaded into provider HTTP calls in Groq/OAC clients and task lifecycle (`task-execution-service.ts:290-324`), but backoff `sleep` in Groq has no signal (`groq-client.ts:87-89`, calls at `:451-456`/`:699-703`), and catalog refresh has its own unrelated AbortController/no caller signal (`dynamic-catalog.ts:97-108`). Cancellation can therefore wait through backoff/refresh.

Observability strengths/gaps:
- Strong structured logs: retry decisions (`retry-controller.ts:79-100`), Groq attempt/outcome/backoff (`groq-client.ts:446-464`), OpenRouter status and fallback attempted-model context (`openai-compatible-client.ts:453-465`, `:1151-1176`), strategy circuit/failure logs (`openrouter.strategy.ts:127-147`), task DB logs/events/receipts with correlation/execution IDs (`task-execution-service.ts:249-259`, `:430-484`, `:507-528`).
- Chat emits per-model provider telemetry (`chat-agent.ts:7471-7479` and registry schema `provider-registry.ts:252-280`) including duration/attempt count; however provider metrics counters are in-memory and reset on restart (`lib/ai-orchestrator/src/provider-metrics.ts:004-018`, `:141-144`), and the exported `recordRequest/recordFailure/recordSuccess/recordLatency` functions have no production call sites found (only definitions/tests), so `/api/ai/metrics` can under-report (`routes/ai/providers.ts:270-356`).
- Telemetry is not a complete aggregate span: task receipts use configured default powerful model, not necessarily actual model (`task-execution-service.ts:124-140`), and set attempts to 1 or 2 based only on provider change (`:379-383`), omitting transport/model retries and recovery calls. `failureReceipt` hardcodes attempts=1 (`:144-170`).
- Catalog status is exposed (`providers.ts:299-355`) with `loaded/usable/age/status`, and settings returns Groq `check_unavailable`; but `/api/ai/metrics` omits `lastRefreshError`, and no request latency/attempt/correlation is attached to Groq catalog checks. Dynamic refresh logs success/failure but does not record duration or caller/request correlation (`dynamic-catalog.ts:110-191`).
- Outer fallback logs provider transitions but not a single aggregate operation span/deadline or total attempts (`ai-route-helpers.ts:325-350`). Consequently operators can see individual retries/candidates but cannot reliably reconstruct end-to-end latency or duplicate-work cost from one durable operation.
