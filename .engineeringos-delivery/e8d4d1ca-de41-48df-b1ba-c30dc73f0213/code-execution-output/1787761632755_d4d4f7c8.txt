## Concrete Task 3 gaps
1. No remediation-plan domain type/table/status/lifecycle or API exists; current “plan” is a generic `Fix:` task.
2. Violation payload loses rule identity, evidence locations/snippets, suggested fix, and verification steps before task creation.
3. Discovery-import tasks are capped at 20, not deduplicated/idempotent, not linked to rules/files/correlation, and do not preserve source discovery/session or scan provenance.
4. No plan generation/orchestration step (template or AI), approval/review boundary, ordered steps, acceptance criteria, dependency handling, or plan-to-task decomposition exists.
5. No API response exposes generated plans, plan generation status/errors, evidence, or task IDs; dashboard only displays aggregate violation rows and a misleading task count.
6. Verification ignores configured `rules.verifySteps` and cannot verify plan steps; regex absence is the sole automated rule signal.
7. Scan and discovery contracts are inconsistent: scan tasks retain richer rule/file data, discovery tasks do not; discovery options are advertised but ignored, undermining completeness/traceability.
8. Rule matcher caps evidence/counts (`lib/scanner/src/rule-matcher.ts:29-33`) and discovery stores only aggregate counts, so any remediation plan would need an explicit bounded-evidence contract and truncation indicator rather than assuming complete findings.
