Findings/root causes:

- Provider selection is centralized in `artifacts/api-server/src/lib/ai-route-helpers.ts:82-153,214-265`: keys are resolved in `PROVIDER_PRIORITY = [openrouter, gemini, deepseek, groq]` (`lib/ai-orchestrator/src/provider-registry.ts:53-62`), then filtered only by `supportsTools` when `requireTools` is set and by circuit state. Quality sorting can reorder the remaining providers (`ai-route-helpers.ts:116-139`). Thus OpenRouter wins whenever configured, even if Groq is healthier; fallback is credential/circuit based, not health-probed.

- Chat routes correctly derive tool requirement and pass it both to initial resolution and fallback: ordinary `artifacts/api-server/src/routes/ai/chat.ts:2167-2170,2222-2251`; SSE `chat.ts:2840-2848,3877-3932`. Gemini is explicitly non-tool-capable (`lib/ai-orchestrator/src/provider-registry.ts:120-143`), while Groq/OpenRouter/DeepSeek are tool-capable. `chatWithFallback` preserves this constraint because it calls `collectAvailableProviders(userId, options)` (`ai-route-helpers.ts:432-435`) and forwards all tool/authorization fields to `chat()` (`ai-route-helpers.ts:470-497`). The fallback therefore does not silently downgrade a tool request to Gemini.

- Cross-provider fallback is triggered for `RATE_LIMITED`, `TIMEOUT`, network/server, model, quota, empty, auth, etc. (`ai-route-helpers.ts:279-300,499-523`). However it only recognizes `GroqClientError`; arbitrary thrown errors bypass fallback (`ai-route-helpers.ts:509-511`). The final exhausted error contains provider messages (`ai-route-helpers.ts:514-523`), although chat HTTP serialization redacts them.

- Groq request path: tool-capable `completeRaw` builds `tools` and `tool_choice` (`lib/ai-orchestrator/src/groq-client.ts:438-480`), retries timeout/network/429/5xx up to `maxRetries` (default 3) (`groq-client.ts:485-523,604-616`), and classifies HTTP 429 as RATE_LIMITED (`groq-client.ts:526-567`). Concrete gap: Groq does not parse or propagate `Retry-After`; 429 retry backoff is hard-coded randomized 8s/16s/32s (`groq-client.ts:71-87,503-507`), so it can retry too early or waste the whole request budget.

- Groq streaming is materially weaker: `completeStream` performs only one provider request and has no retry loop (`groq-client.ts:642-740`). Once any bytes are emitted, upstream stream fallback intentionally stops to avoid duplicate output (`lib/ai-orchestrator/src/openai-compatible-client.ts:1347-1364`). A timeout/disconnect after partial output therefore terminalizes rather than recovering.

- OpenRouter path is direct `fetch` to `https://openrouter.ai/api/v1/chat/completions` (`lib/ai-orchestrator/src/openai-compatible-client.ts:1054-1079,722-762`). It parses Retry-After, capped at 60s (`openai-compatible-client.ts:467-479`), distinguishes 429 quota/credits from per-minute rate limiting (`openai-compatible-client.ts:481-542`), and turns timeout while consuming the JSON body into TIMEOUT (`openai-compatible-client.ts:784-799`).

- OpenRouter model fallback is separate from provider fallback. `openrouterCompleteWithFallback` resolves a free-model chain and advances only for model-unavailable/empty, or transient failures when `retryTransient === false` (`openai-compatible-client.ts:1157-1210,1226-1267`). Default transient behavior retries the same model once (`openai-compatible-client.ts:1082-1121`) and then throws; it does not advance to another model. A 429 with Retry-After explicitly bypasses the same-model retry (`openai-compatible-client.ts:1105-1109`), then still does not model-fallback unless bounded callers set `retryTransient:false`. This is the primary 429 recovery weakness.

- OpenRouter strategy wraps the above and has circuit breaker integration (`lib/ai-orchestrator/src/strategies/openrouter.strategy.ts:41-147`). It refreshes catalog and re-resolves stale pinned models, but catalog refresh is awaited despite comments calling it fire-and-forget (`openrouter.strategy.ts:84-87`), so catalog outage/latency can consume request time before fallback.

- Tool capability is preserved for non-streaming fallback: OpenRouter `openrouterCompleteWithFallback` propagates `tools`, `toolManifest`, `toolChoice`, and `requireTools` into each candidate (`openai-compatible-client.ts:1157-1164,1226-1230`); low-level request applies tools (`openai-compatible-client.ts:668-690`). Provider fallback also filters Gemini before trying it. But model-chain capability matching is inconsistent in streaming: `openrouterCompleteStream` calls `isCatalogFreeModelForCapability` without `requireTools` (`openai-compatible-client.ts:1312-1326`); streaming is documented as no-tool synthesis (`lib/ai-orchestrator/src/provider-strategy.ts:60-75,95-107`), so this is safe only if the caller invariant holds.

- Tests cover classification and safe diagnostics (`artifacts/api-server/src/lib/ai-route-helpers.test.ts:80-137`), route tool-aware selection and fallback expectations (`artifacts/api-server/src/routes/ai/chat-sse.test.ts:796-911`), and structured OpenRouter 429/fallback release behavior (`lib/ai-orchestrator/src/__tests__/structured-review-fallback.release.test.ts:111-181`). The tests do not appear to assert Groq Retry-After parsing (none exists), default OpenRouter 429 advancement to another model, or partial-stream recovery; those are unprotected gaps.

Key findings (read-only inspection):

- Malformed/XML tool calls are intentionally fail-closed at `lib/ai-orchestrator/src/provider-tool-calls.ts:246-280,305-381`. Legacy XML requires exact `<tool_call><function=name>...<parameter=...>...</parameter></function></tool_call>`; malformed markers, duplicate params, invalid JSON/identifiers, pseudo-tools, or names outside manifest throw `GroqClientError(INVALID_TOOL_CALL)` (`:61-77,254-279`). Native calls are similarly strict (`:148-173`). This is a hard terminal provider error: `artifacts/api-server/src/lib/ai-route-helpers.ts:288-300` does NOT include `INVALID_TOOL_CALL` in fallback triggers, and `chatWithFallback` immediately rethrows non-trigger errors (`:499-510`). Thus malformed XML/tool output gets no provider retry/fallback; the route can only classify it as failure later.

- No-tool synthesis protects against models emitting tools, but fallback is narrowly bounded. `lib/ai-orchestrator/src/tool-execution-engine.ts:2271-2317` retries once with `powerModel` only when synthesis response has tool calls and no text; if power model also fails, it returns the first malformed/tool-call response. This can hand recovery a response with no usable synthesis. Synthesis itself is capped by shared attempts/deadline (`:2207-2268`), and empty response gets bounded retry only (`:2165-2204`).

- Duplicate reads/tool calls are cache-based exact-call deduplication, not semantic/path deduplication. The duplicate branch at `tool-execution-engine.ts:4060-4133` escalates exact repeated calls, caches output, hides search after 2 repeats and forces synthesis after 3 (`:4062-4114`), but only rehydrates `fileContents` for cached `read_file` (`:4119-4125`), not `read_file_range`. Therefore equivalent `read_file` vs `read_file_range`, path spelling variants, or differing irrelevant args can evade duplicate-read handling. The general duplicate cache key/normalization is earlier in the engine (search `duplicateCount`/cache key around `:3900-4060`).

- Forced-evidence/no-progress handling is robust but has a deliberate escape-to-synthesis behavior. Two no-progress planning iterations activate persistent forced mode (`tool-execution-engine.ts:4470-4525`); dispatch rejects every non-read/non-validation call (`:3503-3533`). If forced mode itself has two more no-progress turns, `forceSynthesisNext` is set (`:4487-4493`), and terminal classification reports `no_progress` (`:4591-4623`). Novel searches reset the no-progress streak (`:4470-4486`), so protected planning-budget logic is required to catch endless novel-but-useless searches (`:4527-4569`). Root cause of prior looping risk is explicitly documented there: novel searches reset the streak while source reads remain zero.

- Zero-read/stopped results are explicitly differentiated. `classifyZeroReadTerminal` marks `INCOMPLETE_BEFORE_EVIDENCE` and records actual elapsed starving iterations (`:2428-2455`). Iteration exhaustion returns `partial` if any text exists, otherwise `exhausted` (`:4588-4637`), with reasons `no_progress`, `evidence_incomplete`, or `iteration_budget`. Chat-agent stopped-loop handling is deterministic and non-success: `lib/ai-orchestrator/src/agents/chat-agent.ts:5780-5828` emits “stopped after repeated identical tool calls”, routes through Objective Completion Gate, and preserves sources/pending changes.

- Chat-agent fallback/partial behavior is covered by tests: malformed task JSON does not get a correction retry and becomes deterministic PARTIALLY_COMPLETE (`lib/ai-orchestrator/src/__tests__/chat-agent.test.ts:2811-2843`); fallback text normalization and unfinished checklist are tested (`:2966-3029`); provider-timeout loop results become partial reports (`:3032-3070`); evidence is preserved through empty-response recovery and failed fallback models (`:1066-1200`). Recovery can use read tools but not write/replace tools (`:2600-2647`).

- API/SSE terminal handling correctly prevents success-looking completion for incomplete/failure outcomes: `artifacts/api-server/src/routes/ai/chat.ts:3934-4048` classifies terminal outcome before persistence; tool failures emit `error`/blocked recipe terminal, while incomplete reports emit a `done` envelope carrying explicit outcome/errorCode/failureKind/retryability/recovery state. This addresses stopped-result visibility, but malformed provider tool calls still fail before any fallback because `INVALID_TOOL_CALL` is absent from fallback policy.
