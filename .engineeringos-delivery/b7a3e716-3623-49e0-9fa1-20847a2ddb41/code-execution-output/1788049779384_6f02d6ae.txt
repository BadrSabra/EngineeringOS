# Close Candidate Commit Integrity

## What & Why
Close the remaining integrity gap in the approval-controlled AI delivery chain. The current apply path records candidate, change-set, and promoted hashes, but it compares the isolated candidate as a full tree while live promotion and Git commit checks rely primarily on selected-file bytes and correlated events. That leaves partial approvals, unrelated root drift, candidate mutation, and stale apply evidence insufficiently bound to the bytes that are committed and pushed.

## Done looks like
- Candidate and live-root hashing use one versioned deterministic tree-digest contract with identical file inclusion/exclusion rules, normalized relative paths, file-kind handling, symlink representation, and byte encoding.
- Full-file and partial-hunk approvals materialize only the authorized submitted subset in the candidate workspace; omitted proposal files or hunks are not present in the validated candidate.
- The apply receipt, journal, audit record, proposal state, and correlated event retain the same operation identity, base-tree digest, candidate-tree digest, change-set identity, and promoted-tree digest.
- Apply blocks before promotion when any included live-root content changed outside the selected files, blocks when the candidate changed during validation, and verifies the complete promoted tree against the validated candidate. A mismatch or failed rollback is retained as an explicit blocked, mismatch, or unknown-state outcome.
- A scoped AI commit requires complete, matching server-owned apply evidence for the same operation, rechecks the canonical live tree before staging and after committing, and records the Git commit identity separately from the post-commit tree digest. Missing, stale, or mismatched evidence blocks the commit.
- The push trace preserves and checks the same operation/content proof, while generic non-AI Git commits retain their existing behavior.
- Deterministic provider-free tests cover full and partial apply, omitted proposal changes, unrelated-root drift, candidate mutation, promoted-byte mutation, missing/stale commit evidence, and a successful Apply → commit → push trace with matching proof.
- Capability and parity reports describe this only as code-backed or deterministically verified at the evidence level actually established; they do not convert provider, browser, credential, aggregate-release, or production readiness into a pass.

## Out of scope
- Reimplementing model tool-call parsing, AI failure persistence, capability recipes, schema-drift remediation, or aggregate release validation.
- Running a live provider campaign, authenticated browser campaign, production deployment, or real GitHub credential flow.
- Changing approval requirements, evidence gates, redaction rules, server-owned command profiles, or the prohibition on arbitrary model shell execution.
- Treating a deterministic hash-chain receipt as proof of provider quality or as a complete end-to-end Agent journey.

## Steps
1. **Define the canonical tree-integrity contract** — Consolidate candidate and live-root digesting behind one server-owned contract with an explicit version and shared delivery exclusion policy. Specify normalized paths, file and symlink records, byte encoding, and bounded failure codes for base drift, candidate drift, promotion mismatch, missing proof, and unknown recovery state; keep Git commit identity distinct from tree-content digests.
2. **Materialize the exact approved candidate** — Adjust candidate creation and apply preparation so the isolated workspace starts from the current source tree and overlays only the submitted authorized files/hunks, including rebased partial selections, rather than the entire stored proposal. Capture the pre-apply base-tree digest and candidate-tree digest, and retain them with the operation’s server-owned evidence.
3. **Gate validation and promotion on complete-tree identity** — Validate the exact candidate identified by its operation, revision, and tree digest. Recheck the candidate after validation and compare the complete canonical live root with the captured base before promotion so unrelated changes fail closed; after atomic promotion, compare the complete live tree with the candidate and preserve explicit rollback or unknown-state evidence when the comparison fails.
4. **Bind commit and push to promoted content** — Make scoped AI commit consume the correlated apply journal/event/proposal evidence and require all required digests to agree for the same operation and approved scope. Recheck the live tree before staging and after Git commit, persist and emit the commit SHA plus post-commit tree digest as separate fields, and carry the verified chain through the AI push event without weakening generic Git behavior.
5. **Extend deterministic integrity coverage** — Add workspace, apply-route, and Git-route fixtures for canonical exclusions and file kinds, full and partial selections, omitted proposal files/hunks, unrelated root edits, candidate mutation during validation, post-write mutation, rollback mismatch/unknown state, missing or stale evidence, pre/post-commit drift, and a successful local commit/push proof. Include operation/revision/hash assertions across journal, audit, event, proposal, public validation, and operation-history projections, with no live provider or credential dependency.
6. **Refresh evidence reports conservatively** — After implementation and deterministic checks are inspected, update the actual capability baseline and parity assessment to name the exact newly proven integrity transitions and remaining operational limitations. Keep aggregate validation and live/browser/provider claims pending when their completed evidence is absent.

# Bind Recipe Operations Safely

## What & Why
Bind compiled recipe execution to the durable operation, lease, revision, approved scope, and candidate workspace that own it. Every leaf execution and follow-on mutation must be authorized against the live server-owned binding so stale, replayed, cancelled, or cross-project work cannot run.

## Done looks like
- A recipe run has one operation-scoped binding covering project, operation identity, source revision, candidate identity/workspace, approved paths, phase, and lease ownership.
- Lease loss, cancellation, revision/workspace mismatch, stale checkpoint, or cross-project access stops the run before execution or subsequent mutation and records a safe terminal reason.
- All process, validation, browser, and workspace actions continue to use fixed server profiles, bounded execution, root containment, isolated pending-change workspaces, and cleanup guarantees.
- Operation bindings carry server-owned mission and concurrency budgets so independent work can proceed efficiently without exceeding project, process, or resource limits.
- Security tests cover replay, concurrent workers, lease expiry, cancellation races, path escape, process leakage, and attempts to override command controls.

## Out of scope
- Designing the recipe contract or compiler.
- New user-facing SSE event names and dashboard views.
- Arbitrary shell, custom argv, custom cwd, or model-selected environment variables.

## Steps
1. **Create the operation binding** — Extend the existing durable execution context with a validated recipe binding and server-owned identity checks that are required before a node is claimed or run.
2. **Fence execution, concurrency, and mutation** — Enforce operation, project, lease, mission-budget, and concurrency ownership before dispatch or mutation, so parallel work cannot escape scope or exhaust shared resources. Recheck ownership, cancellation, revision, candidate, and scope at node start, completion, retry, and follow-on mutation boundaries; terminalize violations rather than continuing from error-shaped results.
3. **Route every leaf through safe runners** — Adapt recipe adapters to the bounded command kernel, registered validation/browser profiles, and isolated workspace helpers; preserve bounded parallel dispatch for eligible independent nodes without exposing lower-level controls to recipe inputs.
4. **Exercise hostile lifecycle cases** — Add deterministic tests for concurrent claims, late workers, stale revisions, path/process escapes, cleanup failures, and cancellation at each checkpoint boundary.
