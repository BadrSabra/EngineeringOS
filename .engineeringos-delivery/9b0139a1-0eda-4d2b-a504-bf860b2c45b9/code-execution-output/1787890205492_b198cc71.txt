# Normalize Provider Tool Calls

## What & Why
Harden the OpenAI-compatible provider boundary against models that serialize executable requests as ordinary text, including marker dialects such as `<|tool_call_start|>`, `plan(...)`, and `write_file(...)`. The current client handles native `tool_calls` and one legacy XML form, but its textual parser accepts arbitrary names, uses nondeterministic IDs, strips complete XML blocks even when they are not valid calls, and the content-only stream can surface executable-looking text as trusted assistant content.

The normalization boundary should produce canonical calls only for a documented strict grammar and tools present in the request manifest. Unsupported, malformed, partial, pseudo-tool, or mixed-invalid output must fail closed through the existing provider/incomplete diagnostics rather than becoming a successful final answer.

## Done looks like
- Native OpenAI-compatible `tool_calls` remain compatible, while their arguments are canonical safe JSON objects before they enter replayable message history.
- The supported legacy `<tool_call>` form and the newly documented marker forms are parsed only when their complete syntax, object arguments, and function name match a tool actually registered for that request.
- Unknown names such as planning pseudo-tools, unresolved placeholders, malformed or nested-invalid arguments, partial markers, and mixed valid/invalid responses cannot execute, create pending changes, bypass root/scope/approval checks, or be presented as a successful answer.
- Recognized textual call blocks are removed only after successful normalization; surrounding legitimate content is preserved, and invalid executable-looking content is reported as incomplete/invalid rather than silently emitted.
- Normalized calls flow through the existing tool loop, manifest authorization, phase policy, project-root containment, repair-plan scope, and approval-gated pending-change behavior without a second execution path.
- Content-only streaming has an explicit no-tool contract: marker syntax is buffered across chunks and either safely treated as invalid/incomplete or rejected, never emitted as verified assistant content and never executed from the stream.
- Deterministic provider-free tests cover native/XML compatibility, marker whitespace and newlines, nested JSON/string values, multiple and mixed calls, malformed/partial/unknown pseudo-tools, content stripping, stream chunk boundaries, and execution-policy preservation.

## Out of scope
