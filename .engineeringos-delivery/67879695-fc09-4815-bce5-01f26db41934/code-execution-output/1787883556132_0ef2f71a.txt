# Prevent Release Failures from Schema Drift

## What & Why

The application contract already declares and uses the nullable `tasks.remediation_plan` JSONB field across discovery, scanning, task execution, API responses, and the dashboard. The release failure is in physical schema delivery and preflight: the current setup relies on imperative `drizzle-kit push`, has no committed migration artifact for this change, and startup checks do not verify the task table contract before traffic opens. Make schema delivery reviewable, idempotent, and fail closed without redesigning task behavior or duplicating browser/release readiness work.

## Done looks like

- The authoritative task and task-log declarations are compared with the runtime database contract, including `tasks.remediation_plan`, nullability, defaults, indexes, and immediately required columns.
- A narrow, reviewable schema delivery path applies the declared contract to fresh and existing PostgreSQL databases without data loss. If the project retains `drizzle-kit push`, its ownership, environment, and repeatability are explicit and tested rather than assumed.
- An upgrade fixture containing existing tasks, including NULL remediation plans, succeeds; populated remediation plans round-trip unchanged with evidence, verification steps, source, and status preserved.
- Applying the schema delivery and restarting the preflight are idempotent: repeated runs do not duplicate objects, rewrite rows, or silently skip a missing required column.
- Startup schema preflight fails before `app.listen` when `public.tasks.remediation_plan` is absent, names the missing contract and safe delivery action, and proceeds only when the required schema is complete. DDL remains outside the no-DDL startup-migrations contract.
- Task GET/list/execute, task logs REST/SSE, discovery/scan plan persistence, and dashboard task-plan/verification paths pass regression checks against both NULL and populated plans.
- Schema delivery and preflight run before release validation and before server traffic; failures are nonzero and retained as actionable release evidence. The existing audit-outbox check remains separate and is not mistaken for full application-schema validation.

## Out of scope

- Redesigning remediation-plan semantics, task verification, discovery, scan behavior, or dashboard UX.
- Rebuilding browser recovery (Task #46), the controlled journey (Task #47), quality baseline governance (Task #48), aggregate readiness (Task #49), or autonomous-loop integration (Task #50).
- Replacing PostgreSQL, Drizzle, Clerk, or the existing application architecture.
- Hiding schema errors with client fallbacks, weakening authorization, or allowing traffic against a partially validated database.
- Conflating database schema drift with generated API codegen drift; keep codegen checks as a separate release concern.

## Steps

1. **Inventory the declared contract** — Compare the task and task-log schemas, generated/API contract, route queries, discovery/scan writes, and dashboard reads; identify the smallest required schema surface and the current audit-check limitations.
2. **Choose the delivery boundary** — Add or formalize the narrowest reviewable schema delivery path compatible with the current Drizzle setup, covering fresh databases and an upgrade fixture missing `tasks.remediation_plan`; preserve existing rows and avoid DDL inside startup-migrations.
3. **Add fail-closed preflight** — Extend the reusable schema check or startup preflight to verify the task contract before the listener opens, with safe actionable diagnostics for missing or incompatible columns and a successful path for a complete schema.
4. **Exercise application regression paths** — Verify NULL and populated remediation plans through task reads/writes and execution, discovery/scan persistence, task-log REST/SSE, dashboard aggregation, and owner-scoped authorization; assert no unrelated task data changes.
5. **Prove repeatability and release ordering** — Apply the delivery twice, restart/preflight twice, run the focused tests, then wire the schema check before release validation and traffic. Retain sanitized pass/fail evidence and classify any remaining environment issue separately from schema correctness.

# Normalize Model Tool Calls

## What & Why
Harden the provider boundary against model responses that serialize tool calls as unsupported text markers such as `<|tool_call_start|>`, `plan(...)`, and `write_file(...)`. The current OpenAI-compatible client recognizes native `tool_calls` and one legacy `<tool_call>` XML form, so the captured session treated executable-looking text as an ordinary answer, entered forensic recovery, and performed no verified reads or writes.

## Done looks like
- Provider tool-call output is normalized only when it matches a documented, strict grammar and an actually registered tool; otherwise it is classified as an invalid/incomplete provider result rather than presented as a successful final answer.
- `plan`-like pseudo-tools and runtime placeholders cannot create tool calls or bypass the existing tool policy, project-root checks, repair-plan scope, or approval-gated pending-change flow.
- Native OpenAI tool calls and the existing supported XML form continue to dispatch unchanged, with safe JSON-object arguments.
- Marker, malformed, mixed, nested-argument, and content-stripping behavior is covered by deterministic tests; no test relies on a live provider.
- Content-only streaming remains explicit about its no-tool contract: unsupported executable-looking markers are not emitted as if they were verified assistant content.

## Out of scope
- Redesigning the forensic recovery contract, evidence gates, or provider fallback chain.
- Adding an unrestricted shell or arbitrary tool execution path.
- Making the current content-only provider stream execute tools; if that remains unsupported, the result must fail closed and be observable.
- Changes to aggregate release validation, database schema, discovery, scan behavior, or dashboard layout.

## Steps
1. **Define the provider protocol boundary** — Document the accepted native and legacy textual forms, the exact handling of marker dialects, and the distinction between a registered executable tool, ignored planning metadata, and malformed provider output.
2. **Normalize or reject marker responses safely** — Add a deterministic normalization path at provider-response ingestion that produces canonical tool calls only for registered names with valid object arguments, strips only recognized call blocks, and reports unsupported or partial markers through the existing bounded diagnostic/incomplete mechanisms.
3. **Preserve execution policy across normalized calls** — Ensure normalized calls enter the same tool-loop dispatch, scope, authorization, root-containment, and approval paths as native calls; never interpret `plan` or placeholder paths as a new execution capability.
4. **Make streaming behavior explicit** — Keep the provider strategy’s content-only stream contract consistent with the normalization decision so marker syntax is either safely handled as non-executable invalid output or rejected, never surfaced as trusted completed work.
5. **Add protocol regression coverage** — Test native/XML compatibility, single and multiple marker calls, whitespace/newlines and nested JSON arguments, malformed/partial markers, unknown pseudo-tools, mixed native/text calls, and stream chunks or content that contain marker boundaries as applicable.

# Unify AI Failure Persistence

## What & Why
Make required tool failures and terminal recovery failures durable and visible with the same semantics on JSON and SSE chat routes. The tool loop already emits typed failure telemetry, but the streaming route has its own trace inspection while the JSON route always persists and returns `SUCCEEDED`; recovery failures can likewise leave a successful-looking assistant message beside a failed execution.

## Done looks like
- A required `tool_failure` produces one consistent blocked/failed outcome in both `/api/ai/chat` and `/api/ai/chat/stream`; it is never persisted as a successful assistant turn.
- Safe diagnostic code, failure kind, and operation/session correlation are available to the client without exposing provider secrets or raw diagnostics.
- Terminal recovery failure or an explicitly incomplete forensic result is distinguished from an accepted evidence-only or source-grounded `NO_FINDING` fallback; only the latter can complete when its evidence gates pass.
- Failed and interrupted turns remain failed/incomplete after session reload, reconnect, or execution recovery, without duplicate assistant success records.
- Deterministic route, orchestrator, and dashboard tests prove the status contract without live providers or shared-fixture races.

## Out of scope
- Redesigning provider tool-call parsing or adding support for a new model wire dialect.
- Rewriting forensic recovery, evidence validation, objective gating, or autonomous execution algorithms.
- Changing the aggregate AI release gate, database schema, discovery/scan behavior, or dashboard visual design.
- Enabling live-provider validation or weakening redaction and authorization boundaries.

## Steps
1. **Define one terminal outcome classifier** — Derive a shared route-facing status from the bounded trace, covering required tool failure, cancellation, terminal recovery failure, accepted evidence-only fallback, and ordinary successful completion; keep server-owned raw diagnostics out of user-facing fields.
2. **Align the JSON route** — Inspect the trace before the existing success transaction, persist failed or interrupted turns through the established failure path, and return the documented structured failure response without writing a successful assistant outcome.
3. **Align the SSE route and execution state** — Reuse the same classification for SSE error/done events, failed-turn persistence, and durable execution completion/failure so assistant history, reconnect state, and Flight Deck status cannot disagree.
4. **Expose safe correlation and recovery state** — Include only allowlisted session/execution identifiers, diagnostic codes, failure kind, retryability, and incomplete/recovery status in API and SSE contracts; preserve redaction and avoid leaking provider responses or credentials.
5. **Add regression coverage across layers** — Test JSON and SSE required-tool failures, interrupted runs, terminal recovery failure versus accepted fallback, persistence and reload behavior, reconnect/no-replay behavior, and the dashboard’s failed/incomplete rendering using isolated deterministic fixtures.
